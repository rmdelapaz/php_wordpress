🧰 Lesson 4.3: functions.php: Supports, Assets, Menus & Widgets

pagesco-classic can already find and show every kind of content, but it still writes its own <title>, prints an old-style search form, has no stylesheet, no menu and nothing in its footer but an address. All of that is the job of one file, functions.php: the place where a classic theme tells WordPress which features it supports, which CSS and JavaScript it needs, and where menus and widgets may go. In this lesson you finish the classic theme, make it accessible and translatable, and then hand the site back to pagesco, which gets its own first functions.php.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Explain when functions.php runs and choose the right hook for theme setup, widgets and assets
  • Declare theme supports such as title-tag and html5 with add_theme_support(), and say which ones block themes get automatically
  • Enqueue a stylesheet and a deferred script with wp_enqueue_style() and wp_enqueue_script(), with dependencies and a version that busts browser caches
  • Register a menu location and a widget area, print them with wp_nav_menu() and dynamic_sidebar(), and fill them from WP-CLI
  • Add the accessibility and translation basics every theme needs: a skip link, screen-reader text, labeled navigation and strings WordPress can translate
  • ⏱️ Time 140 minutes
  • 📋 Prerequisites Lesson 4.2: Custom Queries
  • 🛠️ You will build the finished pagesco-classic (supports, stylesheet, menu script, primary menu, footer widget area, skip link, translations) and pagesco's first functions.php with a "Pages & Co." pattern category
  • 🧩 WordPress 7.1 on PHP 8.5 (script loading strategies need 6.3+; automatic loading of a theme's languages/ folder needs 6.8+)
  • 🧱 Site your Pages & Co. site from Lesson 4.2, with pagesco-classic active

🧰 What functions.php Is For

You have met functions.php twice: Twenty Twenty-Five's in Lesson 3.1, and the one you started for pagesco-classic in Lesson 4.2 with a single pre_get_posts callback. It is not a template. WordPress never prints it; it includes it on every request while the theme is active, right after the plugins are loaded (the wp-settings.php tour in Lesson 2.2). That includes the admin, AJAX and REST requests, and WP-CLI:

wp eval 'var_dump( function_exists( "pagesco_classic_adjust_main_query" ), did_action( "after_setup_theme" ) );'

Output

bool(true)
int(1)

Your function exists even in a WP-CLI command, and after_setup_theme has fired once. Two consequences follow. First, code at the top level of functions.php runs everywhere, so almost everything in it belongs in a callback on the right hook. Second, it only runs while the theme is active, which is why features that must survive a redesign (the store notice, the Book post type) go into plugins, the decision table from Lesson 3.4.

💡 Mental model: the shop's fit-out instructions

If the templates are the floor plans of the shop (Lesson 3.2), functions.php is the sheet of instructions the theme hands the building manager when it moves in: "we need the shop sign handled by you" (theme supports), "please deliver these crates of paint and these tools" (stylesheets and scripts), "there will be a directory board here and a notice board there" (a menu location and a widget area). The manager, WordPress, does the actual work at the right moment of each day. The instructions only describe what the theme needs; they never paint the walls themselves.

Each kind of instruction has its moment in the request. These are the hooks a theme uses, in the order they fire:

graph TD A["plugins are loaded"] --> B["theme functions.php is included"] B --> C["after_setup_theme: supports, menu locations"] C --> D["init, with widgets_init at priority 1"] D --> E["main query, template chosen"] E --> F["wp_head: wp_enqueue_scripts at 1, styles printed at 8"] F --> G["the template prints the page"] G --> H["wp_footer: footer scripts printed at 20"]

The priorities come from wp-includes/default-filters.php: add_action( 'wp_head', 'wp_enqueue_scripts', 1 ), wp_print_styles at 8 and wp_print_footer_scripts at 20 on wp_footer. That is the real reason a classic template must call wp_head() and wp_footer() (Lesson 3.1): without them, no theme or plugin can add a single stylesheet or script to the page. The convention you will follow is the one core themes use: one small, prefixed function per job, each hooked to its moment.

🧩 Theme Supports

Some features of WordPress are opt-in for classic themes, because old themes did those jobs themselves and would break if WordPress suddenly did them too. A theme switches a feature on with add_theme_support( $feature ) in a callback on after_setup_theme. Look at what get_search_form() prints right now, the form on your 404 page:

wp eval 'echo get_search_form( array( "echo" => false ) );'

Output

<form role="search" method="get" id="searchform" class="searchform" action="http://localhost:8080/">
				<div>
					<label class="screen-reader-text" for="s">Search for:</label>
					<input type="text" value="" name="s" id="s" />
					<input type="submit" id="searchsubmit" value="Search" />
				</div>
			</form>

That is the "xhtml" format from the early 2000s: an id="searchform" that can only exist once per page, a <div> where a label would help, and a plain text field. Now replace wordpress/wp-content/themes/pagesco-classic/functions.php with this version. The new pagesco_classic_setup() comes first; the pre_get_posts callback from Lesson 4.2 is unchanged:

<?php
/**
 * Pages & Co. Classic functions and definitions.
 *
 * @package pagesco-classic
 */

/**
 * Sets up translations and the theme features WordPress should provide.
 */
function pagesco_classic_setup() {
	load_theme_textdomain( 'pagesco-classic', get_template_directory() . '/languages' );

	add_theme_support( 'title-tag' );
	add_theme_support( 'automatic-feed-links' );
	add_theme_support( 'post-thumbnails' );
	add_theme_support( 'responsive-embeds' );
	add_theme_support(
		'html5',
		array( 'search-form', 'comment-form', 'comment-list', 'gallery', 'caption', 'navigation-widgets' )
	);
}
add_action( 'after_setup_theme', 'pagesco_classic_setup' );

/**
 * Shows three posts per page on the blog home.
 *
 * @param WP_Query $query The query WordPress is about to run.
 */
function pagesco_classic_adjust_main_query( $query ) {
	if ( is_admin() || ! $query->is_main_query() ) {
		return;
	}

	if ( $query->is_home() ) {
		$query->set( 'posts_per_page', 3 );
	}
}
add_action( 'pre_get_posts', 'pagesco_classic_adjust_main_query' );

Five supports (the load_theme_textdomain() line is for translations, later in this lesson):

FeatureWhat WordPress then does
title-tagPrints the <title> in wp_head() (_wp_render_title_tag at priority 1, Lesson 2.3), built by wp_get_document_title() with its filters
automatic-feed-linksAdds <link rel="alternate"> tags for the posts and comments RSS feeds
post-thumbnailsShows the Featured image panel in the editor and enables the_post_thumbnail() (books get covers in Module 5)
responsive-embedsLets embedded videos keep their aspect ratio as the page narrows
html5 + listModern markup for the search form, comment form and list, galleries, captions and the navigation widgets

The first one has a visible side effect. Count the <title> elements on the About page:

curl -s http://localhost:8080/about/ | grep '<title>'

Output

	<title>About Us &#8211; Pages &amp; Co.</title>
	<title>About Us &#8211; Pages &amp; Co.</title>

Two titles: WordPress's, printed by wp_head(), and the one header.php still writes by hand from Lesson 4.1. A page must have exactly one, so the hand-written line goes. Delete the <title> line from header.php in your editor, or let sed do it from the WP-CLI container:

sed -i '/<title>/d' wp-content/themes/pagesco-classic/header.php
curl -s http://localhost:8080/about/ | grep '<title>'

Output

	<title>About Us &#8211; Pages &amp; Co.</title>

One title, from WordPress, which plugins can now change through the document_title_parts and document_title_separator filters (you used the second one in Lesson 2.3). SEO plugins rely on exactly that, which is why a theme should never print its own title any more. The search form changed too:

wp eval 'echo get_search_form( array( "echo" => false ) );'

Output

<form role="search" method="get" class="search-form" action="http://localhost:8080/">
				<label>
					<span class="screen-reader-text">Search for:</span>
					<input type="search" class="search-field" placeholder="Search &hellip;" value="" name="s" />
				</label>
				<input type="submit" class="search-submit" value="Search" />
			</form>

role="search", a class instead of an ID, a <label> around a type="search" field and a visually hidden "Search for:" text for screen readers. That screen-reader-text class is important later in this lesson. (html5 also used to accept 'script' and 'style', to drop the old type="text/javascript" attributes. Since WordPress 7.0 those two values are deprecated and do nothing: core never prints the attributes any more.)

What block themes get for free

You never declared a single support in pagesco, yet it had a title and an HTML5 search form. WordPress adds a set of supports to every block theme itself, on after_setup_theme at priority 1:

grep -n -A 14 "^function _add_default_theme_supports" wp-includes/theme.php | grep "add_theme_support"

Output

4400-	add_theme_support( 'post-thumbnails' );
4401-	add_theme_support( 'responsive-embeds' );
4402-	add_theme_support( 'editor-styles' );
4408-	add_theme_support( 'html5', array( 'comment-form', 'comment-list', 'search-form', 'gallery', 'caption', 'style', 'script' ) );
4409-	add_theme_support( 'automatic-feed-links' );

The title is not even on that list: for block themes, wp-includes/block-template.php prints it unconditionally, "regardless of whether theme has title-tag support", as its comment says. Classic themes must ask for each feature, which is why every classic theme you will meet starts with a setup function like yours.

💡 Legacy supports: the Customizer family

Old tutorials also add custom-logo, custom-header and custom-background. Each one adds a panel to the Customizer (Appearance > Customize), where the site owner uploads a logo or picks a background color, and the theme prints it with functions such as the_custom_logo(). They still work in classic themes, and you will see them on client sites. For new work they are legacy: block themes do the same with the Site Logo block and theme.json styles that the Site Editor edits (Lesson 3.1 showed the Customizer stepping aside).

🎨 Enqueueing Styles and Scripts

A block theme gets most of its CSS from theme.json. A classic theme, even a hybrid like yours, has to deliver its own CSS files, and you saw in Lesson 4.1 that WordPress does not print styles.css custom CSS for it. You could type a <link rel="stylesheet"> into header.php, but then WordPress would not know about the file: plugins could not remove or replace it, a child theme could not depend on it, and nothing would stop the same library being loaded twice by two plugins. So themes and plugins enqueue their assets: they put them on WordPress's list with a unique name (the handle), and WordPress prints the list in the right place, in dependency order, each file once.

Argumentwp_enqueue_style( $handle, $src, $deps, $ver, $media )wp_enqueue_script( $handle, $src, $deps, $ver, $args )
handleUnique, prefixed name: pagesco-classic-style. WordPress adds -css / -js for the element's id
srcFull URL: build it with get_parent_theme_file_uri() / get_theme_file_uri() (Lesson 3.4) or plugins_url() in a plugin
depsHandles that must be printed first, for example array( 'pagesco-classic-style' )
verAdded as ?ver=… so browsers fetch the file again when it changes; use the theme's Version
last'all', 'print', or any media queryarray( 'strategy' => 'defer' or 'async', 'in_footer' => true ) (6.3+)

Start with the menu script, because the menu comes next. On a small screen it will fold the menu away behind a "Menu" button. Note how it adds the class that hides the menu only once it runs: without JavaScript, the menu simply stays visible. Create wordpress/wp-content/themes/pagesco-classic/assets/js/navigation.js:

/**
 * Pages & Co. Classic: opens and closes the primary menu on small screens.
 */
( function () {
	const nav = document.querySelector( '.site-nav' );
	const button = nav ? nav.querySelector( '.menu-toggle' ) : null;

	if ( ! button ) {
		return;
	}

	// Only now, with JavaScript running, may the menu start closed.
	nav.classList.add( 'is-collapsible' );

	button.addEventListener( 'click', function () {
		const open = 'true' !== button.getAttribute( 'aria-expanded' );
		button.setAttribute( 'aria-expanded', String( open ) );
		nav.classList.toggle( 'is-open', open );
	} );
}() );

Then add the enqueue callback to the end of functions.php. It runs on wp_enqueue_scripts, the front-end moment for assets (admin screens have admin_enqueue_scripts, the login page login_enqueue_scripts):

/**
 * Loads the theme's stylesheet and its menu script.
 */
function pagesco_classic_enqueue_assets() {
	$version = wp_get_theme( get_template() )->get( 'Version' );

	wp_enqueue_style(
		'pagesco-classic-style',
		get_parent_theme_file_uri( 'style.css' ),
		array(),
		$version
	);

	wp_enqueue_script(
		'pagesco-classic-navigation',
		get_parent_theme_file_uri( 'assets/js/navigation.js' ),
		array(),
		$version,
		array(
			'strategy'  => 'defer',
			'in_footer' => true,
		)
	);
}
add_action( 'wp_enqueue_scripts', 'pagesco_classic_enqueue_assets' );

Three choices in it are worth a sentence each. get_parent_theme_file_uri( 'style.css' ) always means this theme's file, even when someone builds a child theme on pagesco-classic; get_stylesheet_uri() would quietly load the child's style.css instead (the template-versus-stylesheet distinction from Lesson 3.4). For the same reason the version comes from wp_get_theme( get_template() ), the theme in the template option. And the script is deferred: the browser downloads it while it reads the page and runs it at the end, so it never blocks the page from appearing. Look at what WordPress prints:

curl -s http://localhost:8080/ | grep 'pagesco-classic-'

Output

<link rel='stylesheet' id='pagesco-classic-style-css' href='http://localhost:8080/wp-content/themes/pagesco-classic/style.css?ver=1.0.0' media='all' />
<script data-wp-strategy="defer" defer id="pagesco-classic-navigation-js" src="http://localhost:8080/wp-content/themes/pagesco-classic/assets/js/navigation.js?ver=1.0.0"></script>

The stylesheet is a <link> in the <head> with the ID pagesco-classic-style-css; the script a <script defer> at the end of the body (WordPress also writes the strategy into data-wp-strategy, so it can keep dependent scripts in a safe order). Both URLs end in ?ver=1.0.0, the Version line of style.css. When you change the CSS for a release, you raise that number, every visitor's browser sees a new URL, and nobody is stuck with yesterday's styles in their cache. The project does exactly that.

✅ Register once, enqueue where needed

wp_register_style() and wp_register_script() take the same arguments but only make a handle known; a later wp_enqueue_style( 'handle' ) with just the handle puts it on the page. Plugins use that pair to load a file only on the pages that need it, for example a shortcode's CSS only when the shortcode appears. Conditional tags work inside a wp_enqueue_scripts callback, because the main query has run by then: if ( is_front_page() ) { … } (Exercise 2).

🧭 Navigation Menus

Classic menus have two halves. The theme declares locations, named places in its templates where a menu may appear ("primary", "footer"). The site owner builds menus under Appearance > Menus and assigns one to each location. The theme never knows which links a menu holds; it only prints "whatever menu is in the primary location". Register the location at the end of functions.php, on after_setup_theme like the supports (a second, separate callback keeps each job readable):

/**
 * Registers the menu location the header prints.
 */
function pagesco_classic_register_menus() {
	register_nav_menus(
		array(
			'primary' => __( 'Primary menu', 'pagesco-classic' ),
		)
	);
}
add_action( 'after_setup_theme', 'pagesco_classic_register_menus' );

The key 'primary' is the location's ID that templates use; the translatable value is what the admin shows. Now replace header.php. It prints the menu with wp_nav_menu() inside a labeled <nav>, only when a menu is assigned (has_nav_menu()), next to the button your script controls. It also gains a skip link, explained in the accessibility section below:

<?php
/**
 * The header: the document head and the top of every page.
 *
 * @package pagesco-classic
 */

?>
<!DOCTYPE html>
<html <?php language_attributes(); ?>>
<head>
	<meta charset="<?php bloginfo( 'charset' ); ?>">
	<meta name="viewport" content="width=device-width, initial-scale=1">
	<?php wp_head(); ?>
</head>
<body <?php body_class(); ?>>
<?php wp_body_open(); ?>
<a class="skip-link screen-reader-text" href="#main"><?php esc_html_e( 'Skip to content', 'pagesco-classic' ); ?></a>
<header class="site-header">
	<p class="site-title"><a href="<?php echo esc_url( home_url( '/' ) ); ?>"><?php bloginfo( 'name' ); ?></a></p>
	<?php if ( has_nav_menu( 'primary' ) ) : ?>
		<nav class="site-nav" aria-label="<?php esc_attr_e( 'Primary', 'pagesco-classic' ); ?>">
			<button type="button" class="menu-toggle" aria-controls="primary-menu" aria-expanded="false"><?php esc_html_e( 'Menu', 'pagesco-classic' ); ?></button>
			<?php
			wp_nav_menu(
				array(
					'theme_location' => 'primary',
					'menu_id'        => 'primary-menu',
					'container'      => false,
					'depth'          => 1,
				)
			);
			?>
		</nav>
	<?php endif; ?>
</header>
<main id="main" class="site-main">

'container' => false drops the <div> that wp_nav_menu() would wrap around the list (the theme already has its <nav>), menu_id gives the list the ID the button's aria-controls points to, and depth 1 prints top-level items only. Nothing appears yet: the location is empty. Build the shop's menu from the WP-CLI container, with the three pages from Lesson 2.1 by ID, and assign it:

wp menu item add-post main-menu 14
wp menu item add-post main-menu 13

🧱 Widget Areas

A widget area (WordPress still calls it a "sidebar" in function names, from the days when that is where they always went) is a slot in a classic theme where the site owner places small blocks of content: opening hours, a search box, a list of categories. The theme registers the area on widgets_init and prints it in a template. Add the registration to the end of functions.php:

/**
 * Registers the footer widget area.
 */
function pagesco_classic_widgets_init() {
	register_sidebar(
		array(
			'id'            => 'footer',
			'name'          => __( 'Footer', 'pagesco-classic' ),
			'description'   => __( 'Shown in the site footer, above the address.', 'pagesco-classic' ),
			'before_widget' => '<section id="%1$s" class="widget %2$s">',
			'after_widget'  => '</section>',
			'before_title'  => '<h2 class="widget-title">',
			'after_title'   => '</h2>',
		)
	);
}
add_action( 'widgets_init', 'pagesco_classic_widgets_init' );

The id is what templates use (always set it; Common Mistakes shows why). before_widget and after_widget wrap each widget; %1$s becomes the widget's ID and %2$s its classes. The title wrappers are for widgets with a title field. Print the area in footer.php, only when it has widgets (is_active_sidebar()), so an empty area leaves no empty <div>:

<?php
/**
 * The footer: the end of the main content and the bottom of every page.
 *
 * @package pagesco-classic
 */

?>
</main>
<footer class="site-footer">
	<?php if ( is_active_sidebar( 'footer' ) ) : ?>
		<div class="footer-widgets">
			<?php dynamic_sidebar( 'footer' ); ?>
		</div>
	<?php endif; ?>
	<p><?php esc_html_e( 'Pages & Co. · 12 Market Street · 555-0142', 'pagesco-classic' ); ?></p>
</footer>
<?php wp_footer(); ?>
</body>
</html>

Since WordPress 5.8, widgets are blocks: Appearance > Widgets is a block editor, and each widget is stored as a little piece of block markup in the widget_block option. WP-CLI can add one, with the content as block markup (Lesson 2.1):

wp sidebar list --fields=name,id
wp widget add block footer --content='<!-- wp:paragraph --><p>Open Monday to Saturday, and until 9 p.m. on Thursdays.</p><!-- /wp:paragraph -->'
wp widget list footer --fields=name,id,position

Output

| name             | id                  |
+------------------+---------------------+
| Footer           | footer              |
| Inactive Widgets | wp_inactive_widgets |
+------------------+---------------------+
Success: Added widget to sidebar.
+-------+---------+----------+
| name  | id      | position |

| block | block-7 | 1        |

Two areas: your footer and wp_inactive_widgets, where WordPress parks widgets that belong to no area. The new widget is block-7: a fresh install ships five default block widgets (Search, Recent Posts, Recent Comments, Archives, Categories), numbers 2 to 6, which have been sitting among the inactive widgets because Twenty Twenty-Five has no widget areas. The footer now prints it:

			<section id="block-7" class="widget widget_block widget_text"><p class="wp-block-paragraph">Open Monday to Saturday, and until 9 p.m. on Thursdays.</p></section>		</div>

Your before_widget markup with the widget's ID and classes, and inside it the rendered paragraph block. A block widget has no title field, so before_title is unused here; a heading is just another block in the widget.

💡 Widgets are legacy, and still everywhere

Block themes have no widget areas: their templates and patterns hold that content directly, as Lesson 3.3 showed with the opening-hours synced pattern. Widgets matter for classic themes, which is most existing sites. Older "legacy widgets" are PHP classes that extend WP_Widget (the Search, Archives and Recent Posts widgets still exist that way, and plugins add their own); they appear in the block widget editor as a Legacy Widget block. Plugins such as Classic Widgets bring back the old drag-and-drop screen, and a theme can do the same with remove_theme_support( 'widgets-block-editor' ).

♿ Accessibility and Translation

Two jobs are easy to forget because a sighted, English-speaking developer never notices them missing: making the theme work for people who use a keyboard or a screen reader, and making every word in it translatable. WordPress does a lot of both for you, but only if the theme plays along.

Text for screen readers only

Core prints helpful text that is meant to be heard, not seen: the "Search for:" label you just saw, the "Posts pagination" heading in front of page numbers (Lesson 4.2), the "Post navigation" heading. It marks all of it with the class screen-reader-text and expects the theme's CSS to hide it visually while keeping it available to assistive technology. Block themes get that CSS from core. A classic theme has to bring it, and pagesco-classic does not have any CSS yet. Here is what everyone sees in the home page's pagination right now:

http://localhost:8080/   (the pagination, as visible text)

Output

Posts pagination
1
2
Next

The heading "Posts pagination" is printed as a normal, visible h2 above the page numbers. Do not delete such text; hide it the standard way. The project's stylesheet starts with the rule core themes use for .screen-reader-text (clipped to one invisible pixel, not display: none, which would hide it from screen readers too).

The theme's accessibility checklist

  • A skip link as one of the first things in <body>: "Skip to content", pointing at <main id="main">, hidden until it receives keyboard focus. Keyboard users press Tab once and jump past the header and menu on every page. Your header.php now has one, right after the store notice; block themes print the same link automatically (id="wp-skip-link", pointing at #wp--skip-link--target, the ID you saw on pagesco's <main> in Lesson 3.2).
  • Landmarks with names: one <header>, <main> and <footer> per page, and an aria-label on each <nav> ("Primary"; core labels its own, such as "Posts pagination").
  • Real buttons for actions: the menu toggle is a <button> with aria-expanded and aria-controls, which the script keeps up to date, not a clickable <div>.
  • Visible focus and enough contrast: the stylesheet draws a clear outline on :focus-visible and only uses the palette pairs you checked against WCAG AA in Lesson 3.2.
  • One h1 per page, headings in order, which your templates already do (Lessons 4.1 and 4.2). Lesson 8.3 tests all of this with real tools.

🧩 Version note: WordPress 6.7 and older need load_theme_textdomain()

WordPress 7.1 found languages/ by itself: since 6.8, wp-settings.php calls $wp_theme->load_textdomain() for the active theme just before it includes functions.php, using the Text Domain and Domain Path headers (default /languages), and does the same for each active plugin. WordPress 6.7 and older do not (checked in the official 6.7 and 6.8 images): there a theme that ships its own translations must call load_theme_textdomain( 'pagesco-classic', get_template_directory() . '/languages' ) on after_setup_theme. pagesco-classic says Requires at least: 6.6, so it keeps the call; on 7.1 it is harmless. Translations installed from WordPress.org land in wp-content/languages/themes/ and never needed it.

2. Leaving out the version

<?php

	'wp_enqueue_scripts',
	function () {
		wp_enqueue_style( 'pagesco-hours', content_url( 'mu-plugins/hours.css' ) );

What it means: no error, and the file loads. But without a version WordPress uses its own version, ?ver=7.1.3. ❓ Common Questions at This Stage

Should the version be filemtime() instead of the theme's Version?

Many tutorials use filemtime( get_parent_theme_file_path( 'style.css' ) ), the file's modification time, so every save changes the URL. It is convenient while you develop, and costs a file-system check on every request. The theme's Version is the release number your client sees, it changes exactly when you ship, and it also resets the pattern cache (Lesson 3.3), which is why this course uses it; Lesson 8.4 makes bumping it part of every deployment. During development a hard reload in the browser does the rest.

Can I load a CSS framework or a font from a CDN?

Technically yes: $src can be any URL. But each external host is an extra connection that slows the first visit, it can go down or change the file, and fonts from third-party servers send your visitors' IP addresses there, which privacy laws in some countries frown upon. Bundle the files with the theme, as pagesco does with Vollkorn (Lesson 3.3), and keep their licenses in readme.txt.

Does the block theme need wp_enqueue_scripts for anything?

Sometimes. Block themes get their CSS from theme.json and from each block's own stylesheet, so most never enqueue a file (Lesson 3.2's FAQ: WordPress does not even load a block theme's style.css). Twenty Twenty-Five still enqueues a small stylesheet for a few rules theme.json cannot express, and Lesson 3.4's child theme enqueued its style.css the same way. Scripts for interactive features are usually blocks with their own assets (Module 6).

Why did the menu items become posts?

For the same reason as almost everything in WordPress (Lesson 2.1): a menu item needs an order, a parent for submenus, a title and some settings, and posts already have all of that, plus caching and the APIs to edit them. The menu itself is a term that groups them. Block themes moved on to wp_navigation posts that hold block markup, one post per menu.

📝 Lesson Summary

🎓 Key Takeaways

  • functions.php runs on every request while the theme is active, admin and WP-CLI included; put its code in prefixed callbacks on the right hooks
  • Theme supports (title-tag, html5, post-thumbnails…) are declared on after_setup_theme; block themes get most of them automatically, and their title always
  • Enqueue assets on wp_enqueue_scripts with a prefixed handle, dependencies and a version that changes with the file; scripts can be deferred and printed in the footer
  • Menus: the theme registers locations (register_nav_menus()), the owner assigns menus, the template prints wp_nav_menu() behind has_nav_menu()
  • Widget areas: register_sidebar() with a fixed id on widgets_init, printed with is_active_sidebar() and dynamic_sidebar(); widgets are blocks since 5.8, and legacy in block themes
  • Every theme needs a skip link, .screen-reader-text CSS, labeled navigation and strings with its literal text domain; WordPress 6.8+ finds a theme's languages/ folder itself
