🔌 Lesson 5.1: Your First Plugin

Themes decide how Pages & Co. looks; everything the shop does belongs in a plugin, so it survives the next redesign. In this lesson you create pagesco-books, the plugin that the rest of the course grows into a bookstore: books and genres, settings, events, blocks, REST endpoints. Because so much will be added to it, you start with the part most tutorials skip: a structure that stays tidy at fifteen features, with a namespace, Composer autoloading and a clear rule for where new code goes.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Write a plugin header WordPress understands, including the version requirements it checks on activation
  • Organize a plugin as a short main file plus namespaced classes in src/, loaded by Composer's PSR-4 autoloader
  • Start features from one main object on plugins_loaded, and add a new feature by writing one class and listing it
  • Use activation and deactivation hooks and uninstall.php for the right jobs, and say what each must never do
  • Recognize the typical first-plugin failures: direct file access, a missing autoloader, a class the autoloader cannot find, a hook registered too late
  • ⏱️ Time 135 minutes
  • 📋 Prerequisites Lesson 4.3: functions.php: Supports, Assets, Menus & Widgets
  • 🛠️ You will build the pagesco-books plugin skeleton (namespace PagesCo\Books, Composer autoload, a "Bookseller" role on activation, cleanup on uninstall) with its first feature, the store-notice additions moved out of pagesco-site.php
  • 🧩 WordPress 7.1 on PHP 8.5 (the plugin declares WordPress 6.8 and PHP 8.2 as its minimums)
  • 🧱 Site your Pages & Co. site from Lesson 4.3, with pagesco active; Docker for the composer:2 image (Lesson 1.3)

🔌 What a Plugin Is

A plugin is PHP that WordPress loads on every request while it is active, from a folder (or a single file) in wp-content/plugins/. You already know two relatives: a must-use plugin is loaded always, with no way to switch it off in the admin (Lesson 2.3), and a theme's functions.php is loaded only while that theme is active (Lesson 4.3). A normal plugin sits in between: the site owner activates and deactivates it, WordPress runs code once at those moments, and it can clean up after itself when it is deleted. The smallest real example ships with WordPress. Look at the top of Hello Dolly from the WP-CLI container:

sed -n '1,20p' wp-content/plugins/hello.php

Output

<?php
/**
 * @package Hello_Dolly
 * @version 1.7.2
 */
/*
Plugin Name: Hello Dolly
Plugin URI: http://wordpress.org/plugins/hello-dolly/
Description: This is not just a plugin, it symbolizes the hope and enthusiasm of an entire generation summed up in two words sung most famously by Louis Armstrong: Hello, Dolly. When activated you will randomly see a lyric from <cite>Hello, Dolly</cite> in the upper right of your admin screen on every page.
Author: Matt Mullenweg
Version: 1.7.2
Author URI: http://ma.tt/
Text Domain: hello-dolly
*/

// Don't load directly.
if ( ! defined( 'ABSPATH' ) ) {
	exit;
}

Two things make it a plugin. The comment block is the plugin header: WordPress reads those Name: value lines (without running the file) to list the plugin on the Plugins screen; Plugin Name is the only required one. And the first code is a guard: ABSPATH is defined by wp-load.php, so if somebody requests the file directly from a browser, it stops before doing anything. The rest of Hello Dolly is two functions and two hooks, the same toolkit you have used since Lesson 2.3.

💡 Mental model: the shop's departments

Think of pagesco-books as the back office of the shop, and of each feature (the notice additions, the book catalog, the events calendar, the settings page) as a department with its own room. The main file is the front door with the shop's name on it: it unlocks, switches on the lights and hands a list of departments to the manager, the Plugin object, who opens each one in the morning (plugins_loaded). A new department means a new room and one new line on the manager's list, never knocking through the walls of the existing ones.

The layout you build in this lesson, and that later lessons add to:

wp-content/plugins/pagesco-books/
  pagesco-books.php      main file: header, guard, constants, autoloader, hooks; nothing else
  composer.json          the package and its PSR-4 rule: PagesCo\Books\ is in src/
  vendor/                written by Composer (autoload.php + vendor/composer/)
  uninstall.php          removes the plugin's data when it is deleted
  src/
    Plugin.php           PagesCo\Books\Plugin: starts every feature on plugins_loaded
    Feature.php          PagesCo\Books\Feature: the interface every feature implements
    Activator.php        PagesCo\Books\Activator: activation and deactivation
    StoreNotice.php      PagesCo\Books\StoreNotice: the first feature (the project)

📄 The Main File and Its Header

A plugin in a folder needs a main file with the same name as the folder: pagesco-books/pagesco-books.php. That pair, pagesco-books/pagesco-books.php, is how WordPress identifies the plugin in the active_plugins option (Lesson 2.2). Create wordpress/wp-content/plugins/pagesco-books/pagesco-books.php:

<?php
/**
 * Plugin Name:       Pages & Co. Books
 * Plugin URI:        https://example.com/pagesco-books/
 * Description:       The bookstore features of the Pages & Co. website: books, genres, events and the shop's blocks.
 * Version:           1.0.0
 * Requires at least: 6.8
 * Requires PHP:      8.2
 * Author:            Pages & Co.
 * Author URI:        https://example.com/
 * License:           GPL-2.0-or-later
 * License URI:       https://www.gnu.org/licenses/gpl-2.0.html
 * Text Domain:       pagesco-books
 *
 * @package PagesCo\Books
 */

defined( 'ABSPATH' ) || exit;

define( 'PAGESCO_BOOKS_VERSION', '1.0.0' );
define( 'PAGESCO_BOOKS_FILE', __FILE__ );
define( 'PAGESCO_BOOKS_DIR', plugin_dir_path( __FILE__ ) );

Plugin NameRequired: the name on the Plugins screen
Description, Author, Plugin URI, Author URIShown on the Plugins screen
VersionShown, and compared with the directory for updates; also your asset and upgrade version
Requires at least, Requires PHPChecked on activation: WordPress refuses to activate on an older WordPress or PHP (Exercise 1)

Requires PHP: 8.2 is the line Lesson 1.3 promised: above it, the plugin may use typed properties, match, nullsafe calls and the rest of modern PHP, even though core sticks to PHP 7.4 syntax. Requires at least: 6.8 matches what @wordpress/create-block will need for the blocks in Module 6. Below the header come the guard and three constants, the only global names this plugin defines, prefixed PAGESCO_BOOKS_: the version, the main file's path (functions such as plugins_url() and the activation hooks need it) and the plugin's folder with a trailing slash, from plugin_dir_path(). 🗂️ A Structure That Grows: Namespaces and Composer

Lesson 1.3 gave every global name a prefix. That works for a handful of functions; for a plugin with dozens of classes, PHP has a better tool, the one you used in PHP Foundations: a namespace. Every class of the plugin lives in PagesCo\Books, so its short names (Plugin, Activator, later BookPostType) cannot collide with anybody else's, and the namespace is the prefix. Hook names, options and other things WordPress stores globally still get the pagesco_books_ prefix, because a namespace does not reach into the database.

The second tool is autoloading: instead of a require line per class, the plugin tells PHP "classes in PagesCo\Books live in src/", and PHP loads each file the first time its class is used. The PSR-4 rule turns a class name into a path by replacing the namespace prefix with the folder and the backslashes with slashes, so the class name and the file name must match exactly, case included:

ClassFile (PSR-4: PagesCo\Books\ = src/)
PagesCo\Books\Pluginsrc/Plugin.php
PagesCo\Books\StoreNoticesrc/StoreNotice.php
PagesCo\Books\Admin\SettingsPage (a later lesson)src/Admin/SettingsPage.php

These file names follow PSR-4, not the class-pagesco-book-card.php style from Lesson 1.3: core's style is for WordPress's own non-namespaced classes, and PHPCS can be told to accept PSR-4 names in src/ (Lesson 8.1). Composer writes the autoloader for you. Create wordpress/wp-content/plugins/pagesco-books/composer.json:

{
	"name": "pagesco/pagesco-books",
	"description": "The bookstore features of the Pages & Co. website.",
	"type": "wordpress-plugin",
	"license": "GPL-2.0-or-later",
	"require": {
		"php": ">=8.2"
	},
	"autoload": {
		"psr-4": {
			"PagesCo\\Books\\": "src/"
		}
	}
}

The plugin needs no packages, only the autoloader, so the command is composer dump-autoload. Run it in the composer:2 container from Lesson 1.3, in the plugin's folder. From your project folder (on Windows PowerShell, leave out --user and write ${PWD}, as in Lesson 1.3):

docker run --rm -it --user "$(id -u):$(id -g)" -v "$PWD/wordpress:/var/www/html" -w /var/www/html/wp-content/plugins/pagesco-books composer:2 composer dump-autoload
composer dump-autoload

Output

Composer could not detect the root package (pagesco/pagesco-books) version, defaulting to '1.0.0'. See https://getcomposer.org/root-version
...
Generated autoload files

The first line is a harmless note (a plugin's composer.json usually has no version, so Composer assumes 1.0.0); depending on your setup Composer may also warn that it cannot write its cache, which is harmless too. The ... stands for those lines. Composer wrote vendor/autoload.php and a few files in vendor/composer/, among them platform_check.php, which stops with a clear message if the plugin ever runs on a PHP older than the "php": ">=8.2" you required. You run dump-autoload again only when the autoload section of composer.json changes; new class files in src/ are found without it, as you will see in the project.

The feature contract and the main object

Every feature will be a class with one public entry point, register(), that adds its hooks, and nothing that happens before it is called. An interface writes that rule down so PHP enforces it. Create src/Feature.php:

<?php
/**
 * The contract every feature of the plugin follows.
 *
 * @package PagesCo\Books
 */

namespace PagesCo\Books;

/**
 * A feature adds its hooks in register(), and does nothing before that.
 */
interface Feature {

	/**
	 * Adds the feature's actions and filters.
	 */
	public function register(): void;
}

The main object, src/Plugin.php, keeps the list of feature classes, starts each one, and remembers it, so that other code can reach a running feature (to remove one of its hooks, the rule from Lesson 2.3: you need the same object). Its list is empty for now:

<?php
/**
 * The plugin's main object.
 *
 * @package PagesCo\Books
 */

namespace PagesCo\Books;

/**
 * Starts the plugin's features and keeps them reachable.
 */
final class Plugin {

	/**
	 * The one instance, created on first use.
	 *
	 * @var Plugin|null
	 */
	private static ?Plugin $instance = null;

	/**
	 * The running features, keyed by class name.
	 *
	 * @var array<class-string, Feature>
	 */
	private array $features = array();

	/**
	 * Returns the plugin's one instance.
	 */
	public static function instance(): Plugin {
		if ( null === self::$instance ) {
			self::$instance = new self();
		}

		return self::$instance;
	}

	/**
	 * Creates every feature and lets it add its hooks. Runs on plugins_loaded.
	 */
	public function boot(): void {
		/**
		 * Filters the feature classes the plugin starts.
		 *
		 * @since 1.0.0
		 *
		 * @param string[] $classes Fully qualified class names of Feature implementations.
		 */
		$classes = apply_filters( 'pagesco_books_features', $this->feature_classes() );

		foreach ( $classes as $class ) {
			$feature = new $class();
			$feature->register();
			$this->features[ $class ] = $feature;
		}
	}

	/**
	 * Returns a running feature, for example to remove one of its hooks.
	 *
	 * @param string $class Fully qualified class name.
	 */
	public function feature( string $class ): ?Feature {
		return $this->features[ $class ] ?? null;
	}

	/**
	 * The plugin's features. Add a new feature class here.
	 *
	 * @return string[]
	 */
	private function feature_classes(): array {
		return array(
			// One feature class per line, for example StoreNotice::class.
		);
	}
}
  • instance() creates the object once and returns that same object every time after, so Plugin::instance() is the plugin's handle anywhere in PHP.
  • boot() runs the list through a filter of its own, pagesco_books_features (a custom hook, Lesson 2.3), then creates each feature and calls register(). new $class() is where the autoloader loads the file.
  • The types (?Plugin, array, : void) are fine here because the plugin requires PHP 8.2 and these methods are called by your own code. Hook callbacks that WordPress or other plugins call, such as a filter's $text, stay untyped, the advice from Lesson 1.3: another callback may hand you something unexpected.

Now finish the main file. Add these lines to the end of pagesco-books.php: load the autoloader, then hand boot() to plugins_loaded, the action that fires once every plugin is loaded (the table in Lesson 2.3), so a feature may rely on another plugin's functions:

require PAGESCO_BOOKS_DIR . 'vendor/autoload.php';

add_action( 'plugins_loaded', array( PagesCo\Books\Plugin::instance(), 'boot' ) );

The main file is not namespaced, so it writes the full class name, PagesCo\Books\Plugin. Activate the plugin and check that the autoloader found the class and that boot() is hooked:

wp plugin activate pagesco-books
wp eval 'var_dump( has_action( "plugins_loaded", array( PagesCo\Books\Plugin::instance(), "boot" ) ), class_exists( "PagesCo\Books\Plugin", false ) );'

Output

Plugin 'pagesco-books' activated.
Success: Activated 1 of 1 plugins.
int(10)
bool(true)

Hooked at priority 10, and the class is loaded (false as the second argument of class_exists() means "do not autoload just for this question"). The plugin is running, with no features yet.

🔄 Activation, Deactivation and Uninstall

Most plugin code runs on every request. Three moments are different, and each has a job:

graph TD A["files in wp-content/plugins"] --> B["activate: activation hook, once"] B --> C["every request: main file, then plugins_loaded"] C --> D["Plugin::boot() registers each feature"] D --> E["deactivate: deactivation hook, data kept"] E --> F["delete: uninstall.php removes the data"]
MomentRegistered withIts jobNever
Activationregister_activation_hook( __FILE__, $callback )One-time setup: roles, default options, database tables (5.5), rewrite rules for post types (5.2)Print output, or do work every request needs
Deactivationregister_deactivation_hook( __FILE__, $callback )Undo what is temporary: scheduled events (7.3), rewrite rulesDelete the owner's data: deactivating is a pause
Uninstallan uninstall.php fileRemove everything the plugin stored: options, roles, tablesRun without checking WP_UNINSTALL_PLUGIN

Lesson 2.1's FAQ suggested the first job: a Bookseller role for shop staff. Roles are stored in the database (the wp_user_roles option), so they are created once, on activation, not on every request. Create src/Activator.php. The new role starts with exactly the capabilities of the Author role; later lessons can give it more:

<?php
/**
 * What happens when the plugin is activated or deactivated.
 *
 * @package PagesCo\Books
 */

namespace PagesCo\Books;

/**
 * Activation and deactivation callbacks (uninstall.php cleans up for good).
 */
final class Activator {

	/**
	 * Runs once, when an administrator activates the plugin.
	 */
	public static function activate(): void {
		$author = get_role( 'author' );

		add_role(
			'pagesco_bookseller',
			'Bookseller',
			$author ? $author->capabilities : array( 'read' => true )
		);
	}

	/**
	 * Runs once, when the plugin is deactivated. Keeps all data.
	 */
	public static function deactivate(): void {
		// Nothing to undo yet: later lessons flush rewrite rules and clear scheduled events here.
	}
}

Register both callbacks at the end of the main file. They must be registered while the file loads, at the top level, because WordPress fires the activation hook during the activation request itself (Common Mistakes, number 3):

register_activation_hook( __FILE__, array( PagesCo\Books\Activator::class, 'activate' ) );
register_deactivation_hook( __FILE__, array( PagesCo\Books\Activator::class, 'deactivate' ) );

And the cleanup, uninstall.php in the plugin's folder. WordPress runs this file when an administrator deletes the plugin, and defines WP_UNINSTALL_PLUGIN first; the guard makes sure nothing else can run it:

<?php
/**
 * Removes the plugin's data when an administrator deletes the plugin.
 *
 * @package PagesCo\Books
 */

defined( 'WP_UNINSTALL_PLUGIN' ) || exit;

remove_role( 'pagesco_bookseller' );

The plugin is already active, so the activation hook has not run yet. Deactivate and activate again, and follow the role through the life cycle. wp plugin uninstall --skip-delete runs the uninstall procedure without deleting the files, which is how you test uninstall.php without losing your work:

wp plugin deactivate pagesco-books
wp plugin activate pagesco-books
wp role list --fields=name,role
wp plugin deactivate pagesco-books
wp role list --field=role | grep -c pagesco_bookseller
wp plugin uninstall pagesco-books --skip-delete
wp role list --field=role | grep -c pagesco_bookseller
wp plugin activate pagesco-books

Output

🧩 Version note: plugins and load_plugin_textdomain()

Old plugins call load_plugin_textdomain( 'my-plugin', false, … ) on init so WordPress finds the translations in their languages/ folder. Since WordPress 6.8, wp-settings.php registers each active plugin's Text Domain and Domain Path itself (the same change you met for themes in Lesson 4.3), and translations from WordPress.org never needed the call. pagesco-books requires 6.8, so it leaves the call out; a plugin that supports 6.7 or older and ships its own translations still needs it. Either way, never translate strings at the top level of the main file: WordPress 6.7+ reports "Translation loading for the pagesco-books domain was triggered too early" when a translation exists. Lesson 8.3 builds the translation files.

⚠️ Common Mistakes

Each mistake breaks the plugin on purpose and repairs it right after, so pagesco-books ends as it started.

1. No guard against direct access

Every PHP file in wp-content/ can be requested by URL. Comment out the guard line in the main file for a moment and request the file directly, as an attacker's scanner would:

sed -i "s#^defined( 'ABSPATH' ) || exit;#// &#" wp-content/plugins/pagesco-books/pagesco-books.php
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/wp-content/plugins/pagesco-books/pagesco-books.php
sed -i "s#^// defined#defined#" wp-content/plugins/pagesco-books/pagesco-books.php
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/wp-content/plugins/pagesco-books/pagesco-books.php

Output

500
200

What it means: without the guard the file runs on its own, without WordPress, and dies on the first WordPress function: a 500 error, and in the server log (docker compose logs wordpress, Lesson 1.2) the line PHP Fatal error: Uncaught Error: Call to undefined function plugin_dir_path() in /var/www/html/wp-content/plugins/pagesco-books/pagesco-books.php:22. On a host that displays errors, every visitor sees that message, with your server's file paths. Worse, a file that does something at the top level (deletes data, sends mail) would do it for anyone who knows the URL. With the guard back, the request ends quietly with 200 and an empty page. Fix: defined( 'ABSPATH' ) || exit; at the top of every PHP file that can run on its own: the main file, uninstall.php (its own constant) and any file with top-level code. Files in src/ only declare a class, so a direct request does nothing there.

wp plugin activate pagesco-books

3. Registering the activation hook too late

A tidy-minded developer moves everything into a plugins_loaded callback, the activation hook included. Try it with a one-file plugin, wordpress/wp-content/plugins/pagesco-late-hook.php:

<?php
/**
 * Plugin Name: Late Hook Demo
 */

add_action(
	'plugins_loaded',
	function () {
		register_activation_hook( __FILE__, 'pagesco_late_hook_activate' );
	}
);

/**
 * Should run once, on activation.
 */
function pagesco_late_hook_activate() {
	update_option( 'pagesco_late_hook', 'activated' );
}
wp plugin activate pagesco-late-hook
wp option get pagesco_late_hook

Output

Plugin 'pagesco-late-hook' activated.
Success: Activated 1 of 1 plugins.
Error: Could not get 'pagesco_late_hook' option. Does it exist?

What it means: the plugin activated, and the activation callback never ran: no option, no warning. On the activation request plugins_loaded has already fired before WordPress includes the new plugin's file, so the closure that would register the hook is never called. Fix: call register_activation_hook() and register_deactivation_hook() at the top level of the main file, with __FILE__, as pagesco-books.php does. Remove the demo:

wp plugin deactivate pagesco-late-hook
wp plugin delete pagesco-late-hook

Output

Plugin 'pagesco-late-hook' deactivated.
Success: Deactivated 1 of 1 plugins.
Deleted 'pagesco-late-hook' plugin.
Success: Deleted 1 of 1 plugins.

4. A file name that does not match the class

This one waits for the project's first feature, so it is the project's last step. Read on.

🛠️ Project: The First Feature Moves In

Since Lesson 2.3, two callbacks in mu-plugins/pagesco-site.php have been waiting for a better home: the Thursday hours and the "See events" link, code that, as Lesson 2.3 said, "in Module 5 ... moves into the pagesco-books plugin". The notice bar itself stays in the must-use plugin (it is site furniture that must always be there); the shop's additions to it become the plugin's first feature. Allow about 30 minutes.

🛠️ Step 1: Write the feature and list it (10 min)

Create src/StoreNotice.php. It implements Feature, and its register() attaches two methods to the notice's own hooks, at the same priorities as the old functions. The strings now belong to the plugin's text domain:

<?php
/**
 * The shop's additions to the store notice from the pagesco-site must-use plugin.
 *
 * @package PagesCo\Books
 */

namespace PagesCo\Books;

/**
 * Adds the late-opening hours and an events link to the store notice.
 */
final class StoreNotice implements Feature {

	/**
	 * Hooks into the notice's own filter and action (Lesson 2.3).
	 */
	public function register(): void {
		add_filter( 'pagesco_store_notice', array( $this, 'add_late_opening' ), 20 );
		add_action( 'pagesco_store_notice_end', array( $this, 'print_events_link' ) );
	}

🛠️ Step 3: The case of the missing class (5 min)

Common Mistake number 4, on purpose. Rename the feature's file with a lowercase n (as might happen when a file is created on a laptop and deployed to a Linux server) and load a page:

mv wp-content/plugins/pagesco-books/src/StoreNotice.php wp-content/plugins/pagesco-books/src/Storenotice.php

#0 /var/www/html/wp-includes/class-wp-hook.php(353): PagesCo\Books\Plugin->boot('')
#1 /var/www/html/wp-includes/class-wp-hook.php(377): WP_Hook->apply_filters(NULL, Array)
#2 /var/www/html/wp-includes/plugin.php(523): WP_Hook->do_action(Array)

What it means: boot(), called from plugins_loaded in wp-settings.php, asked for PagesCo\Books\StoreNotice; the autoloader looked for exactly src/StoreNotice.php and found nothing, because Linux file names are case-sensitive. (With WP_DEBUG off, visitors would see "There has been a critical error on this website" and the admin would get a recovery-mode email, which Mailpit would catch.) 🏋️ Exercise 2: Add a Feature the Plugin's Way

Lesson 2.3's bonus challenge added a pagesco-site class to the <body> tag. Do it as a pagesco-books feature: a class BodyClasses that implements Feature and filters body_class, listed in Plugin::feature_classes(). Check the home page's body tag, then remove the feature again (file and list line).

<?php
/**

 *
 * @package PagesCo\Books

 * Adds the pagesco-site class to the body of every front-end page.

		$classes[] = 'pagesco-site';
		return $classes;
	}
}

❓ Common Questions at This Stage

Is Composer worth it for a plugin with no dependencies?

For one or two files, a require line is fine. pagesco-books will have a dozen classes by Module 7, plus tests in Lesson 8.1 that need the same autoloader, and every require you do not write is one you cannot forget. The cost is one command and a vendor/ folder. If the plugin later needs a library from Packagist, the setup is already there; for plugins distributed to many sites, tools such as Strauss or PHP-Scoper rename bundled libraries so two plugins cannot load clashing versions of the same one.

Why a static instance() instead of a global variable?

Both give other code a way to reach the plugin's object. A global ($GLOBALS['pagesco_books']) can be overwritten by any code by accident; Plugin::instance() can only ever return the one object, and its name lives in your namespace. Some developers prefer to avoid single instances altogether and pass objects around (dependency injection). The course keeps one small, predictable entry point, because hooks need a way to find the object that added them.

Should vendor/ go into Git?

Usually not: you commit composer.json (and composer.lock once there are packages) and run Composer when building or deploying, so the repository holds only your code. A site plugin that is deployed by copying files, or a plugin submitted to the directory, must include vendor/ in the files that reach the server. Lesson 8.4 sets this up for Pages & Co.

Why is the store notice itself still a must-use plugin?

Because nobody should be able to switch it off by accident, and it has no settings or data: it is site furniture. The shop-specific extras became a feature of pagesco-books, where they can be turned off or replaced with the plugin. Many agencies use exactly this split: a small must-use plugin for what must always run, and a normal plugin for the client's features.

🎓 Key Takeaways

  • A plugin is a folder in wp-content/plugins/ with a main file of the same name whose header comment has at least Plugin Name; Requires at least and Requires PHP are checked on activation
  • Guard every file that can run on its own with defined( 'ABSPATH' ) || exit;
