🧭 Lesson 1.1: WordPress for Developers

You can write PHP, and you can design and query a MySQL database. That puts you one step away from one of the most in-demand skills in web development: building for WordPress, the PHP application that runs a huge share of the web. This lesson is your map. You will see what WordPress is when you look at it as a developer rather than as a site owner, follow one request through its core files, learn where your own code is allowed to live, and meet Pages & Co., the bookstore website you will build from an empty theme to a deployed site over this course.

By the end of this lesson, you will be able to:

  • Describe WordPress 7.1 as a developer sees it: a PHP and MySQL application with themes, plugins, blocks and APIs as extension points

  • Trace a front-end request from index.php to the finished HTML, naming the core files on the way
  • Say where your code belongs (themes, plugins, must-use plugins in wp-content/) and why you never edit core files

🌍 What WordPress Is, for a Developer

A site owner sees WordPress as a dashboard where you write posts, upload photos and pick a theme. A developer sees something else: a PHP application that stores its content in a MySQL database and builds every page on request, the same kind of program you wrote in PHP Foundations, only much bigger and with twenty years of design decisions behind it. It is free, open-source software under the GPL license, built by a worldwide community of contributors, and it runs everything from personal blogs to news sites, university sites and online stores. Surveys such as W3Techs have measured it running more than four in ten of all websites for years, which is why WordPress skills show up in so many job listings and freelance requests.

What makes WordPress a platform rather than just a program is that it was designed to be extended without being edited. Almost everything a professional WordPress developer does falls into one of these extension points, and each has its own module in this course:

HooksNamed moments where core calls your functions (actions) or lets you change a value (filters)Lesson 2.3, then everywhere
ThemesDecide how the site looks: templates, styles, layouts. Modern ones are block themes configured with theme.jsonModules 3 and 4

That is why the course teaches both: block themes first because new sites start there, classic and hybrid themes right after.

💡 Mental model: a building with rooms you may rent

Think of WordPress core as an apartment building. The owner (the WordPress project) maintains the structure, the wiring and the plumbing, and renovates it a few times a year. You are a tenant. You can paint and furnish your rooms as you like (themes), plug appliances into the sockets the building provides (plugins and hooks), and even add a doorbell that rings in the lobby (the REST API). What you never do is knock down a wall in the building itself: the next renovation would put it back, and your changes would be gone. Every rule in this course about where code goes comes from this picture.

🏢 WordPress.org vs WordPress.com

The two names cause more confusion for newcomers than anything else, so get it straight once:

  • WordPress.org is the home of the open-source software: the download, the documentation (the developer handbooks and Code Reference), the free plugin and theme directories, the support forums and the community that builds WordPress. When people say "self-hosted WordPress" they mean this software, installed on a server you control.
  • WordPress.com is a commercial hosting service run by Automattic, a company co-founded by WordPress co-founder Matt Mullenweg. It runs the same software for you. Its plans differ in what you are allowed to change: the lower ones do not let you upload your own plugins or themes; the higher ones do.

A useful comparison: WordPress.org is like the Android operating system, open for any manufacturer to use; WordPress.com is one company's phone that ships with it. Plenty of other companies host WordPress too, from cheap shared hosting to managed WordPress hosts that handle updates, caching and backups for you (Lesson 8.4 compares them).

✅ Rule of thumb for client work

If a project needs custom code, which is every project in this course, you need an environment where you can install your own theme and plugin. Before you quote a job, ask where the site is hosted and on which plan: "we are on WordPress.com" may mean "you cannot install a plugin until we upgrade".

🔄 One Request, Start to Finish

In PHP Foundations you wrote pages where one PHP file handled one URL. WordPress works differently: almost every front-end URL, /, /hello-world/, /books/dune/, is handled by the same file, index.php in the WordPress root. The web server sends every request that does not match a real file to it (that is what "pretty permalinks" set up, Lesson 1.2). From there WordPress loads itself, works out what you asked for from the URL, and picks a template to draw it with.

graph TD A["Browser asks for /hello-world/"] --> B["index.php"] B --> C["wp-blog-header.php"] C --> D["wp-load.php finds wp-config.php"] D --> E["wp-settings.php: core, plugins, theme"] E --> F["action: init"] F --> G["wp(): parse the URL, run the main query"] G --> H["template-loader.php picks a template"] H --> I["HTML sent to the browser"]

You do not have to take the diagram on trust: the files are short and readable. These outputs come from the course's development site, the one you set up in the next lesson; once you have it, you can run the same commands yourself. The first two lines of real code in index.php and the heart of wp-blog-header.php:

grep -n "WP_USE_THEMES\|require" index.php
grep -n "require\|wp();" wp-blog-header.php

Output

14:define( 'WP_USE_THEMES', true );
17:require __DIR__ . '/wp-blog-header.php';
13:	require_once __DIR__ . '/wp-load.php';
16:	wp();
19:	require_once ABSPATH . WPINC . '/template-loader.php';

That is the whole front door. index.php sets one constant (WP_USE_THEMES, "draw this request with the theme") and hands over to wp-blog-header.php, which does three things in order:

  1. Load WordPress (wp-load.php). It finds wp-config.php, your site's settings (database name and password, debug switches), and that file ends by loading wp-settings.php, which loads the core library, connects to the database, loads must-use plugins, active plugins and the active theme, and fires actions such as plugins_loaded and init along the way. By the end, everything your code registered is known.
  2. Work out the request (wp()). WordPress matches the URL against its rewrite rules, turns it into query variables ("the post with the slug hello-world") and runs the main query against the database. This is the step that replaced the router you might have written yourself.
  3. Draw the page (template-loader.php). From what the query found (one post, a page, an archive, a 404), WordPress picks the most specific template the theme has, using the template hierarchy (Lesson 3.1), and runs it. The theme's markup, the blocks and the content come together into HTML.

You can see the end of the trip from the outside. From the WP-CLI container (Lesson 1.2), curl asks the site for a page just as a browser would; this prints the page's <title>:

curl -s http://localhost:8080/hello-world/ | grep -o '<title>.*</title>'

Output

<title>Hello world! &#8211; Pages &amp; Co.</title>

"Hello world!" is the post the URL asked for, found by the main query; "Pages & Co." is the site title stored in the database (as &amp;, the HTML way of writing an ampersand, a detail Lesson 1.2 comes back to). The &#8211; between them is an en dash written as an HTML entity, WordPress's default separator, which your browser tab shows as a plain dash. None of it is written in any file. This is the same request/response cycle as PHP Foundations Lesson 1.1, with WordPress doing the routing, the database work and the templating for you, and with hooks along the whole path where your code can join in.

💡 Why this matters before you write any code

Most WordPress bugs are timing bugs: code that runs before the thing it needs exists. "Is the user known yet?" "Has the theme loaded?" "Has the main query run?" If you keep this sequence in mind (load, then query, then template), most of those questions answer themselves. Lesson 2.2 walks through wp-settings.php in detail, and Lesson 2.3 hangs your first code on its hooks.

🛑 Never edit core files

Changing a file in wp-admin/, wp-includes/ or the root "to make it work" is the classic beginner fix, and it always comes back to bite. Every WordPress update replaces those files, so your change silently disappears, and a security update may be applied automatically in the middle of the night. A modified core file is also exactly what security scanners look for when a site has been hacked. If you need WordPress to behave differently, there is a hook, a theme or a plugin for it. Common Mistakes 1 shows how WordPress itself notices an edited core file.

💡 What changes most: you write less of the program

In your own PHP apps you wrote the main program and called libraries. In WordPress, core is the main program and calls you. Developers call this "inversion of control", and it takes a few lessons to feel natural. If you catch yourself asking "where do I put the code that runs first?", the WordPress answer is almost always "in a function, attached to the right hook".

🧠 How to Learn in This Course

This is a hands-on course. Each lesson teaches an idea, shows it working, breaks it on purpose, and then has you build part of Pages & Co. with it. A few habits will make it go much more smoothly.

Type the examples, and trust the outputs

Every command and every piece of code in this course was run on a real WordPress 7.1.3 site on PHP 8.5, and the Output card under it shows what it really printed. If your output differs, that difference is information: a typo, a missed step, a file in the wrong folder. Cards labeled "your ... will differ" show things that change on every run, such as dates and security tokens. Type the examples rather than pasting them, at least the short ones: your fingers learn the function names faster than your eyes do. Copy buttons are there for the long ones.

Read the errors on purpose

Every lesson has a Common Mistakes section where you make real mistakes deliberately and read what WordPress says. A developer who can read "Fatal error: Uncaught ArgumentCountError" calmly fixes it in a minute; one who panics takes an afternoon. The messages in this course are the real ones, so you will recognize them when they show up in your own work.

Use the official documentation

Nobody memorizes WordPress. Professionals look things up all day, mostly in two places at developer.wordpress.org: the Code Reference (every core function, class and hook with its source) and the handbooks (Theme, Plugin, Block Editor, REST API). When a lesson introduces a function, open its Code Reference page once; you will get faster at it every time. Be careful with older blog posts and videos: check which WordPress version they were written for, because much of what you find is from before blocks.

Keep a learning journal

At the end of every lesson there is a short journal prompt. Writing down what clicked and what did not is one of the most reliable ways to make knowledge stick, and your journal becomes the place you look up "how did I fix that last time?". A notebook or a plain text file is enough. Start it today with the first entry at the end of this lesson.

✅ Growth mindset: add the word "yet"

WordPress is big, and at some point in this course you will think "I don't get hooks" or "blocks are too much". Add one word: "I don't get hooks yet." Every WordPress developer you will ever work with felt lost in core at first; the difference between them and someone who gave up is only that they kept going. Plateaus are normal, mistakes are feedback, and this course is a marathon you run one lesson at a time.

⏱️ Plan your time

Each lesson shows an honest time at the top: reading, typing every example, the project, the exercises, the quiz and the journal. Most lessons take between one and a half and two and a half hours. Two shorter sessions work better than one long one, and stopping in the middle of a project is fine: your site keeps its state until you come back.

⚠️ Common Mistakes

You do not have a site of your own until the next lesson, so here you watch these mistakes on the course site. Come back and repeat them on yours once Lesson 1.2 is done: each takes a minute.

1. "Fixing" something by editing a core file

Suppose a tutorial tells you to add a line to wp-includes/functions.php. This makes a backup in wp-content/, appends a harmless comment to that core file, and asks WP-CLI to compare every core file with the official checksums from WordPress.org:

cp wp-includes/functions.php wp-content/functions.php.bak
echo '// my quick fix' >> wp-includes/functions.php
wp core verify-checksums

Output

Warning: File doesn't verify against checksum: wp-includes/functions.php
Warning: File should not exist: wp-config-docker.php
Error: WordPress installation doesn't verify against checksums.

What it means: WordPress knows exactly what every core file should contain, and the edited one fails the check (the other warning, about wp-config-docker.php, is the Docker image's extra file, expected on a Docker site). Updates replace a modified file without asking, and security plugins report it as a possible hack. Fix: put the change in a plugin or theme, attached to a hook, and leave core alone. Restore the file and check again:

mv wp-content/functions.php.bak wp-includes/functions.php
wp core verify-checksums

Output

Warning: File should not exist: wp-config-docker.php
Success: WordPress installation verifies against checksums.

2. Copying code from an old tutorial

A tutorial from years ago gets the current user with get_currentuserinfo(). The function still exists, so the code "works", but WordPress tells you it should not be used:

wp eval 'get_currentuserinfo();'

Output

Deprecated: Function get_currentuserinfo is <strong>deprecated</strong> since version 4.5.0! Use wp_get_current_user() instead. in /var/www/html/wp-includes/functions.php on line 6260

What it means: deprecated functions are kept so old sites keep running, but they may be removed one day, and the replacement is usually better. The message names the version that deprecated it (4.5.0, many years ago) and the replacement. The <strong> tags are there because WordPress formats the message for a web page. You only see messages like this with debugging turned on, which is one reason your development site will always have it on (Lesson 1.2). Fix: use wp_get_current_user(), and check the date and the WordPress version of any tutorial before you copy from it.

3. Customizing a theme you did not write

It is tempting to add a few lines to wp-content/themes/twentytwentyfive/functions.php or to tweak one of its templates. Twenty Twenty-Five is updated through the dashboard like a plugin, and an update replaces the whole twentytwentyfive/ folder: your lines are gone, without a warning. The same goes for any theme or plugin from the WordPress.org directory or a marketplace. Fix: site features go in your own plugin (Module 5), design changes go in your own theme or a child theme of the one you want to change (Lesson 3.4). Ask "who updates this folder?" before you edit any file in wp-content/: if the answer is not "me", do not edit it.

🛠️ Project: Meet WordPress and Plan Pages & Co.

Before you install anything, take WordPress for a test drive and write down what you are going to build. You will use WordPress Playground, a complete WordPress that runs inside your browser tab (PHP compiled to WebAssembly, with an in-browser database). Nothing is installed, and the site disappears when you close the tab unless you choose to save it. Allow about 40 minutes.

🛠️ Step 1: Start a WordPress in your browser (5 min)

Open this address in a current desktop browser. After a few seconds you are looking at a fresh WordPress site, logged in as an administrator:

https://playground.wordpress.net/

Use Playground's settings panel to check which WordPress and PHP versions it is running, and pick WordPress 7.1 if it offers a choice. (Playground's default PHP version can be older than 8.5; for looking around that makes no difference.) Click through the dashboard: Posts, Pages, Appearance, Plugins, Settings. Note what is in the left-hand menu; Lesson 2.1 explains each part from a developer's point of view.

🛠️ Step 2: Look at content the way WordPress stores it (10 min)

Go to Pages and add a new page titled "About Us". Add a heading "Our Story" and a paragraph "Pages & Co. has sold books on Main Street since the day it opened." Then open the editor's options menu (the ⋮ button at the top right) and choose Code editor. You are looking at what WordPress saves in the database for this page:

<!-- wp:heading -->
<h2 class="wp-block-heading">Our Story</h2>
<!-- /wp:heading -->

<!-- wp:paragraph -->
<p>Pages &amp; Co. has sold books on Main Street since the day it opened.</p>
<!-- /wp:paragraph -->

Plain HTML, wrapped in HTML comments that name each block. That is the whole trick of the block editor: the comments let the editor rebuild the blocks, and the HTML between them is what visitors get. Switch back to the Visual editor, publish the page and view it. Write in your journal one thing that surprised you about this markup; Lesson 2.1 goes deeper.

🏋️ Hands-on Exercises

These are thinking exercises: pen and paper (or your plan file) is enough. Try each one before you open the solution.

🏋️ Exercise 1: Theme, Plugin or Content?

For each item, decide where it belongs: theme, plugin or content. (a) A "Staff Pick" badge setting that marks some books. (b) The header layout with the logo on the left. (c) The text of the store's return policy. (d) An email to staff whenever a new event is added. (e) The font used for book titles. (f) Google Analytics tracking code that the store wants on every page whatever the design.

💡 Hint

Ask of each one: should it survive a redesign? Is it something staff type in, or something a developer builds?

✅ Solution

(a) Plugin: it is data about books, and books must survive a new theme (it would be book meta, Lesson 5.2). (b) Theme: pure layout. (c) Content: staff write it in a page. (d) Plugin: behavior, unrelated to design. (e) Theme: theme.json typography (Lesson 3.2). (f) Plugin (or a must-use plugin): it is required "whatever the design", the exact test. Putting tracking code in a theme is a common reason it vanishes after a redesign.

🏋️ Exercise 2: Follow /books/dune/

A visitor opens http://localhost:8080/books/dune/ on the finished Pages & Co. site. List, in order, the core files and steps WordPress goes through, from the first file that runs to the HTML. Where along the way does your pagesco-books plugin get the chance to say "there is a post type called book"? Why must that happen before the main query?

💡 Hint

Use the diagram in "One Request, Start to Finish". Plugins are loaded inside one of those files, and init fires before wp().

✅ Solution

index.php → wp-blog-header.php → wp-load.php → wp-config.php → wp-settings.php (core, must-use plugins, plugins including pagesco-books, the theme, then the init action) → wp() matches the URL to the rewrite rule for books and runs the main query for the book with the slug dune → template-loader.php picks the theme's template for a single book → HTML. The plugin registers the post type on init (Lesson 5.2). It must happen before the main query because the rewrite rule for /books/… and the post type itself only exist once they are registered; if they were registered later, wp() would not recognize the URL and the visitor would get a 404.

🏋️ Exercise 3: Choose the Hosting

Three people ask for your advice. (a) A retired teacher wants a simple blog about birds, no budget for a developer, and never wants to think about updates. 💡 Hint

Who needs custom code, and who needs someone else to do the maintenance?

✅ Solution

(a) WordPress.com (or another fully managed host) on a basic plan: no custom code, maintenance done for her. (b) Self-hosted WordPress on a host that allows custom themes and plugins, typically a managed WordPress host or a VPS; this course's choice. (c) A managed WordPress host or a VPS with staging, SSH and WP-CLI (Lesson 8.4). For (b) on WordPress.com, ask: "Which plan are you on, and does it allow uploading your own plugins and themes?" If not, the store must upgrade or move before you can deliver.

(2) What is the last line of real code in wp-config-sample.php, and what does that tell you about where your own settings must go in wp-config.php? (3) After Lesson 1.2, find the line where the function wp() is defined.

💡 Hint

For (3), grep -n "^function wp(" wp-includes/functions.php from the WP-CLI container. Functions are defined in wp-includes/.

✅ Solution

(1) So the file only does its work once, even if it is included twice; with require_once plus the flag, a second include does nothing. (2) require_once ABSPATH . 'wp-settings.php';, right under the comment "That's all, stop editing!". Anything you define in wp-config.php must come above that line, because by the time wp-settings.php runs, WordPress has already read your constants. (3) On the course site:

grep -n "^function wp(" wp-includes/functions.php

1349:function wp( $query_vars = '' ) {

The one-line call wp(); in wp-blog-header.php leads here, to the function that sets off the whole query process. Reading core is often just that: following one function into the next.

❓ Common Questions at This Stage

Do I need to know JavaScript and React for this course?

For Modules 1 to 5, no: it is PHP, SQL, HTML and some CSS. Module 6 (custom blocks) uses modern JavaScript and a little React, and the lessons explain what you need as they go; if you have written JavaScript before, you will be fine. The build tooling (Node 24, @wordpress/scripts) is set up step by step in Lesson 6.1.

Is WordPress still worth learning with so many newer platforms around?

Yes, for a practical reason: the sheer number of existing WordPress sites means a steady demand for people who can maintain, extend and rebuild them, and new sites keep being built on it because clients can edit their own content. WordPress has also kept moving: block themes, the REST API, the Interactivity API and AI building blocks in 7.x. The skills transfer too: PHP, SQL, React, REST and good security habits are useful well beyond WordPress.

What about page builders like Elementor or Divi?

They are plugins that replace much of the editor and theme with their own drag-and-drop system, and you will meet them on client sites. This course teaches the core platform underneath: blocks, themes and plugins written in code. That is what lets you extend any site, page builder or not, and what page-builder add-ons are themselves built with.

My computer is old. Can I still do the course?

Lesson 1.2 runs WordPress in Docker, which works best with 8 GB of memory or more and a few gigabytes of free disk space. If that is a struggle, the lesson also shows wp-env and WordPress Playground, and many lessons can be followed in Playground with some limits. Lesson 1.2's FAQ has details.

📝 Lesson Summary

🎓 Key Takeaways

  • For a developer, WordPress is a PHP application on MySQL that you extend through hooks, themes, plugins, blocks and APIs, never by editing core
  • WordPress.org is the open-source software and its community; WordPress.com is one hosting service, where custom code depends on the plan
  • Every front-end request goes index.php → wp-blog-header.php → wp-load.php / wp-config.php → wp-settings.php → wp() (the main query) → template-loader.php → HTML
  • Your code lives in wp-content/: themes for looks, plugins for features, must-use plugins for site-wide code; everything else WordPress knows is in the database
  • Your PHP and MySQL skills carry over; WordPress adds its own conventions: hooks, escaping functions, WP_Query, capabilities
  • WordPress 7.1 is block-first (block themes, theme.json, the Interactivity API) while classic APIs stay supported and widely used
