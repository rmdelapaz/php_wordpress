🎨 Lesson 3.1: Theme Anatomy & the Template Hierarchy

Your site already has content (Lesson 2.1) and behavior of its own (the store notice from Lesson 2.3). What it does not have yet is a look of its own: every page is still drawn by Twenty Twenty-Five. Before you build the Pages & Co. theme in the next lesson, you will take a theme apart, meet the three kinds of theme you will find on real client sites, and learn the rule WordPress follows to choose a template for every URL: the template hierarchy.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Explain what belongs in a theme and what belongs in a plugin, and where WordPress records which theme is active
  • Tell block, classic and hybrid themes apart by their files, and confirm it with wp_is_block_theme() and wp_theme_has_theme_json()
  • Find your way around a block theme: style.css, theme.json, templates/, parts/, patterns/, styles/ and functions.php in Twenty Twenty-Five
  • Predict which template WordPress uses for a URL, for block themes and classic themes, from the template hierarchy
  • Watch WordPress make that choice on a running site with the *_template_hierarchy filters and template_include

  • 📋 Prerequisites Lesson 2.3: The Hooks System

  • 🧩 WordPress 7.1 on PHP 8.5 (block themes exist since WordPress 5.9; everything here works on 6.6 and later)

🖼️ What a Theme Does

A theme decides how the site looks: the layout of each kind of page, the colors and fonts, the header and footer, the markup around your content. It does not decide what the site is. Posts, pages, users and settings live in the database (Lesson 2.1), and features such as the store notice live in plugins (Lesson 2.3). Switch the theme and all of that stays; only the presentation changes.

💡 Mental model: the shop fit-out

Think of Pages & Co. moving its stock into a newly decorated shop. The books (content) and the till system (plugins) move across unchanged. The shelving, the signs, the paint and the window display (the theme) are what is new. A good theme is like a good fit-out: you can replace it next year without losing a single book. That is the test to apply whenever you wonder where code belongs: "would we want to keep this after a redesign?" If yes, it goes in a plugin.

Every theme is a folder in wp-content/themes/. Your site has the three recent default themes; WP-CLI lists them, and the one marked active is drawing your pages:

wp theme list

Output

| name              | status   | update | version | update_version | auto_update |

WordPress remembers the active theme in two options (you saw their rows, template and stylesheet, in Lesson 2.2). stylesheet is the folder of the active theme; template is the folder of its parent. For a normal theme both are the same. They differ for a child theme, which borrows everything it does not override from a parent (Lesson 3.4):

wp option get template

🧱 Block, Classic and Hybrid Themes

WordPress has been through one big change in how themes are built. For most of its history, themes were folders of PHP files: index.php, single.php, header.php, each printing HTML around template tags such as the_title(). Since WordPress 5.9 a theme can instead be built from blocks: its templates are HTML files full of block markup, the same kind you met in post_content in Lesson 2.1, and its design settings live in a JSON file, theme.json. You will meet both kinds on client sites for years to come, plus a mix of the two.

In this coursepagesco (3.2 to 3.4)pagesco-classic (Module 4)Module 4 adds theme.json

"Hybrid" is not an official type; it is what developers call a classic theme that adopted some block features, most often a theme.json file for colors and fonts in the editors. Most existing commercial themes are classic or hybrid, and new default themes have been block themes since Twenty Twenty-Two. You do not have to guess which kind you are looking at. WordPress tells you:

wp eval 'var_dump( wp_is_block_theme(), wp_theme_has_theme_json() );'

Output

bool(true)
bool(true)

wp_is_block_theme() is true when the active theme has a templates/index.html; wp_theme_has_theme_json() when it has a theme.json. Twenty Twenty-Five has both. A classic theme answers false, false and a hybrid false, true; you will produce all three answers with one small theme in the project.

Same request, two ways of drawing it

Up to the moment WordPress has chosen a template, block and classic themes are handled the same way: the same hierarchy, the same hooks. The difference is what happens next. A classic theme's PHP template is simply included and prints the page itself. For a block theme, WordPress includes its own file, wp-includes/template-canvas.php, which renders the block template to HTML first and then prints the document around it, calling wp_head(), wp_body_open() and wp_footer() for the theme ("core prints the page" in the diagram). A classic theme's template has to call those three itself. That is why your store notice from Lesson 2.3 appeared without Twenty Twenty-Five containing a single line of PHP for it.

graph TD A["GET /about/"] --> B["template-loader.php"] B --> C["hierarchy: candidate names"] C --> D{"block theme?"} D -->|"yes"| E["page.html"] D -->|"no"| F["page.php"] E --> G["core prints the page"] F --> H["theme prints the page"]

The legacy screens

Classic themes are edited with three older admin tools: the Customizer (live preview of theme options), Menus and Widgets. With a block theme they step aside. WordPress hides the Customize menu item unless a plugin or theme still hooks into it, and the Menus screen refuses to open. Logged in as admin, try http://localhost:8080/wp-admin/nav-menus.php:

http://localhost:8080/wp-admin/nav-menus.php

Output

Your theme does not support navigation menus or widgets.

Navigation in a block theme is a block, and the menus it shows are wp_navigation posts (post 4 on your site, Lesson 2.1). The Customizer, Menus and Widgets are legacy: not wrong, still fully supported for classic themes, and you will use menus and widget areas in Lesson 4.3. New themes just do not need them.

theme.json: the design system

Twenty Twenty-Five's theme.json is over 700 lines, but it has only a handful of top-level keys. WordPress reads JSON files with wp_json_file_decode(), so you can ask it for the outline:

wp eval '$json = wp_json_file_decode( get_theme_file_path( "theme.json" ), array( "associative" => true ) ); echo implode( ", ", array_keys( $json ) ), "\n", implode( ", ", array_keys( $json["settings"] ) ), "\n", implode( ", ", array_keys( $json["styles"] ) ), "\n";'

Output

$schema, version, settings, styles, templateParts, customTemplates
appearanceTools, color, layout, spacing, typography, useRootPaddingAwareAlignments
color, spacing, typography, blocks, elements

Line one: the schema and version (3, the current format), then settings (what the editors offer: which colors, sizes and controls), styles (what is applied: the actual colors of the page, headings, links and individual blocks), templateParts (names and areas of the parts) and customTemplates (extra templates editors can pick for a page). Lines two and three are the sections inside settings and styles. Lesson 3.2 writes one of these files from scratch.

It is all block markup. wp:template-part {"slug":"header"} pulls in parts/header.html. wp:post-title, wp:post-featured-image and wp:post-content are dynamic blocks: they have no HTML of their own in the file because they are rendered by PHP when the page is requested, from whichever post is being viewed. wp:group is a static wrapper with its HTML saved inline. wp:pattern inserts a registered pattern (Lesson 3.3). Template parts are block markup too, and Twenty Twenty-Five's header is a one-liner that only inserts a pattern:

functions.php in a block theme

A block theme does not need a functions.php at all, but most have one for the jobs JSON cannot do. What does Twenty Twenty-Five hook into?

🛑 Look, do not edit

Reading Twenty Twenty-Five is encouraged; editing it is not. A theme update replaces the whole folder, the same way a core update replaces wp-includes/ (Lesson 1.1), and your changes vanish without a warning. To change a theme someone else maintains, write a child theme (Lesson 3.4) or your own theme (Lesson 3.2).

🪜 The Template Hierarchy

A theme does not register "use single.html for posts". It just provides files with the right names, and WordPress works out which one to use. For each request it builds a list of candidate template names, from the most specific to the most general, and uses the first one the theme has. The list is the template hierarchy, and it is the same for both kinds of theme: a classic theme answers with single.php, a block theme with templates/single.html.

💡 Mental model: asking at the information desk

A customer asks for Dune. The bookseller checks the most specific place first: is there a display just for this book? No. A shelf for Frank Herbert? No. The science fiction section? Yes: done. If there were no science fiction section either, the customer would be sent to the general shelves, and every shop has those. In WordPress the "general shelves" are index: every theme must have it, so the search always ends somewhere.

For a single blog post with the slug hello-world, the chain looks like this:

graph TD A["single-post-hello-world"] -->|"not found"| B["single-post"] B -->|"not found"| C["single"] C -->|"not found"| D["singular"] D -->|"not found"| E["index"]

The main chains you need, with Pages & Co. examples (a block theme looks for each name with .html in templates/, a classic theme with .php in its folder):

Three details that trip people up. The slug-based names use the slug, never the title: page-about, not page-About Us. Post names include the post type: single-post-hello-world, not single-hello-world. And home means "the list of latest posts", not "the home page"; that one gets its own Common Mistake.

Where the list comes from

The hierarchy is not magic; it is code you can read. wp-includes/template-loader.php asks a series of yes/no questions about the current request (is_404(), is_search(), is_front_page(), is_home() and so on, in a fixed order) and, for the first that is true, calls a function like get_single_template() in wp-includes/template.php, which builds the candidate list. Each list passes through a filter named after its type before WordPress searches for files:

grep -n "_template_hierarchy\", \$templates\|apply_filters( 'template_include'" wp-includes/template.php wp-includes/template-loader.php

Output

wp-includes/template.php:62:	$templates = apply_filters( "{$type}_template_hierarchy", $templates );
wp-includes/template-loader.php:114:	$template   = apply_filters( 'template_include', $template );

Two hooks, two jobs. {$type}_template_hierarchy (for example single_template_hierarchy) filters the list of candidate names; template_include filters the final file path just before WordPress includes it. Plugins use them to supply templates of their own; you will use them right now to watch the decision being made.

👀 Watching WordPress Choose

A small must-use plugin can log every candidate list and the template WordPress settles on. It changes nothing: each callback returns what it received (a filter must always return, Lesson 2.3). Create wordpress/wp-content/mu-plugins/pagesco-template-map.php:

<?php
/**
 * Plugin Name: Pages & Co. Template Map
 * Description: Lesson 3.1 tool: logs which templates WordPress looks for on each front-end request, and which one it uses.
 */

$pagesco_template_types = array( 'embed', '404', 'search', 'frontpage', 'home', 'privacypolicy', 'archive', 'taxonomy', 'attachment', 'single', 'page', 'singular', 'category', 'tag', 'author', 'date', 'paged', 'index' );

foreach ( $pagesco_template_types as $pagesco_template_type ) {
	add_filter( "{$pagesco_template_type}_template_hierarchy", 'pagesco_log_template_candidates' );
}

/**
 * Logs one list of candidate templates and returns it unchanged.
 */
function pagesco_log_template_candidates( $templates ) {
	error_log( 'looked for: ' . implode( ', ', $templates ) );
	return $templates;
}

/**
 * Logs the file WordPress is about to include and, for a block theme, the block template it rendered.
 */
function pagesco_log_chosen_template( $template ) {
	error_log( 'file: ' . str_replace( ABSPATH, '', $template ) );

	if ( ! empty( $GLOBALS['_wp_current_template_id'] ) ) {
		error_log( 'block template: ' . $GLOBALS['_wp_current_template_id'] );
	}
	return $template;
}
add_filter( 'template_include', 'pagesco_log_chosen_template', 99 );

The loop adds the same callback to all eighteen hierarchy filters. $_wp_current_template_id is a global core sets when it picks a block template (the admin bar's "Edit site" link uses it); the leading underscore marks it as core-internal, which is fine for a debugging tool but not something to build features on. Now open http://localhost:8080/hello-world/ and read the new lines in wordpress/wp-content/debug.log:

http://localhost:8080/hello-world/

Output (the new lines of wp-content/debug.log)

[25-Oct-2026 22:10:35 UTC] looked for: single-post-hello-world.php, single-post.php, single.php
[25-Oct-2026 22:10:35 UTC] file: wp-includes/template-canvas.php
[25-Oct-2026 22:10:35 UTC] block template: twentytwentyfive//single

Read it top to bottom. WordPress built the single-post list (the names end in .php because the same list serves classic themes; a block theme looks for the same names as .html in templates/). Twenty Twenty-Five has no single-post-hello-world or single-post, but it has templates/single.html, so the search stopped there. The file WordPress included is core's template-canvas.php, which rendered the block template twentytwentyfive//single. Now a category archive:

http://localhost:8080/category/news/

Output (the new lines of wp-content/debug.log)

[25-Oct-2026 22:10:35 UTC] looked for: category-news.php, category-2.php, category.php
[25-Oct-2026 22:10:35 UTC] looked for: archive.php
[25-Oct-2026 22:10:35 UTC] file: wp-includes/template-canvas.php
[25-Oct-2026 22:10:35 UTC] block template: twentytwentyfive//archive

Two "looked for" lines this time. The category list found nothing (Twenty Twenty-Five has no category template), so template-loader.php moved on to its next question, is_archive(), which built the archive list, and archive.html answered. That fall-through is the hierarchy in action. Keep this plugin for now: Common Mistakes and the project use it, and the project deletes it at the end.

✅ The Site Editor shows the same thing

In Appearance > Editor > Templates, each template has a description such as "Displays a single post on your website unless a custom template has been applied to that post or a dedicated template exists". When you add a template there ("Add New Template"), the editor offers the hierarchy names for you, for example "Category: News". Under the hood it uses get_template_hierarchy(), the same rules you just logged; you will call it yourself in Exercise 1.

⚠️ Common Mistakes

Theme mistakes are often silent: no error, just the wrong page or a missing piece. Make each one on purpose, see what WordPress does, then undo it.

1. A theme folder without a template

You start a new theme with just a style.css and try to switch to it:

/*
Theme Name: Pages & Co. Broken
*/
wp theme activate pagesco-broken

Error

Error: Template is missing. Standalone themes need to have a <code>templates/index.html</code> or <code>index.php</code> template file. <a href="https://developer.wordpress.org/themes/advanced-topics/child-themes/">Child themes</a> need to have a <code>Template</code> header in the <code>style.css</code> stylesheet.

What it means: WordPress found the header, but a theme needs at least one template it can always fall back to: index. (The <code> and <a> tags are there because the same message is shown as HTML on the Themes screen, where the folder appears under "Broken Themes".) Fix: add templates/index.html for a block theme or index.php for a classic one. A child theme is the exception: it has a Template: header naming its parent instead (Lesson 3.4).

rm -r wp-content/themes/pagesco-broken

2. Making home.html for the home page

The shop decides that the site's front page should be the About Us page, not the latest news. In Settings > Reading that is "Your homepage displays: A static page"; with WP-CLI it is two options. Then load http://localhost:8080/:

wp option update show_on_front page
wp option update page_on_front 12

Output

Success: Updated 'show_on_front' option.
Success: Updated 'page_on_front' option.
http://localhost:8080/

Output (the new lines of wp-content/debug.log)

[25-Oct-2026 22:10:36 UTC] looked for: front-page.php
[25-Oct-2026 22:10:36 UTC] looked for: page-about.php, page-12.php, page.php
[25-Oct-2026 22:10:36 UTC] file: wp-includes/template-canvas.php
[25-Oct-2026 22:10:36 UTC] block template: twentytwentyfive//page

What it means: home is not in the list at all. With a static front page, the front page is a page, so after front-page WordPress follows the page chain and uses page.html. home means "the blog index" (the "Posts page" you can pick in Settings > Reading), whatever URL it lives at. A developer who wrote home.html to design the shop's front page would see no change at all, and a designer who wanted the front page to look different from other pages needed front-page.html. Fix: use front-page for "the site's front page, whatever it shows" and home for "the list of latest posts". Put the setting back:

wp option update show_on_front posts
wp option update page_on_front 0

Output

Success: Updated 'show_on_front' option.
Success: Updated 'page_on_front' option.

3. A classic theme that forgets wp_body_open()

In a classic theme the PHP template prints the whole document, so the theme itself must call the hooks that core calls for block themes. Here is a minimal classic theme whose index.php calls wp_head() and wp_footer() but not wp_body_open():

/*
Theme Name: Pages & Co. Bare
*/
<!DOCTYPE html>
<html <?php language_attributes(); ?>>
<head>
	<meta charset="<?php bloginfo( 'charset' ); ?>">
	<?php wp_head(); ?>
</head>
<body <?php body_class(); ?>>
	<h1><?php bloginfo( 'name' ); ?></h1>
	<?php wp_footer(); ?>
</body>
</html>
wp theme activate pagesco-bare

❓ Common Questions at This Stage

If new themes are block themes, why does this course still teach classic themes?

Because most WordPress sites you will be paid to work on were built before block themes existed, and many popular commercial themes are still classic or hybrid. Classic templates also teach the Loop and WP_Query, which every dynamic block you write in Module 6 uses under the hood. Module 4 builds a classic theme for exactly that reason.

Can a block theme use the Customizer?

Only if something hooks into customize_register; then WordPress shows the Customize menu item again. A few plugins do that for their own settings. For colors, fonts and layout, block themes use the Site Editor's Styles panel, which reads and writes the same theme.json data you saw in this lesson.

Where exactly are Site Editor changes stored?

As posts. Changed templates are wp_template posts, changed parts wp_template_part posts (both tagged with the theme's slug in the wp_theme taxonomy), and style changes one wp_global_styles post per theme. They live in the database, so they survive theme updates, but they also do not travel with your theme's files until you export them (Lesson 3.3).

Do I have to create every template in the hierarchy?

No, only index. Every other template is optional and is used only when it is the most specific match. A small theme with six templates, like the one you will build next, handles every page of a typical site; you add a more specific template only when one kind of page needs to look different.

🌟 Going Further: Bonus Challenge

Plugins can add templates too. register_block_template() (WordPress 6.7 and later) registers a block template from PHP, for example pagesco-books//single-book with block markup as its content, and it then appears in the Site Editor next to the theme's templates. Read its documentation in the Code Reference and the source in wp-includes/block-template.php, then answer: if both the active theme and a plugin provide single-book, which one wins, and why is that the right decision for a site owner?

🎓 Key Takeaways

  • A theme owns presentation; content lives in the database and features in plugins, so switching themes keeps both. The template and stylesheet options record the active theme
