⚙️ Lesson 5.4: Admin Pages, Settings API & Options

Every time Pages & Co. wants a different sentence in the store notice, someone has to edit PHP. That does not scale: the shop's staff should change their own settings, in the admin, safely. In this lesson you give pagesco-books a settings page under Settings, built with the WordPress Settings API, which brings the nonce, the capability check and the save handler with it. The values live in one option, pagesco_books_settings, and the store notice starts reading it. You will also settle a question Lesson 5.2 left open: what should deleting the plugin delete?

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Store a plugin's settings as one array option with defaults, and read it safely with get_option() and wp_parse_args()
  • Add an admin page with add_options_page() (or a top-level menu) protected by the right capability
  • Build a settings form with the Settings API: register_setting(), sections, fields, settings_fields() and do_settings_sections()
  • Validate submitted values in a sanitize callback and report problems with add_settings_error()
  • Trace what happens between Save Changes and the database: options.php, the nonce, the allowed options list
  • Decide what uninstall.php removes, and remove the plugin's own settings
  • ⏱️ Time 125 minutes
  • 📋 Prerequisites Lesson 5.3: Security in WordPress
  • 🛠️ You will build a Settings > Pages & Co. Books page that stores pagesco_books_settings and controls the store notice
  • 🧩 WordPress 7.1 on PHP 8.5 (the Settings API has been stable for years; register_setting() defaults need 4.7+)
  • 🧱 Site your Pages & Co. site from Lesson 5.3, with pagesco-books active

🗃️ Options: Where Settings Live

You met the wp_options table in Lesson 2.2: one row per option, a name, a value and an autoload flag, with everything that is autoloaded fetched in a single query at the start of every request. Every screen under Settings in the admin is a form over a handful of those rows (Lesson 2.1 matched them up). Your plugin's settings belong there too, with the Options API you already know: get_option(), add_option(), update_option(), delete_option().

💡 Mental model: one labelled box on the shared shelf

Think of wp_options as a shelf in the back office that every plugin shares. You could put each of your settings on it loose, four little notes with your name on them, or you could put one labelled box there, pagesco_books_settings, with all your notes inside. One box is easier to find, to load in one go, and to throw away when you leave. WordPress stores the box as a serialized PHP array (you saw serialized values in Lesson 2.2) and hands it back to you as an array.

The Pages & Co. plugin gets exactly one option for its settings, as the course plan says. Ask for it before it exists, and WordPress has nothing to give:

wp option get pagesco_books_settings

Error

Error: Could not get 'pagesco_books_settings' option. Does it exist?

In PHP the same question returns false, or the second argument of get_option( $name, $default ) if you pass one. Rather than spreading defaults over every place that reads a setting, the plugin gets one class that knows the option's name, its defaults and how to clean it. Create wordpress/wp-content/plugins/pagesco-books/src/Settings.php:

<?php
/**
 * The shop's settings: one option, an array of values with defaults.
 *
 * @package PagesCo\Books
 */

namespace PagesCo\Books;

/**
 * Registers the pagesco_books_settings option and reads it for the rest of the plugin.
 */
final class Settings implements Feature {

	/**
	 * The option's name in wp_options.
	 */
	public const OPTION = 'pagesco_books_settings';

	/**
	 * The option group the settings form posts (settings_fields() prints it).
	 */
	public const GROUP = 'pagesco_books';

	/**
	 * Registers the setting on init, so its sanitizing and default apply everywhere, not only in wp-admin.
	 */
	public function register(): void {
		add_action( 'init', array( $this, 'register_setting' ) );
	}

	/**
	 * Every setting with its default value.
	 *
	 * @return array{notice_extra: string, show_events_link: bool, books_per_page: int, events_limit: int}
	 */
	public static function defaults(): array {
		return array(
			'notice_extra'     => __( 'Open until 9 p.m. on Thursdays.', 'pagesco-books' ),
			'show_events_link' => true,
			'books_per_page'   => 6,
			'events_limit'     => 5,
		);
	}

	/**
	 * Returns one setting: the saved value, or its default when nothing is saved yet.
	 *
	 * @param string $key A key of defaults().
	 * @return mixed
	 */
	public static function get( string $key ) {
		$settings = wp_parse_args( get_option( self::OPTION, array() ), self::defaults() );

		return $settings[ $key ] ?? null;
	}

	/**
	 * Tells WordPress about the option: its group, type, sanitize callback and default.
	 */
	public function register_setting(): void {
		register_setting(
			self::GROUP,
			self::OPTION,
			array(
				'type'              => 'object',
				'sanitize_callback' => array( $this, 'sanitize' ),
				'default'           => self::defaults(),
			)
		);
	}

	/**
	 * Cleans the submitted values before WordPress stores them. Out-of-range numbers keep the saved value.
	 *
	 * @param mixed $input The submitted settings.
	 * @return array
	 */
	public function sanitize( $input ): array {
		$input = is_array( $input ) ? $input : array();
		$saved = wp_parse_args( get_option( self::OPTION, array() ), self::defaults() );

		$clean = array(
			'notice_extra'     => sanitize_text_field( $input['notice_extra'] ?? '' ),
			'show_events_link' => ! empty( $input['show_events_link'] ),
			'books_per_page'   => absint( $input['books_per_page'] ?? $saved['books_per_page'] ),
			'events_limit'     => absint( $input['events_limit'] ?? $saved['events_limit'] ),
		);

		if ( $clean['books_per_page'] < 1 || $clean['books_per_page'] > 24 ) {
			add_settings_error( self::OPTION, 'books_per_page', __( 'Books per list must be between 1 and 24.', 'pagesco-books' ) );
			$clean['books_per_page'] = $saved['books_per_page'];
		}
		if ( $clean['events_limit'] < 1 || $clean['events_limit'] > 20 ) {
			add_settings_error( self::OPTION, 'events_limit', __( 'Events to show must be between 1 and 20.', 'pagesco-books' ) );
			$clean['events_limit'] = $saved['events_limit'];
		}

		return $clean;
	}
}

Four settings, chosen because the shop will really use them: the sentence the plugin adds to the store notice (today it is hard-coded in StoreNotice), whether the notice shows its "See events" link, how many books a list shows (the book blocks in Module 6 use it), and how many events the events listing shows (Lesson 5.5). Three parts of the class matter now:

  • defaults() is the single place the default values live. The notice sentence is the one the shop already shows, so nothing changes on the site until someone saves something different.
  • get( $key ) reads the option and fills any missing key from the defaults with wp_parse_args() (Lesson 1.3). That matters when a later version of the plugin adds a fifth setting: sites that saved the old four still get a value for the new one.
  • register_setting() tells WordPress about the option: the group its form belongs to, its type (object: an associative array, in the JSON terms the REST API uses), the callback that cleans every value before it is stored, and its default. The sanitize() method is that callback; you will put it to work when you save the form.

The setting is registered on init, not only in the admin, so its cleaning and its default apply everywhere the option is written or read, WP-CLI included. Add the feature to the list in src/Plugin.php (in your editor, after Admin\StockAction::class,), then ask again:

Now wp option get answers with the defaults, yet the database still has no row for the option (the count is 0). The registered default is handed out whenever the option is missing; nothing is written until someone saves. And Settings::get() returns a real integer, 5, not the string a single option row would give you (Lesson 1.3's "all options are strings" rule applies to scalar options; arrays come back with their types).

✅ One array option, or several options?

One option per plugin (or per screen) is the usual choice: one row, one autoloaded value, one delete_option() on uninstall. Split a value into its own option when it is large and rarely needed (give it autoload off, Lesson 2.2) or when it changes on every request, such as a counter: rewriting a whole settings array to bump one number is wasteful. Never store per-post or per-user data in options; that is what post meta and user meta are for.

🧭 Admin Menus and Pages

An admin page is a callback that prints HTML inside the admin's frame, registered on the admin_menu action (Lesson 2.3's table listed it). WordPress gives you one function to add a top-level menu and a family of shortcuts for submenus under the existing ones:

FunctionAddsUse it for
add_menu_page()A top-level menu (with a Dashicon and a position)A plugin that is a whole application: a shop, a forms builder
add_submenu_page( $parent, … )An item under any menu, by the parent's slugScreens that belong to your post type: edit.php?post_type=book
add_options_page()An item under Settings (options-general.php)Configuration you set once and rarely touch
add_management_page(), add_theme_page(), add_users_page()…Items under Tools, Appearance, Users…Tools and maintenance screens

Every one of them takes the same core arguments: the page title (the browser tab and the <h1>), the menu title, the capability a user needs to see the item and open the page, a slug that becomes ?page=… in the URL, and the callback that prints the page. The shop's settings are configuration, so they go under Settings, guarded by manage_options, the capability only administrators have. Create src/Admin/SettingsPage.php with the page and a placeholder body:

<?php
/**
 * The Settings > Pages & Co. Books screen.
 *
 * @package PagesCo\Books
 */

namespace PagesCo\Books\Admin;

use PagesCo\Books\Feature;

/**
 * Adds the settings page (the form follows in the next section).
 */
final class SettingsPage implements Feature {

	/**
	 * The page's slug: options-general.php?page=pagesco-books.
	 */
	public const SLUG = 'pagesco-books';

	/**
	 * Hooks the menu item into the admin menu.
	 */
	public function register(): void {
		add_action( 'admin_menu', array( $this, 'add_page' ) );
	}

	/**
	 * Adds the page under Settings, for users who can manage options.
	 */
	public function add_page(): void {
		add_options_page(
			__( 'Pages & Co. Books Settings', 'pagesco-books' ),
			__( 'Pages & Co. Books', 'pagesco-books' ),
			'manage_options',
			self::SLUG,
			array( $this, 'render' )
		);
	}

	/**
	 * Prints the page.
	 */
	public function render(): void {
		if ( ! current_user_can( 'manage_options' ) ) {
			return;
		}
		?>
		<div class="wrap">
			<h1><?php echo esc_html( get_admin_page_title() ); ?></h1>
			<p><?php esc_html_e( 'Settings for the Pages & Co. shop features.', 'pagesco-books' ); ?></p>
		</div>
		<?php
	}
}

The current_user_can() check inside render() repeats what the menu already enforces. That is Lesson 5.3's defense in depth: the callback should never depend on how it was reached. List the feature and look at the Settings menu as the administrator sees it (logged in as admin):

A 403 before your callback even runs: editors do not have manage_options, so WordPress refuses the page and hides the menu item from them. Choose the capability for what the page can change, not for who you think will use it.

📝 The Settings API

You could print a <form> by hand and handle it at admin-post.php, as the stock action in Lesson 5.3 did. For settings, WordPress has done that work for you. The Settings API describes a form as data, prints it in the admin's standard layout, and saves it through core's own handler, wp-admin/options.php, which checks a nonce and a capability for you and runs your sanitize callback. You describe four things:

PieceFunctionIn this plugin
The option and its groupregister_setting( $group, $option, $args )group pagesco_books, option pagesco_books_settings (done in Settings)
Sections: headings that group fieldsadd_settings_section( $id, $title, $callback, $page )"Store notice", "Catalog and events"
Fields: one row each, with your inputadd_settings_field( $id, $title, $callback, $page, $section, $args )four fields
The form on your pagesettings_fields( $group ), do_settings_sections( $page ), submit_button()inside render()

Sections and fields are registered on admin_init, the action that fires at the start of every admin request. Replace src/Admin/SettingsPage.php with the full version:

<?php
/**
 * The Settings > Pages & Co. Books screen.
 *
 * @package PagesCo\Books
 */

namespace PagesCo\Books\Admin;

use PagesCo\Books\Feature;
use PagesCo\Books\Settings;

/**
 * Adds the settings page and builds its form with the Settings API.
 */
final class SettingsPage implements Feature {

	/**
	 * The page's slug: options-general.php?page=pagesco-books.
	 */
	public const SLUG = 'pagesco-books';

	/**
	 * Hooks the menu item, the sections and fields, and the Plugins screen link.
	 */
	public function register(): void {
		add_action( 'admin_menu', array( $this, 'add_page' ) );
		add_action( 'admin_init', array( $this, 'add_fields' ) );
		add_filter( 'plugin_action_links_' . plugin_basename( PAGESCO_BOOKS_FILE ), array( $this, 'add_settings_link' ) );
	}

	/**
	 * Adds the page under Settings, for users who can manage options.
	 */
	public function add_page(): void {
		add_options_page(
			__( 'Pages & Co. Books Settings', 'pagesco-books' ),
			__( 'Pages & Co. Books', 'pagesco-books' ),
			'manage_options',
			self::SLUG,
			array( $this, 'render' )
		);
	}

	/**
	 * Describes the form: two sections, four fields.
	 */
	public function add_fields(): void {
		add_settings_section(
			'pagesco_books_notice',
			__( 'Store notice', 'pagesco-books' ),
			array( $this, 'render_notice_intro' ),
			self::SLUG
		);
		add_settings_field(
			'notice_extra',
			__( 'Notice addition', 'pagesco-books' ),
			array( $this, 'render_text_field' ),
			self::SLUG,
			'pagesco_books_notice',
			array(
				'key'         => 'notice_extra',
				'label_for'   => 'pagesco-notice-extra',
				'description' => __( 'Added after the free-shipping text. Leave empty to show only that text.', 'pagesco-books' ),
			)
		);
		add_settings_field(
			'show_events_link',
			__( 'Events link', 'pagesco-books' ),
			array( $this, 'render_checkbox_field' ),
			self::SLUG,
			'pagesco_books_notice',
			array(
				'key'       => 'show_events_link',
				'label_for' => 'pagesco-show-events-link',
				'label'     => __( 'Show a "See events" link in the notice', 'pagesco-books' ),
			)
		);

		add_settings_section(
			'pagesco_books_lists',
			__( 'Catalog and events', 'pagesco-books' ),
			'__return_false',
			self::SLUG
		);
		add_settings_field(
			'books_per_page',
			__( 'Books per list', 'pagesco-books' ),
			array( $this, 'render_number_field' ),
			self::SLUG,
			'pagesco_books_lists',
			array(
				'key'       => 'books_per_page',
				'label_for' => 'pagesco-books-per-page',
				'max'       => 24,
			)
		);
		add_settings_field(
			'events_limit',
			__( 'Events to show', 'pagesco-books' ),
			array( $this, 'render_number_field' ),
			self::SLUG,
			'pagesco_books_lists',
			array(
				'key'       => 'events_limit',
				'label_for' => 'pagesco-events-limit',
				'max'       => 20,
			)
		);
	}

	/**
	 * Prints the page: the form posts to options.php, which checks the nonce and saves the option.
	 */
	public function render(): void {
		if ( ! current_user_can( 'manage_options' ) ) {
			return;
		}
		?>
		<div class="wrap">
			<h1><?php echo esc_html( get_admin_page_title() ); ?></h1>
			<form action="options.php" method="post">
				<?php
				settings_fields( Settings::GROUP );
				do_settings_sections( self::SLUG );
				submit_button();
				?>
			</form>
		</div>
		<?php
	}

	/**
	 * Prints the text under the Store notice heading.
	 */
	public function render_notice_intro(): void {
		echo '<p>' . esc_html__( 'The bar at the top of every page of the shop.', 'pagesco-books' ) . '</p>';
	}

	/**
	 * Prints a text input for one setting.
	 *
	 * @param array $args The field's arguments from add_settings_field().
	 */
	public function render_text_field( $args ): void {
		printf(
			'<input type="text" id="%1$s" name="%2$s[%3$s]" value="%4$s" class="regular-text"><p class="description">%5$s</p>',
			esc_attr( $args['label_for'] ),
			esc_attr( Settings::OPTION ),
			esc_attr( $args['key'] ),
			esc_attr( Settings::get( $args['key'] ) ),
			esc_html( $args['description'] )
		);
	}

	/**
	 * Prints a checkbox for one setting.
	 *
	 * @param array $args The field's arguments from add_settings_field().
	 */
	public function render_checkbox_field( $args ): void {
		printf(
			'<label><input type="checkbox" id="%1$s" name="%2$s[%3$s]" value="1"%4$s> %5$s</label>',
			esc_attr( $args['label_for'] ),
			esc_attr( Settings::OPTION ),
			esc_attr( $args['key'] ),
			checked( Settings::get( $args['key'] ), true, false ),
			esc_html( $args['label'] )
		);
	}

	/**
	 * Prints a number input for one setting.
	 *
	 * @param array $args The field's arguments from add_settings_field().
	 */
	public function render_number_field( $args ): void {
		printf(
			'<input type="number" id="%1$s" name="%2$s[%3$s]" value="%4$s" min="1" max="%5$d" step="1" class="small-text">',
			esc_attr( $args['label_for'] ),
			esc_attr( Settings::OPTION ),
			esc_attr( $args['key'] ),
			esc_attr( Settings::get( $args['key'] ) ),
			absint( $args['max'] )
		);
	}

	/**
	 * Adds a Settings link next to Deactivate on the Plugins screen.
	 *
	 * @param string[] $links The plugin's action links.
	 * @return string[]
	 */
	public function add_settings_link( $links ) {
		$url = admin_url( 'options-general.php?page=' . self::SLUG );
		array_unshift( $links, sprintf( '<a href="%s">%s</a>', esc_url( $url ), esc_html__( 'Settings', 'pagesco-books' ) ) );

		return $links;
	}
}

Read it in the order WordPress uses it:

  • add_fields() registers two sections on the page pagesco-books and four fields in them. Each field names a callback that prints its input and passes $args to it: the setting's key, and label_for, which WordPress uses to wrap the row's title in a <label for="…"> pointing at your input (clickable labels and screen readers both need that). '__return_false' is a core function that does nothing, handy for a section without intro text.
  • The field callbacks print inputs named pagesco_books_settings[notice_extra] and so on. That array syntax is what makes PHP deliver all four values as one array in $_POST['pagesco_books_settings'], ready to be stored as one option. Every value is escaped for its attribute with esc_attr(); the checkbox uses core's checked() helper.
  • render() prints a form that posts to options.php. settings_fields( 'pagesco_books' ) prints the hidden fields that tell options.php which group this is, plus its nonce; do_settings_sections() prints the sections and fields; submit_button() prints the standard Save Changes button.
  • add_settings_link() adds a Settings link to the plugin's row on the Plugins screen, through the plugin_action_links_{basename} filter, a small kindness to whoever just activated your plugin.

The markup and classes (form-table, regular-text, small-text, description) are the admin's own, so the page looks like every other settings screen, in the 7.0 admin design and in whatever comes after it.

💾 What Save Changes Does

When you press Save Changes, the browser posts the form to wp-admin/options.php. Core's handler then runs the same checks you wrote by hand in Lesson 5.3, in this order:

graph TD A["Save Changes: POST options.php"] --> B["check_admin_referer: nonce for pagesco_books-options"] B --> C["current_user_can manage_options"] C --> D["is pagesco_books on the allowed options list?"] D --> E["update_option for each option in the group"] E --> F["sanitize_option runs your sanitize callback"] F --> G["redirect back with settings-updated=true"] G --> H["the page prints Settings saved or your errors"]

The nonce action is the group name plus -options, which is why settings_fields() needs the same group as register_setting(). The capability defaults to manage_options (the filter option_page_capability_pagesco_books can change it). The allowed options list is built from your register_setting() calls: only options registered in that group can be written through this form, so a forged field such as siteurl is ignored. And the value goes through sanitize_option(), which calls your sanitize() method.

Watching the round trip

You can save the form in your browser at any time. To see exactly what travels, and to let the course check every step, here is a small shell script that does what the browser does: log in, open the page, read the hidden fields settings_fields() printed, and post the form. Save it as wordpress/pagesco-save.sh (the WordPress root) and run it from the WP-CLI container, one argument per form field:

#!/bin/sh
# Does what your browser does when you press "Save Changes" on
# Settings > Pages & Co. Books (Lesson 5.4). Run it in the WP-CLI container:
#   sh pagesco-save.sh 'pagesco_books_settings[events_limit]=5' ...
# A field you leave out is not sent, exactly like an unticked checkbox.

SITE=http://localhost:8080
PAGE="$SITE/wp-admin/options-general.php?page=pagesco-books"
JAR=/tmp/pagesco-cookies.txt

# 1. Log in as admin (WordPress wants its test cookie first).
curl -s -o /dev/null -c "$JAR" "$SITE/wp-login.php"
curl -s -o /dev/null -b "$JAR" -c "$JAR" -d log=admin -d pwd=password -d testcookie=1 "$SITE/wp-login.php"

# 2. Open the settings page and read the hidden fields settings_fields() printed.
FORM=$(curl -s -b "$JAR" "$PAGE")
GROUP=$(echo "$FORM" | grep -o "name='option_page' value='[^']*'" | cut -d"'" -f4)
NONCE=$(echo "$FORM" | grep -o 'name="_wpnonce" value="[^"]*"' | cut -d'"' -f4)

# 3. Post the form to options.php, one --data-urlencode per field you passed.
for FIELD in "$@"; do
	shift
	set -- "$@" --data-urlencode "$FIELD"
done
ANSWER=$(curl -s -b "$JAR" -c "$JAR" -o /tmp/pagesco-answer.html -w '%{http_code} %{redirect_url}' \
	-d "option_page=$GROUP" -d action=update -d "_wpnonce=$NONCE" \
	--data-urlencode "_wp_http_referer=/wp-admin/options-general.php?page=pagesco-books" \
	"$@" "$SITE/wp-admin/options.php")
echo "options.php answered: $ANSWER"

# 4. Print the notices the page shows next ("Settings saved." or your errors), or the error page.
if [ "${ANSWER%% *}" = 302 ]; then
	curl -s -b "$JAR" "$PAGE&settings-updated=true" | grep -o '<p><strong>[^<]*</strong></p>' | sed 's/<[^>]*>//g'
else
	grep -o '<div class="wp-die-message">.*</div>' /tmp/pagesco-answer.html | sed 's/<[^>]*>//g'
fi

Send all four fields, as the browser would with the box ticked, but with an Events to show value the sanitize callback should refuse:

sh pagesco-save.sh 'pagesco_books_settings[notice_extra]=Open until 9 p.m. on Thursdays.' 'pagesco_books_settings[show_events_link]=1' 'pagesco_books_settings[books_per_page]=8' 'pagesco_books_settings[events_limit]=50'
wp option get pagesco_books_settings

Output

options.php answered: 302 http://localhost:8080/wp-admin/options-general.php?page=pagesco-books&settings-updated=true
Events to show must be between 1 and 20.
array (
  'notice_extra' => 'Open until 9 p.m. on Thursdays.',
  'show_events_link' => true,
  'books_per_page' => 8,
  'events_limit' => 5,
)

Read it from the top. options.php answered with a 302 redirect back to your page with settings-updated=true: the nonce, the capability and the allowed options list all passed. The page then printed your error, "Events to show must be between 1 and 20.", instead of "Settings saved.". And the option row now exists: Books per list was stored as 8, while Events to show kept its old value, 5, because sanitize() refused 50 and fell back to the saved value.

💡 What a sanitize callback must do

It receives whatever arrived (treat it as hostile: it might not even be an array) and must return the complete value to store. Clean each key with the function for its type (sanitize_text_field(), absint()), turn the checkbox into a real boolean (an unticked box sends nothing at all, so "missing" means "off"), and for a value you reject, call add_settings_error( $setting, $code, $message ) and keep the old value rather than storing nonsense. Errors are kept for one page load and printed above your form by settings_errors(), which core calls for you on pages under Settings.

⚠️ Common Mistakes

1. Passing the page slug to settings_fields()

The page slug (pagesco-books) and the option group (pagesco_books) look alike, and mixing them up is the classic Settings API bug. Make it on purpose: change settings_fields( Settings::GROUP ); in render() to settings_fields( self::SLUG ); (the sed line does it), then save:

sed -i 's/settings_fields( Settings::GROUP );/settings_fields( self::SLUG );/' wp-content/plugins/pagesco-books/src/Admin/SettingsPage.php
sh pagesco-save.sh 'pagesco_books_settings[events_limit]=5'

Output

options.php answered: 500
Error: The pagesco-books options page is not in the allowed options list.

What it means: the form now says it belongs to a group called pagesco-books. The nonce matches (it was made for that same wrong name), so options.php gets as far as the allowed options list, finds no setting registered in that group and stops with a 500 error page. Fix: the argument of settings_fields() is the first argument of register_setting(); the argument of do_settings_sections() is the page slug. Keeping both in constants (Settings::GROUP, SettingsPage::SLUG) is what makes the mix-up visible. Put it back:

sed -i 's/settings_fields( self::SLUG );/settings_fields( Settings::GROUP );/' wp-content/plugins/pagesco-books/src/Admin/SettingsPage.php

2. Reading a checkbox that was not sent

An unticked checkbox is not sent as "0": it is not sent at all. A sanitize callback that reads it without checking, here in a throwaway must-use plugin, warns on every save with the box unticked:

<?php
/**
 * Plugin Name: Mistake: Unticked Checkbox
 */

add_action(
	'init',
	function () {
		register_setting(
			'pagesco_demo',
			'pagesco_demo_settings',
			array(
				'sanitize_callback' => function ( $input ) {
					return array(
						'show_events_link' => (bool) $input['show_events_link'],
					);
				},
			)
		);
	}
);
wp eval 'var_export( sanitize_option( "pagesco_demo_settings", array( "notice_extra" => "Hello" ) ) );'
rm wp-content/mu-plugins/mistake-checkbox.php

Output

Warning: Undefined array key "show_events_link" in /var/www/html/wp-content/mu-plugins/mistake-checkbox.php on line 15
array (
  'show_events_link' => false,
)

What it means: $input['show_events_link'] does not exist, so PHP warns and uses null, which happens to cast to false. The value is right by luck and the warning lands in the debug log on every save with the box unticked. Fix: test for the key: ! empty( $input['show_events_link'] ), as Settings::sanitize() does, or isset(), or $input['key'] ?? false.

3. Updating part of the array from code

The form always sends every field. Code does not have to. A one-line "just change the events limit" goes wrong in a way no error reports:

wp eval 'update_option( "pagesco_books_settings", array( "events_limit" => 8 ) );'
wp option get pagesco_books_settings

Output

array (
  'notice_extra' => '',
  'show_events_link' => false,
  'books_per_page' => 8,
  'events_limit' => 8,
)

What it means: update_option() replaces the whole value, and your sanitize callback (registered on init, so it runs here too) treats each missing key as empty: the notice sentence is now '' and the events link is off. Once the project wires these settings into the store notice, this one line would quietly strip the notice bar. Fix: merge before you update, update_option( $name, array_merge( get_option( $name, array() ), array( 'events_limit' => 8 ) ) ), or from the command line use wp option patch update pagesco_books_settings events_limit 8 (Exercise 1). Put the saved settings back the way the form left them:

sh pagesco-save.sh 'pagesco_books_settings[notice_extra]=Open until 9 p.m. on Thursdays.' 'pagesco_books_settings[show_events_link]=1' 'pagesco_books_settings[books_per_page]=6' 'pagesco_books_settings[events_limit]=5'

Output

options.php answered: 302 http://localhost:8080/wp-admin/options-general.php?page=pagesco-books&settings-updated=true
Settings saved.

🛠️ Step 1: Let the store notice read the settings (8 min)

Replace src/StoreNotice.php. The two callbacks keep their names, so anything that unhooks them (Lesson 2.3's removal rules) keeps working; only their bodies change:

<?php
/**
 * The shop's additions to the store notice from the pagesco-site must-use plugin.
 *
 * @package PagesCo\Books
 */

namespace PagesCo\Books;

/**
 * Adds the shop's own sentence and an events link to the store notice, as the settings say.
 */
final class StoreNotice implements Feature {

	/**
	 * Hooks into the notice's own filter and action (Lesson 2.3).
	 */
	public function register(): void {
		add_filter( 'pagesco_store_notice', array( $this, 'add_late_opening' ), 20 );
		add_action( 'pagesco_store_notice_end', array( $this, 'print_events_link' ) );
	}

	/**
	 * Adds the "Notice addition" setting to the notice text.
	 *
	 * @param string $text The notice text so far.
	 * @return string
	 */
	public function add_late_opening( $text ) {
		$extra = Settings::get( 'notice_extra' );

		return '' === $extra ? $text : $text . ' ' . $extra;
	}

	/**
	 * Prints a link to the events page inside the notice bar, unless the settings turn it off.
	 */
	public function print_events_link(): void {
		if ( ! Settings::get( 'show_events_link' ) ) {
			return;
		}

		printf(
			' <a href="%s">%s</a>',
			esc_url( home_url( '/events/' ) ),
			esc_html__( 'See events', 'pagesco-books' )
		);
	}
}

With the saved values equal to the defaults, the notice must look exactly as it has since Lesson 2.3:

🏋️ Exercise 4: Expose the Settings to the REST API (Stretch)

The block editor and any JavaScript settings screen read and write options through /wp/v2/settings, but only settings registered with show_in_rest. Without editing Settings.php, use the register_setting_args filter in a throwaway must-use plugin to add show_in_rest with a schema for the four keys, and fetch the setting as the administrator.

💡 Hint

The filter receives ( $args, $defaults, $option_group, $option_name ); change $args only when $option_name is pagesco_books_settings. An object setting needs a schema that lists its properties: 'show_in_rest' => array( 'schema' => array( 'type' => 'object', 'properties' => array( 'notice_extra' => array( 'type' => 'string' ), … ) ) ). The settings endpoint requires manage_options, so the request needs the administrator's credentials (Lesson 7.1 explains application passwords).

✅ Solution 
<?php
/**
 * Plugin Name: Exercise: Settings in REST
 */

add_filter(
	'register_setting_args',
	function ( $args, $defaults, $option_group, $option_name ) {
		if ( 'pagesco_books_settings' !== $option_name ) {
			return $args;
		}
		$args['show_in_rest'] = array(
			'schema' => array(
				'type'       => 'object',
				'properties' => array(
					'notice_extra'     => array( 'type' => 'string' ),
					'show_events_link' => array( 'type' => 'boolean' ),
					'books_per_page'   => array( 'type' => 'integer' ),
					'events_limit'     => array( 'type' => 'integer' ),
				),
			),
		);
		return $args;
	},
	10,
	4
);
GET http://localhost:8080/wp-json/wp/v2/settings   (as admin)

Output

{
  "title": "Pages &amp; Co.",
  "pagesco_books_settings": {
    "notice_extra": "Open until 9 p.m. on Thursdays.",
    "show_events_link": true,
    "books_per_page": 6,
    "events_limit": 5
  }
}

❓ Common Questions at This Stage

Should deleting the plugin also delete the books?

Lesson 5.2 left this open, and the course's answer is no. The rule used here: uninstall.php removes what belongs to the plugin and is useless without it, and keeps what belongs to the shop. The settings option and the Bookseller role are the plugin's own, so they go (and in Lesson 5.5, the events table and its version option join them). The eleven books, their genres and their meta are the shop's catalog: ordinary rows in wp_posts, wp_terms and wp_postmeta that Tools > Export can still export and that reappear the moment the plugin is installed again. An administrator who clicks Delete on the Plugins screen is usually removing code, not asking to wipe a catalog, and that delete cannot be undone. If a site really needs a full wipe, the professional pattern is opt-in: a constant in wp-config.php or a setting such as "Remove all data when the plugin is deleted", checked in uninstall.php before any books are deleted (with wp_delete_post( $id, true ), never raw SQL, so meta and term links go too). Lesson 8.3 looks at what the plugin directory expects here.

When should I use the Settings API, and when my own form?

Use the Settings API for values that are stored as options: it gives you the nonce, the capability check, the allowed options list, the save, the redirect and the messages for free, and a page that looks like the rest of the admin. Use your own form posted to admin-post.php (Lesson 5.3) for actions that are not "store these options": importing a file, sending a test email, clearing a cache. Newer plugins sometimes build settings screens in React with @wordpress/components, saving through /wp/v2/settings (Exercise 4 shows the server side); the option, the registration and the sanitize callback stay exactly as here.

Should my settings get a top-level menu?

Only if the plugin is a large part of what the site does. A top-level menu for a handful of options crowds the admin for everyone, and users expect configuration under Settings. Pages & Co.'s Books menu already exists for the catalog; if the settings were about books only, a submenu there (add_submenu_page( 'edit.php?post_type=book', … )) would be a good alternative. Exercise 3 shows the top-level version so you know how.

What about the Customizer and theme mods?

The Customizer (Appearance > Customize) and get_theme_mod() store values per theme, for looks. They are legacy for block themes (Lesson 3.1: the menu item is hidden unless something uses it), and they are the wrong home for a plugin's settings anyway: switch themes and the values are gone. Store shop features in your plugin's option; let block themes keep their looks in theme.json and Global Styles.

📝 Lesson Summary

🎓 Key Takeaways

  • Plugin settings live in wp_options; one array option per plugin, read through one class that knows the name, the defaults and the sanitizing
  • register_setting() (on init) gives the option a group, a type, a sanitize_callback and a default that applies whenever the row is missing
  • Admin pages hang off admin_menu with add_options_page(), add_submenu_page() or add_menu_page(); the capability guards the menu item and the URL
  • The Settings API describes the form (add_settings_section(), add_settings_field()) and prints it (settings_fields(), do_settings_sections(), submit_button()); options.php checks the nonce, the capability and the allowed options list, then saves
  • A sanitize callback returns the complete value, treats a missing checkbox as off, and rejects bad values with add_settings_error() while keeping the old one
  • uninstall.php deletes the plugin's own data (option, role) and keeps the shop's content (books)
