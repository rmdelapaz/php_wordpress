🏛️ Lesson 2.2: Core Architecture & the Database

In Lesson 2.1 you met the content model through WP-CLI and PHP: posts with a type, terms, users, options and block markup. Now you open the hood. You will walk the files of a WordPress install, read wp-config.php line by line, follow wp-settings.php as it loads WordPress, and then go into the database you already know how to query from MySQL Foundations. Twelve tables hold everything, and once you see their keys, their joins and the key-value pattern WordPress uses for extra fields, the content model stops being magic and becomes SQL you can read.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Find your way around a WordPress install: what lives in wp-admin/, wp-includes/ and wp-content/, and what a drop-in is

  • Trace how wp-settings.php loads WordPress, and say what is available at each stage
  • Map the twelve wp_* tables, their keys and indexes, and join them with SQL the way WordPress's own queries do
  • Explain the meta (key-value) pattern, serialized values and options autoloading, with their trade-offs
  • Query the Pages & Co. site with wp db cli, wp db query and WP-CLI, and choose the API over raw SQL in your code

📁 The Files of a WordPress Install

Lesson 1.1 showed you the WordPress root and drew one line through it: everything belongs to core except wp-content/ (yours) and wp-config.php (your site's settings). Today you look inside core, not to change it, but because reading it is how you answer questions no tutorial covers. Run these from the WP-CLI container (docker compose run --rm wpcli sh, Lesson 1.2), where the current folder is the WordPress root:

Drop-ins: special files in wp-content

A few file names in wp-content/ itself are reserved: if a file with that name exists, WordPress loads it instead of part of core. They are called drop-ins, and hosts and caching plugins install them. WordPress keeps the list in a function:

wp eval 'echo implode( "\n", array_keys( _get_dropins() ) ), "\n";'
wp plugin list --status=dropin

The most important ones: db.php replaces the database class, object-cache.php plugs in a persistent cache such as Redis (Lesson 8.2), advanced-cache.php serves cached pages before WordPress even loads, and maintenance.php, db-error.php and php-error.php replace the pages shown during updates, database outages and fatal errors. Your site has none, which is why the plugin list is empty. (The leading underscore in _get_dropins() marks a function as private to core: fine to call for a look, not something to build on.) When a site behaves strangely, wp plugin list --status=dropin is a good early check: a forgotten object-cache.php explains many "my change does not show up" mysteries.

⚙️ wp-config.php: The File You Configure

wp-config.php is plain PHP that runs on every request before anything else of WordPress. It defines how to reach the database, a set of secret keys, the table prefix and any switches you add, and its last line hands over to the loader. The Docker image wrote yours from the settings in compose.yaml (Lesson 1.2), so most values are read with getenv_docker(). Look at its skeleton, leaving out the secret keys (their values are unique to your site):

🛑 wp-config.php holds secrets

The database password and the eight keys in this file are enough to take over a site. Never put a real site's wp-config.php in Git or in a support forum post, never e-mail it, and never let your web server show it as text. Two habits help: version only your theme and plugin folders (Lesson 8.4), and know that wp-load.php also looks for wp-config.php one folder above the WordPress root, outside the web root, where many hosts keep it. On your development site the values come from compose.yaml, and the passwords are throwaway ones that only work on your computer.

Read it as the order in which things become available:

  1. The database (line 136, require_wp_db()): the global $wpdb connects, using the constants from wp-config.php. Then the object cache starts, an in-memory store for this one request (unless an object-cache.php drop-in makes it persistent).
  2. Must-use plugins (line 506): every PHP file in wp-content/mu-plugins/, in alphabetical order, then the muplugins_loaded action.
  3. Active plugins (line 582), then plugins_loaded. Only after them, at line 612, comes pluggable.php: functions such as wp_mail() and wp_get_current_user() that a plugin may replace by defining them first. That is why calling wp_get_current_user() at the top of a plugin file is a fatal "Call to undefined function": it does not exist yet.
  4. The theme (line 741): the active theme's functions.php (a child theme's first, then its parent's, Lesson 3.4), then after_setup_theme.
  5. The current user (line 766, $GLOBALS['wp']->init()) is worked out from the login cookie, and then init fires: everything is loaded, and this is where plugins register post types, taxonomies and blocks. wp_loaded closes the file.

Only then does wp-blog-header.php call wp() to run the main query and load the template, as you saw in Lesson 1.1. Notice where the options are: $wpdb is ready at line 136, and the first thing WordPress reads with it, before any plugin runs, is the set of autoloaded options. You will see why that matters in the options section below. The admin follows the same path (wp-admin/admin.php loads wp-load.php too), and so does WP-CLI, which is why wp eval can call any WordPress function.

💡 Mental model: opening the shop in the morning

Think of a bookseller opening Pages & Co. First the lights and the till (the database and the cache). Then the things that are always there, no matter what (must-use plugins), then the departments that are open today (active plugins), then the window display (the theme). Only when the staff member on duty has signed in (the current user) does the shop open its doors (init) and serve the first customer (the main query). Code that tries to serve a customer while the lights are still off is the "too early" bug that Lesson 2.3 teaches you to avoid with hooks.

🔑 Keys, Indexes and No Foreign Keys

Look at a table the way MySQL Foundations taught you. wp db columns is WP-CLI's DESCRIBE:

wp db columns wp_postmeta

Output

+------------+-----------------+------+-----+---------+----------------+
| Field      | Type            | Null | Key | Default | Extra          |
+------------+-----------------+------+-----+---------+----------------+
| meta_id    | bigint unsigned | NO   | PRI |         | auto_increment |
| post_id    | bigint unsigned | NO   | MUL | 0       |                |
| meta_key   | varchar(255)    | YES  | MUL |         |                |
| meta_value | longtext        | YES  |     |         |                |
+------------+-----------------+------+-----+---------+----------------+

A surrogate primary key (meta_id, BIGINT UNSIGNED AUTO_INCREMENT), the post it belongs to, a key name, and the value as LONGTEXT: any meta value, a number, a date or a whole serialized array, is stored as text. MUL means "part of a non-unique index". Which indexes exist on the two content tables? information_schema knows:

SELECT TABLE_NAME, INDEX_NAME,
       GROUP_CONCAT(CONCAT(COLUMN_NAME, IFNULL(CONCAT('(', SUB_PART, ')'), '')) ORDER BY SEQ_IN_INDEX) AS columns
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME IN ('wp_posts', 'wp_postmeta')
GROUP BY TABLE_NAME, INDEX_NAME
ORDER BY TABLE_NAME, INDEX_NAME;

Every index matches a question WordPress asks all the time, which is the indexing advice of MySQL Foundations Lesson 6.1 applied:

  • type_status_date (post_type, post_status, post_date, ID) is a composite index for the most common query of all, "the latest published posts of this type", the query behind every blog page and archive. type_status_author serves author archives and the admin's "Mine" filter.
  • post_name(191) finds a post by its slug, which is how /about/ becomes page 12.
  • post_id and meta_key(191) on wp_postmeta find a post's meta, and the posts that have a given key. There is no index on meta_value: it is LONGTEXT.

Why (191)? These are prefix indexes on the first 191 characters. In utf8mb4 a character can take 4 bytes, and 191 × 4 = 764 bytes fits under the 767-byte index limit of older MySQL versions that WordPress still supports. Now the surprising part, for anyone who took MySQL Foundations Lesson 4.2:

The tables are InnoDB today, but the schema dates from the time of MyISAM, which had no foreign keys, and WordPress keeps it portable across every MySQL and MariaDB version it supports. Five rows, all written by core. The two pages that came with the install store which template they use (_wp_page_template, "default"). Your three News posts carry _pingme: when a post is published WordPress plans to notify the sites it links to, and on a local environment WordPress 7.1 never sends those pings, so the flag stays (if you opened posts in the editor you will also see _edit_lock and _edit_last). A leading underscore marks a key as "protected": the editor's Custom Fields panel hides it.

This table is the key-value pattern, known in database design as EAV (entity-attribute-value): instead of one column per field, each field of each post is a row of which post (entity), which field (attribute) and its value. In MySQL Foundations you designed a books table with a price column. WordPress cannot add a column to wp_posts for every plugin's fields, so a book's price becomes a row in wp_postmeta: post_id 30, meta_key pagesco_price, meta_value '14.99' (Lesson 5.2 registers that key). wp_usermeta, wp_termmeta and wp_commentmeta have the same shape, and one API, in wp-includes/meta.php, serves all four:

wp eval 'var_dump( get_post_meta( 2, "_wp_page_template", true ), get_user_meta( 2, "first_name", true ), get_metadata( "user", 2, "last_name", true ) );'

string(5) "Maria"
string(5) "Lopez"

get_post_meta() and get_user_meta() are short forms of get_metadata( 'post' | 'user', ... ). The third argument, true, means "one value"; Common Mistakes 4 shows what you get without it.

🧩 Version note: yes and no before WordPress 6.6

Until WordPress 6.5 the autoload column held only yes or no, and countless tutorials and Stack Overflow answers query WHERE autoload = 'yes'. On WordPress 6.6 and later, including 7.1, that query finds nothing on a new site; use WHERE autoload IN ('yes', 'on', 'auto-on', 'auto'), the list that wp_autoload_values_to_autoload() returns. Sites upgraded from older versions keep their old yes/no rows until those options are saved again, which is why yes is still in the list. In PHP, the third argument of update_option() used to be 'yes'/'no'; pass true/false now.

⚠️ Common Mistakes

The database is where WordPress mistakes are quiet: most of these produce no error at all. Each one is reversible on your development site, which is the place to make them.

1. Editing serialized data with SQL

The shop's details are stored as one option holding an array (WP-CLI turns the JSON into a PHP array). Then someone renames the city with a quick SQL REPLACE():

wp option add pagesco_demo_shop '{"city":"Springfield","phone":"555-0142"}' --format=json
wp db query "UPDATE wp_options SET option_value = REPLACE(option_value, 'Springfield', 'Portland') WHERE option_name = 'pagesco_demo_shop'"
wp db query "SELECT option_value FROM wp_options WHERE option_name = 'pagesco_demo_shop'"
wp option get pagesco_demo_shop

Error

Success: Added 'pagesco_demo_shop' option.
Success: Query succeeded. Rows affected: 1
option_value
a:2:{s:4:"city";s:11:"Portland";s:5:"phone";s:8:"555-0142";}

Error: Could not get 'pagesco_demo_shop' option. Does it exist?

What it means: the stored text still says s:11:"Portland", "a string of 11 characters", but Portland has 8. PHP's unserialize() fails, WordPress returns false, and WP-CLI reports that the option does not exist. In a theme, get_option() silently returns false and the shop's address disappears from the page. The same happens to widgets, theme settings and plugin settings when a site moves to a new domain and someone runs REPLACE() on the old URL. Fix: change values through WordPress (update_option(), or wp option patch update pagesco_demo_shop city Portland), and for whole-site changes use wp search-replace, which unserializes, replaces and serializes again (Lesson 8.4). Remove the broken option:

wp option delete pagesco_demo_shop

Output

Success: Deleted 'pagesco_demo_shop' option.

2. Deleting rows with SQL (orphans)

A draft post with a reading time, deleted the "database way":

wp post create --post_title="Orphan demo" --porcelain
wp post meta add 19 pagesco_reading_minutes 1
wp db query "DELETE FROM wp_posts WHERE ID = 19"

Output

19
Success: Added custom field.
Success: Query succeeded. Rows affected: 1

No error. But a LEFT JOIN that looks for meta and term rows whose post is gone (MySQL Foundations Lesson 4.3) finds the leftovers:

SELECT 'wp_postmeta' AS in_table, pm.post_id AS missing_post, pm.meta_key AS detail
FROM wp_postmeta AS pm LEFT JOIN wp_posts AS p ON p.ID = pm.post_id
WHERE p.ID IS NULL
UNION ALL
SELECT 'wp_term_relationships', tr.object_id, tr.term_taxonomy_id
FROM wp_term_relationships AS tr LEFT JOIN wp_posts AS p ON p.ID = tr.object_id
WHERE p.ID IS NULL;

Output

+-----------------------+--------------+-------------------------+
| in_table              | missing_post | detail                  |
+-----------------------+--------------+-------------------------+
| wp_postmeta           |           19 | pagesco_reading_minutes |
| wp_term_relationships |           19 | 1                       |
+-----------------------+--------------+-------------------------+

What it means: two orphans, the reading time and the draft's link to Uncategorized (term_taxonomy_id 1; every post gets a category, even a draft). With no foreign keys, MySQL had no reason to stop you or to cascade. Orphans waste space, confuse reports, and can resurface: some plugins count meta rows, and a later post that reused the ID would inherit them if IDs were ever reset. DELETE tr FROM wp_term_relationships AS tr LEFT JOIN wp_posts AS p ON p.ID = tr.object_id WHERE p.ID IS NULL;

3. A table name typed by hand

Code that writes its own table names breaks on the first site with another prefix, and a typo breaks it everywhere. Both fail the same way. Save as wordpress/count-posts.php:

<?php
global $wpdb;

$pagesco_count = $wpdb->get_var( 'SELECT COUNT(*) FROM wp_post' );
var_dump( $pagesco_count );
wp eval-file count-posts.php

Output

<div id="error"><p class="wpdberror"><strong>WordPress database error:</strong> [Table &#039;wordpress.wp_post&#039; doesn&#039;t exist]<br /><code>SELECT COUNT(*) FROM wp_post</code></p></div>NULL

What it means: MySQL said Table 'wordpress.wp_post' doesn't exist; because WP_DEBUG is on, $wpdb printed it as an HTML error box meant for a browser (hence &#039; for each quote), and get_var() returned NULL. 4. Forgetting the third argument of get_post_meta() (silent)

A theme wants to label long reads, posts of more than 10 minutes:

wp eval 'var_dump( get_post_meta( 15, "pagesco_reading_minutes" ), get_post_meta( 15, "pagesco_reading_minutes" ) > 10, get_post_meta( 15, "pagesco_reading_minutes", true ) > 10 );'

bool(true)

What it means: without true, get_post_meta() returns every value of that key as an array, because a post may have the same meta key several times (add_post_meta() adds another row each time). 🏋️ Exercise 1: The Only Comment

Every new site has one comment. With SQL, show its ID, its author, whether it is approved, and the title of the post it belongs to. Then get the same comment through WordPress with get_comments().

🏋️ Exercise 4: Watch WordPress Query (Stretch)

How many queries does WordPress run to build the home page, and which one is the main query? Write a must-use plugin exercise-queries.php that turns on the SAVEQUERIES constant, and on shutdown writes the number of queries and the main query to the debug log, for front-end requests only. Then explain why the big "load all autoloaded options" query is not in your list.

💡 Hint

With SAVEQUERIES defined as true, $wpdb->queries collects every query as an array whose first element is the SQL. The main query of a blog page starts with SELECT SQL_CALC_FOUND_ROWS. For the last question, look at where must-use plugins load in wp-settings.php, and when the options were read.

✅ Solution 
<?php
/**
 * Plugin Name: Exercise: Queries
 */

define( 'SAVEQUERIES', true );

add_action(
	'shutdown',
	function () {
		global $wpdb;

		if ( is_admin() || wp_doing_cron() || defined( 'WP_CLI' ) ) {
			return;
		}

		error_log( sprintf( '%d queries', $wpdb->num_queries ) );
		foreach ( $wpdb->queries as $pagesco_query ) {
			if ( str_contains( $pagesco_query[0], 'SQL_CALC_FOUND_ROWS' ) ) {
				error_log( 'main query: ' . preg_replace( '/\s+/', ' ', $pagesco_query[0] ) );
			}
		}
	}
);
http://localhost:8080/

[25-Oct-2026 21:40:27 UTC] 24 queries
[25-Oct-2026 21:40:27 UTC] main query: SELECT SQL_CALC_FOUND_ROWS wp_posts.ID FROM wp_posts WHERE 1=1 AND ((wp_posts.post_type = 'post' AND (wp_posts.post_status = 'publish'))) ORDER BY wp_posts.post_date DESC LIMIT 0, 10

❓ Common Questions at This Stage

My host runs MariaDB, or MySQL 8.4. Does anything change?

Almost nothing. WordPress supports MySQL 5.5.5 and later and MariaDB, and its own SQL uses only features they all share; wp-env (Lesson 1.2) runs MariaDB, and everything in this lesson works there. The differences you might notice are around the edges: SELECT VERSION() prints a version ending in -MariaDB, EXPLAIN output looks different (MariaDB prints a table, not MySQL 9.7's tree), MariaDB's JSON type is an alias for LONGTEXT, and a few MySQL-only functions from MySQL Foundations' later lessons may be missing. Write your plugin's SQL in the plain style core uses and you will not meet them.

Why doesn't WordPress use foreign keys or JSON columns?

History and reach. The schema was designed when MyISAM, which supports neither, was MySQL's default, and WordPress has never broken old sites to adopt newer features: it runs on servers twenty years apart. Serialized PHP predates MySQL's JSON type by a decade. The price is what you saw today: integrity is enforced in PHP, so you change data through the API, and arrays are opaque to SQL.

Can my plugin add a column to wp_posts?

Technically yes, and you should not. A WordPress update may alter the table, other plugins and backup tools do not know your column, and nothing in core (REST API, revisions, exports) will carry it. Use post meta for fields of a post, a taxonomy for groupings, or your own table for data with its own life, like the events you build in Lesson 5.5.

MySQL warns that SQL_CALC_FOUND_ROWS is deprecated. Is WP_Query broken?

No. MySQL 9.7 still runs it and only records warning 1287 ("SQL_CALC_FOUND_ROWS is deprecated and will be removed in a future release") if you ask with SHOW WARNINGS; WordPress 7.1 still uses it to count matches for pagination. When you do not need page numbers, pass 'no_found_rows' => true to WP_Query and it leaves it out, which is also faster (Lesson 4.2).

🎓 Key Takeaways

  • Core is wp-admin/, wp-includes/ and the root files; yours is wp-content/, where drop-ins such as object-cache.php can also replace parts of core
  • wp-config.php holds the database connection, eight secret keys and the table prefix, and ends by loading wp-settings.php; nothing after that line takes effect

  • Twelve tables, linked by ID columns but with no foreign keys: integrity lives in PHP, so change data through WordPress, not with UPDATE/DELETE
