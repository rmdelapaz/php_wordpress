🚀 Lesson 8.4: Deployment & Maintenance

Pages & Co. has a block theme, a tested and translated plugin and a release ZIP, and all of it lives at http://localhost:8080, where only you can see it. This lesson takes the shop live the way professionals do: the shop's code in Git, release files built from a tagged commit, the database moved with WP-CLI, and a production configuration with no debugging, no development mode and no secrets in the code. You will rehearse the whole launch on your own machine, on a second WordPress set up the way a real server is, and then keep it running: a real cron job, a backup you have actually restored, an update deploy, and a hardening and maintenance checklist.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Choose a hosting type for a WordPress project by what it needs, and explain how code, content and configuration move between development, staging and production
  • Keep a WordPress project's own code in Git with a .gitignore, and build release files from a tagged commit with composer install --no-dev, npm ci, npm run build and the plugin ZIP
  • Move a database with wp db export, wp db import and wp search-replace, including serialized values and a plugin's own tables
  • Configure WordPress for production: debugging and development mode off, the environment type, secrets outside the code, a real cron job, file editing disabled and a least-privilege database account
  • Back up a site and prove the backup with a restore, deploy an update, and keep a maintenance checklist

🌍 Code, Content and Configuration

Think of the day Pages & Co. moves into a bigger store. The carpenter builds the new shelves in the workshop, tests them, and carries them in finished: nobody saws wood in the shop while customers browse. The books on the shelves belong to the shop; on moving day they come along once, and from then on the booksellers add and sell them in the store, not in the workshop. And the alarm code and the key to the safe are set for the new building and never painted on a shelf. A WordPress site moves the same way, and almost every deployment mistake comes from treating one of these three like another.

💡 Mental model: code goes up, content comes down, configuration stays

Code (the theme, the plugin, the must-use plugin) is written on your computer, kept in Git, built into release files and deployed to the live site. Nobody edits it on the server. Content (the database and wp-content/uploads) is created on the live site by the shop's staff from launch day on: it travels from your machine to the server exactly once, at the launch, and afterwards only the other way, as a copy from live to your machine or to staging when you need real data. Configuration (wp-config.php, passwords, API keys, server settings) is written for each environment and never copied between them.

Professional projects have up to three environments:

  • Development (local in WordPress's terms): your machine. Debugging on, test data, the supplier sandbox from Lesson 7.3.
  • Staging: a copy of the live site on the same kind of server, hidden from the public and from search engines, where a release or an update is tried with real data before it reaches customers.
  • Production: the live shop. Real customers, real orders, the real supplier.
graph TD A["development: your computer"] -->|"code: Git, a release build"| B["staging: a copy of production"] B -->|"the same release files, tested"| C["production: the live shop"] C -->|"content: copies of the database"| D["staging or development: real data to test with"]

One consequence surprises people the first time: an edit an administrator makes in the Site Editor on the live site is content. Lesson 3.2 showed that the Site Editor saves templates and styles as posts in the database, and those posts win over the theme's files. If the shop's manager changes the header on the live site and you deploy a new parts/header.html, the manager's version stays visible. Changes that should become code are exported into the theme (Lesson 3.3), committed and deployed; everything else stays content.

In this lesson you rehearse the launch on your own machine. A download gives you a second WordPress, pagesco-live, at http://localhost:8081, configured as a server would be: its own database with a restricted account, no debugging, secrets in a private file, a scheduler instead of WP-Cron. It behaves like production in everything this lesson tests, with one exception: it is not on the internet, so it has no domain name and no HTTPS. Your development site at http://localhost:8080 keeps running next to it, untouched.

Whatever the label, check a plan against what the project actually needs. For Pages & Co.:

  • PHP 8.2 or newer (the plugin's Requires PHP) and WordPress 6.9 or newer (its Requires at least, Lesson 8.3); MySQL 8.0 or newer (or a current MariaDB), as WordPress.org recommends.
  • SSH access with WP-CLI: this lesson's launch, migration and backups are WP-CLI commands, and so is every repair from Lesson 8.1.
  • A real cron job that can run a command on a schedule, for the nightly supplier sync (Lesson 7.3, and Running a Live Site below).
  • HTTPS with automatically renewed certificates, which almost every host now includes.
  • Backups you can restore yourself, kept somewhere other than the server, and ideally staging copies.
  • Nice to have: page caching and a persistent object cache (Redis or Memcached), the host's job as Lesson 8.2 concluded.

🧩 Version note: PHP on hosting plans

Many hosts still start new sites on PHP 8.3 or 8.4, and some keep old sites on 8.1 until someone changes it in the control panel. Pages & Co. Books runs on 8.2 and newer, so 8.3 and 8.4 are fine: WordPress refuses to activate it on 8.1 because of its Requires PHP: 8.2 header. The differences you have seen in this course (closure names in fatal errors, Lesson 2.3; fatal-error stack traces, Lesson 1.3) are cosmetic. Choose the newest version the host offers, and test on staging before you switch a live site.

The environment type

wp_get_environment_type() returns local, development, staging or production, from the WP_ENVIRONMENT_TYPE constant (or an environment variable of the same name), and production when neither is set. Core reads it in several places you have met: WordPress 7.1 sends pingbacks only from production sites, application passwords work without HTTPS only on local sites (Lesson 7.1), and Site Health reports it. Your own code may read it too, carefully: different safety rules per environment are fine (a plugin that allows a plain-HTTP sandbox on local only), different features make staging lie about production. The project adds one such safety rule to the plugin.

Secrets

A secret is anything that lets someone act as the site: the database password, the authentication keys and salts (Lesson 2.2), the supplier's API key, an SMTP password. Where yours are on the development site:

grep -n -e "define( 'WP_DEBUG'" -e "WORDPRESS_CONFIG_EXTRA" -e "SUPPLIER" wp-config.php

Output

127:if ($configExtra = getenv_docker('WORDPRESS_CONFIG_EXTRA', '')) {
131:define( 'PAGESCO_BOOKS_SUPPLIER_URL', 'http://localhost:8080/supplier-sandbox/v1/' );

The Docker image's wp-config.php reads most values from environment variables (getenv_docker(), Lesson 2.2), and Lesson 7.3 wrote the sandbox's address and key into the file itself with wp config set. On your machine that is fine: the file is not in Git (it is outside wp-content, which you will put in Git), and the key only opens a fake supplier. For production the rules are:

  • Secrets live on the server only: in its wp-config.php, written there and never committed, or in environment variables that wp-config.php reads, which hosting panels and container platforms let you set. The rehearsal site reads them from a file named .env next to its compose.yaml.
  • Every environment has its own: live database passwords, salts and the supplier's live key are not the ones on your machine or on staging, so a leaked development file opens nothing.
  • The supplier sandbox never ships. The supplier-sandbox folder from Lesson 7.3 sits in your WordPress folder, outside wp-content. It is not in Git and not in any release file, so it cannot reach the live site by accident; the live site gets the distributor's real HTTPS address and key instead.
  • Unique salts per site: the WordPress image generates random ones on first start, and wp config shuffle-salts (Lesson 2.2) replaces them, which logs everybody out.

🗂️ The Shop's Code in Git

Git is the source of truth for code: every release is a commit you can name, compare and rebuild, and the live site gets nothing that is not in one. The question for a WordPress project is what belongs in the repository. The rule: your own source code and the files that describe how to build it, and nothing that someone else maintains, that a tool generates, or that is content.

✅ Commit often, tag what you deploy

Commit whenever something works, with a message that says why. When a commit goes live, give it an annotated tag (git tag -a release-1 -m "..."): the tag is the answer to "what exactly is on the live site?", the starting point for the next release's changelog, and the commit you rebuild if you ever need to roll back. Push the repository to a private remote (a Git hosting service, or a server you control), so that it does not live only on your laptop.

📦 Release Builds

The repository holds sources; the live site needs runnable files. A release build turns one into the other, and it starts from a commit, in a clean folder, never from your working copy. Your working copy has files that are not committed yet, the development packages of Lesson 8.1, and whatever you were trying out this afternoon. Here is the difference that matters most, in your working copy's Composer autoloader:

grep -o "/[a-z-]*/[a-z-]*/[A-Za-z/_-]*\.php" wp-content/plugins/pagesco-books/vendor/composer/autoload_files.php

Output

/myclabs/deep-copy/src/DeepCopy/deep_copy.php
/phpunit/phpunit/src/Framework/Assert/Functions.php

Three files from development packages that the autoloader requires on every load. A ZIP of this vendor/composer without those packages dies on the client's site with "Failed opening required" (Lesson 8.3, Common Mistake 3). Lesson 8.3 worked around it by regenerating the autoloader and putting it back. 🗄️ Moving the Database

At the launch, the database travels once: the books, genres, pages, settings, events and users you made on your machine become the live shop's starting point. WordPress stores addresses in it as full URLs, so they must change on the way. Ask WP-CLI what would change, without changing anything (--dry-run), for the rehearsal site's address:

(If you edited these in the editor, you have a few more revisions.) Nothing in the theme or plugin code contains the address; it is all content. Three options matter:

  • --all-tables-with-prefix: by default wp search-replace and wp db commands work on the tables WordPress registers, the core ones. The plugin's wp_pagesco_events table (Lesson 5.5) is not among them. Here it has no addresses, but Common Mistake 2 shows what leaving it out costs.
  • --skip-columns=guid: the guid column of wp_posts looks like a URL (http://localhost:8080/?p=30) but is an identifier, which feed readers use to recognize posts they have seen. It is not used as a link, and WP-CLI's documentation leaves it alone in its own examples. Leave it.
  • The Type column: SQL means WP-CLI used MySQL's REPLACE(), which is safe because no value in that column is serialized; PHP means it loaded every value into PHP, unserialized it where needed, replaced, and serialized it again.

Serialized data

That last point is why WordPress migrations use wp search-replace and not SQL. Lesson 2.2 showed that a serialized value records the length of every string (s:34:"…"), and that a plain SQL REPLACE() to a longer address breaks it. Your shop happens to have no serialized addresses yet, but plugins store them all the time: a settings array with a page address, a widget with a link. A demo option shows what wp search-replace does with one, for the real shop's address, https://www.pagesco.example (--export without a file name writes the changed SQL to the screen instead of changing the database):

wp option add pagesco_demo_links '{"shop":"http://localhost:8080/find-a-book/"}' --format=json
wp db query "SELECT option_value FROM wp_options WHERE option_name = 'pagesco_demo_links'"
wp search-replace 'http://localhost:8080' 'https://www.pagesco.example' wp_options --export | grep -o "pagesco_demo_links', '[^']*'"
wp option delete pagesco_demo_links

Output

The string grew from 34 to 40 characters, and WP-CLI rewrote the length with it (the backslashes only escape the quotes inside the SQL). Your database was not touched, because --export writes instead of saving: the project uses exactly that, with a file name, to produce the launch database in one command.

💡 WP_HOME and WP_SITEURL

Lesson 2.2 mentioned two constants that override the home and siteurl options from wp-config.php. They help when a moved site redirects to its old address and you cannot reach wp-admin, but they change only those two values: the links in content still need wp search-replace. Use the replace, and leave the constants for emergencies.

🔧 Running a Live Site

A launch is one day; the site then runs for years. Four routines keep it healthy.

Scheduled tasks: a real cron job

WP-Cron (Lesson 7.3) is not a scheduler: on each page view, WordPress checks whether an event is due and, if so, starts wp-cron.php with a request to itself. On a quiet night with no visitors, the 03:00 supplier sync runs when the first customer arrives at 07:40; on a busy site, the checks cost a little on every request; and behind some caches no request reaches PHP at all. Production sites turn the page-view trigger off with define( 'DISABLE_WP_CRON', true ); and let the server's own scheduler run due events every few minutes. Your site's job, as WP-CLI sees it:

wp cron event list --hook=pagesco_books_daily_sync --fields=hook,recurrence

Output

+--------------------------+------------+
| hook                     | recurrence |
+--------------------------+------------+
| pagesco_books_daily_sync | 1 day      |
+--------------------------+------------+

On a server with SSH, the scheduler is cron, and its table (crontab -e) gets one line that runs WP-CLI every five minutes in the site's folder:

*/5 * * * * cd /var/www/pagesco && wp cron event run --due-now --quiet

Hosting panels offer the same as "cron jobs" in a form; without WP-CLI, the line requests https://www.pagesco.example/wp-cron.php?doing_wp_cron instead. The rehearsal site has a small cron container that does this every minute. WP-Cron's events and functions do not change at all: wp_schedule_event(), the Activator's DailySync::schedule() and the hook stay exactly as Lesson 7.3 wrote them. Only the trigger moves.

Backups and restores

Code is in Git, and configuration is written down; what only exists on the live server is content, so that is what a backup must hold:

The usual rule is 3-2-1: three copies, on two kinds of storage, one of them somewhere else (a backup on the same server burns with the server). Keep several days and a few older copies, because a problem is often noticed a week late. And above all: a backup you have never restored is a hope, not a backup. Restore one on purpose, on staging or a rehearsal site, before you need to; you do it in the project.

⚠️ Common Mistakes

1. A database dump in the web root

The quickest way to make a backup on a server is wp db export in the WordPress folder. Try it on your machine and then ask for the file like a stranger would (from the WP-CLI container):

wp db export pagesco-dev.sql
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/pagesco-dev.sql
curl -s http://localhost:8080/pagesco-dev.sql | grep -o "'admin','[$]wp[$]2y[$][0-9]*"

Output

Success: Exported to 'pagesco-dev.sql'.
200
'admin','$wp$2y$12

What it means: 200: the whole database is a download, with every user's email address and password hash (the last line is the start of the administrator's), every setting and every order. Bots try names like backup.sql and dump.sql on every site, all day. Fix: write dumps outside the web root (the rehearsal site's /backups), move them off the server, and make the web server refuse .sql and .log files as a second line of defense (the rehearsal site's Apache configuration does; you will see the 403). Remove the file:

rm pagesco-dev.sql

2. A migration that loses the plugin's table

The launch database comes from wp search-replace … --export=file. Without --all-tables-with-prefix:

wp search-replace 'http://localhost:8080' 'http://localhost:8081' --skip-columns=guid --export=/tmp/check.sql > /dev/null
grep -c '^CREATE TABLE' /tmp/check.sql
grep -c 'CREATE TABLE `wp_pagesco_events`' /tmp/check.sql

Output

12
0

What it means: twelve tables, the core ones, and no events table: --export writes only the tables it searched, and by default it searches the tables WordPress registers. The command says "Success", the file imports without an error, the books and pages are all there. On the rehearsal site, with a launch database made this way, the Events page says "No events are scheduled right now. Check back soon!", and only the server's log tells the truth (docker compose logs wordpress in pagesco-live, recorded):

3. The repository in the web root

Your Git repository lives in wp-content, inside the web root. On your machine nobody else can reach it. Put a repository like that on a server (the tempting "deploy" is git clone or git pull in the live wp-content), and:

curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/wp-content/.git/config
curl -s http://localhost:8080/wp-content/.git/HEAD

Output

200
ref: refs/heads/main

What it means: the web server hands out .git like any other folder. With the configuration file and HEAD, freely available tools download the objects one by one and rebuild the whole repository: all the code, its history, and every secret anyone ever committed by mistake. Fix: deploy release files, not the repository; and deny hidden files and folders in the server configuration (the rehearsal's Apache configuration has a rule for it). On your machine, leave it: it is your development site.

<?php
/**
 * The supplier's API (Riverside Books), over HTTP.
 *
 * @package PagesCo\Books
 */

namespace PagesCo\Books\Supplier;

use WP_Error;

/**
 * Asks the supplier what it has, and places orders. Every method returns data or a WP_Error, never both.
 *
 * The address and the API key come from wp-config.php: PAGESCO_BOOKS_SUPPLIER_URL and PAGESCO_BOOKS_SUPPLIER_KEY.
 * Outside a local development site, the address must use HTTPS, because the key is sent with every request.
 */
final class Client {

	/**
	 * Seconds to wait for the supplier before giving up.
	 */
	private const TIMEOUT = 5;

	/**
	 * GET /availability: copies at the supplier and the next delivery date, keyed by ISBN.
	 *
	 * @param string[] $isbns ISBN-13s without dashes.
	 * @return array<string, array{available: int, next_delivery: string}>|WP_Error
	 */
	public function availability( array $isbns ) {
		$url = $this->url( 'availability' );
		if ( is_wp_error( $url ) ) {
			return $url;
		}

		$response = wp_remote_get(
			add_query_arg( 'isbns', rawurlencode( implode( ',', $isbns ) ), $url ),
			array(
				'timeout' => self::TIMEOUT,
				'headers' => $this->headers(),
			)
		);

		$data = $this->decode( $response );
		if ( is_wp_error( $data ) ) {
			return $data;
		}
		if ( ! isset( $data['items'] ) || ! is_array( $data['items'] ) ) {
			return new WP_Error( 'pagesco_supplier_bad_response', __( 'The supplier answered without a list of items.', 'pagesco-books' ) );
		}

		$availability = array();
		foreach ( $data['items'] as $item ) {
			$availability[ (string) ( $item['isbn'] ?? '' ) ] = array(
				'available'     => (int) ( $item['available'] ?? 0 ),
				'next_delivery' => (string) ( $item['next_delivery'] ?? '' ),
			);
		}

		return $availability;
	}

	/**
	 * POST /orders: orders copies of a book. Returns the supplier's order confirmation.
	 *
	 * @param string $isbn     ISBN-13 without dashes.
	 * @param int    $quantity How many copies.
	 * @return array|WP_Error
	 */
	public function order( string $isbn, int $quantity ) {
		$url = $this->url( 'orders' );
		if ( is_wp_error( $url ) ) {
			return $url;
		}

		$response = wp_remote_post(
			$url,
			array(
				'timeout' => self::TIMEOUT,
				'headers' => $this->headers() + array( 'Content-Type' => 'application/json' ),
				'body'    => wp_json_encode(
					array(
						'isbn'     => $isbn,
						'quantity' => $quantity,
					)
				),
			)
		);

		return $this->decode( $response );
	}

	/**
	 * The full address of one of the supplier's endpoints, from the URL in wp-config.php.
	 *
	 * @param string $endpoint The endpoint's path, such as availability.
	 * @return string|WP_Error
	 */
	private function url( string $endpoint ) {
		if ( ! defined( 'PAGESCO_BOOKS_SUPPLIER_URL' ) || ! defined( 'PAGESCO_BOOKS_SUPPLIER_KEY' ) ) {
			return new WP_Error( 'pagesco_supplier_not_configured', __( 'The supplier is not configured in wp-config.php.', 'pagesco-books' ) );
		}

		// The API key goes with every request: only over HTTPS, except on a local development site (Lesson 8.4).
		if ( 'https' !== wp_parse_url( PAGESCO_BOOKS_SUPPLIER_URL, PHP_URL_SCHEME ) && 'local' !== wp_get_environment_type() ) {
			return new WP_Error( 'pagesco_supplier_insecure', __( 'The supplier address must start with https:// on this site.', 'pagesco-books' ) );
		}

		return trailingslashit( PAGESCO_BOOKS_SUPPLIER_URL ) . $endpoint;
	}

	/**
	 * The headers every request sends: what we accept, and who we are.
	 */
	private function headers(): array {
		return array(
			'Accept'    => 'application/json',
			'X-Api-Key' => PAGESCO_BOOKS_SUPPLIER_KEY,
		);
	}

	/**
	 * Turns an HTTP response into data, or into a WP_Error for each way it can go wrong.
	 *
	 * @param array|WP_Error $response What wp_remote_get() or wp_remote_post() returned.
	 * @return array|WP_Error
	 */
	private function decode( $response ) {
		// 1. No answer at all: DNS, connection refused, timeout.
		if ( is_wp_error( $response ) ) {
			return $response;
		}

		$code = wp_remote_retrieve_response_code( $response );
		$data = json_decode( wp_remote_retrieve_body( $response ), true );

		// 2. An answer, but not a success: 401, 404, 422, 503...
		if ( $code < 200 || $code > 299 ) {
			return new WP_Error(
				'pagesco_supplier_http_error',
				sprintf(
					/* translators: 1: HTTP status code, 2: the supplier's message. */
					__( 'The supplier answered %1$d: %2$s', 'pagesco-books' ),
					$code,
					is_array( $data ) && isset( $data['message'] ) ? $data['message'] : wp_remote_retrieve_response_message( $response )
				),
				array(
					'status'      => $code,
					'retry_after' => wp_remote_retrieve_header( $response, 'retry-after' ),
				)
			);
		}

		// 3. A success that is not the JSON we expect.
		if ( ! is_array( $data ) ) {
			return new WP_Error( 'pagesco_supplier_bad_response', __( 'The supplier\'s answer is not JSON.', 'pagesco-books' ) );
		}

		return $data;
	}
}

❓ Common Questions at This Stage

Do I really need a staging site?

For a shop that takes money, yes, if the host makes it easy (many managed hosts create a staging copy in one click). Staging is where updates and releases meet real data and the real server before customers do. Give it WP_ENVIRONMENT_TYPE staging, keep it out of search engines (Settings > Reading, "Discourage search engines", and a password in front), point the supplier at its sandbox, and make sure it cannot send email to real customers. Refresh it from production now and then with the same wp search-replace in the other direction.

How do I get the live content onto my machine to debug something?

The launch in reverse: wp db export on the live site, then on your machine wp db import and wp search-replace 'https://www.pagesco.example' 'http://localhost:8080' --all-tables-with-prefix --skip-columns=guid. Two cautions. The copy contains customers' personal data: keep it encrypted, delete it when you are done, and consider replacing email addresses (a small wp eval loop) before you work with it. And your machine will then have the live passwords' hashes: reset the admin password locally to something simple again.

My host cannot run Composer or npm. Should I commit vendor/ and build/?

Not to main. Build the release on your machine or in a build service, as in this lesson, and upload the ZIP. If the host insists on deploying from Git, give it a separate branch or repository that holds only built releases (the unpacked ZIPs), so that the source repository stays clean and every built file still comes from a tagged commit.

Something is broken on the live site right now. May I fix it there?

Fix it in Git, release a patch version (1.1.2), and deploy it: with a release script that takes a few minutes, which is rarely slower than editing carefully on a server. With DISALLOW_FILE_EDIT there is no editor anyway, and an edit made over SFTP disappears at the next deploy, along with the fix. If the site is down, roll back first: install the previous release's ZIP with --force (that is what the tags are for: rebuild the ZIP from the previous tag, or better, keep each release's ZIPs under a name with its version, as Lesson 9.1 does, so a rollback is one command), then fix calmly.

🎓 Key Takeaways

  • Code goes up (Git, a release build, a deploy), content comes down (the database moves once at launch, then only copies from live), configuration stays (written for each environment)
  • Choose hosting by what the project needs: PHP and WordPress versions, SSH and WP-CLI, a real cron job, HTTPS, restorable off-server backups, staging
  • Production: WP_DEBUG off and errors only in the log, WP_ENVIRONMENT_TYPE production, no WP_DEVELOPMENT_MODE, DISALLOW_FILE_EDIT, secrets on the server only; raise the theme's Version with each release (the pattern cache)
  • Git tracks only your own source; a .gitignore that ignores everything and lets your folders back in keeps it that way; tag every release
  • Build releases from a tag in a clean folder: composer install --no-dev --optimize-autoloader, npm ci, npm run build, npm run plugin-zip; never deploy the repository
  • wp search-replace handles serialized data; use --all-tables-with-prefix, --skip-columns=guid, --dry-run first and --export for a launch file; after importing a development database, reset passwords and remove application passwords and transients
  • DISABLE_WP_CRON plus a server cron job; daily backups kept elsewhere, proven by a restore; updates through staging; a least-privilege database account (with LOCK TABLES for backups); a maintenance checklist
