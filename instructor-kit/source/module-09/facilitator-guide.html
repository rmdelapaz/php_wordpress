Session 9: Your First Plugin and Custom Post Types

How to teach the first session of Part 2. Open Part 2 for two groups at once (learners coming from Part 1 and learners joining here) with a refresher, a starting note and the Part 2 environment check, then build the pagesco-books plugin the way it will grow for ten sessions (a header, a namespace, Composer's autoloader, one class per feature, a life cycle) and teach WordPress about books: a post type, a genre taxonomy, typed meta and the seeded catalog.

The #1 risk of Session 9: two rooms in one

Learners who finished Part 1 a week ago have the Lesson 4.3 site and the habits (debug.log, WP-CLI, hooks). Learners who join at Part 2 may have neither: their machine may not run the course project, their site may be a fresh install, and "the store notice from Lesson 2.3" means nothing to them. Before: send the setup guide (Docker, the project, the Part 2 starting site pagesco-part2-start.zip from the course's downloads) and the starting note below to every new learner a week ahead, and ask everyone to reply with the last line of check_environment.sh --part2. In the room: the check gets 12 minutes; a learner whose site is not where Part 2 starts sits with a ready partner for the demos and installs the Part 2 starting site at the break, not during Lesson 5.1. Both groups get the same refresher: R1 and R2 are exactly what Lesson 5.1 builds on.

Your First Plugin

Objectives (from the lesson page)
  • Write a plugin header WordPress understands, including the version requirements it checks on activation
  • Organize a plugin as a short main file plus namespaced classes in src/, loaded by Composer's PSR-4 autoloader

Mental model to say

Draw the shop on the board: "pagesco-books is the shop's back office. Each feature, the notice additions, the catalog, the events calendar, the settings page, is a department with its own room. The main file is the front door with the shop's name on it: it unlocks, switches on the lights and hands a list of departments to the manager, the Plugin object, who opens each one in the morning, on plugins_loaded. A new department means a new room and one new line on the manager's list, never knocking through the walls of the existing ones."

Then the three relatives in one line each: must-use plugin = always on, no switch (Lesson 2.3); functions.php = only while that theme is active (Lesson 4.3); plugin = the owner switches it on and off, and it can clean up after itself. "Everything the shop DOES goes in a plugin, so it survives the next redesign."

Then the two tools for a plugin that will have fifteen features: a namespace (PagesCo\Books, the prefix for classes) and autoloading (Composer's PSR-4 rule: PagesCo\Books\Admin\SettingsPage lives in src/Admin/SettingsPage.php, letter for letter).

Three mistakes to expect, and how to coach each
  • A file name that does not match the class. storeNotice.php, Store_Notice.php, class-store-notice.php (Lesson 1.3's style). Coach: "Read the class name, swap PagesCo\Books\ for src/, add .php: is that the file?" (Self-check Q3; the psr4_paths lab.)
  • Hooks registered in the wrong place. The activation hook inside a callback; add_action( 'init', ... ) inside a class constructor that nothing creates. Coach: "Who calls this line, and when?" For features: only register() adds hooks, and boot() calls it. (Self-check Q6.)
  • Deleting data on deactivation. "Clean up" in deactivate(). Coach with the life-cycle line on the board: deactivate is a pause. (Self-check Q4; the gift_wrap lab's uninstall.php.)

Mental model to say

Back to Lesson 2.1's picture: "wp_posts is one big filing cabinet. A custom post type is a new labeled drawer in it, not a new cabinet: books are stored in the same table as posts and pages, with the same columns, so the Loop, WP_Query, revisions and the block editor work on them for free. A taxonomy is the colored tabs you clip onto the files to group them, a book's genres. Meta is the index card in each file with its own facts: this book's price, its author, its page count."

Then the three functions on the board, all called on init: register_post_type() (a kind of content: book), register_taxonomy() (a way to group it: genre), register_post_meta() (a named, typed field: pagesco_price). Each is one feature class in pagesco-books, the rule from Lesson 5.1.

Then the one thing that surprises everyone: "Registering a type adds URL rules, and WordPress keeps the rules in the database. Until something flushes them, /books/ is a 404." The activation hook gets its second job.

Three mistakes to expect, and how to coach each
  • "It's a 404, my code is wrong." Coach: "When did the rules last change? wp rewrite list --match=/books/." Then the fix in the right place: the activator. (Self-check Q10.)
  • The activator that only flushes. It trusts init to have registered the type; on the activation request it has not. Coach with the warning box "Registering is not enough on activation". (The book_quotes lab's TODO 4.)
  • Taxonomy or meta? A "genre" meta key, a "price" taxonomy. Coach with the lesson's test: "Would you want a page that lists everything with this value?" (Self-check Q9.)

Checks for understanding

Ask these out loud during the demo and the lab:

  • Where are books stored? Answer: in wp_posts, with post_type book; their meta in wp_postmeta; genres in the term tables.
  • Why does the activator register the type itself? Answer: on the activation request the plugin's own init callback has not run, so the rules would be flushed without the type.
  • Why pagesco_price and not _pagesco_price? Answer: an underscore key is protected: hidden from the Custom Fields box, not writable through REST without an auth callback, refused by block bindings.
  • What happens to the books when the plugin is deactivated? Answer: they stay in the database; the type is unregistered, so they vanish from the admin and their URLs 404 until it is active again.
