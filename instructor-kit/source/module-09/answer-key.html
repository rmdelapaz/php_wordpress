5.1 · Your First Plugin: self-check

Q1
A client's server runs PHP 8.1. pagesco-books says Requires PHP: 8.2. What happens when the administrator clicks Activate?
A) The plugin activates, and the first page that uses PHP 8.2 syntax dies with a fatal error
B) WordPress refuses to activate it and says which PHP version the plugin requires
C) The plugin activates with the features that need PHP 8.2 switched off
D) Composer's platform_check.php deletes the vendor folder
Why: The requirement lines are read before a line of the plugin runs; activation fails with "Current PHP version ... does not meet minimum requirements" (Lesson 5.1, Exercise 1). Without the header, PHP 8.2 syntax on an old server would have been a fatal error instead.
A is wrong: That is what happens WITHOUT the header line.
C is wrong: WordPress knows nothing about your features; it refuses the whole plugin.
D is wrong: platform_check.php stops with a message on an old PHP; it never deletes anything, and WordPress refuses earlier anyway.
Q2
On the course site after Lesson 5.1, what does this print?
wp eval 'echo PAGESCO_BOOKS_DIR, "\n";'
/var/www/html/wp-content/plugins/pagesco-books/
Why: plugin_dir_path( __FILE__ ) returns the folder of the main file WITH a trailing slash, as the container sees it (your wordpress/wp-content/plugins/pagesco-books/). The trailing slash is why the main file can write PAGESCO_BOOKS_DIR . 'vendor/autoload.php' with no slash in between.
Q3
A learner creates src/Admin/BookColumns.php but writes namespace PagesCo\Books; at the top of it, and lists Admin\BookColumns::class in feature_classes(). What happens on the next request?
A) Nothing: PSR-4 only looks at the file name
B) Composer must be run again before the class is found
C) A fatal error: Class PagesCo\Books\Admin\BookColumns not found
D) WordPress shows a "called incorrectly" notice and skips the feature
Why: The autoloader finds and includes src/Admin/BookColumns.php, but that file declares PagesCo\Books\BookColumns, so the class boot() asked for still does not exist: the same fatal as the project's Step 3. The namespace line must match the folder: PagesCo\Books\Admin for src/Admin/.
A is wrong: PSR-4 builds the file name from the class name, then expects the file to declare exactly that class.
B is wrong: dump-autoload is only needed when composer.json's autoload section changes.
D is wrong: WordPress is not involved: this is PHP's own class loading, and it is fatal.
Q4
A site owner deactivates pagesco-books for five minutes to find a conflict. Which of these must the deactivation callback NOT do?
A) Delete the Bookseller role and the plugin's options
B) Clear the plugin's scheduled events
C) Flush the rewrite rules
D) Nothing at all (an empty callback)
Why: Deactivation is a pause: it undoes what is temporary (scheduled events, rewrite rules) and keeps the owner's data. Deleting data is uninstall.php's job, and only when the plugin is deleted (Lesson 5.1, the life-cycle table).
B is wrong: Clearing scheduled events is exactly a deactivation job (Lesson 7.3).
C is wrong: Lesson 5.2's deactivate() does this so /books/ stops answering while the plugin is off.
D is wrong: An empty callback is fine: Lesson 5.1's first Activator::deactivate() was one.
Q5
On the course site after Lesson 5.1, what does the second command print, and why?
wp plugin uninstall pagesco-books --deactivate --skip-delete > /dev/null
wp eval 'var_dump( get_role( "pagesco_bookseller" ) );'
NULL: uninstall.php removed the role, so get_role() finds nothing
Why: --skip-delete runs the uninstall procedure (uninstall.php) without deleting the files: the safe way to test cleanup. Afterwards wp plugin activate pagesco-books re-creates the role, because activation runs Activator::activate() again.
Q6
Why must register_activation_hook() be called at the top level of the main file, not inside a plugins_loaded callback?
A) Because hooks registered on plugins_loaded run twice
B) Because the activation hook needs the autoloader, which loads later
C) Because WordPress only reads the main file's header at the top level
D) Because on the activation request plugins_loaded has already fired before WordPress includes the new plugin's file
Why: WordPress activates a plugin by including its main file during an admin (or WP-CLI) request that has already loaded everything else. A plugins_loaded callback added then never runs, so the activation hook is never registered, and nothing warns you (Lesson 5.1, Common Mistakes 3).
A is wrong: Callbacks run once per firing; plugins_loaded fires once per request.
B is wrong: The autoloader is required at the top of the main file, before the hooks are registered.
C is wrong: The header is read without running the file at all; it has nothing to do with where hooks are registered.

5.2 · Custom Post Types, Taxonomies & Meta: self-check

Q7
BookPostType registers 'has_archive' => 'books' and 'rewrite' => array( 'slug' => 'books' ). Which address lists all books?
A) /book/
B) /books/
C) /?post_type=books
D) /wp-json/wp/v2/book
Why: has_archive gives the archive its slug; the rewrite slug is the first part of each single book's address (/books/dune/). After a flush the rule books/?$ maps to index.php?post_type=book (Lesson 5.2's wp rewrite list).
A is wrong: That would be the default if rewrite and has_archive were just true: the type's NAME, book.
C is wrong: The query variable is the type's name, book, not the archive slug.
D is wrong: The REST route uses rest_base, books: /wp-json/wp/v2/books.
Q8
The Great Gatsby (book 33) is out of stock; pagesco_in_stock is registered as a boolean. What does this print on the finished Lesson 5.2 site?
wp eval 'var_export( get_post_meta( 33, "pagesco_in_stock", true ) ); echo "\n";'
'' (an empty string)
Why: Meta values are stored as strings: true is saved as '1', false as ''. get_post_meta() returns the stored string; only the REST API (and block bindings) cast it back to the registered type, which is why /wp/v2/books/33 says false. Compare a value with '' or cast it with (bool), as BookColumns does.
Q9
The shop wants a page /publisher/penguin/ listing every Penguin book, and filters by publisher on the Books screen. How should the publisher be stored?
A) As a taxonomy on the book type
B) As a meta key, pagesco_publisher
C) As an option
D) In the post content of each book
Why: Many books share one publisher, and the shop wants to browse by it: that is a taxonomy, with its own archive at /publisher/<slug>/ and an admin column for free. The lesson's test: would you want a page listing everything with that value? (Lesson 5.2 FAQ.)
B is wrong: Meta suits a fact that belongs to one item and that you read rather than browse, such as a price.
C is wrong: An option is one site-wide value, not one per book.
D is wrong: Content cannot be filtered, queried or listed by value.
Q10
"To be safe", a developer calls flush_rewrite_rules() on init. What is wrong with that?
A) Nothing: it is the recommended place
B) The rules are flushed before the post type is registered, so books 404
C) WordPress refuses to flush on init and logs a notice
D) It rewrites the whole rules option on every page load: a needless, slow database write
Why: Rebuilding the rules is expensive, which is why WordPress keeps them in an option and only rebuilds them when something flushes. Flush once, in the activator, after registering the type and taxonomy; deactivation flushes again (Lesson 5.2, Common Mistakes 1).
A is wrong: The handbook and the lesson both say: on activation, never on every request.
B is wrong: Registration at the default priority runs first and the URLs work; the cost is the problem.
C is wrong: WordPress lets you; it just costs a write per request.
Q11
Genre 8 is Fantasy. What does this print on the finished Lesson 5.2 site?
curl -s 'http://localhost:8080/wp-json/wp/v2/books?genres=8&_fields=title.rendered&orderby=id&order=asc'
[{"title":{"rendered":"The Hobbit"}},{"title":{"rendered":"Lord of the Rings"}}]
Why: The genre taxonomy is registered with rest_base genres, so the books route accepts genres=8 as a filter (term IDs, not slugs); _fields trims the response. Two books are filed under Fantasy (the term list's count).
Q12
A WP-CLI seeding script creates a book with wp_insert_post() and must give it two genres. Which reliably works?
A) 'tax_input' => array( 'genre' => $genres ) in the post array
B) A 'genres' key in the post array
C) wp_set_object_terms( $id, $genres, 'genre' ) after the insert
D) update_post_meta( $id, 'genre', $genres )
Why: tax_input is checked against the current user's assign_terms capability, and a script runs as no user, so the genres are silently dropped (Lesson 5.2, Common Mistakes 2). wp_set_object_terms() sets them without a capability check.
A is wrong: It works in the editor, as a logged-in user, and silently does nothing in a script.
B is wrong: wp_insert_post() ignores keys it does not know.
D is wrong: That stores a meta value named genre; the taxonomy never hears of it.

5.2 · Custom Post Types, Taxonomies & Meta: predict, then run

P3

curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/genre/fantasy/
200
Why: 200: the seeding created the Fantasy term, and the activator's flush gave /genre/<slug>/ its rule. Before the seeding it was a 404 for lack of a term, not of a rule.
P4
Predict the output, then run it.
wp eval 'var_dump( get_post_meta( 30, "pagesco_pages", true ),
    get_post_meta( 30, "pagesco_pages" ) );'
string(3) "412"
array(1) {
  [0]=>
  string(3) "412"
}
Why: A string both times: the database stores meta as text, and get_post_meta() hands back what is stored (the single value, or an array of all values without true). The REST API casts it to an integer because the key is registered as one.

The Lesson Pages' Own Quick Quizzes

Lesson 5.1 · Your First Plugin
  1. C A Plugin Name line in the header comment: WordPress reads the header comment without running the file, and Plugin Name is the one required field; everything else is optional, though the requirement lines are strongly recommended.
  2. A Once, during the request that activates the plugin: It runs once, during the request that activates the plugin, which is why one-time setup such as add_role belongs there and per-request code does not.
  3. B src/Rest/BooksController.php: PSR-4 replaces the prefix PagesCo\Books\ with src/, turns the remaining backslashes into slashes and adds .php, with the exact same letters and case.
  4. C In uninstall.php: uninstall.php runs only when the plugin is deleted, guarded by WP_UNINSTALL_PLUGIN. Deactivation is a pause and must keep the data.
  5. A Nothing; the autoloader finds the new class by its name: Nothing: the PSR-4 autoloader finds new classes by name. composer dump-autoload is only needed when the autoload section of composer.json changes, as the project showed with StoreNotice.
Lesson 5.2 · Custom Post Types, Taxonomies & Meta
  1. B init: init is the action WordPress fires once it is loaded and ready for plugins to register post types, taxonomies and meta; registering earlier or later misses the editor and REST setup.
  2. A The rewrite rules were not flushed after the type was registered: New rewrite rules are written only when flush_rewrite_rules() runs, which is why the activation hook flushes once; without it the pretty URL matches nothing.
  3. C A leading underscore would make them protected: not writable through REST and refused by block bindings: A leading underscore marks meta as protected: hidden from the Custom Fields box, not writable through REST without an auth_callback, and refused by block bindings. The shop wants these keys editable through the API and usable in bindings, so it leaves the underscore off.
  4. B The post type (or array of types) the taxonomy applies to: The second argument is the object type (or array of types) the taxonomy is attached to, here the book post type; that is what makes genre a taxonomy of books.
  5. C wp_set_object_terms( $id, $genres, 'genre' ): wp_set_object_terms( $id, $genres, 'genre' ) assigns terms directly, with no capability check, so it works in a script where no user is logged in.

Exit Ticket

  1. Three files: a class in src/ that implements Feature (its hooks in register()); one line in Plugin::feature_classes(); and, if the feature stores data, a line in uninstall.php that removes it.
  2. The role: activation creates it (Activator::activate()), deactivation keeps it (a pause), uninstall.php removes it (and the next activation creates it again).
  3. The 404: the rewrite rules in the database were saved before the book type existed and nothing rebuilt them. wp rewrite flush fixes it today; the permanent fix is the activator: register the type and taxonomy, then flush_rewrite_rules() (and flush again in deactivate()).

Common Wrong Answers and What They Reveal

  • Q1 A ("it activates, then dies"). Has not seen the header do work. Run Exercise 1 of Lesson 5.1 (Requires PHP 9.0) together.
  • Q3 B ("run Composer again"). Thinks the autoloader keeps a list of classes. Show vendor/composer/autoload_psr4.php: one line per PREFIX, not per class.
  • Q4 C or D. Reads "what must deactivation NOT do" as "what does it do". Point at the life-cycle line on the board.
  • Q7 A (/book/). Mixes up the type's name and its archive slug. wp rewrite list --match=/books/.
  • Q8 false. Expects get_post_meta() to return the registered type. It returns the stored string; REST casts (P4 is the same idea).
  • Q9 B (meta). Fine for a fact you only display; the /publisher/penguin/ page is the clue.
