2.2

Core Architecture & the Database

By the end you can
  • Find your way around a WordPress install: what lives in wp-admin/, wp-includes/ and wp-content/, and what a drop-in is
  • Read wp-config.php and explain its settings, including the table prefix and the security keys
  • Trace how wp-settings.php loads WordPress, and say what is available at each stage
  • Map the twelve wp_* tables, their keys and indexes, and join them with SQL the way WordPress's own queries do
  • Explain the meta (key-value) pattern, serialized values and options autoloading, with their trade-offs
  • Query the Pages & Co. site with wp db cli, wp db query and WP-CLI, and choose the API over raw SQL in your code
Key ideas
  • Core is wp-admin/, wp-includes/ and the root files; yours is wp-content/ (where drop-ins such as object-cache.php can replace parts of core) and wp-config.php.
  • wp-config.php holds the database connection, eight secret keys and $table_prefix, and its last line loads wp-settings.php: nothing defined after it takes effect.
  • wp-settings.php loads in a fixed order: database, must-use plugins, plugins, pluggable functions, theme, current user, then init and wp_loaded.
  • Twelve tables in five groups (content, taxonomies, users, comments, settings), linked by ID columns but with no foreign keys: integrity lives in PHP, so change data through WordPress.
  • Meta tables are key-value rows: flexible, but every value is text, each condition is one more join, and values are not indexed.
  • Arrays are stored serialized, lengths included: never edit them as text (wp option patch, update_option(), wp search-replace).
  • Autoload: on, auto, auto-on are loaded with every request; off, auto-off are read on demand (one query, then cached). In code: {$wpdb->posts}, never wp_posts.
Worked example: a slug lookup and its index

How does WordPress turn /about/ into page 12 so fast? Ask MySQL how it would find a page by its slug (EXPLAIN, from MySQL Foundations Lesson 6.1; \G prints the plan vertically):

wp db query "EXPLAIN SELECT ID FROM wp_posts WHERE post_name = 'about' AND post_type = 'page'\G"
*************************** 1. row ***************************
EXPLAIN: -> Filter: ((wp_posts.post_name = 'about') and (wp_posts.post_type = 'page'))  (cost=0.295 rows=0.455)
    -> Index lookup on wp_posts using post_name (post_name = 'about')  (cost=0.295 rows=1)

"Index lookup on wp_posts using post_name": the prefix index post_name(191) exists for exactly this question, so MySQL reads one row instead of the table. WordPress asks the same question through its API:

wp post list --post_type=page --name=about --field=ID
12

Every index on wp_posts matches a question WordPress asks all the time: by slug, by parent, by author, and "the latest published posts of this type" (type_status_date). There is no index on wp_postmeta.meta_value, which is why searching meta by value alone reads the whole table.

2.3

The Hooks System

By the end you can
  • Explain the difference between an action and a filter, and choose the right one for a task
  • Attach callbacks with add_action() and add_filter(), using priorities and the accepted-arguments count correctly
  • Remove a hook someone else added with remove_action() / remove_filter(), and say why a removal silently fails
  • Create your own action and filter hooks with do_action() and apply_filters() so other code can extend yours
  • Find the hook you need: in the core source, with has_filter() and $wp_filter, and from the command line with WP-CLI
  • Build the Pages & Co. store notice as a must-use plugin that others can customize through its own hooks
Key ideas
  • A hook is a named point where WordPress calls the functions registered for it: how you change WordPress without editing core.
  • Actions (add_action, do_action) run code at a moment; filters (add_filter, apply_filters) receive a value and must return it.
  • Priority (default 10, lower first, ties in the order added) orders callbacks; accepted args (default 1) must match what the callback asks for: 10, 2.
  • Removing needs the same hook, callback and priority, after the hook was added; remove_action() returns false silently when nothing matches. Closures cannot be removed by anyone else.
  • Your own hooks make code extensible: prefix them, a filter for values and an action for moments, pass context, document them with a DocBlock.
  • Finding hooks: the Code Reference, the function you want to change, grep -rn in wordpress/, and has_filter() / $wp_filter on the running site.
  • "Too early" is the most common hook bug: code at the top of a plugin file runs while plugins load; move it into a callback on init or later.
Worked example: the two hooks of mailpit-smtp.php

Since Lesson 1.2 a must-use plugin has been sending your site's email to Mailpit. It is two hooks. Find them:

grep -n "add_filter\|add_action" wp-content/mu-plugins/mailpit-smtp.php
11:add_filter( 'wp_mail_from', function ( $from ) {
15:add_action( 'phpmailer_init', function ( $phpmailer ) {

A filter on wp_mail_from (the sender address: a value, so the closure returns it) and an action on phpmailer_init (a moment: WordPress hands over its mailer object and the closure configures it for Mailpit). Ask the running site whether the filter is attached, and run the value through it the way wp_mail() does:

wp eval 'var_dump( has_filter( "wp_mail_from" ), apply_filters( "wp_mail_from", "wordpress@localhost" ) );'
bool(true)
string(21) "wordpress@example.com"

has_filter() without a callback answers "is anything attached?" (with a callback it returns the priority). And apply_filters() is all it takes to ask a filter for its answer: wordpress@localhost, which the mailer would reject, comes back as wordpress@example.com. Both callbacks are closures, so nobody else can remove them: fine for a must-use plugin on your own site.

Glossary

TermMeaning
drop-inA reserved file name in wp-content/ (object-cache.php, db.php ...) that replaces part of core
$table_prefixThe first letters of every table name (wp_), set in wp-config.php; in code $wpdb->prefix
pluggable functionA core function (wp_mail(), wp_get_current_user()) loaded after plugins, so a plugin may define it first
$wpdbWordPress's database object: get_var(), get_col(), get_row(), get_results(), prepare(), table names
key-value (EAV) patternExtra fields stored as rows of (object, key, value) in the four meta tables
serialized valueAn array saved as PHP's serialize() text, lengths included (a:1:{s:6:"editor";b:1;})
autoloadWhether an option is loaded with every request (on, auto, auto-on) or on demand (off, auto-off)
orphanA meta or term row whose post no longer exists
action / filterA hook for a moment (your callback does something) / for a value (your callback returns it)
callbackThe function a hook calls: a name, a closure, an object or static method
priorityThe third argument of add_action/add_filter: lower runs first, default 10
accepted argsThe fourth argument: how many of the hook's values the callback receives, default 1
must-use pluginA PHP file in wp-content/mu-plugins/: loaded on every request, before plugins, no activation
