Session 3: Core Architecture, the Database and Hooks

How to teach the session where WordPress opens up: the files and the load order, the twelve tables and their key-value pattern read with SQL from the course site, then the hooks system that every theme and plugin is built on, ending with the first file of the course that stays, the Pages & Co. store notice as a must-use plugin with hooks of its own.

How to Use This Guide

  • Same rhythm for both lessons: frame (the goal and one mental model) → live demo (you type, they type along) → guided lab (a kit lab, new practice on the lesson's ideas) → start the lesson's own project. The lesson exercises, quiz and journal are homework.
  • Type, do not paste (the long grep of wp-settings.php is the exception). Every command below was run to produce the output printed under it, on WordPress 7.1.3, PHP 8.5 and MySQL 9.7, on the site exactly as Lesson 2.1 leaves it: the users maria and devon, the pages About Us, Contact and Events, three News posts. Ask for a prediction before every run.
  • The lessons are the reference. Keep lesson_05.html and lesson_06.html open in browser tabs (the table diagram, the action table, the full stack trace of Mistake 2). Labs live in labs/module-03/: _starter files are handouts, _solution files and the title_parts_solution/ folder are yours.
  • Session 3 is the hinge of Part 1. Lesson 2.2 is read-only: the site ends exactly as it started. Lesson 2.3's project, mu-plugins/pagesco-site.php with the store notice, is the first file of the course that STAYS: Session 4 and every lesson after it assume it. Protect its start in the room.
  • Lesson 2.2 is SQL-heavy. Learners came through MySQL Foundations, so the joins are review; the new ideas are the schema (no foreign keys, the key-value pattern, serialized arrays, autoload) and the rule that follows from them: change WordPress data through WordPress.
The #1 risk of Session 3: the database hour eats the hooks hour

Lesson 2.2 is the longest lesson so far (140 minutes for a learner alone) and full of queries learners enjoy running; every one invites "what if I also ...". Lesson 2.3 is shorter but it is the lesson the rest of the course stands on, and its project must exist on every machine before Session 4. Hold the line at the break (1:15): the 2.2 demo is 20 minutes and has a cut list (below), the inventory starts with two SQL steps and its PHP half goes home. After the break, the 2.3 project start gets 30 minutes, the longest segment of the day: learners who leave with pagesco-site.php printing the notice are ready for Session 4; Steps 3 and 4 can be finished at home in 20 minutes.

Retrieval questions and answers
  1. Which escaping function goes around a URL in an href attribute? Answer: esc_url() (text between tags: esc_html(), other attribute values: esc_attr()).
  2. Name the four shapes a WordPress callback can take. Which one is hard for anyone else to unhook? Answer: A function name, a closure, array( $object, 'method' ), a static method ('Class::method' or array( 'Class', 'method' )). The closure: nobody else has a handle on it (Lesson 2.3 comes back to this).
  3. A page and a post: which table holds each, and which column tells them apart? Answer: Both are rows in wp_posts; post_type is page or post (Lesson 2.1's filing cabinet).
  4. Code must decide whether the current user may publish pages. What does it check, and why not the role? Answer: current_user_can( 'publish_pages' ): a capability. Roles are bundles that sites change; capabilities are what WordPress checks.
  5. What does wp_parse_args( $args, $defaults ) return? Answer: One array: the defaults, overridden by whatever the caller passed in $args.

Mental model to say

Draw on the load-order column from the board: "Think of a bookseller opening Pages & Co. in the morning. First the lights and the till: the database connection and the cache. Then the things that are always there, whatever happens: must-use plugins. Then the departments open today: active plugins. Then the window display: the theme. Only when the staff member on duty has signed in, the current user, does the shop open its doors, init, and serve the first customer, the main query. Code that tries to serve a customer while the lights are still off is the 'too early' bug of the next lesson."

Then the database in three sentences: "Twelve tables, the same on every WordPress site, linked by ID columns but with no foreign keys: integrity lives in PHP, so you change data through WordPress. Extra fields are rows, not columns: post_id, meta_key, meta_value, the key-value pattern, and every value is text. Arrays are stored serialized, with their lengths inside, so you never edit them as text." Write the rule under the drawing: read with SQL if you like; write through the API.

Three mistakes to expect, and how to coach each
  • Typing wp_posts in PHP. It works on the course site and breaks on the first client site with the prefix pc_. Coach: "Where does the prefix come from?" {$wpdb->posts} in code, wp_posts only at the prompt. (The lesson's Mistake 3; wpdb_report_starter.php.)
  • Fixing data with UPDATE or DELETE because it is quicker. Coach with the two broken demos: "Which PHP would have run if you had used wp post delete?" (wp_delete_post()'s four cleanup lines.) The prompt is for reading. (Self-check Q5.)
  • Comparing meta as numbers in SQL. ORDER BY meta_value and meta_value > 10 on text. Coach: "What type is meta_value?" (LONGTEXT.) CAST in SQL, meta_value_num in WP_Query. Forgetting true in get_post_meta() is the PHP version of the same surprise (self-check Q4, debug_meta_report.php).

Mental model to say

"WordPress is a radio host working through a running order. An action is the host saying 'we are now at the weather, any callers?': callers may talk, and the show goes on the same way afterwards. A filter is the host saying 'here is today's headline, any corrections?': each caller gets the headline, may rewrite it, and hands it to the next caller, and the host reads out whatever comes back from the last one. If a caller keeps the headline and hands back nothing, the host reads out nothing." (That is Mistake 1, the filter that forgets to return: promise it.)

Then the box on the board: action = a moment, your function does something · filter = a value, your function returns it. Then where hooks live until Module 5: "a must-use plugin, any PHP file in wp-content/mu-plugins/, loaded on every request without activation, before all plugins. You wrote a throwaway one in Lesson 1.2; today you write one that stays." And the prefix rule in one breath: everything you name, pagesco_.

Three mistakes to expect, and how to coach each
  • Echoing in a filter or returning nothing. Coach with the radio host: "What does the host read out if you hand back nothing?" Every path of a filter ends in return. (Self-check Q11, debug_price_tag.php.)
  • Calling instead of naming: add_action( 'wp_footer', pagesco_hello_footer() ). The function runs immediately, while plugins load, and WordPress gets its return value (null) as the callback. Coach: "Are you calling it now, or telling WordPress what to call later?" Strings, no parentheses.
  • "My removal does nothing." Wrong priority, too early, or a closure. Coach: var_dump( remove_action( ... ) ) first, then the three rules on the board. (Self-check Q9, the lab's TODO 3.)

Exit ticket (3 questions, no notes, 4 minutes)

  1. Why should code change WordPress data through WordPress (functions or WP-CLI) and not with UPDATE or DELETE? Answer: there are no foreign keys, so WordPress's PHP does the cascading (meta, terms, revisions, comments); serialized values carry their lengths; and the API keeps caches and hooks in step.
