Security in WordPress

70 min

Mental model to say

"Your plugin's write handlers are the shop's back door, where deliveries come in. A nonce is checking the delivery has the token you handed the courier this morning, so it is not a stranger with a forged clipboard. The capability check is making sure the person signing for it works here. Sanitizing is unwrapping and inspecting the goods before they go on the shelf. Escaping is how you display a customer's name in the window: you print it as text, never as a sign someone else wrote for you. Skip any one step and the shop is exposed in a different way."

Then the flow on the board, one box per habit, left to right: request → genuine? (nonce) → allowed? (capability) → sanitize → store → escape → page, and under the store box: SQL by hand → $wpdb->prepare(). Every demo step below lands in one box: say which before you run it.

And one sentence on where WordPress helps: "The block editor and the REST API check nonces and capabilities for you. The moment you write your own form handler, admin action or AJAX endpoint, those checks are your job."

  4. A prepared query (4m). "When you write SQL by hand, every value goes through a placeholder." Show the anti-example (concatenation) first, then run the safe report and read the SQL prepare() built:

  5. Mistake: the wrong context (2m). "Escaping is not one function." 
    wp eval '$url = home_url( "/books/?genre=sci-fi&sort=price" );
echo "esc_url:  ", esc_url( $url ), "\n";
echo "esc_html: ", esc_html( $url ), "\n";'
    esc_url:  http://localhost:8080/books/?genre=sci-fi&#038;sort=price

    esc_url() keeps a usable link (the & becomes &#038; for an attribute); esc_html() turns it into display text.
  6. Mistake: a nonce but no capability (2m). "A nonce proves the request is genuine, not that the user is allowed." 
    wp eval 'wp_set_current_user( 2 );

  7. Mistake: trusting an insert (2m). "Database functions assume you already checked." 
    wp eval 'wp_set_current_user( 3 );

    An author created a published book (ID 41); the last line deleted it. Broken access control without any error message.
Three mistakes to expect, and how to coach each
  • Escaping at input instead of output. esc_html() in the save, raw echo in the column. Coach: "Where does the value land? Escape there, at the last moment, even if you sanitized it." (Self-check Q1, Q2.)
  • One check standing in for another. A nonce instead of a capability, a capability instead of a nonce, is_admin() as a permission check (it only says the request is for an admin screen). Coach with the flow: "Which box does this function fill?" (Self-check Q3, Q5.)
  • Sanitizing a value that needs validating. A date run through sanitize_text_field(). Coach: "Clean it, or judge it?" (Self-check Q6.)

Checks for understanding

Ask these out loud during the demo and the lab:

  • When do you escape? Answer: at the point of output, for the context it lands in.
  • What does a nonce prove, and what does it not? Answer: that the request came from a page this site served to this user; not that the user is allowed.
  • Does wp_insert_post() check capabilities? Answer: no; check current_user_can() yourself first.
  • Why does the save skip autosaves? Answer: an autosave carries no form fields and would wipe the stored values.

Workbook self-check, items Q1 to Q6 (learners do them at the end of the block or at home).

Three mistakes to expect, and how to coach each
  • The group and the slug swapped. "not in the allowed options list". Coach: "settings_fields() takes the FIRST argument of register_setting()." (Lesson quiz Q1.)
  • A sanitize callback that returns only what changed, or $input unchanged. Coach: "It returns the complete value to store; what happens to a key you leave out?" (Self-check Q10; the newsletter lab's TODO 2.)
  • The wrong capability. edit_posts so editors can "help". Coach: "What can this page change? Site-wide behavior: manage_options." (Self-check Q11.)

Checks for understanding

Ask these out loud during the demo and the lab:

  • Why does wp option get pagesco_books_settings answer although the table has no row? Answer: register_setting()'s default is handed out while the row is missing.
  • Where does the form post, and what does that file check? Answer: wp-admin/options.php: the nonce, manage_options, the allowed options list; then it saves through your sanitize callback.
  • What arrives for an unticked checkbox? Answer: nothing; missing means off.
  • What should uninstall.php do with the settings option, and with the books? Answer: delete the option (the plugin's own); keep the books (the shop's content).

Closing

Exit ticket (3 questions, no notes, 4 minutes)

Put the three questions on the slide. Learners answer in the workbook's Exit Ticket box or on a sticky note. Before Session 11, sort question 1's notes: anyone who cannot name the four checks gets the support card in the warm-up.

  1. Name the four checks a handler that changes data makes, in order. Answer: genuine (nonce: check_admin_referer() / wp_verify_nonce()), allowed (current_user_can() for this object), sanitize and validate every value, and escape whatever it prints; SQL by hand through $wpdb->prepare().
  2. What does options.php do between Save Changes and the database? Answer: checks the nonce of the group, manage_options and the allowed options list, then update_option() runs your sanitize callback, then it redirects back with settings-updated=true.
  3. Your sanitize callback refuses a value. What should it store, and how does the user find out? Answer: the old (saved) value, and add_settings_error() queues a message the page prints above the form.
