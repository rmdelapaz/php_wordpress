5.3

Security in WordPress

By the end you can
  • Sanitize input on the way in and escape output on the way out, choosing the right function for each context
  • Protect every state change with a nonce and a current_user_can() capability check
  • Write safe database queries with $wpdb->prepare() and explain how SQL injection works
  • Name the common WordPress vulnerabilities (XSS, CSRF, SQL injection, broken access control) and the defense against each
  • Harden a real save handler and an admin action in the pagesco-books plugin
Key ideas
  • One data flow: request → genuine? (nonce) → allowed? (capability) → sanitize → store → escape → page.
  • Escape late, for the context: esc_html() text, esc_attr() attributes, esc_url() links, wp_kses_post() HTML that may keep safe tags; even for data you sanitized.
  • Sanitize and validate on the way in: sanitize_text_field(), absint(), a cast; a value with a shape (a date) is validated and rejected if wrong.
  • Nonces (wp_nonce_field(), wp_nonce_url(), check_admin_referer()) stop forged requests (CSRF); capabilities (current_user_can( 'edit_post', $id )) stop the wrong user. You need both.
  • $wpdb->prepare() with %s, %d, %f, %i: no variable ever goes directly into SQL.
  • Database functions trust their caller: wp_insert_post() and update_post_meta() check nothing; guard every write yourself. save_post handlers skip autosaves and revisions.
Worked example: one value, three destinations

One value with tags, an ampersand and quotes, escaped for three destinations:

wp eval '$v = "Dune: <b>signed</b> & \"rare\"";
echo esc_html( $v ), "\n", esc_attr( $v ), "\n", wp_kses_post( $v ), "\n";'
Dune: &lt;b&gt;signed&lt;/b&gt; &amp; &quot;rare&quot;
Dune: &lt;b&gt;signed&lt;/b&gt; &amp; &quot;rare&quot;
Dune: <b>signed</b> &amp; "rare"

esc_html() and esc_attr() both turn the value into text (the quotes too, so it cannot end an attribute); wp_kses_post() keeps the tags a post may contain and escapes the rest. The function is chosen by the destination: text, attribute, or HTML that may keep safe tags. An unknown value printed into a page is never echoed raw.

5.4

Admin Pages, Settings API & Options

By the end you can
  • Store a plugin's settings as one array option with defaults, and read it safely with get_option() and wp_parse_args()
  • Add an admin page with add_options_page() (or a top-level menu) protected by the right capability
  • Build a settings form with the Settings API: register_setting(), sections, fields, settings_fields() and do_settings_sections()
  • Validate submitted values in a sanitize callback and report problems with add_settings_error()
  • Trace what happens between Save Changes and the database: options.php, the nonce, the allowed options list
  • Decide what uninstall.php removes, and remove the plugin's own settings
Key ideas
  • One array option per plugin (pagesco_books_settings), read through one class that knows the name, the defaults (wp_parse_args()) and the cleaning.
  • register_setting( $group, $option, $args ) on init: type, sanitize_callback, default (handed out while the row is missing).
  • Admin pages hang off admin_menu: add_options_page() under Settings; the capability (manage_options) guards the menu item and the URL.
  • The Settings API describes the form as data (add_settings_section(), add_settings_field() with label_for) and prints it (settings_fields( $group ), do_settings_sections( $page ), submit_button()).
  • options.php checks the nonce, the capability and the allowed options list, then saves through your callback. The callback returns the COMPLETE value, treats a missing checkbox as off, and refuses bad values with add_settings_error() (keeping the old one).
  • uninstall.php deletes the plugin's own data (the option, the role) and keeps the shop's content (the books).
Worked example: defaults without a row

The setting is registered with a default, and nothing has been saved since the lesson's uninstall test. Is get_option() handing out the defaults?

wp eval 'var_dump( get_option( "pagesco_books_settings" ) === PagesCo\Books\Settings::defaults() );'
bool(true)

And is there a row?

wp db query "SELECT COUNT(*) AS rows_named FROM wp_options WHERE option_name = 'pagesco_books_settings'"
rows_named
0

Exactly the defaults, and no row: register_setting()'s default applies while the row is missing. That is why the notice looks the same after a reactivation, and why Settings::get() still fills keys from defaults() for sites that saved an older array.

Glossary

TermMeaning
XSS (cross-site scripting)Someone else's HTML or script printed into your page; stopped by escaping on output
CSRF (cross-site request forgery)A forged request riding a logged-in user's session; stopped by a nonce
SQL injectionA crafted value that rewrites your query; stopped by $wpdb->prepare()
broken access controlA user doing what their role should forbid; stopped by current_user_can()
nonceA token tied to a user, an action and a few hours; proves a request is genuine
capabilityA permission such as edit_post or manage_options, granted through roles
sanitize / validateClean a value / accept or reject it by its shape
escapeMake a value safe for where it is printed: text, attribute, URL, allowed HTML
optionA named row in wp_options; pagesco_books_settings holds the shop's settings as one array
Settings APIregister_setting(), sections and fields, settings_fields(); saved by options.php
sanitize callbackYour function that cleans a setting before it is stored and returns the complete value
admin-post.phpCore's endpoint for your own form handlers and admin actions (admin_post_<action>)
