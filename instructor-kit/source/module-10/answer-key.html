Start Here · Warm-up

The five retrieval questions on Session 9, with the answers to give.

W1

A class in src/ implementing Feature (hooks in register()), one line in Plugin::feature_classes(), and uninstall.php if it stores data.
W2
Why does Activator::activate() register the book type itself before it flushes?
On the activation request the plugin's own init callback has not run, so the rules would be rebuilt without the type.
W3
get_post_meta( 33, 'pagesco_in_stock', true ) on The Great Gatsby returns what?
'': meta is stored as strings, false as an empty string. REST casts it to false.
W4
Where did Lesson 5.2's meta box already use a nonce?

W5

5.3 · Security in WordPress: self-check

Q1
A book title goes into a link's tooltip: <a href="/books/dune/" title="...">. Which function escapes it there?
A) esc_html()
B) esc_url()
C) esc_attr()
D) sanitize_text_field()
Why: The destination decides: inside an attribute value it is esc_attr(), which also escapes the double quote that would end the attribute (Lesson 5.3, "Escape Late"). The meta box uses it on every value="…".
A is wrong: esc_html() is for text between tags; it happens to escape quotes too, but say what you mean: the attribute function.
B is wrong: esc_url() is for href and src, and would mangle a title into a URL.
D is wrong: Sanitizing cleans input on the way IN; output is escaped on the way out.
Q2
What does this print?
wp eval 'echo esc_html( "Pride & Prejudice <2nd ed.>" ), "\n";'
Pride &amp; Prejudice &lt;2nd ed.&gt;
Why: esc_html() turns &, < and > into entities: the browser shows the text, never runs it. In a terminal you see the entities themselves, which is how you check escaping from WP-CLI (the lesson's XSS demo did the same with the Books column).
Q3
A form handler calls check_admin_referer() and it passes. What does that prove?
A) The user is allowed to make the change
B) The request came from a page this site served to this user, for this action, recently
C) The submitted values are safe to store
D) The request was not sent by a script
Why: A nonce is tied to a user, an action and a few hours: it stops a forged request from another site (CSRF). Whether the user may do it is a separate question, current_user_can(); whether the values are clean is a third, sanitizing (Lesson 5.3, Common Mistakes 2).
A is wrong: Any logged-in user who can open the form gets a valid nonce.
C is wrong: A nonce says nothing about the values; sanitize and validate them.
D is wrong: A script with the user's cookies and a fresh nonce passes too; the nonce defeats forgery from ANOTHER site.
Q4
What does this print?
wp eval 'global $wpdb; echo $wpdb->prepare( "SELECT ID FROM {$wpdb->posts} WHERE post_title = %s", "Ender\x27s Game" ), "\n";'
SELECT ID FROM wp_posts WHERE post_title = 'Ender\'s Game'
Why: prepare() quoted the %s value and escaped the apostrophe inside it, so the title cannot end the string early: SQL injection is impossible through this placeholder. {$wpdb->posts} is WordPress's own value (the prefixed table name), never user input.
Q5
This handler is reached from a link on the Books screen. Which defense is missing?
$book_id = absint( $_GET['book'] );
check_admin_referer( 'pagesco_books_feature_' . $book_id );
update_post_meta( $book_id, 'pagesco_featured', 1 );
A) current_user_can( 'edit_post', $book_id ) before the update
B) A nonce check
C) esc_html() on the book ID
D) $wpdb->prepare() around the update
Why: The nonce is checked, the ID is forced to an integer, and update_post_meta() builds safe SQL itself; but nothing asks whether THIS user may edit THIS book. Database functions trust their caller (Lesson 5.3, Common Mistakes 3), so a subscriber with a valid link could feature any book.
B is wrong: check_admin_referer() is the nonce check.
C is wrong: Nothing is printed; esc_html() is for output.
D is wrong: update_post_meta() prepares its own query.
Q6
The meta box's "First published" field receives soon. What keeps it out of the database?
A) sanitize_text_field(): it removes words that are not dates
B) esc_attr() when the box prints the value
C) absint(), which turns it into 0
D) Validating it: DateTime::createFromFormat( 'Y-m-d', $v ) must give back exactly $v, else store ''
Why: Sanitizing cleans characters; it happily stores "soon". A value that must have a shape needs validating: accept or reject. The hardened save's valid_date() helper does exactly the round trip in option D (Lesson 5.3, Exercise 1).
A is wrong: sanitize_text_field() strips tags and extra whitespace, not words.
B is wrong: Escaping on output is still required, but it does not stop a bad value being stored.
C is wrong: A date is not an integer; absint() would store 0.

5.3 · Security in WordPress: predict, then run

P1
Predict the output, then run it.
wp eval 'echo esc_url( "javascript:alert(1)" ) === "" ? "(empty)" : "kept", "\n";'
(empty)
Why: esc_url() only lets through the protocols WordPress allows (http, https, mailto and a few more); a javascript: URL becomes an empty string, so an href built from it cannot run code.
P2
Predict the output, then run it.
wp eval 'echo sanitize_text_field( "  Pages <b>&</b> Co.\n\tBooks  " ), "|\n";'
Pages & Co. Books|
Why: sanitize_text_field() strips the tags (keeping their text), turns the line break and tab into nothing it keeps, and trims the outer spaces: one clean line. The ampersand stays a plain &: sanitizing is not escaping; escape when you print it.

5.4 · Admin Pages, Settings API & Options: self-check

Q7
An administrator presses Save Changes on Settings > Pages & Co. Books. Which code checks the nonce and the capability?
A) Core's own handler, wp-admin/options.php, before it calls your sanitize callback
B) Your SettingsPage::render() method
C) Your Settings::sanitize() method
D) Nothing: the Settings API has no nonce
Why: The form posts to options.php, which checks the nonce settings_fields() printed (action <group>-options), current_user_can( 'manage_options' ) and the allowed options list, then runs update_option() and with it your sanitize callback (Lesson 5.4, "What Save Changes Does").
B is wrong: render() only prints the form; its own capability check is defense in depth.
C is wrong: The sanitize callback cleans values; by the time it runs the checks have passed.
D is wrong: settings_fields() prints the nonce; options.php verifies it.
Q8
On the finished Lesson 5.4 site (the uninstall test deleted the row; nothing was saved since), what does this print?
wp option get pagesco_books_settings --format=json
{"notice_extra":"Open until 9 p.m. on Thursdays.","show_events_link":true,"books_per_page":6,"events_limit":5}
Why: register_setting()'s default is handed out while the row is missing, so WP-CLI prints the defaults although wp_options has no row named pagesco_books_settings (count it: 0). Nothing is written until someone saves.
Q9
The Events link checkbox is unticked when the form is saved. What does options.php receive for it?
A) show_events_link=0
B) show_events_link=false
C) Nothing: an unticked checkbox is not sent at all
D) show_events_link=off
Why: Browsers send only checked boxes. A sanitize callback that reads the key without a test warns (Undefined array key) on every save with the box off; ! empty( $input['show_events_link'] ) turns "missing" into false (Lesson 5.4, Common Mistakes 2).
A is wrong: That would need a hidden field with the same name before the box.
B is wrong: HTML forms send strings, never booleans.
D is wrong: "on" is what a checkbox WITHOUT a value attribute sends when it is ticked; unticked sends nothing.
Q10
On the finished Lesson 5.4 site, what does this print, and why is the notice sentence empty?
wp eval 'echo wp_json_encode( sanitize_option( "pagesco_books_settings",
    array( "books_per_page" => "0", "events_limit" => "7" ) ) ), "\n";'
{"notice_extra":"","show_events_link":false,"books_per_page":6,"events_limit":7}: 0 is out of range, so books_per_page keeps the saved value (6, the default); notice_extra and show_events_link were not in the array, so they come back empty and false
Why: sanitize() always returns the complete option: a missing key means empty (the form always sends every field, code does not). That is Common Mistakes 3: merge before you update, or wp option patch update. The rejected 0 also queued an add_settings_error() message.
Q11
Maria, an editor, opens options-general.php?page=pagesco-books and gets a 403. Which line decided that?
A) The current_user_can() check inside render()
B) The nonce in settings_fields()
C) register_setting()'s type 'object'
D) The manage_options capability passed to add_options_page()
Why: The capability argument guards both the menu item and the URL: WordPress refuses the page before your callback runs ("Sorry, you are not allowed to access this page."). The check inside render() is the second, defensive layer.
A is wrong: It would also refuse, but WordPress stops the request earlier.
B is wrong: No form is posted when a page is opened.
C is wrong: The type describes the value, for REST and sanitizing.
Q12
Which value deserves its own option instead of a key in the pagesco_books_settings array?
A) The notice sentence
B) A counter of page views, updated on every request
C) Books per list
D) Whether the notice shows the events link
Why: One array option per plugin is the usual choice: one row, one autoloaded read, one delete_option(). Split out a value that changes on every request (rewriting the whole array to bump a number is wasteful) or one that is large and rarely needed (autoload off) (Lesson 5.4, the box "One array option, or several?").
A is wrong: A setting the shop edits now and then: exactly what the array is for.
C is wrong: The same; Module 6 reads it through Settings::get().
D is wrong: The same; a boolean in the array.

5.4 · Admin Pages, Settings API & Options: predict, then run

P3
Predict the output, then run it.
wp eval 'var_dump( get_option( "pagesco_no_such_option", array() ) );'
array(0) {
}
Why: The option does not exist, so get_option() returns its second argument, here an empty array (without it: false). Settings::get() relies on exactly this, then fills the keys with wp_parse_args().
P4
Predict the output, then run it.
wp eval 'echo wp_json_encode( sanitize_option( "pagesco_books_settings", "not an array" ) ), "\n";'
{"notice_extra":"","show_events_link":false,"books_per_page":6,"events_limit":5}
Why: The callback treats hostile input as hostile: not an array becomes an empty array, every key falls back to its cleaned value (an empty sentence, the box off) and the two numbers keep the saved values (the defaults). It returns a complete option either way.

Without remove_placeholder_escape() the printed SQL shows a long random string where each literal % is: prepare() protects them until the query runs.

The Lesson Pages' Own Quick Quizzes

Lesson 5.3 · Security in WordPress
  1. B At the point of output, for its context: Escape late: at the point of output, with the function for that context (esc_html, esc_attr, esc_url), because you cannot be sure where a stored value has been.
  2. A Any logged-in user, regardless of role, can perform the action: A valid nonce only proves the request came from this user's genuine page; any logged-in user, whatever their role, gets one. The capability check decides whether they are allowed to act.
  3. C $wpdb->prepare( $sql, $value ): The prepare() method inserts each value through a typed placeholder (%s, %d, %f, %i), quoting and escaping it so it cannot break out of the query.
  4. B An autosave carries no form fields and would wipe the saved values: save_post fires on autosaves and revisions, which carry no meta-box fields; without the guard an autosave would overwrite the saved values with empty ones.
  5. C No; you must check the capability yourself before calling it: No. wp_insert_post() and update_post_meta() trust the caller; you must call current_user_can() yourself before writing. The REST API and block editor add that check, but your own handlers must too.
Lesson 5.4 · Admin Pages, Settings API & Options
  1. A settings_fields( 'pagesco_books' ) and do_settings_sections( 'pagesco-books' ): settings_fields takes the option group from register_setting, which names the nonce and the allowed options list; do_settings_sections takes the page slug the sections and fields were added to.
  2. C 7, and the page shows the error: 0 fails the range check, so the callback queues the error and puts the saved value, 7, back. The other fields are still stored; the page shows the error instead of Settings saved.
  3. B A 403: Sorry, you are not allowed to access this page: add_options_page was given manage_options, which editors lack, so WordPress hides the menu item and answers the URL with a 403 Sorry, you are not allowed to access this page.
  4. C So keys added in a later version still have a value on sites that saved an older array: A site that saved the settings before a new key existed has an array without that key. Merging with the defaults gives every key a value, so code can rely on it.
  5. A Delete it, because it only makes sense with the plugin: The option belongs to the plugin and is useless without it, so uninstall deletes it. Deactivation keeps it, so a reactivated plugin finds its settings again.

Exit Ticket

  1. Four checks: genuine (the nonce: check_admin_referer() or wp_verify_nonce()), allowed (current_user_can() for this object), clean (sanitize, and validate what must have a shape), and safe output (escape for the context); with SQL by hand, every value through $wpdb->prepare().
  2. options.php: check_admin_referer( '<group>-options' ), current_user_can( 'manage_options' ) (filterable), the allowed options list built from register_setting(), then update_option() for each option of the group, which runs sanitize_option() and so your callback; then a redirect back with settings-updated=true, and the page prints "Settings saved." or the queued errors.
  3. A refused value: store the old (saved) value, never nonsense, and call add_settings_error( $option, $code, $message ); settings_errors() prints it above the form on the next page load.

Common Wrong Answers and What They Reveal

  • Q1 A (esc_html). Works by accident here; ask what function the meta box uses in value="…" and why.
  • Q3 A ("the user is allowed"). The most important confusion of the lesson. Run the lesson's Common Mistakes 2 again.
  • Q5 B ("a nonce check"). Did not recognize check_admin_referer() as the nonce check; put the two functions side by side on the board.
  • Q6 A. Expects sanitizing to judge values. Exercise 1's validator makes the difference visible.
  • Q7 B or C. Thinks the plugin's code saves the form. Show the form's action attribute: options.php.
  • Q9 A. Expects HTML to send a zero. Show the request with the box unticked (the test's own post has no such field).
  • Q11 A. True as a second layer; the 403 comes before render() runs (the page never prints).
