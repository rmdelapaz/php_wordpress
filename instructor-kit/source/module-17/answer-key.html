9.1 · Self-check

Q1
Why does the reference solution keep holds in a custom table rather than a post type?
A) A post type cannot store a date
B) A hold is one customer, one book, a status and a date: typed columns with indexes answer "this customer's holds" and "what is waiting" directly, and old rows can be deleted cleanly
C) Custom tables are always faster than wp_posts
D) Post types cannot be private
Why: Lesson 9.1, "The data: why a custom table": a hold has no title, content, URL or revisions; as posts every question would be a meta query, and holds would leak into places built for content (exports, search, the posts routes).
A is wrong: Post meta can store any date; the problem is querying it.
C is wrong: Not always: the point is the shape of the data and the two questions the shop asks.
D is wrong: They can (public => false); that is not the reason.
Q2
Where does the reference solution keep the status expired?
A) In the status column, set by the daily cron job
B) In a post meta field on the book
C) In a transient that expires after hold_days
D) Nowhere: Holds::status() computes it from pickup_by and today's date every time a hold is shown
Why: A stored "expired" needs a job to update it and is wrong between the moment it should change and the moment the job runs. The table stores waiting, collected or cancelled; expired is derived.
A is wrong: The daily job deletes old holds 30 days after pickup; it never marks them.
B is wrong: Holds are not book data, and a book can have many holds.
C is wrong: A transient could vanish at any time (Lesson 7.3): never the only home of data.
Q3
On the course site at the end of Lesson 8.4, what does this print? And after Milestone 4?
grep -c '::class,' wp-content/plugins/pagesco-books/src/Plugin.php
20 (twenty features); 25 after Milestone 4 (five new features, one line each)
Why: Lesson 5.1's rule: one class in src/, one line in Plugin::feature_classes(). Add each line together with its file: a line for a class that does not exist yet stops every request with "Class not found".
Q4
The plugin is already active on your development site. You add Holds\HoldsTable::install() to Activator::activate(). When is the holds table created on YOUR site?
A) On the next request that loads WordPress: maybe_upgrade() runs on init, finds no version option and installs it
B) Never, until you deactivate and reactivate the plugin
C) When you run wp db query
D) At 3 a.m., with the daily job
Why: An active plugin's activation hook does not run again, and neither does it on an update (Lesson 8.4). Milestone 2's check proves it: wp db query (which does not start WordPress) sees no table, one curl later the table and version 1 exist. The same happens on the live site in Milestone 9.
B is wrong: That would work too, but the design makes it unnecessary, and it is impossible on a live update.
C is wrong: wp db query talks to MySQL without loading WordPress: no PHP of yours runs.
D is wrong: The daily job deletes old holds; it does not create tables.
Q5
A reviewer finds these lines in Holds::cancel() (the reference has one call on one line). What can a logged-in customer now do?
$done = HoldsTable::finish(
	$hold_id,
	'cancelled'
);
if ( ! $user_id || ! $done ) {
A) Nothing new: the $user_id check still stops it
B) Cancel only their own holds, as before
C) Cancel ANY customer's waiting hold by sending its ID
D) Collect holds as staff
Why: finish() puts the user ID into the SQL WHERE only when it is passed. Without it, the WHERE is id and status: any logged-in customer cancels anyone's hold. This is the insecure direct object reference of the Security and Privacy Checklist; HoldsTest's test_only_the_customer catches it (Milestone 7).
A is wrong: $user_id only proves someone is logged in, not that the hold is theirs.
B is wrong: That needs the owner in the query, which this line no longer passes.
D is wrong: Collecting is another method and another capability.
Q6
Why does Holds::place() answer the limit, a duplicate and a sold-out book with status 409, not 400 or 403?
A) 409 is the only status WordPress allows in a WP_Error
B) The request is well formed and the customer is allowed to ask; the shop's current state says no (Conflict)
C) 403 would log the customer out
D) 409 makes the browser retry automatically
Why: 400 means a malformed request (a missing or wrong argument, which the REST route's args catch), 401/403 who is asking, 404 no such thing. Every door passes the status in the error's data on, so the REST route and the form handler answer the same.
A is wrong: Any status can go in the data array.
C is wrong: No status logs anyone out.
D is wrong: Browsers do not retry on 409.
Q7
Common Mistake 2, run as Devon (an author) about Maria's post 15. What does it print, and which check belongs in a handler?
wp eval 'var_dump( current_user_can( "delete_posts" ), current_user_can( "delete_post", 15 ) );' --user=devon
bool(true) then bool(false): the meta capability with the ID, delete_post, 15
Why: delete_posts asks "may this user delete posts at all?" (his own, yes). A handler must ask about THIS post. Holds are not posts and have no meta capability, so there ownership goes into the SQL WHERE with the user ID from the login.
Q8
Why does the confirmation email live in HoldMail, listening to pagesco_books_hold_placed, instead of a wp_mail() call inside Holds::place()?
A) wp_mail() cannot be called from a class
B) Actions run faster than function calls
C) Emails must be sent from a must-use plugin
D) The rules class knows nothing about email: others (an SMS, a staff notice in Exercise 2) attach to the same moment without changing the rules
Why: An action is an extension point for a moment others may want to act at (Lesson 2.3). The rules class stays one job; Exercise 2 adds the shop's email at priority 20 from outside the plugin.
A is wrong: Any PHP code can call wp_mail().
B is wrong: do_action() adds a little work, not speed.
C is wrong: Any plugin can send email.
Q9
Which line computes the last day of pickup, three days from today, the way the reference does?
A) wp_date( 'Y-m-d', time() + $days * DAY_IN_SECONDS )
B) date( 'Y-m-d', time() + $days * DAY_IN_SECONDS )
C) current_time( 'mysql', true )
D) gmdate( 'Y-m-d' ) . ' + 3'
Why: pickup_by is a date in the shop's time zone (the counter's calendar): wp_date() formats a timestamp in the site's time zone. date() and gmdate() use PHP's own zone (UTC in WordPress), which moves the day near midnight.
B is wrong: date() ignores the site's time zone setting.
C is wrong: That is now, in UTC, as a datetime: what created_at stores.
D is wrong: String concatenation, not date arithmetic.
Q10
HoldsTable::waiting() uses this trick. What does it print, and what does it mean for the query?
wp eval 'global $wpdb; echo $wpdb->prepare( "WHERE ( %d = 0 OR user_id = %d )", 0, 0 ), "\n";'
WHERE ( 0 = 0 OR user_id = 0 ): always true, so the user filter is switched off (all customers); with 4 it becomes ( 4 = 0 OR user_id = 4 )
Why: One prepared statement serves every combination of filters: a 0 turns its filter off, any other value keeps it, and every value still goes through prepare().
Q11
Milestone 4 sends a forged "Mark collected" from Maria's own logged-in session, but without the form's nonce. What does admin-post.php answer?
A) 303, back to Books > Holds with ?pagesco_hold=collected
B) 401: Maria is not logged in
C) 403 with The link you followed has expired.
D) 400: the action is unknown
Why: check_admin_referer() fails without a valid nonce for pagesco_books_collect_hold_5, and WordPress dies with Lesson 5.3's message and 403. The nonce is what tells a real button press from a request another page sent with Maria's cookies.
A is wrong: That is what the real button gets.
B is wrong: Her cookies are valid: that is what makes the forgery dangerous.
D is wrong: The handler exists; 400 is what admin-post.php answers when no handler does.
Q12
The lesson's mental model is the shop's counter. Name its three layers and the one job of each.
the data (a table class that only stores), the rules (one class, Holds, that only decides), the doors (REST routes, forms, blocks that only check who is asking and pass the question on)
Why: When a rule changes, it changes in one place and every door follows. The guide's requirement map shows which layer handles each line of the brief.

  3. Next milestone: any honest answer with the lesson's done-when; Milestone 4's is the forged request answered 403 and the commit, Milestone 5's the smoke test's eight ok lines.

Common Wrong Answers and What They Reveal

  • Q1 C ("tables are faster"). Speed is not the argument; the shape of the data and its two questions are. Ask what a hold's title would be.
  • Q2 A ("the cron job marks them"). Thinks of a status as something stored. Ask: what does the page show between midnight and the job's run?
  • Q4 B ("reactivate"). Has not yet met the update path; it matters on the live site, where nobody reactivates (Milestone 9).
  • Q5 A. Confuses "logged in" with "owns it". The guided lab separates the two.
  • Q6 C or D. Guessing at statuses: hand out the five used (200/201, 401, 403, 404, 409) as a card.
  • Q9 B ("date()"). Works on most days and moves the pickup day near midnight. Show wp_timezone_string() on their site.
  • Q11 A. Thinks the logged-in cookie is enough: exactly why forgeries work without a nonce.
