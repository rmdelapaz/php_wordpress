Session 17: Final Project Kickoff and Studio I

How to run the first studio of the final project: turn Maria's brief for Reserve & Pick Up into data, rules and doors, meet the three most expensive mistakes on purpose, measure before building, then let learners build Milestones 1 to 4 (the plan, the holds table and settings, the rules and the email, the first doors) with real done-when outputs for every milestone and a check-in for every learner.

1 lesson (first studio) 3 hrs session Lesson 9.1 · Milestones 1–4 Session 17 of 18 · Part 2

How to Use This Guide

  • Session 17 is the first of two studios for the final project, Lesson 9.1's Reserve & Pick Up, the course's capstone. There is no new lesson content to present: the room turns Maria's brief into a design, then learners build Milestones 1 to 4 with you circulating. Session 18 finishes Milestones 7 to 9, holds the showcase and teaches Lesson 9.2.
  • The lesson is 300 minutes for a learner working alone, 250 of them for the ten milestones. Where they happen: Milestones 1 to 3 and the start of 4 in this room; the rest of 4, then 5 (the two blocks) and 6 (live prices) at home; 7 (quality), 8 (release 1.2.0) and 9 (the code-only deploy) in the Session 18 studio; 10 (the write-up) at home. Submission: one week after Session 18. The rubric, the scoring guidance, the grading run and the reference numbers are in final-assessment.html at the kit's root.
  • Learners met the brief at the end of Session 16 (the brief, the milestones table, the security and privacy checklist and the rubric were the reading). Today they need their site exactly as Lesson 8.4 left it: the wp-content Git repository with release-1 and release-2, plugin and theme 1.1.1, and the pagesco-live rehearsal server. The warm-up checks it.
  • Every command and file below is the lesson's own, run on a site at the end of Lesson 8.4 (WordPress 7.1.3, PHP 8.5, MySQL 9.7, WP-CLI 2.12); the outputs are real and each one matches the lesson's own output card line for line. Each milestone has a "done when" with the output learners compare; the lesson hides a reference solution behind each one. The rule for the room, as the lesson says: try first, then open the reference and compare; different names are fine when the brief, the checklist and the checks are met.
  • The kit's labs for this session (labs/module-17/l9_1-final-project/) are short practice on the same habits for the guided lab and for stuck learners, never the project. Teal blocks are hands-on, amber blocks are watch-outs.
The #1 risk of Session 17: building on the wrong site

Reserve & Pick Up is built on the site Lesson 8.4 left: Git in wp-content, release-2, the rehearsal server. A learner who skipped Lesson 8.4's Git steps or whose pagesco-live is broken can build Milestones 1 to 7 on their development site, but cannot release or deploy in Session 18 without it. In the warm-up: git tag -n in wordpress/wp-content (release-1 and release-2) and docker compose ps in pagesco-live, for everyone. Fix now or plan: a missing repository is five minutes (Lesson 8.4's .gitignore, git init, commit, tag release-2) and is done before Milestone 1; a broken pagesco-live is rebuilt at home with Lesson 8.4's launch steps and checked at the start of Session 18. Nobody starts Milestone 2 on a site that is not at 1.1.1.

Frame: from Maria's brief to layers (20m)

Read the brief aloud, one requirement at a time, and underline on the board as the lesson says: nouns are data (customer, book, hold, three days, the counter's list), verbs are actions (reserve, cancel, collect, email), and each rule gets sorted by where WordPress lets you enforce it. Then the mental model, in the lesson's words:

Think of the counter at Pages & Co. The shelf behind it holds the books (the data). The house rules hang on the wall: three days, three books, no sold-out books (the rules). Customers can ask at the counter, phone, or use the website (the doors: a form, the REST API, a block). Whoever answers, they read the same house rules on the same wall. In code: one table class that only stores, one service class that only decides, and several thin doors that only check who is asking and pass the question on. When a rule changes, you change it in one place, and every door follows.

Three mistakes to expect, and how to coach each
  • Building the doors first. A learner starts with the REST route or the block because that is what shows. Coach with the counter: "Which rule does this door enforce? Then it is in the wrong layer." The order of the milestones is the order of the layers. (Self-check Q12.)
  • Ownership in PHP, after the query. $hold = HoldsTable::get( $id ); if ( $hold->user_id !== $user ) ... works, but tells a stranger that hold 12 exists (403 instead of 404) and is one forgotten if away from the IDOR. Coach: "Put the owner in the WHERE and let a miss be not found." (Self-check Q5, the guided lab.)
  • Copying the reference without reading it. The reference panels are complete; a learner can paste ten files in ten minutes and learn nothing. Coach: "Close the panel. Tell me what waiting() does with a 0." (Q10.) Pasting is allowed after trying; the showcase's "one decision you would defend" and the write-up are where it shows.

Checks for understanding

Ask these out loud during the studio:

  • Which layer enforces "at most three books"? Answer: the rules, in Holds::place(); every door calls it (the lesson's quiz Q2).
  • Why does cancel() answer "not found" for another customer's hold? Answer: so a stranger cannot even learn that the hold exists; the owner is in the WHERE.
  • Who creates the holds table on the live site in Milestone 9? Answer: HoldsTable::maybe_upgrade() on the first request that loads the new code.
  • Where do the user's ID and the hold's ID come from in the cancel handler? Answer: the user from the login (get_current_user_id()), the hold from the form, checked by the nonce for its action and that ID.

Workbook self-check, items Q1 to Q12 (learners do them at the end of the studio or at home).

Answers: Q1 B) A hold is one customer, one book, a status and a date: typed columns with indexes answer "this customer's holds" and "what is waiting" directly, and old rows can be deleted cleanly; Q2 D) Nowhere: Holds::status() computes it from pickup_by and today's date every time a hold is shown; Q3 20 (twenty features); 25 after Milestone 4 (five new features, one line each); Q4 A) On the next request that loads WordPress: maybe_upgrade() runs on init, finds no version option and installs it; Q5 C) Cancel ANY customer's waiting hold by sending its ID; Q6 B) The request is well formed and the customer is allowed to ask; the shop's current state says no (Conflict); Q7 bool(true) then bool(false): the meta capability with the ID, delete_post, 15; Q8 D) The rules class knows nothing about email: others (an SMS, a staff notice in Exercise 2) attach to the same moment without changing the rules; Q9 A) wp_date( 'Y-m-d', time() + $days * DAY_IN_SECONDS ); Q10 WHERE ( 0 = 0 OR user_id = 0 ): always true, so the user filter is switched off (all customers); with 4 it becomes ( 4 = 0 OR user_id = 4 ); Q11 C) 403 with The link you followed has expired.; Q12 the data (a table class that only stores), the rules (one class, Holds, that only decides), the doors (REST routes, forms, blocks that only check who is asking and pass the question on).
