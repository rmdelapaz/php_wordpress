Lessons

8.1

Debugging & Testing

By the end you can
  • Configure WP_DEBUG, the debug log and error display for development and production, and keep the log private
  • Trace a problem with error_log(), hooks such as http_api_debug and doing_it_wrong_run, and wp_debug_backtrace_summary()
  • Recover from a fatal error with recovery mode and WP-CLI's --skip-plugins, and use Query Monitor to look inside a request
  • Write PHPUnit integration tests with WP_UnitTestCase, factories and pre_http_request, and run them in a wp-env test environment
  • Set up PHPCS with the WordPress Coding Standards for a plugin, fix what it finds, and justify the exceptions with a ruleset or phpcs:ignore
Key ideas
  • Debugging is detective work: symptom, suspects, evidence. Make the program tell you what it does; never change code until the symptom goes away.
  • Debug settings: locally WP_DEBUG, WP_DEBUG_LOG and WP_DEBUG_DISPLAY on; on a live site display always off and the log outside the web root (wp-content/debug.log is downloadable).
  • Make code talk: error_log() with wp_json_encode(); hooks such as http_api_debug; wp_debug_backtrace_summary() on doing_it_wrong_run names the code behind a notice. Remove debugging code afterwards; never log secrets.
  • When the site goes down: the fatal error handler and recovery mode (an email for protected pages); wp --skip-plugins=<slug> repairs from the command line; a broken must-use plugin is renamed.
  • Query Monitor shows queries, hooks, HTTP calls and more for each page: install it to investigate, remove it (and its db.php) afterwards.
  • Integration tests run the plugin in a real, fresh WordPress: WP_UnitTestCase, factories, a rollback after each test; pre_http_request instead of the network; a wp-env test environment of their own; the project's vendor/bin/phpunit.
  • PHPCS with WPCS reads every line: a phpcs.xml.dist with the text domain, prefixes and scope; every finding is fixed, auto-fixed (composer lint:fix) or documented, narrowly and with a reason.
Worked example: what a test asks of a WP_Error

Every test of the supplier client asks the same three questions of what the client returned: is it an error, which one, and what is in its data? A WP_Error up close, on your site:

wp eval '$e = new WP_Error( "pagesco_supplier_http_error", "The supplier answered 503", array( "status" => 503 ) ); var_dump( is_wp_error( $e ), $e->get_error_code(), $e->get_error_data()["status"] );'
bool(true)
string(27) "pagesco_supplier_http_error"
int(503)

is_wp_error() is the first question, the code the second (tests compare it with assertSame(): an exact string, not "some error"), the data the third (here the status a 503 left behind). And the fake that answers in place of the network exists only inside the test: on the real site nothing is hooked to pre_http_request:

wp eval 'var_dump( has_filter( "pre_http_request" ) );'
bool(false)

has_filter() returns false when nothing is attached. A filter added inside a WP_UnitTestCase test is removed after that test; a filter added in a lab script ends with the script. Neither ever reaches your visitors.

8.2

Performance & Caching

By the end you can
  • Measure what a request costs with SAVEQUERIES and $wpdb->queries, read an EXPLAIN of a meta query, and recognize missing options and N+1 queries
  • Explain the object cache, its persistent version and transients, choose between them, and cache your own query with a key that is invalidated when the data changes
  • Describe how WordPress 7.1 loads block CSS, script modules and classic scripts, and use wp_preload_resources and fetchpriority where they help
  • Explain srcset, sizes, lazy loading and why block templates get no automatic image optimization
  • Measure LCP, CLS and interaction timing in a browser, and say honestly what a local lab measurement can and cannot tell you
Key ideas
  • Measure first, several times, one change at a time. Three places: the server (queries), the network (what the page downloads), the browser (Core Web Vitals).
  • SAVEQUERIES in wp-config.php keeps every query with its time and caller in $wpdb->queries; $wpdb->num_queries counts. For measuring sessions only.
  • Missing options cost a query per request; N+1 (one meta read per item after 'fields' => 'ids') costs a query per item: update_postmeta_cache( $ids ) loads them in one.
  • The object cache remembers within a request; a persistent one (object-cache.php: Redis, Memcached) between requests, and it moves transients out of wp_options. Transients outlive the request on any site.
  • Cache with an invalidation plan: a key with wp_cache_get_last_changed( $group ), renewed by wp_cache_set_last_changed( $group ) on every write.
  • What the browser downloads: block CSS only for blocks on the page, inlined up to 40,000 bytes; script modules deferred; speculation rules prefetch the next page.
  • Images: content images get srcset, sizes, lazy loading and fetchpriority; a block theme's template images get nothing: give them an aspect ratio, and preload the LCP image (wp_preload_resources, fetchpriority). Never lazy-load the LCP image.
  • Core Web Vitals (LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1) are judged on field data; lab numbers compare changes.
Worked example: what every request loads

Every autoloaded option is loaded on every request, used or not (Lesson 2.2). How many does your site have, and which are the biggest?

wp option list --autoload=on --format=count; echo
101

The largest three, by the size of their value:

wp db query "SELECT option_name, LENGTH(option_value) AS bytes FROM wp_options WHERE autoload IN ('yes', 'on', 'auto-on', 'auto') ORDER BY bytes DESC LIMIT 3"
option_name	bytes
_transient_wp_core_block_css_files	23778
rewrite_rules	11118
wp_user_roles	3451

WordPress's own caches lead (the list of core block stylesheets, the rewrite rules, the roles). Lesson 8.2's settings row is in this list too since Step 2, as a few bytes: one row loaded with all the others costs nothing extra, which is why it is cheaper than a missing option asked for on every request. Site Health warns when autoloaded options pass 800 KB in total.

Glossary

TermMeaning
WP_DEBUG_DISPLAY / WP_DEBUG_LOGPrint PHP's messages into the page / write them to a log file (true = wp-content/debug.log, or a path)
http_api_debugAn action that fires after every HTTP request WordPress makes: a place to log it
backtraceThe chain of calls that led to a line of code; wp_debug_backtrace_summary() writes it as one line
recovery modeAfter a fatal error in a plugin or theme, a login link (emailed to the admin) that pauses that plugin
--skip-pluginsWP-CLI loads WordPress without the named plugins (all of them without a name)
integration testA test that runs your code inside a real, freshly installed WordPress with a test database
WP_UnitTestCaseWordPress's test base class: a rollback after each test, factories, WordPress assertions
pre_http_requestA filter that can answer an HTTP request instead of the network: how tests fake an API
PHPCS / WPCS / phpcbfThe code sniffer / the WordPress Coding Standards for it / its automatic fixer
SAVEQUERIESA constant that makes $wpdb keep every query of the request with its time and caller
N+1One query for a list, then one more per item; fixed by loading all items' data in one query
object cache / persistent object cacheWordPress's in-memory cache for one request / the same kept between requests by a drop-in (Redis, Memcached)
last-changedA group's timestamp in every cache key, renewed on every write, so old entries are never read again
LCP · INP · CLSCore Web Vitals: when the largest element is drawn · how fast the page responds · how much it jumps
