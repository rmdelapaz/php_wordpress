Session 15: Debugging, Testing and Performance

How to teach Lessons 8.1 and 8.2: debugging with evidence instead of guesses (the debug log, a hook that logs, a backtrace, recovery mode, --skip-plugins), checks that machines run (PHPUnit in wp-env, shown as recorded; PHPCS to zero findings), and performance work that starts with a number: the query report, the object cache, N+1, and the Core Web Vitals of the front page.

How to Use This Guide

  • Same rhythm for both lessons: frame (the goal and one mental model) → live demo (you type, they type along) → guided lab (a kit lab, new practice on the lesson's ideas) → start the lesson's own project. The lesson exercises, quiz and journal are homework.
  • Type, do not paste. Every command below was run to produce the output printed under it, on WordPress 7.1.3, PHP 8.5, MySQL 9.7 and WP-CLI 2.12: Lesson 8.1's demos on the site as Lesson 7.3 leaves it, Lesson 8.2's on the site as Lesson 8.1 leaves it, which is what your projector site has at that point. Four kinds of output are recordings quoted from the lessons, and say so: the PHPUnit runs in wp-env, the SQLite Object Cache, the browser measurements (LCP, CLS, INP) and the PHPCS reports of the project.
  • The lessons are the reference. Keep lesson_26.html and lesson_27.html open in browser tabs. Labs live in labs/module-15/ (learners keep the folder in their project folder, next to compose.yaml): _starter files and next_event_starter/ are handouts, _solution files and next_event_solution/ are yours.
  • Each lesson was written for 150 minutes of work alone (Lesson 8.2: 150); the room has 130 minutes for both. The room does the mental models, the demos, two labs and the first three steps of each project; the tests in wp-env (8.1 Step 4), the browser measurements (8.2 Step 4) and the exercises go home. The Agenda says exactly what.
  • Part 2 (Sessions 9 to 18) builds on the site each lesson leaves; a learner who is a lesson behind does the guided labs from their own state and catches up on the projects at home. Teal blocks are hands-on, amber blocks are watch-outs. Lesson codes (8.1, 8.2) match the course site.
The #1 risk of Session 15: the tooling eats the session

Lesson 8.1's project installs 34 Composer packages (PHPUnit, PHPCS, the WordPress Coding Standards) from the internet, and its tests need Node.js 22.13 or newer for wp-env, which downloads images and WordPress on its first start. Lesson 8.2 installs a plugin from WordPress.org. On venue Wi-Fi, all of it at once is half an hour of progress bars. Before: ask learners to run composer update in the plugin folder at home (Step 1 of Lesson 8.1, with the alias), and to start wp-env once (npx @wordpress/env start, then stop). In the room: the 8.1 project starts with composer show --direct on every machine; whoever has no packages yet runs composer update during the demo, not during the project. wp-env runs at home only. Instead of installing in the room: Query Monitor and the SQLite Object Cache are shown from the lesson's recorded cards; nothing later depends on either.

Questions and answers
  1. W1 (Lesson 7.3). Name the three ways a call to the supplier can go wrong, and what wp_remote_get() returns for each. Answer: No answer at all (a WP_Error: DNS, refused, timeout); an answer that is not a success (an array with a 401 or 503 status); a success whose body is not the JSON you expect. Only the first is a WP_Error.
  2. W2 (Lesson 7.3). The Supplier column reads a transient. What happens when the transient has vanished? Answer: Availability::get() reads through: it calls the supplier, stores the answer again (12 hours, 5 minutes after an error) and returns it. A transient may vanish at any time, so code never relies on it being there.
  3. W3 (Lesson 7.3). Why does the lesson run the daily job with wp eval 'do_action( "pagesco_books_daily_sync" );' instead of wp cron event run? Answer: wp cron event run on a recurring event reschedules it to now plus the interval: the 03:00 job would move to whenever you ran it.
  4. W4 (Lesson 7.2). Your REST route returns a WP_Error without a status. What does the client get? Answer: A 500. The route's callback should give its WP_Error array( 'status' => 404 ) (or the right code); permission callbacks use rest_authorization_required_code().
  5. W5 (Lesson 7.3). Where do the supplier's address and key live on your site, and why there? Answer: In wp-config.php (PAGESCO_BOOKS_SUPPLIER_URL and _KEY, set with wp config set): configuration per environment, never in the plugin's code. Lesson 8.4 moves them to the server's environment.

Mental model to say

"Debugging is detective work. A symptom: the Supplier column says 'not reachable'. Suspects: the network, the address, the key, the code. Evidence rules them out, one by one. The worst habit is changing code until the symptom goes away. The best is making the program tell you what it is doing." Write symptom → suspects → evidence on the board.

Then the two professional habits in one sentence each: "When something goes wrong, find out why with evidence: the log, a hook that logs, a backtrace, recovery mode. Before anything goes wrong, let machines check the code: tests that run the plugin inside a real WordPress, and PHPCS, which reads every line for what tests rarely catch."

Then the testing picture: unit tests run one function without WordPress (fakes for WordPress), integration tests run your code in a freshly installed WordPress with a test database: WP_UnitTestCase, a rollback after each test, factories for data. "And one rule: tests never use the network. pre_http_request answers instead, so a test decides exactly what the supplier says, including its bad days."
