Session 15: Debugging, Testing and Performance

Answers and reasoning for every Session 15 item: the warm-up, both self-checks, the predict-then-run items, the lab reference outputs, the lessons' recorded cards, the lesson pages' own quizzes and the exit ticket.

Session 15 12 self-check items Confidential

Warm-up

  1. W1 (Lesson 7.3). No answer at all (a WP_Error: DNS, refused, timeout); an answer that is not a success (an array with a 401 or 503 status); a success whose body is not the JSON you expect. Only the first is a WP_Error.
  2. W2 (Lesson 7.3). Availability::get() reads through: it calls the supplier, stores the answer again (12 hours, 5 minutes after an error) and returns it. A transient may vanish at any time, so code never relies on it being there.
  3. W3 (Lesson 7.3). wp cron event run on a recurring event reschedules it to now plus the interval: the 03:00 job would move to whenever you ran it.
  4. W4 (Lesson 7.2). A 500. The route's callback should give its WP_Error array( 'status' => 404 ) (or the right code); permission callbacks use rest_authorization_required_code().
  5. W5 (Lesson 7.3). In wp-config.php (PAGESCO_BOOKS_SUPPLIER_URL and _KEY, set with wp config set): configuration per environment, never in the plugin's code. Lesson 8.4 moves them to the server's environment.

8.1 · Debugging & Testing: self-check

Q1
The live Pages & Co. shop should keep a record of PHP warnings for the developer, and show visitors none. Where should WP_DEBUG_LOG point?
A) true, so the messages go to wp-content/debug.log
B) A file outside the web root, such as /home/pagesco/logs/wordpress.log
C) false: a live site must never record anything
D) The theme's folder, where only the theme developer looks
Why: With display off and the log in a folder the web server does not serve, the messages are kept and nobody can download them. Lesson 8.1's Mistake 1: on the course site curl gets wp-content/debug.log with status 200.
A is wrong: That is the default, inside the web root: bots try that address on every site.
C is wrong: Then a live problem leaves no evidence at all; logging is fine, the location is the point.
D is wrong: Also inside the web root, and a theme update would delete it.
Q2
On the course site after Lesson 7.3, with WordPress loaded (wp eval-file): what does this print?
<?php
add_filter(
	'pre_http_request',
	fn() => array(
		'headers'  => array(),
		'body'     => '<h1>Service Unavailable</h1>',
		'response' => array( 'code' => 503, 'message' => 'Service Unavailable' ),
		'cookies'  => array(),
		'filename' => null,
	)
);
$result = ( new PagesCo\Books\Supplier\Client() )->availability( array( '9780441172719' ) );
echo $result->get_error_code(), ' ', $result->get_error_data()['status'], "\n";
pagesco_supplier_http_error 503
Why: pre_http_request answers in place of the network, so the client never calls the sandbox. A 503 is an answer, not a transport failure: Client::decode() turns any status outside 200 to 299 into pagesco_supplier_http_error with the status in the error's data. That exact code and that exact number are what SupplierClientTest asserts, and why a test that only asked "is it an error?" would miss the bug of Lesson 8.1's red run.
Q3
A plugin crashes on init and every WP-CLI command now dies with the same fatal error. Which command still deactivates it?
A) wp plugin deactivate pagesco-crash --force
B) wp eval 'deactivate_plugins( "pagesco-crash/pagesco-crash.php" );'
C) wp plugin delete pagesco-crash
D) wp --skip-plugins=pagesco-crash plugin deactivate pagesco-crash
Why: WP-CLI loads WordPress, and with it every active plugin, before it runs any command. --skip-plugins loads WordPress without the named plugin, so the deactivation can run. Recovery mode is the browser's way out; for a must-use plugin only renaming the file helps.
A is wrong: There is no --force that skips loading the plugin: the fatal error happens first.
B is wrong: wp eval loads WordPress too, so it dies before your code runs.
C is wrong: Also loads WordPress first; and deleting is not the first move when deactivating will do.
Q4
Why does the lesson name its temporary backtrace logger 0-pagesco-debug-backtrace.php?
A) Must-use plugins load in alphabetical order: it must be there before the plugin that asks too early
B) WordPress ignores must-use plugins whose names start with a letter
C) The 0- tells WordPress to load it only when WP_DEBUG is on
D) So that PHPCS skips the file
Why: A hook added after the notice fired would miss it. wp_get_mu_plugins() sorts the files by name, so 0- loads before pagesco-too-early.php, adds its doing_it_wrong_run callback, and catches the notice with the call stack.
B is wrong: Every PHP file directly in mu-plugins/ loads.
C is wrong: WordPress gives file names no meaning beyond their order.
D is wrong: PHPCS only checks what its ruleset names; mu-plugins are not in the plugin's ruleset at all.
Q5
PHPCS reports 30 times PrefixAllGlobals.NonPrefixedVariableFound in the blocks' render.php files. What did Lesson 8.1 do, and why?
A) Renamed every variable to start with pagesco_books_
B) Turned the rule off for the whole plugin
C) Excluded that rule for those two file patterns in phpcs.xml.dist, with a comment: WordPress includes them inside a function, so the variables are local
D) Added // phpcs:ignore to each of the 30 lines
Why: A ruleset exception that is narrow (one rule, the files it does not fit) and explained (the comment) is a decision a reviewer can read. Thirty ignore comments would hide the same decision thirty times; a plugin-wide switch would hide real globals elsewhere.
A is wrong: Possible, but noisy, and it fixes nothing: the variables are not globals.
B is wrong: Too wide: a real global anywhere else would go unreported.
D is wrong: phpcs:ignore is for a single line that is right despite the rule; thirty of them is a ruleset decision.
Q6
In the plugin's folder, with the wp-env test environment started: which command runs the plugin's PHPUnit tests, and why not just phpunit?
npx @wordpress/env run cli --env-cwd=wp-content/plugins/pagesco-books vendor/bin/phpunit: the plugin's own PHPUnit 9.6; the container's global phpunit is 10.5, which the WordPress 7.1 test library does not support
Why: Two versions of PHPUnit in one process fail with "Call to undefined method PHPUnit\Framework\TestSuite::empty()" (Lesson 8.1, Common Mistake 2). --env-cwd is the folder to run in, relative to the WordPress root inside the container. composer test runs the same vendor/bin/phpunit.

8.1 · Debugging & Testing: predict, then run

P1
Predict the output, then run it.
wp eval 'var_dump( WP_DEBUG_DISPLAY, ini_get( "display_errors" ) );'
bool(true)
string(6) "stderr"
Why: WP_DEBUG_DISPLAY is true, and WP-CLI sets PHP's display_errors to stderr: messages go to the terminal's error stream, which is why your terminal shows warnings that a pipe into a file would not catch. On a web request the same setting prints them into the page.
P2
Predict the output, then run it.
wp eval 'add_filter( "pre_http_request", fn() => new WP_Error( "http_request_failed", "down" ) ); $r = wp_remote_get( "https://api.riverside.example/v1/availability" ); echo get_class( $r ), ": ", $r->get_error_message(), "\n";'
WP_Error: down
Why: pre_http_request answered with a WP_Error before any connection was tried (the fictional address would not resolve anyway). wp_remote_get() returns it unchanged: a transport failure is a WP_Error, an HTTP error status is not (Lesson 7.3).

8.2 · Performance & Caching: self-check

Q7
On the course site: what does this print?
wp eval 'global $wpdb; $b = $wpdb->num_queries; get_option( "pagesco_lab_nope" ); get_option( "pagesco_lab_nope" ); echo $wpdb->num_queries - $b, "\n";'
1
Why: The first get_option() of an option with no row asks the database and finds nothing; WordPress then remembers the name in the notoptions cache for the rest of the request, so the second costs nothing. One query per request is what pagesco_books_settings cost every page until Lesson 8.2 gave it an autoloaded row.
Q8
On a site without a persistent object cache, these two commands run one after the other. What does the second print?
wp eval 'wp_cache_set( "stock", 24, "pagesco_demo" );'
wp eval 'var_dump( wp_cache_get( "stock", "pagesco_demo" ) );'
A) int(24)
B) bool(false)
C) NULL
D) A Warning: the group pagesco_demo does not exist
Why: Each WP-CLI command is its own PHP process, a request of its own, and WordPress's own object cache lives in that process's memory: the second starts empty and wp_cache_get() returns false for a miss. With an object-cache.php drop-in (Redis, Memcached, the lesson's SQLite Object Cache) it would print int(24).
A is wrong: That needs a persistent object cache; the course site has none (wp_using_ext_object_cache() is NULL).
C is wrong: A cache miss is false, which is why the lesson's code checks is_array() or is_string() for a hit.
D is wrong: Groups need no registration; an unknown key is simply a miss.
Q9
A shop with 500 books runs get_posts( array( 'post_type' => 'book', 'fields' => 'ids', 'posts_per_page' => -1 ) ), then get_post_meta() for each ID, with an empty cache. About how many queries is that, and what is the fix?
A) 2 queries: WordPress loads the meta with the IDs
B) 500 queries; the fix is a persistent object cache
C) 501 queries; the fix is update_postmeta_cache( $ids ) before the loop: 2 queries
D) 1 query; meta is autoloaded like options
Why: With 'fields' => 'ids' get_posts() skips priming the meta cache, so each get_post_meta() asks for its own post: N+1. update_postmeta_cache() loads the meta of all IDs in one query (Lesson 8.2 measured 12 to 2 for eleven books; the lab query_count shows 11 and 1).
A is wrong: That is what a normal WP_Query does; fields => ids is the shortcut that skips it.
B is wrong: Off by one (the ID query), and a warm persistent cache only hides the problem until it is flushed.
D is wrong: Post meta is never autoloaded; only options have autoload.
Q10
EventsTable::find() treats a cached value as a hit with if ( is_array( $events ) ). A colleague suggests the shorter if ( $events ). What would break?
A) Nothing: both conditions treat every cached value the same way
B) A cached empty result, array(), would count as a miss: a location without events would query the database on every call
C) A cached WP_Error would reach the shortcode
D) Two different limits would share one cache entry
Why: An empty array is falsy in PHP, so a truthiness check turns a valid, cached answer (no events here) into a miss, every time. is_array() states what a hit is; false !== $events would work too, since a miss is false (run: wp eval 'var_dump( false !== array(), (bool) array() );'). Two limits sharing an entry is a different bug, prevented by the key: the debug handout debug_events_cache.php has exactly that one.
A is wrong: array() is falsy: if ( array() ) does not run its block.
C is wrong: find() never stores a WP_Error.
D is wrong: That is prevented by the key, md5( $limit . '|' . $location ), not by the check.
Q11
In Lesson 8.2's lab measurement the front page had a CLS of 0.101, just over the 0.1 limit. What caused it, and what fixed it?
A) The web fonts; font-display: swap fixed it
B) The speculation rules prefetching the next page
C) The Navigation block's external stylesheet; inlining it fixed it
D) The hero image had no reserved space; the Image block's aspectRatio attribute fixed it
Why: The browser laid the page out without knowing the image's height, and moved everything below it when it arrived. Block templates get no automatic width and height (wp_filter_content_tags skips the template context), so the theme adds the aspect ratio itself: CLS fell to 0.001.
A is wrong: The font swap caused only the 0.001 that was left.
B is wrong: Prefetching happens on a click and moves nothing on the current page.
C is wrong: A render-blocking stylesheet delays the first paint; it does not shift content afterwards.
Q12
Which WordPress filter adds a <link rel="preload"> for the front page's hero image to the head, and which attribute tells the browser to fetch it first?
wp_preload_resources, with 'fetchpriority' => 'high' (and 'as' => 'image')
Why: The browser finds the preload in the head before it reads the body. In the lesson's lab measurement LCP went from about 1.48 s to about 1.40 s: a modest gain, honestly reported, because the image was in the HTML anyway.

8.2 · Performance & Caching: predict, then run

P3
Predict the output, then run it.
wp eval 'global $wpdb; $b = $wpdb->num_queries; get_post( 30 ); get_post( 30 ); echo $wpdb->num_queries - $b, "\n";'
1
Why: The first get_post() loads the row and caches it in the posts group; the second comes from the object cache. Within one request WordPress never asks twice for the same post.
P4
Predict the output, then run it.
wp eval 'var_dump( wp_using_ext_object_cache() );'
NULL
Why: NULL: no object-cache.php drop-in, so WordPress uses its own in-memory cache (wp_using_ext_object_cache() is only set to true by a drop-in). In Lesson 8.2 it printed bool(true) while the SQLite Object Cache was installed.

Lesson 8.1 · Debugging & Testing
  1. B WP_DEBUG true, WP_DEBUG_DISPLAY false, WP_DEBUG_LOG set to a path outside the web root: Errors are recorded but never shown, and the log lives where the web server does not serve it, unlike the default wp-content/debug.log.
  2. A An email with the plugin's name, the error and a recovery mode link: The fatal error handler finds the plugin from the file in the error and emails a recovery mode link that logs in with that plugin paused.
  3. C So that the test controls the answer, including failures, and does not depend on the network: The filter answers in place of the network, so each test decides exactly what the supplier says, including 503s and broken JSON, and the result depends only on your code.
  4. C A phpcs:ignore comment for that rule on that line, with the reason: The output is escaped by core, which PHPCS cannot know; an ignore comment for exactly that rule on exactly that line, with the reason, documents the decision.
  5. A The test library reinstalls that site's database on every run: The test library drops and reinstalls the tables of the database it is configured with on every run, so it must never be a database you care about.
Lesson 8.2 · Performance & Caching
  1. B One query per request; an autoloaded row for the option removes it: Each request asks the database once and learns that the row does not exist; an autoloaded row is read with all other autoloaded options, for no extra query.
  2. C Until the end of the current request: The default object cache is an array in PHP's memory, emptied at the end of every request; only a drop-in such as Redis keeps it between requests.
  3. A So that every change to the table makes all older cached results unreachable: Every write renews the group's last-changed value, so all keys built before the write are never read again: no stale result without having to find and delete each entry.
  4. B Because WordPress skips loading optimizations for block templates, and the image is not in the Media Library: wp_get_loading_optimization_attributes() returns early for the template context, and width and height are only added for Media Library images; the theme must take care of its own images.
  5. C That a change you make can be compared against it on the same machine; field data from real visitors decides the rest: Lab measurements compare changes on one machine with the same settings; real visitors' phones and networks, measured as field data after launch, decide the Core Web Vitals.

Exit Ticket

  1. A critical error: the server's error log (on development: wordpress/wp-content/debug.log) and the recovery mode email WordPress sent the admin address (it names the plugin, the file and the line); from the command line wp --skip-plugins=<plugin> plugin deactivate <plugin> works although every other command dies. A must-use plugin: rename the file.
  2. The last-changed value in the key: flush_cache() renews it after every insert or delete, so after a change every key is new and every old answer is simply never read again; nothing has to find and delete old entries. Without it, a persistent cache would show the old list until it expired.
  3. Lab against field: a lab measurement compares before and after a change on the same machine and setup (CLS 0.101 to 0.001 is real); it cannot say what visitors on mid-range phones over weak connections experience, how a full catalog or real traffic behaves, or what a page cache changes: field data after the launch (Lesson 8.4).

Common Wrong Answers and What They Reveal

  • Q1 A ("true, wp-content/debug.log"). Remembers that logging is good, not where the log goes. Run Mistake 1's curl again: 200.
  • Q2 with pagesco_supplier_bad_response. Thinks an HTML body makes it a bad response first. The status is checked before the body (Client::decode()): read the method's three numbered comments.
  • Q3 B ("wp eval deactivate_plugins"). Thinks wp eval runs before WordPress loads. Everything in WP-CLI except a few commands loads WordPress, plugins included.
  • Q8 A ("int(24)"). Does not separate one request from the next. Two WP-CLI commands are two PHP processes; show P4 (wp_using_ext_object_cache() is NULL).
  • Q9 B ("500, persistent cache"). A warm persistent cache hides N+1; flush it and the 501 queries are back. The fix is in the code.
  • Q10 A ("nothing breaks"). Forgets that an empty array is falsy. Run wp eval 'var_dump( false !== array(), (bool) array() );': the second value is the truthiness of array(). A good moment to say: verify claims about code by running them.
  • Q11 A ("the fonts"). Remembers the 0.001 that was left. The 0.1 jump was the image without reserved space.
