Session 1: WordPress for Developers and Your Local Environment

How to teach the first session of PHP and WordPress Development. Welcome a room of PHP and MySQL developers, find out which machines run the course's Docker project and what the room remembers from the Foundations courses, then show WordPress as a developer sees it (one request through core, the folder that is yours, an edited core file and an old tutorial caught) and make every laptop ready: an install clinic, WP-CLI and debugging on the real site, a site-report lab, and a health check learners can rerun all course.

2 lessons 3 hrs session Lessons 1.1–1.2 Session 1 of 18 · Part 1

How to Use This Guide

  • Same rhythm for both lessons: frame (the goal and one mental model) → live demo (you type, they type along) → guided lab (a kit lab, new practice on the lesson's ideas) → start the lesson's own project. The lesson exercises, quiz and journal are homework.
  • Type, do not paste. Every command below was run to produce the output printed under it, on WordPress 7.1.3, PHP 8.5.12, MySQL 9.7 and WP-CLI 2.12.0: a fresh course site, exactly what a learner has at the end of Lesson 1.2. Ask for a prediction before every run, and read every message from the left, out loud: the level, the message, the file, the line.
  • The lessons are the reference. Keep lesson_01.html and lesson_02.html open in browser tabs for the request diagram and the per-platform Docker sections. Labs live in labs/module-01/ (learners keep the folder in their project folder, next to compose.yaml): _starter files are handouts, _solution files and the store_hours_solution/ folder are yours.
  • Session 1 is different in two ways. It opens with 30 minutes of welcome, environment check and diagnostic instead of the usual 10-minute warm-up, and Lesson 1.2's room time is mostly an install clinic: setting up Docker and the course project is prework (the kit's setup guide follows Lesson 1.2), so the room fixes what went wrong instead of watching downloads.
  • Part 1, "Themes" (Sessions 1 to 8), can run on its own as a short course; nothing in this session depends on Part 2. Teal blocks are hands-on, amber blocks are watch-outs. Lesson codes (1.1, 1.2) match the course site.
The #1 risk of Session 1: the setup eats the session

Docker installs differently on every platform, and each path has its own trap: Windows needs WSL 2, Docker Desktop's WSL integration switched on, and the project in the Linux file system; Linux needs the docker group (and a new login) and the course's file-owner fix before the first start; every platform downloads about a gigabyte of images on the first docker compose up -d. Done together on venue Wi-Fi, setup fills three hours and nobody looks at WordPress. Before: send the setup guide a week ahead (Docker, the pagesco-dev project, the install commands, the labs/ folder in the project folder, then check_environment.sh) and ask every learner to reply with its last line. In the room: the check gets 12 minutes in the opening; a NOT READY machine gets a ready partner until the 25-minute install clinic at 1:40, not your attention during Lesson 1.1. After: whoever is still not ready leaves with a numbered plan and runs the check again before Session 2.

Ask learners to reply with the last line it prints. No reply means a setup risk: chase it.

  • ☐ Print or share: the workbook (its Start Here page has the environment checklist and the diagnostic), sticky notes for help flags and the exit ticket.

Sequence and talking points
  • Welcome (5m). One minute on yourself, including a WordPress site you once had to fix (the plugin that broke on an update, the theme someone edited by hand). Then a quick round: name, what they want to build with WordPress (client sites, a plugin to sell, the site at work), and which PHP and MySQL they already know. Write three or four goals on the board; they come back in the 1.1 journal prompt. Housekeeping in one breath: break at 1:20, where the lab files are, and "if you are stuck, put a sticky note on your laptop lid and keep trying while I get to you."
  • How the course runs (5m). Show the course home page. Say: "Eighteen sessions of three hours in two parts. Part 1, Themes, the first eight sessions, takes you from a local site to the Pages & Co. block theme, a child theme and a classic theme; Part 2, Plugins to Launch, builds the pagesco-books plugin, custom blocks, REST endpoints, tests and a deployment, and ends with the whole site launched." Then the deal: "Each lesson was written for someone working alone for 100 to 150 minutes, so two do not fit in three hours. In this room we do what is hard alone: the mental model, a live demo, a guided lab, and the first steps of each project. At home you finish the projects and do the exercises, quiz and journal: plan on two to three hours a week." Scroll once through lesson_01.html: objectives, sections with real output, common mistakes made on purpose, a project in steps, exercises with hidden solutions, a quiz, a journal prompt.
  • Environment check (12m). Say: "Before any new ideas, we find out which machines are ready." On the projector, then theirs: 1 open a terminal in the project folder (cd ~/pagesco-dev, the folder with compose.yaml and labs/); 2 docker compose up -d if the site is not running; 3 bash labs/module-01/l1_0-orientation/check_environment.sh. Done = the last line says READY for PHP and WordPress Development (READY WITH NOTES on PHP 8.4 or a project on the Windows drive is fine for today). Anyone who saw READY at home runs it again and becomes a helper. NOT READY falls into three piles: Docker not running or not reachable (often one minute: start Docker Desktop, fix the WSL integration), FIX lines on a running site (the site is not installed, the Mailpit plugin is missing, the Linux owner fix: two to five minutes, fix now), no Docker or no project at all (do not start a download now: pair with a ready neighbor; install clinic at 1:40). Write the third pile's names on a sticky note.
  • Diagnostic (8m). Say: "Six quick questions on what WordPress development builds on: PHP arrays, escaping, SQL, the terminal, HTTP and callbacks. Not a test, nobody collects it. It tells you what to brush up and tells me what to slow down for." Learners answer D1 to D6 on the workbook's Start Here page (about four minutes), then show fingers (1 to 4 for A to D) as you reveal each. Keep a tally of wrong answers per question on a sticky note.
Diagnostic answers and how to read the tally

Answers: D1 A) 3 Dune; D2 B) Hello, &lt;b&gt;Maya&lt;/b&gt;; D3 C) SELECT title FROM books WHERE price < 10 ORDER BY price;; D4 D) cd pagesco-dev, then docker compose up -d; D5 A) 404 Not Found; D6 B) DUNE! EMMA!.

  • D1 (arrays) and D6 (callbacks) predict the next two sessions: Lesson 1.3 is arrays of arguments and callbacks in every form, Lesson 2.3 hooks your functions into core by name. Two or more misses on D6: say "core calls YOUR function" every time a callback appears in Sessions 2 and 3.
  • D2 (escaping) comes back in Lesson 1.3 (esc_html() and friends) and Lesson 5.3 (security). A miss here is the most important one to follow up: escaping is non-negotiable in WordPress code.
  • D3 (SQL) comes back in Lesson 2.2 (WordPress's own tables) and 5.5 ($wpdb). Learners who miss it are usually rusty, not lost: point them to MySQL Foundations' SELECT lessons before Session 3.
  • D4 (folders) predicts trouble in the next hour: no configuration file provided is almost always it. Learners who missed it get the typing role in the lab pair, with you nearby for the first command.
  • D5 (HTTP) matters from Module 3 on (the 404 template, redirects). Misses are rare.
  • Three or more wrong: not a problem to announce. Pair them with a strong neighbor today, and at the wrap-up hand them labs/module-01/l1_0-orientation/diagnostic_starter.php: D1, D2 and D6 done by PHP on their own site, one small gap each (diagnostic_solution.php is your reference). The workbook's Start Here page says where each skill comes back; PHP Foundations and MySQL Foundations are the review.
Watch-outs
  • Do not debug one machine in front of the room. Two minutes per machine during the check, then pair and move on: the install clinic at 1:40 exists so that you can say "we will fix that at 1:40" with a straight face.
  • Mixed backgrounds. Some learners have built WordPress sites in the dashboard and never written a plugin; some write PHP daily and have never used WordPress. The diagnostic and the check are for both groups; say so.
  • "I use Local / XAMPP / MAMP." Those work for WordPress, but the course's outputs, paths, port, mail catcher and WP-CLI fixes are tested on the Docker project (Lesson 1.2 FAQ). Ask them to run the course project alongside for the labs; nothing needs uninstalling.
  • "I already know WordPress." Welcome them and give them a job: helper during the check and the clinic, and the stretch tasks in each lab. Old habits (editing a theme's functions.php from the dashboard, FTP to the live site, tutorials from before blocks) are exactly what Module 1 replaces.

WordPress for Developers

50 min
Objectives (from the lesson page)
  • Describe WordPress 7.1 as a developer sees it: a PHP and MySQL application with themes, plugins, blocks and APIs as extension points
  • Explain the difference between WordPress.org (the software) and WordPress.com (a hosting service), and pick the right one for a project
  • Trace a front-end request from index.php to the finished HTML, naming the core files on the way

  • Map what you know from PHP Foundations and MySQL Foundations to the way WordPress does the same jobs
  • Describe the Pages & Co. project and plan how you will work through this course

Mental model to say

Tell it while you draw it: "WordPress core is an apartment building. The owner, the WordPress project, maintains the structure, the wiring and the plumbing, and renovates a few times a year. You are a tenant. You paint and furnish your rooms (themes), plug appliances into the sockets the building provides (plugins and hooks), and you can add a doorbell that rings in the lobby (the REST API). You never knock down a wall of the building: the next renovation would put it back."

Then the extension points as a list on the board: hooks (Lesson 2.3), themes (Modules 3 and 4), plugins (Module 5), blocks (Module 6), APIs (Module 7). "Almost everything a WordPress developer does is one of these five. Each has its module." Then WordPress.org and WordPress.com in two sentences: "WordPress.org is the free software and its community; WordPress.com is one company's hosting of it, where your own plugins depend on the plan. This course is self-hosted: your own site from Lesson 1.2."

Then the trip, one box at a time, on the drawing from the board: "Every front-end address goes to index.php. WordPress loads itself, settings first, then core, must-use plugins, plugins and the theme, and fires init. Then wp() turns the address into a query and runs it. Then the template loader picks the theme's template and draws the page. Load, then query, then template." Write inversion of control: core runs the program and calls you under it.

Live demo (you type, they follow)

The lesson's own commands, typed live on the projector in the WP-CLI container shell (docker compose run --rm wpcli sh; the prompt changes to /var/www/html $). Ready learners type along; the others watch and get their turn after the clinic. Ask for a prediction before every run.

  1. The front door (3m). "In PHP Foundations one file answered one address. Here almost every address goes to ONE file. Let us read it." Open a shell in the WP-CLI container (docker compose run --rm wpcli sh) and grep the two front-door files. Ask first: how many lines of real code does index.php have? 
    grep -n "WP_USE_THEMES\|require" index.php
grep -n "require\|wp();" wp-blog-header.php
    14:define( 'WP_USE_THEMES', true );
17:require __DIR__ . '/wp-blog-header.php';
13:	require_once __DIR__ . '/wp-load.php';
16:	wp();
19:	require_once ABSPATH . WPINC . '/template-loader.php';
    Two: one constant and one require. Then wp-blog-header.php does three things in order: load WordPress, wp(), the template loader. Draw them on the board as three boxes: load, query, template.
  2. The end of the trip (2m). "Now from the outside, the way a browser asks." curl runs inside the container, where http://localhost:8080 is the site. 
    curl -s http://localhost:8080/hello-world/ | grep -o '<title>.*</title>'
    <title>Hello world! &#8211; Pages &amp; Co.</title>
    "Hello world!" came from the main query, "Pages & Co." from the options table, the dash is an HTML entity. None of it is in a file: it is the database plus the theme.
  3. Where code lives (3m). "Everything in the root belongs to WordPress, except two things." List the root, then the one folder that is yours. 
    ls
ls -d wp-content/*/
ls wp-content/themes wp-content/plugins
    index.php             wp-activate.php       wp-comments-post.php  wp-config.php         wp-includes           wp-login.php          wp-signup.php
license.txt           wp-admin              wp-config-docker.php  wp-content            wp-links-opml.php     wp-mail.php           wp-trackback.php
readme.html           wp-blog-header.php    wp-config-sample.php  wp-cron.php           wp-load.php           wp-settings.php       xmlrpc.php
wp-content/mu-plugins/  wp-content/plugins/     wp-content/themes/      wp-content/uploads/
wp-content/plugins:
akismet    hello.php  index.php

wp-content/themes:
index.php          twentytwentyfive   twentytwentyfour   twentytwentythree
    Point at wp-config.php (your settings) and wp-content/ (your themes, plugins, must-use plugins, uploads). Ask: "who updates each folder?" Core: WordPress. Twenty Twenty-Five: its own updates. pagesco: you.
  4. Mistake 1: a quick fix in core (3m). "A tutorial says: add a line to wp-includes/functions.php. Watch WordPress notice." The lesson's block makes a backup, appends a harmless comment, then compares every core file with the official checksums. 
    cp wp-includes/functions.php wp-content/functions.php.bak
echo '// my quick fix' >> wp-includes/functions.php
wp core verify-checksums
    Warning: File doesn't verify against checksum: wp-includes/functions.php
Warning: File should not exist: wp-config-docker.php
Error: WordPress installation doesn't verify against checksums.
    Read it from the top: the edited file fails; the second warning is the Docker image's own extra file (expected on every Docker site); the verdict is an Error. Restore and check again: 
    mv wp-content/functions.php.bak wp-includes/functions.php
wp core verify-checksums
    Warning: File should not exist: wp-config-docker.php
Success: WordPress installation verifies against checksums.
    "The next update would have removed your line without asking, at night, and a security scanner would have reported a hack."
  5. Mistake 2: an old tutorial (2m). "This one still works. Listen to what WordPress says about it." 
    wp eval 'get_currentuserinfo();'
    Deprecated: Function get_currentuserinfo is <strong>deprecated</strong> since version 4.5.0! Use wp_get_current_user() instead. in /var/www/html/wp-includes/functions.php on line 6260
    The message names the version that deprecated it (4.5.0, years ago) and the replacement. You only see it because debugging is on: that is why the course site always runs with WP_DEBUG (Lesson 1.2).
  6. What gives WordPress away (2m). "Every WordPress site announces itself." Ask for the response headers only: 
    curl -sI http://localhost:8080/ | grep -i '^link'
    Link: <http://localhost:8080/wp-json/>; rel="https://api.w.org/"
    The REST API's address in a header (Module 7). Learners try the Bonus Challenge on a site they admire at home; hiding these clues is not security (Lesson 2.3). Type exit to leave the container shell.
Three mistakes to expect, and how to coach each
  • "Just edit the file." A learner finds the line in core (or in Twenty Twenty-Five) that does what they want and changes it. Coach with the drawing and one question: "Who updates this folder?" If the answer is not "me", the change goes in a plugin or theme, on a hook. (Self-check Q1 and Q4.)
  • Thinking in pages, not in requests. "Where is the file for /about/?" Coach: "There is none. index.php answers, wp() finds the page in the database, the theme draws it." (Self-check Q5, the lesson's Exercise 2.)
  • Trusting an old tutorial. Classic-only code, get_currentuserinfo(), query_posts(), editing functions.php from the dashboard. Coach: "Which version was it written for? What does debug.log say when you run it?" (Mistake 2, the debug handout.)
Guided lab

File: learners copy labs/module-01/l1_1-wordpress-for-developers/core_tour_starter.sh into wordpress/ and run it in the WP-CLI container; your reference is labs/module-01/l1_1-wordpress-for-developers/core_tour_solution.sh. Checks for understanding

Ask these out loud during the demo and the lab (cold-call gently, or think-pair-share):

  • Which folder of the WordPress root is yours? Answer: wp-content/ (and your settings in wp-config.php); everything else is core.
  • In which order: init, the main query, the template? Answer: init (end of loading), then wp() runs the main query, then the template loader draws the page.
  • A client is on WordPress.com and wants your plugin. What do you ask first? Answer: which plan they are on: only some allow your own plugins.
  • Why does get_currentuserinfo() still work if it is deprecated? Answer: WordPress keeps old functions so old sites keep running; the message says what replaced it and since which version.

Workbook self-check, items Q1 to Q6 (learners do them at the end of the block or at home).

Answers: Q1 C) wp-includes/; Q2 <title>Pages &amp; Co.</title>; Q3 C) the init action fires, after plugins and the theme are loaded; Q4 D) Someone edited a core file: restore it and put the change in a plugin or theme, on a hook; Q5 B) index.php in the WordPress root; Q6 esc_html(). Full set with explanations in the Answer Key.

Differentiation

Support: learners whose machines are not ready do the lab with a ready neighbor (one keyboard, two heads, the NOT READY learner reads the core lines aloud and says what each does). For learners new to grep, write grep -n "text" file on the board and leave it there; Step 1 of the starter is the model.

Stretch: wp_paths_starter.php and debug_old_tutorial.php; then the lesson's Exercise 4 (read the front door yourself, including where wp() is defined) and the Bonus Challenge (spot WordPress on a site they admire).

Mental model to say

Back to the board: "Installing a server stack on your laptop is building a restaurant kitchen into your home. Docker is a food truck parked next to the house: everything the kitchen needs comes with the truck, you can drive it away with docker compose down and park an identical one tomorrow. The one thing that stays in the house is your work: the wordpress/ folder, which the truck reaches through a window, the bind mount."

Then the four services in a row: wordpress (Apache and PHP 8.5, the site on port 8080), db (MySQL 9.7, its data in a volume), wpcli (WP-CLI, started only when you call it, removed afterwards), mailpit (a fake mail server with an inbox on port 8025). "Everyone in this room runs the same images, so your site behaves like the one every lesson was tested on."

Then the two habits that save the most time: "Every command runs in the project folder, and wp is a shortcut for docker compose run --rm wpcli wp. When something breaks, the answer is in wordpress/wp-content/debug.log." Triage line on the board: docker not found = install · daemon = start Docker · no configuration file = wrong folder · Permission denied = the Linux fix · critical error = debug.log.

Install clinic

Learners from the opening's NOT READY pile sit together by platform; ready learners pair with them as helpers. You move from table to table; each fix ends with check_environment.sh run again. Twenty-five minutes is enough to start Docker, fix an owner or a missing plugin, and to start a download, not to download a gigabyte on slow Wi-Fi: use the USB stick.

Done for each machine = check_environment.sh prints READY (or READY WITH NOTES). Anyone not done by 2:05 leaves with a numbered plan written in their workbook's Start Here box, and you check it at the start of Session 2.

  5. A warning in the page and in the log (5m). "A real mistake, caught twice." Create the must-use plugins folder in the container shell, save the lesson's buggy demo in VS Code as wordpress/wp-content/mu-plugins/pagesco-debug-demo.php, reload the home page. Have learners tail the log in a second terminal: tail -f wordpress/wp-content/debug.log. 
    <?php
/**

function pagesco_debug_demo_footer() {

}
add_action( 'wp_footer', 'pagesco_debug_demo_footer' );
    The new line in debug.log (the time stamp is the time of your reload): 
    [26-Oct-2026 11:58:58 UTC] PHP Warning:  Undefined variable $pagesco_name in /var/www/html/wp-content/mu-plugins/pagesco-debug-demo.php on line 8
    And in the page itself, just above the footer greeting (here with curl from the container): 
    curl -s http://localhost:8080/ | grep -o 'Warning: [^<]*\|<p class="pagesco-demo">[^<]*</p>'

Three mistakes to expect, and how to coach each
  • Typing commands in the wrong folder. no configuration file provided, or a wp eval-file that cannot find a file. Coach: "Where is compose.yaml? And wp eval-file x.php means wordpress/x.php: where did you save it?" (Self-check Q10.)
  • Reaching for sudo or chmod 777 on Linux and WSL when the editor cannot save. Coach: "Who owns the files? ls -ln wordpress. The fix is to run the containers as you, once." (Lesson quiz Q2.)
  • Ignoring the log. "The page is blank" or "There has been a critical error" with debug.log never opened. Coach: "What does the last line of debug.log say? Read it from the left." Make tail -f wordpress/wp-content/debug.log in a second terminal a habit from today.

Start the lesson project

The lesson project is the Dev Site Health Check: a PHP script that WP-CLI runs with WordPress loaded and that checks every piece the lesson set up. In the room: Steps 1 to 3 (15 minutes); the environment check already did most of Step 1.

  • Step 1: docker compose ps, the site, the admin login, Mailpit, wp core version in a new terminal (two minutes after the check).
  • Step 2: type wordpress/pagesco-check.php from the lesson (ten minutes). Type, do not paste: every line is PHP they know plus one WordPress function explained in its comment.
  • Step 3: wp eval-file pagesco-check.php until all nine lines say OK, then find the health-check email in Mailpit.
  • Done in the room = "All checks passed." on the screen. Goes home: Step 4 (stop Mailpit, watch one check fail, start it again, delete the script) and the checklist.
Checks for understanding

Ask these out loud during the clinic, the demo and the lab:

  • Where does wp option get blogname actually run? Answer: in a new wpcli container that is removed when the command ends (Lesson quiz Q1).
  • Your posts after docker compose down and up -d? And after down -v? Answer: still there; gone (the volume holds the database).
  • A page shows "There has been a critical error on this website." First move? Answer: read the end of wordpress/wp-content/debug.log.
  • Why is there a Mailpit at all? Answer: so test email from a development site never reaches real people; the mu-plugin sends it there, and fixes the sender address WordPress would build from localhost.

Workbook self-check, items Q7 to Q12 (learners do them at the end of the block or at home).

Answers: Q7 C) docker compose down -v; Q8 Pages &amp; Co.; Q9 B) wordpress/wp-content/mu-plugins/pagesco-debug-demo.php in your project folder; Q10 A) You are not in the project folder: Docker Compose found no compose.yaml here or above; Q11 D) WordPress calls its own address, http://localhost:8080, from inside the container (WP-Cron, Site Health), and that must reach Apache; Q12 local: for example, Mailpit's mu-plugin only reroutes email when the environment is local; application passwords work over plain HTTP; WordPress 7.1 turns pings off. Full set with explanations in the Answer Key.

Closing

Exit ticket (3 questions, no notes, 4 minutes)

Put the three questions on the slide. Learners answer in the workbook's Exit Ticket box or on a sticky note and leave it on the way out. Sort the notes into "got it" and "not yet" before Session 2: question 1's pile tells you how much of Session 2's warm-up goes back to "core is not yours".

  1. Where does your own code go in WordPress, and why never in core? Answer: in wp-content/: your theme, your plugin, a must-use plugin; core files are replaced by every update (and an edited core file looks like a hack).
  2. Name the four services of the course project and the job of each. Answer: wordpress (Apache + PHP, the site on 8080), db (MySQL, data in a volume), wpcli (WP-CLI on demand), mailpit (catches email, inbox on 8025).
  3. A page says "There has been a critical error on this website." Where do you look first, and with which command? Answer: wordpress/wp-content/debug.log, for example tail -n 20 wordpress/wp-content/debug.log (or tail -f while you reload).
