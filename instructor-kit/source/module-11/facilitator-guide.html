Shortcodes, $wpdb & Custom Tables

65 min
Objectives (from the lesson page)
  • Register shortcodes with add_shortcode() whose callbacks return escaped HTML, with attributes handled by shortcode_atts()
  • Decide when a custom table is the right storage, and when post types, meta, taxonomies or options are
  • Create and upgrade a table with dbDelta() and a schema version stored in an option

Mental model to say

"Picture the shop window with a small card that reads 'Book of the Month goes here'. Whoever dresses the window does not need to know the price or the stock; every morning someone swaps the card for the real book. A shortcode is that card: the editor writes [pagesco_book id="30"], and on every page view your callback swaps it for the book's current title, price and stock."

Then the second picture: "Post types, meta, taxonomies and options give you admin screens, REST, revisions and export for free. A table of your own gives all that up, so it is the last choice, for many rows with the same few fields, queried by those fields: events, later bookings and holds." And the one rule for both: values reach SQL only through placeholders.

Three mistakes to expect, and how to coach each
  • A shortcode that echoes. Coach: "Where does echo print, and when does the callback run?" (the open_hours lab shows it).
  • Hard-coding wp_ or interpolating values into SQL. Coach: "Who controls this string? $wpdb->prefix is WordPress's; anything from a visitor goes through a placeholder." (Self-check Q3.)
  • A schema change without DB_VERSION, or a rename expected from dbDelta(). Coach with the two mistakes of the lesson: dbDelta only ADDS, and only when asked. (Self-check Q5.)

Checks for understanding
  • What must a shortcode callback do with its HTML? Answer: return it, escaped; never echo.
  • When is a custom table the right storage? Answer: many rows with the same few fields, queried by those fields, not edited as content.

Mental model to say

"The source files in src/blocks/book-card/ are a flat-pack kit: modern JavaScript with JSX and SCSS that no browser reads as is. The build is the workshop: @wordpress/scripts assembles the kit into plain JavaScript and CSS in build/blocks/book-card/. WordPress only ever looks at the shelf, the build/ folder, through the registration call in your plugin. Change the kit and nothing happens on the shelf until the workshop runs again."

Then the four parts on the board: block.json (metadata, read by PHP and the editor) · edit (the editing view, a React component) · save (the HTML stored in post_content) · styles (and later a PHP render). "A static block's front end needs no JavaScript: visitors get the stored HTML."

Closing

Exit ticket (3 questions, no notes, 4 minutes)
  1. Why must a shortcode callback return its HTML instead of echoing it? Answer: it runs while the content is filtered, before the page is printed (in a block theme before the <head>); echoed output lands outside the content.
  2. You add a column to schema(). What else must change, and why? Answer: DB_VERSION must go up, so maybe_upgrade() runs install() on the next request; updates do not rerun activation.
  3. Name the path of the Book Card from your files to the editor. Answer: src/blocks/book-card → npm run build → build/blocks + blocks-manifest.php → the Blocks feature registers them on init → the editor (and the front end gets the saved HTML and style-index.css).
