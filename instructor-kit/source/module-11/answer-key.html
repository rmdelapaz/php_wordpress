Genuine (nonce), allowed (current_user_can() for this object), sanitize and validate, escape on output; SQL by hand through $wpdb->prepare().
W2
settings_fields() takes the group or the page slug?
The group (pagesco_books), the first argument of register_setting(); do_settings_sections() takes the slug.
W3
What does an unticked checkbox send?
Nothing: missing means off (! empty( ... )).
W4
$wpdb->prepare(): which placeholder for a table name?
%i (WordPress 6.2+), today's lesson builds a whole table with it.
W5
What does uninstall.php remove, and what does it keep?
The plugin's own data (the settings option, the role); the shop's books stay. Today the events table joins the "remove" list.

5.5 · Shortcodes, $wpdb & Custom Tables: self-check

Q1
What does this print?
wp eval 'echo wp_json_encode( shortcode_atts( array( "limit" => 5, "location" => "" ),
    array( "limit" => "3", "color" => "red" ), "pagesco_events" ) ), "\n";'
{"limit":"3","location":""}
Why: shortcode_atts() keeps exactly the keys of the defaults: limit takes the given value, as the STRING "3" (attributes are always strings: absint() it before use), location keeps its default, and color, never declared, is dropped. The third argument creates the shortcode_atts_pagesco_events filter.
Q2
Which of these do you get for free with a post type, but must build yourself for a custom table?
A) A REST route, admin screens, revisions and export
B) Fast queries on an indexed column
C) A schema you control column by column
D) JOINs with wp_posts
Why: That is the price of a table (Lesson 5.5, "When a Custom Table Is Right"): the events got a shortcode now, a REST route in Lesson 7.2, and their cleanup in uninstall.php, all written by hand. In return the table has typed columns and an index on starts_at.
B is wrong: That is what the table GIVES you (KEY starts_at); meta queries sort a string column.
C is wrong: Also a benefit of the table, and a duty: you write the migrations.
D is wrong: Any table can be joined; the wishlist lab joins wp_posts.
Q3
On the finished Lesson 5.5 site, what does this print?
wp eval 'global $wpdb; echo $wpdb->prepare( "SELECT title FROM %i WHERE location = %s",
    PagesCo\Books\EventsTable::name(), "Café" ), "\n";'
SELECT title FROM `wp_pagesco_events` WHERE location = 'Café'
Why: %i quotes an identifier with backticks (WordPress 6.2+), %s quotes and escapes a value. The table name comes from EventsTable::name(), built from $wpdb->prefix, never a hard-coded wp_.
Q4
EventsTable::add() calls $wpdb->insert(). Where does it find the new row's ID?
A) In the return value of insert()
B) $wpdb->insert_id
C) $wpdb->last_query
D) Only with a second query, SELECT LAST_INSERT_ID()
Why: insert() returns the number of rows inserted (1) or false; the auto-increment ID of the new row is in $wpdb->insert_id right after it (the lesson's add() returns it, or 0 when the insert failed).
A is wrong: The return value is a count (or false), not an ID.
C is wrong: last_query is the SQL that ran, useful for debugging.
D is wrong: Not needed: wpdb reads it for you.
Q5
Why does EventsTable check the schema version on every request (maybe_upgrade() on init), and not only on activation?
A) Because dbDelta() must run on every request
B) Because the activation hook cannot create tables
C) Because a plugin update replaces the files but does not run the activation hook again
D) Because the version option is not autoloaded
Why: An update ships a higher DB_VERSION and a new schema(); the next request sees the stored version is lower and runs install() once. The check costs one autoloaded get_option() (Lesson 5.5, Project Step 1: no reactivation).
A is wrong: dbDelta() runs only when the stored version is older than the code.
B is wrong: Activation does create it: Activator::activate() calls install().
D is wrong: update_option() autoloads it, which is why the check is cheap.
Q6
On the finished Lesson 5.5 site, what does this print?
wp eval 'echo do_shortcode( "[pagesco_events location=\"Reading corner\" limit=\"1\"]" ), "\n";'
<ul class="pagesco-events"><li class="pagesco-event"><strong>Book club: Dune</strong> <time datetime="2027-11-04T19:00">Thursday, November 4, 7:00 pm</time> <span class="pagesco-event__where">Reading corner, 20 seats</span></li></ul>
Why: location narrows the list (an exact match, through a %s placeholder in EventsTable::find()), limit caps it; the dates come from mysql2date() in the shop's local time. Two events are in the Reading corner; the first by date is the Dune book club.

6.1 · Block Development Setup: self-check

Q7
Which file in build/blocks/book-card/ has no source file of its own in src/?
A) block.json
B) index.js
C) style-index.css
D) index.asset.php, the dependency list and version hash
Why: The build writes index.asset.php itself: the WordPress script handles index.js needs (react-jsx-runtime, wp-block-editor, wp-blocks, wp-i18n) and a hash of its content for cache busting. block.json is copied; index.js and style-index.css are compiled from the sources.
A is wrong: block.json is copied from src/blocks/book-card/block.json.
B is wrong: index.js is compiled from index.js, edit.js and save.js.
C is wrong: style-index.css is compiled from style.scss.
Q8
On the finished Lesson 6.1 site, what does this print?
wp eval 'echo implode( ", ", WP_Block_Type_Registry::get_instance()
    ->get_registered( "pagesco/book-card" )->style_handles ), "\n";'
pagesco-book-card-style
Why: Registration turned block.json's "style": "file:./style-index.css" into a registered style with a handle derived from the block name. That handle is what a block theme prints (inlined) on pages that contain the block, and only there.
Q9
You worked all afternoon with npm start running. What do you run before you commit or deploy?
A) npm run build: the minified production files, without .map files
B) npm install again
C) npx @wordpress/create-block again
D) Nothing: npm start already wrote build/
Why: npm start writes a development build (not minified, with source maps) and watches for changes; npm run build rewrites build/ with the small production files (Lesson 6.1, "While you work").
B is wrong: npm install only installs the tools; it builds nothing.
C is wrong: create-block scaffolds a NEW block.
D is wrong: It did, but the development version, with .map files that should not ship.
Q10
Posts already contain the Book Card. A developer renames the block from pagesco/book-card to pagesco/staff-pick. What happens to those posts?
A) WordPress renames the block in every post automatically
B) Nothing visible: names are cosmetic
C) Their stored comments still say wp:pagesco/book-card, a block that no longer exists: the editor cannot handle them
D) The posts are deleted
Why: The name is stored in every post that uses the block (), so it is a permanent identifier: never rename it once content exists (Lesson 6.1, Reading block.json). Change the title instead; it is only a label.
A is wrong: Nothing rewrites stored content for you.
B is wrong: The name is the block's identity; the title is the cosmetic part.
D is wrong: The content stays; only the editor no longer knows the block.
Q11
On the finished Lesson 6.1 site, what does this print, and why not 4?
grep -c "'wp-" wp-content/plugins/pagesco-books/build/blocks/book-card/index.asset.php
3: wp-block-editor, wp-blocks and wp-i18n; the fourth dependency, react-jsx-runtime, does not start with wp-
Why: The build replaced every @wordpress/* import with the matching global script handle and listed them; WordPress loads them before index.js. That is why the block's own file is about a kilobyte.
Q12
What does npx @wordpress/create-block@latest book-card --no-plugin --target-dir=src/blocks/book-card NOT create?
A) A block.json
B) A plugin PHP file, a package.json and node_modules/
C) An edit.js and a save.js
D) A view.js
Why: --no-plugin writes only the block's own files into the target folder: block.json, index.js, edit.js, save.js, view.js and the two SCSS files. The plugin, its package.json and the npm install are yours (Lesson 6.1, Building with @wordpress/scripts).
A is wrong: block.json is the first file it writes.
C is wrong: Both are scaffolded (edit for the editor, save for the stored HTML).
D is wrong: It writes view.js too; the project deletes it.

6.1 · Block Development Setup: predict, then run

wp eval 'echo implode( ", ", array_keys( require WP_PLUGIN_DIR . "/pagesco-books/build/blocks/blocks-manifest.php" ) ), "\n";'
book-card
Why: The manifest is plain PHP that returns an array keyed by the block's folder in build/blocks: one block, book-card.

curl -s http://localhost:8080/ | grep -c 'pagesco-book-card-style'

Why: 0 (and grep exits 1): block themes print a block's styles only on pages that contain the block. The home page has no Book Card.

The Lesson Pages' Own Quick Quizzes

Lesson 5.5 · Shortcodes, $wpdb & Custom Tables
  1. B At the very top of the page, above the doctype: echo prints immediately, and a block theme renders the content before it prints the head, so the HTML ends up above the doctype; the shortcode's place in the content stays empty.
  2. C Thousands of bookings, each with the same few fields, listed by date: Many rows with the same fields, queried by those fields and not edited as content, are where a custom table beats post meta: real column types, indexes and simple SQL.
  3. A A higher DB_VERSION, so maybe_upgrade() runs install() again: maybe_upgrade only calls dbDelta when the stored version is lower than DB_VERSION. Without raising the constant, the new statement never runs.
  4. C {"limit":5,"location":""}: shortcode_atts compares keys exactly and keeps only declared ones, so LIMIT and color are both ignored and the defaults stay. In a real tag, the parser lowercases names before this step, which is why [pagesco_book ID=35] worked.
  5. B $wpdb->get_results( $wpdb->prepare( 'SELECT title FROM %i WHERE location = %s', $table, $loc ) ): prepare puts the table name in through %i and the visitor's value through %s, quoted and escaped, so it can never change the query.
Lesson 6.1 · Block Development Setup
  1. B build/blocks/ and its blocks-manifest.php: The Blocks feature passes build/blocks and its manifest to the registration function; src/ is only read by the build, which is why an unbuilt change never shows up.
  2. A To add the block to the existing pagesco-books plugin instead of creating a second plugin: Without it create-block scaffolds a separate plugin with its own PHP file and build setup; --no-plugin writes only the block files, so the block lives in pagesco-books with everything else.
  3. C It lists the WordPress scripts index.js depends on, and a version hash for caching: The build writes the script handles the file needs (wp-blocks, wp-block-editor...) and a content hash; WordPress loads those dependencies first and uses the hash as the version.
  4. B The build has not run since the change: Registration reads build/blocks-manifest.php and build/, which still hold the old title until npm run build (or npm start) runs again.
  5. C Only the styles from style-index.css; the HTML is already in the post: The HTML was stored when the editor saved the post; the front end only needs the shared styles, which a block theme adds (here inlined) only on pages that contain the block.

Exit Ticket

  1. Return, not echo: the callback runs while the content is filtered, before the page is printed; in a block theme the template is rendered before the <head>, so echoed text lands above the doctype (in a classic theme at the top of the content).
  2. DB_VERSION: raise it; maybe_upgrade() compares it with pagesco_books_db_version on init and runs install(), whose dbDelta() adds the column. Plugin updates replace files without running activation.
  3. The path: src/blocks/book-card → npm run build → build/blocks/book-card + blocks-manifest.php → Blocks::register_blocks() on init → registered type and handles → the editor loads index.js; visitors get the saved HTML and style-index.css.

Common Wrong Answers and What They Reveal

  • Q1 with limit as the number 3. Attributes are strings: absint() them.
  • Q2 B. Lists a benefit of tables as a cost: read the question again.
  • Q5 B. Thinks activation cannot create tables; it does, the problem is updates.
  • Q7 A. block.json is copied (and reformatted), not generated.
  • Q10 B. Thinks the name is a label; the title is.
