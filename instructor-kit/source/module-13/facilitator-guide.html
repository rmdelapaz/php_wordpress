Session 13: The Interactivity API and Using the REST API

How to teach the session where the shop's pages react without reloading and its data answers over HTTP: the Interactivity API's server-first model (directives the server already evaluates, a small store that takes over), then the REST API's routes, headers, authentication and errors, and Checkpoint 2 on Modules 5 and 6.

How to Use This Guide

  • Same rhythm for both lessons: frame (the goal and one mental model) → live demo (you type, they type along) → guided lab (a kit lab, new practice on the lesson's ideas) → start the lesson's own project. Today ends with Checkpoint 2 at 2:20: 30 minutes, scored, open notes, on Modules 5 and 6. The lesson exercises, quiz and journal are homework.
  • Every command below was run on WordPress 7.1.3 / PHP 8.5 to produce the output printed under it: Lesson 6.4's demo on the site after Lesson 6.3 (after:lesson_21), Lesson 7.1's on the site after Lesson 6.4 (after:lesson_22).   • Part 2, Session 5 of 10. Teal blocks are hands-on, amber blocks are watch-outs. Lesson codes (6.4, 7.1) match the course site.
The #1 risk of Session 13: two big lessons squeeze the checkpoint

The Interactivity API

55 min
Objectives (from the lesson page)
  • Explain how the Interactivity API splits the work: server-rendered HTML with directives, then hydration by a store in a script module
  • Scaffold an interactive block into the plugin, and build its viewScriptModule with --experimental-modules
  • Set state and per-element context in PHP with wp_interactivity_state() and wp_interactivity_data_wp_context(), including derived state the server can compute
  • Write a store with store(), state getters, getContext() and actions, and connect it with data-wp-on, bind, class and text
  • Build interactive features that stay accessible and keep working without JavaScript

Mental model to say

"The server builds the stage: every book is on it, every genre link, finished and visible. Directives are cables from each light to a fader on the lighting desk: 'this book is lit while isVisible is true'. The store is the desk: move the genre fader and every light wired to it changes at once. You only ever touch the faders; the cables do the rest."

Then the two consequences on the board: the server evaluates directives too (the page is right before any JavaScript) and one shared runtime, loaded as a module only where an interactive block is. Then the design question before any code: "What is the ONE thing that changes when a customer clicks?" (the genre). "Everything else is derived. What does each element need to know about itself?" (its slug, its genres: context).

Three mistakes to expect, and how to coach each
  • No --experimental-modules: "compiled successfully", no view.js, and a filter that reloads the page. Coach: "Is view.js in build/? Does the page load on every click?" (Lesson quiz Q1.)
  • A JavaScript getter that disagrees with its PHP closure: the page changes on hydration (a flash). Coach: "Write the closure and the getter side by side; same inputs, same answer." (Self-check Q2, the guided lab.)
  • Per-element data in the state, or a typo in the namespace. Coach: "Is this the same for every element (state) or one element's own (context)? Is the namespace spelled the same in render.php and view.js?" (Self-check Q4, the debug handout.)

Checks for understanding

Ask these out loud during the demo and the lab:

  • What is the state of the Book Filter, and what is derived? Answer: the state is the genre (and the books' genres); isVisible, isSelected and visibleCount are derived.
  • Why are the genres links and not buttons? Answer: without JavaScript the link is followed and the server renders the filtered page; with it, the action prevents the navigation.
  • Which directives does the server process? Answer: interactive, context, bind, class, style, text, each; not on, watch, init, run.
  • What does the page load only where the block is? Answer: the view.js script module (and the import map entry for @wordpress/interactivity).

Using the REST API

Objectives (from the lesson page)

Mental model to say

"The shop floor is the website: customers browse the shelves, which is HTML. At the back is a service counter with a list of what it handles: 'ask for a book by its number', 'change a price'. Anyone may ask the counter for public information. For anything that changes the shop, the clerk first checks who you are, authentication, and then whether your role allows it, permission. What you get back is a neat package, JSON, with a slip stapled to it: the status code and the headers."

Then the five words on the board with the site's examples: base /wp-json/ · namespace wp/v2 · route /wp/v2/books/(?P<id>[\d]+) · endpoint GET or POST on a route · response JSON + status + headers. And the trip: authentication → route and method → arguments validated → permission → callback → JSON. "Lesson 7.2 builds counters of the shop's own."

Three mistakes to expect, and how to coach each
  • _fields without _links, so _embed embeds nothing. No error, no genres. Coach: "What does _embed follow? Is it still in the answer?" (Self-check Q10.)
  • fetch() without the nonce: "not logged in" on a screen where Maria plainly is. Coach: "Which header proves the request comes from your own page?" (Self-check Q12; lesson quiz Q2.)
  • The account password with --user: 401 rest_not_logged_in, indistinguishable from a typo in an application password. Coach: "Which password did you create for this program? Users > Profile: was it ever used?"

Checks for understanding

Ask these out loud during the demo and the lab:

  • Where do the totals of a collection travel? Answer: in the headers X-WP-Total and X-WP-TotalPages (and Link for the neighbors), so the body stays a plain list.
  • Cookie without a nonce, cookie with a wrong nonce: what does each get? Answer: treated as anonymous (401 for anything protected); 403 rest_cookie_invalid_nonce.
  • Devon gets rest_cannot_edit. 401 or 403, and what does it mean? Answer: 403: WordPress knows him and his role says no.
  • Why one application password per program? Answer: revoking one (a lost laptop, a retired script) cuts off exactly that program.

Workbook self-check, items Q7 to Q12 (learners do them at the end of the block or at home).

Answers: Q7 C) 401 rest_forbidden_context; Q8 X-WP-TotalPages: 2; Q9 A) 403 rest_cookie_invalid_nonce: the page must fetch a fresh nonce; Q10 D) _fields removed _links, so there was nothing to follow, and _embedded is cut off too; Q11 B) WP_ENVIRONMENT_TYPE is local; elsewhere WordPress offers them only on HTTPS; Q12 The REST nonce (X-WP-Nonce) for the logged-in user, and the API's root URL (also _locale=user, a JSON body and the server's error object on failure).
