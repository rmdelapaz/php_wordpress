Lessons

8.3

Internationalization, Accessibility & Distribution

By the end you can
  • Generate a POT file with wp i18n make-pot, write translator-friendly strings, and produce .mo, .l10n.php and JavaScript .json translations with WP-CLI
  • Explain how WordPress 7.1 finds a plugin's translations, for PHP (Domain Path) and for scripts (wp_set_script_translations() and block.json)
  • Check a theme and its blocks for accessibility with contrast ratios, a keyboard walk and an automated axe audit, and say what automated checks miss
  • Prepare a plugin for distribution: a valid readme.txt, version numbers, the directory guidelines, a release ZIP without development files, and a clean Plugin Check report
  • Write an uninstall routine that removes content only when an administrator has opted in
Key ideas
  • i18n is your code (translation functions, one text domain); l10n is translation files; a11y is a quality of every page.
  • Translator-friendly strings: whole sentences, numbered placeholders, a translators comment, _n() for counts, _x() for ambiguous words, literals only; escape translations too.
  • make-pot → POT → PO → make-mo, make-php, make-json --no-purge. Since 6.8, Text Domain and Domain Path are enough for PHP; scripts need wp_set_script_translations() (block.json's textdomain for blocks) and a JSON named after the MD5 of the script's path.
  • Accessibility: contrast computed (4.5:1, 3:1), a keyboard walk (order, visible focus), axe or Lighthouse; then a screen reader. Tools find perhaps a third of the problems.
  • Distribution: a valid readme.txt, consistent versions, honest requirements, ABSPATH guards, documented external services, Plugin Check; a ZIP without development files, built with a production autoloader.
  • Uninstall deletes content only on the administrator's opt-in, and registers what it needs: the plugin is not loaded.
Worked example: a plural and its comments

_n() chooses the form for a count; the language's plural rule decides how many forms there are. On your site, in English:

wp eval 'echo esc_html( sprintf( _n( "%d seat", "%d seats", 1, "pagesco-books" ), 1 ) ), " | ", esc_html( sprintf( _n( "%d seat", "%d seats", 20, "pagesco-books" ), 20 ) ), "\n";'
1 seat | 20 seats

How many strings of the plugin carry a translators comment? Count them in a fresh POT (in /tmp, so nothing changes):

wp i18n make-pot wp-content/plugins/pagesco-books /tmp/pagesco-w.pot --exclude=src/blocks,tests > /dev/null
grep -c '^#. translators:' /tmp/pagesco-w.pot
rm /tmp/pagesco-w.pot
14

Every one of them has a placeholder; make-pot warns about each placeholder string without one.

8.4

Deployment & Maintenance

By the end you can
  • Choose a hosting type for a WordPress project by what it needs, and explain how code, content and configuration move between development, staging and production
  • Keep a WordPress project's own code in Git with a .gitignore, and build release files from a tagged commit with composer install --no-dev, npm ci, npm run build and the plugin ZIP
  • Move a database with wp db export, wp db import and wp search-replace, including serialized values and a plugin's own tables
  • Configure WordPress for production: debugging and development mode off, the environment type, secrets outside the code, a real cron job, file editing disabled and a least-privilege database account
  • Back up a site and prove the backup with a restore, deploy an update, and keep a maintenance checklist
Key ideas
  • Code goes up, content comes down, configuration stays. A Site Editor change on the live site is content.
  • Production: WP_DEBUG off and errors only in a log, WP_ENVIRONMENT_TYPE production, no WP_DEVELOPMENT_MODE, DISALLOW_FILE_EDIT, DISABLE_WP_CRON with a real cron job, secrets on the server only; raise the theme's Version with each release.
  • Git tracks only your own source: a .gitignore that ignores everything and lets your folders back in; tag every release; never deploy the repository.
  • Release builds from a tag in a clean folder: composer install --no-dev --optimize-autoloader, npm ci, npm run build, npm run plugin-zip.
  • Migrations: wp search-replace (serialized data), --all-tables-with-prefix, --skip-columns=guid, --dry-run first, --export for a launch file; after importing a development database, reset passwords and remove application passwords.
  • Running a live site: a cron job, daily backups kept elsewhere and proven by a restore, updates through staging, a least-privilege database account, a maintenance checklist.
Worked example: production settings, asked

Three of the production settings, asked of your development site:

wp eval 'printf( "%s | %s | %s\n", wp_get_environment_type(), wp_get_development_mode(), defined( "DISALLOW_FILE_EDIT" ) ? "no file editor" : "file editor on" );'
local | theme | file editor on

And one that core derives from the environment: application passwords work without HTTPS only on local sites:

wp eval 'var_dump( wp_is_application_passwords_available() );'
bool(true)

On the rehearsal server the same commands print production, an empty development mode, no file editor, and false (recorded in the lesson, Step 5).
