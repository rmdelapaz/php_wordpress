8.3 · Internationalization, Accessibility & Distribution: self-check

Q1
make-pot prints Warning: Multiple placeholders should be ordered. for __( 'Showing %s of %s books', 'pagesco-books' ). What is the fix?
A) Nothing: it is only a warning, and the POT file was written
B) Split it into two strings, one per number
C) Numbered placeholders, 'Showing %1$s of %2$s books', with a translators comment naming both
D) Use _n() instead of __()
Why: With %1$s and %2$s a language can put the numbers in another order (the lab's Spanish translation does: "De %2$s libros, se muestran %1$s"); the comment tells the translator what each number is. make-pot writes the file anyway and exits 0, which is why its warnings scroll by unnoticed.
A is wrong: The string ships untranslatable in languages with another word order.
B is wrong: Fragments are worse: a translator cannot know how they join.
D is wrong: _n() chooses a plural form; it does not number placeholders.
Q2
The Book Card's editor script is build/blocks/book-card/index.js. In the WP-CLI container this prints its hash. Which file holds its Spanish strings?
printf '%s' 'build/blocks/book-card/index.js' | md5sum | cut -d' ' -f1
languages/pagesco-books-es_ES-f9065c2ff2c4d291b5b56d1be2a45f3f.json
Why: WordPress looks for the JSON whose name contains the MD5 of the script's path relative to the plugin; make-json computes it from the PO's #: references, which is why the POT must point at the built file (--exclude=src/blocks). Lesson 8.3's languages/ folder has exactly this file.
Q3
The contrast script printed slate on paper 5.8:1 AA. What does that allow?
A) Normal-size text in slate on paper meets WCAG AA (4.5:1), but not AAA (7:1)
B) Only large text: normal text needs 7:1
C) Nothing: anything under 7:1 fails WCAG
D) Slate is safe on every background of the palette
Why: AA needs 4.5:1 for normal text and 3:1 for large text and control outlines; 7:1 is AAA. The pair passes AA, which is what most contracts mean. Exercise 2 shows slate failing on ink and on oxblood: a ratio belongs to a pair, not to a color.
B is wrong: 4.5:1 is the AA limit for normal text; 3:1 for large.
C is wrong: AAA is the stricter level; AA is the usual target.
D is wrong: Slate on ink is 2.4:1 and slate on oxblood 1.5:1 (Exercise 2).
Q4
Why does the new uninstall.php read the opt-in with get_option( 'pagesco_books_settings', array() ) and not with Settings::get( 'delete_data' )?
A) get_option() is faster
B) Settings::get() would translate the value
C) uninstall.php runs after the option is deleted
D) During uninstall the plugin is not loaded: its classes, post type and taxonomy are not there
Why: WordPress runs uninstall.php without booting the plugin. That is also why the file registers the genre taxonomy before get_terms() (Common Mistake 2: invalid_taxonomy, and five orphaned genres). An empty row means delete_data is missing, which means off.
A is wrong: Both read the same autoloaded row; speed is not the point.
B is wrong: Settings::get() translates nothing about delete_data.
C is wrong: uninstall.php reads the option first and deletes it near the end.
Q5
Which of these must NOT be in the release ZIP of Pages & Co. Books?
A) build/blocks/blocks-manifest.php
B) phpcs.xml.dist
C) languages/pagesco-books-es_ES.l10n.php
D) vendor/autoload.php
Why: Development files (rulesets, phpunit.xml.dist, .wp-env.json, tests/) do not ship: Plugin Check reports them (application_detected, hidden_files), and the lab release_check.sh fails a ZIP that contains them. The build, the translations and the autoloader are what the plugin runs.
A is wrong: Without the manifest no block is registered.
C is wrong: The Spanish translation is part of the release.
D is wrong: The plugin requires it on every load; only the development packages must stay out.
Q6
What does --no-purge change in wp i18n make-json pagesco-books-es_ES.po --no-purge?
It keeps the JavaScript strings in the PO file; without it make-json moves them into the JSON files and removes them from the PO
Why: Strings used in both PHP and JavaScript ("Mark sold out") would otherwise go missing from the next .mo, and the source PO loses entries.

8.4 · Deployment & Maintenance: self-check

Q7
Maria changed the header in the live site's Site Editor. You deploy theme 1.2.0 with a new parts/header.html. What do visitors see?
A) The new header from the theme's file
B) Maria's header: Site Editor changes are saved in the database, and they win over the theme's files
C) Both headers, one above the other
D) An error until someone resets the template part
Why: Code goes up, content comes down: an edit in the Site Editor on the live site is content (a wp_template_part post). Changes that should become code are exported into the theme, committed and deployed (Lesson 3.3); then the database copy is reset.
A is wrong: Only if the template part had never been edited on the live site.
C is wrong: WordPress uses one version of a template part.
D is wrong: Nothing is broken; the database version simply wins.
Q8
On the course site after Lesson 8.3: what does this print, and which table makes the difference?
echo "$(wp db tables | wc -l) $(wp db tables --all-tables-with-prefix | wc -l)"
12 13: wp_pagesco_events, the plugin's own table, which WordPress does not register
Why: wp db tables and wp search-replace work on the registered (core) tables by default; --all-tables-with-prefix adds the plugin's table. A launch export without it has 12 tables, and the live Events page says "No events are scheduled" (Common Mistake 2; the debug handout debug_launch_check.sh).
Q9
Why does every migration command in Lesson 8.4 say --skip-columns=guid?
A) The GUID is an identifier feed readers use to recognize posts, not a link: it must not change
B) GUID columns are serialized and would break
C) The guid column is too long for search-replace
D) WordPress rewrites GUIDs itself on the first request
Why: http://localhost:8080/?p=30 looks like a URL but identifies the post; changing it makes feed readers show every post as new. The launch database keeps 34 GUIDs with the old address, and that is right.
B is wrong: The guid column holds plain strings.
C is wrong: Length is not the issue.
D is wrong: WordPress never rewrites GUIDs.
Q10
The project's .gitignore says !/themes/, then /themes/*, then !/themes/pagesco/. Why not just !/themes/pagesco/ after /*?
A) Git reads .gitignore from the bottom up
B) The order does not matter; it is only for readability
C) Without the first line Git would also track Twenty Twenty-Five
D) Git cannot let a file back in when its folder is ignored: the folder is let in, its contents ignored again, then the one subfolder let in
Why: /* ignores the themes folder itself, so a rule for something inside it is never even read. The three-line pattern is the documented way. git check-ignore -v names the line that ignores a file when you wonder why it is missing.
A is wrong: Git reads it top to bottom; the last matching rule wins.
B is wrong: With only the last line, themes/pagesco/ stays ignored.
C is wrong: Twenty Twenty-Five is ignored by /themes/* either way.
Q11
In a clean copy of the tagged plugin (git archive), which Composer command builds the production autoloader, and what does it leave out?
composer install --no-dev --optimize-autoloader: the development packages (PHPUnit, PHPCS), so vendor/composer has no autoload_files.php that requires them
Why: The working copy's autoloader requires files from development packages on every load (deep_copy.php, PHPUnit's Functions.php, the polyfills); a ZIP without those packages dies with "Failed opening required" (Lesson 8.3's Mistake 3). --optimize-autoloader writes a class map.
Q12
On the rehearsal server the account pagesco_app has no LOCK TABLES right. What happens to wp db export "$BACKUP"?
A) It works: WP-CLI locks nothing
B) It asks for the root password
C) It fails with error 1044, and leaves a small header-only file under the backup's name
D) It exports only the tables the account may lock
Why: mariadb-dump locks each table while it reads it. The recorded run shows the error and an 831-byte file: a file in the backup folder is not a backup; its size and a restore test are what count. The lesson grants exactly LOCK TABLES, as root, and then proves the backup by restoring a deleted book.
A is wrong: wp db export runs mariadb-dump, which uses LOCK TABLES.
B is wrong: WP-CLI uses wp-config.php's account and asks nothing.
D is wrong: It stops at the first table it cannot lock.

The Lesson Pages' Own Quick Quizzes

Lesson 8.3 · Internationalization, Accessibility & Distribution
  1. C 'Showing %1$s of %2$s books' with a translators comment naming both numbers: A whole sentence with numbered placeholders and a translators comment: the translator sees what each part is and may change the order.
  2. A The MD5 hash of the script's path in the plugin, assets/js/stock-widget.js: WordPress hashes the path of the script it is about to print, relative to the plugin, and looks for a JSON file with that hash; make-json takes the paths from the PO references.
  3. B The page passed the rules a machine can check; keyboard and screen reader tests are still needed: Automated rules catch a part of the problems, such as markup and contrast; focus visibility, meaningful alternative text, reading order and screen reader experience need people to test.
  4. C Because the plugin is not loaded, so the genre taxonomy is not registered: During uninstall the plugin is not loaded, so its taxonomy is not registered, and get_terms() rejects unregistered taxonomies with invalid_taxonomy; register it in uninstall.php first.
  5. B Because the development autoloader requires files from packages the ZIP does not contain: With development packages installed, the autoloader requires some of their files on every load; the ZIP does not contain them, so the plugin would die with a fatal error on the client's site.
Lesson 8.4 · Deployment & Maintenance
  1. B Only the plugin ZIP built from the release tag: Code goes up, content comes down: after the launch the live database is the original, so an update deploys only the release files built from the new tag.
  2. C The plugin's own events table: By default WP-CLI works on the tables WordPress registers; the plugin's wp_pagesco_events table is not one of them, so the export silently leaves it out.
  3. A The new pattern stays unknown until the cached pattern list expires: Without development mode WordPress caches the theme's pattern list in a site transient for the current Version, for up to 30 minutes; a new Version makes the cache invalid at once.
  4. C Read and change the shop's database, and nothing beyond it: Least privilege limits the damage: the account can read and change the shop's own database, which is serious, but it reaches no other database and cannot manage users or the server.
  5. B It never runs: the event stays scheduled and nothing starts it: With page-view spawning off, nothing runs due events until something calls wp-cron.php or wp cron event run: the job waits, scheduled, forever.

Exit Ticket

  1. Code, content, configuration: the plugin or theme (Git, a tagged release, a ZIP deployed: up); the books, events and pages (the database: once at launch, then created live; copies come down); wp-config.php's secrets and the supplier's key (written per environment, never copied).
  2. String rules: any two of: whole sentences with placeholders; numbered placeholders when there are several; a translators comment; _n() for counts; _x() for ambiguous words; literal strings only; escape the translation.
  3. Hard requirements: accept any honest pair with the right layer; the brief's own table ("Where each requirement is handled") is the reference for the conversation in Session 17.

Common Wrong Answers and What They Reveal

  • Q1 A ("only a warning"). Treats warnings as noise. Show the lab's Spanish line that reorders the numbers.
  • Q3 C ("under 7:1 fails"). Mixes AA and AAA.
  • Q5 A or D. Thinks build/ or the autoloader are development files; they are what runs.
  • Q7 A ("the new header"). The code/content split has not landed: show Lesson 3.2's wp_template_part posts.
  • Q9 B ("serialized"). Confuses GUIDs with options; the guid column is a plain string.
  • Q12 A ("it works"). Has never restored a backup; restore_drill is the cure.
