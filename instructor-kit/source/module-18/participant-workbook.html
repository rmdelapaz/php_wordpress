9.1

Final Project: Launch the Pages & Co. Website

By the end you can
  • Turn a client's brief into data, rules, routes, blocks and screens, and decide where each rule is enforced
  • Build a feature through every layer of the course: a custom table, settings, a service class with a custom hook, REST routes with real permission callbacks, form handlers, a staff screen, a dynamic and an interactive block, and a theme pattern with live data
  • Make it secure and private by default: nonces and capabilities on every change, ownership in every query, escaping, and personal data kept no longer than needed
  • Prove the feature with coding standards, PHPUnit tests, a smoke test from outside, accessibility checks and a performance measurement
  • Release it from a tagged commit and deploy it as code only, then present your work against a rubric
Key ideas
  • Prove it four ways: coding standards (a documented exception, not a silenced sniff), unit tests that would catch the dangerous bug, a smoke test from outside, numbers before and after.
  • A new feature is a minor version: 1.2.0 everywhere a version lives; the theme too when its templates or patterns change (the live pattern cache).
  • Release from a tag, build in a clean copy, and check the ZIP before upload: the new folder is in it and its autoloader finds the new classes.
  • Code only: back up, install the ZIPs, let maybe_upgrade() create the table; create on the live site the content the feature needs (My holds, a test customer). Never the development database.
  • Showcase: the problem, the browser, the rules, the proof, one decision you would defend, one thing next.

9.2

Next Steps: Headless, AI in Core & Your Career

By the end you can
  • Explain what "headless" WordPress means, when it is worth its costs, and build a small front end on your own REST routes that pages through results, handles HTML fields correctly and works across origins
  • Describe what WordPress 7.0 and 7.1 ship for AI (the AI client, wp_supports_ai(), the Connectors screen) and what they do not (a model, a provider, an AI feature), and write code that degrades gracefully when no provider is set up
  • Show how an ability such as pagesco/check-stock becomes a tool an AI model can call, and why its permission callback still decides
  • Find your way into contributing to WordPress: the Make teams, Trac and GitHub, Learn WordPress, meetups and WordCamps
  • Choose a career direction, turn the Pages & Co. project into a portfolio piece without leaking secrets, and keep up with WordPress releases
Key ideas
  • Headless keeps WordPress for content and rules and moves the front end elsewhere; it pays for apps and many front ends and costs previews, plugins' front ends and a second deployment.
  • A front end reads every page (X-WP-TotalPages), knows which fields are HTML, puts text on the page with textContent, and relies on permission callbacks, not CORS.
  • WordPress 7 ships AI plumbing: wp_ai_client_prompt(), wp_supports_ai(), the Connectors screen; no model, no provider, no core feature. Every result is text or a WP_Error.
  • using_abilities() turns abilities into tools a model may call; the resolver runs them as the current user, so permission callbacks and input schemas still decide.
  • Contribute with evidence (make.wordpress.org, Trac and GitHub, Learn WordPress, meetups); publish code, never secrets (search the whole history first).
Worked example: what another origin may read

A front end on another origin asks the shop's API. What may that page read?

curl -s -I -H 'Origin: http://localhost:3000' http://localhost:8080/wp-json/pagesco/v1/books | tr -d '\r' | grep -i '^HTTP\|^access-control\|^x-wp-total'
HTTP/1.1 200 OK
Access-Control-Expose-Headers: X-WP-Total, X-WP-TotalPages, Link
Access-Control-Allow-Headers: Authorization, X-WP-Nonce, Content-Disposition, Content-MD5, Content-Type
X-WP-Total: 11
X-WP-TotalPages: 2
Access-Control-Allow-Origin: http://localhost:3000
Access-Control-Allow-Methods: OPTIONS, GET, POST, PUT, PATCH, DELETE
Access-Control-Allow-Credentials: true

WordPress repeats the page's origin in Access-Control-Allow-Origin, so any origin may read public data, and exposes the paging headers (X-WP-Total, X-WP-TotalPages) so the page can read every page of results. None of this lets a page do what its visitor may not: the permission callbacks decide.
