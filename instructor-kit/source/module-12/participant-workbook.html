6.2

Static Blocks: Attributes, Controls & Supports

By the end you can
  • Declare attributes in block.json and choose where each one is stored: in the saved HTML (source and selector) or in the block's comment
  • Make text editable on the canvas with RichText and save it with RichText.Content
  • Add settings to the block sidebar with InspectorControls and components from @wordpress/components
  • Opt into color, spacing and typography block supports and read the classes and styles they save
  • Explain block validation, and change save safely with a deprecated entry and migrate
Key ideas
  • Attributes with a source and selector live in the saved HTML (title, author, a link's href); attributes without one live in the block comment, and only when they differ from their default. parse_blocks() sees only the comment.
  • RichText edits text on the canvas (allowedFormats), RichText.Content saves it; setAttributes() is the only way to change attributes.
  • InspectorControls puts @wordpress/components controls into the sidebar's Settings tab; BlockControls into the toolbar. Both live in edit.
  • Block supports (color, spacing, typography) add attributes, controls, classes and styles through useBlockProps() / useBlockProps.save(), with the theme's presets saved as slugs.
  • Validation: the editor re-runs save() and compares it with the stored HTML. save() must be pure: no translations, dates or random values.
  • Changing save() for existing content needs a deprecated entry: the old attributes, supports and save, newest first, with an optional migrate().
  • In PHP, a static block is finished HTML: read it with the HTML API, or store the value in the comment, or make the block dynamic.
Worked example: the supports, and the style engine

Supports add attributes, controls, classes and styles without code of yours. Ask the registry which supports the finished card declares (the site after Lesson 6.2):

wp eval 'echo wp_json_encode( WP_Block_Type_Registry::get_instance()->get_registered( "pagesco/book-card" )->supports ), "\n";'
{"html":false,"color":{"background":true,"text":true,"link":true},"spacing":{"margin":true,"padding":true},"typography":{"fontSize":true,"lineHeight":true}}

A padding chosen in the Styles tab is saved in the comment as var:preset|spacing|medium and printed as an inline style. The style engine does that translation; ask it directly:

wp eval 'echo wp_style_engine_get_styles( array( "spacing" => array( "padding" => array( "top" => "var:preset|spacing|medium", "bottom" => "var:preset|spacing|medium" ) ) ) )["css"], "\n";'
padding-top:var(--wp--preset--spacing--medium);padding-bottom:var(--wp--preset--spacing--medium);

The value points at the theme's spacing preset (a CSS custom property), never at a number of pixels: change the preset in theme.json and every block that uses it follows, exactly like the color slugs.

6.3

Dynamic Blocks & Block Bindings

By the end you can
  • Explain when a block should be dynamic, and what a dynamic block stores in post_content
  • Render a block on the server with render.php: attributes, a WP_Query through get_posts(), get_block_wrapper_attributes(), and escaping
  • Preview a dynamic block in the editor with ServerSideRender, and fill its controls from the REST API through @wordpress/core-data
  • Offer ready-made versions of a block as variations, generated in PHP
  • Bind core blocks to post meta with core/post-meta, and write a custom binding source with register_block_bindings_source()
Key ideas
  • A dynamic block stores only its comment. "render": "file:./render.php" makes WordPress run the PHP on every view, with $attributes, $content and $block; the build copies render.php into build/.
  • In render.php treat attributes as input: check optional ones with isset() (WordPress fills in defaults only for attributes that have one), cast, clamp, sanitize; query with get_posts(); start the wrapper with get_block_wrapper_attributes(); escape what you print.
  • An attribute without a default can mean "use the site's setting": the Book List's count follows Books per list.
  • ServerSideRender previews render.php through the block-renderer REST route; @wordpress/core-data fills controls with the site's data.
  • Variations are presets of a block; "variations": "file:./variations.php" builds them in PHP, only when something asks.
  • Block bindings connect core blocks' attributes to sources: core/post-meta returns raw values of registered, public meta; register_block_bindings_source() with uses_context gives formatted ones. They fail silently to the fallback.
Worked example: a dynamic block rendered from PHP

A dynamic block can be rendered anywhere PHP runs, with any attributes: do_blocks() finds the comment and runs render.php, as a page view does (the site after Lesson 6.3):

wp eval 'echo do_blocks( "<!-- wp:pagesco/book-list {\"genre\":\"dystopian\",\"count\":2} /-->" );'
<ul class="wp-block-pagesco-book-list">
			<li class="wp-block-pagesco-book-list__item"><span class="pagesco-book"><a href="http://localhost:8080/books/1984/">1984</a> by George Orwell, <span class="pagesco-book__price">$9.99</span> <span class="pagesco-book__stock">In stock</span></span></li>
			<li class="wp-block-pagesco-book-list__item"><span class="pagesco-book"><a href="http://localhost:8080/books/brave-new-world/">Brave New World</a> by Aldous Huxley, <span class="pagesco-book__price">$9.49</span> <span class="pagesco-book__stock">In stock</span></span></li>
	</ul>

Two of the three dystopian books, in title order, each printed by BookShortcode::render(). The variations come from variations.php, built from the genre terms:

wp eval 'foreach ( WP_Block_Type_Registry::get_instance()->get_registered( "pagesco/book-list" )->get_variations() as $v ) { if ( "new-arrivals" !== $v["name"] ) { echo $v["title"], " "; } } echo "\n";'
Classic Books Dystopian Books Fantasy Books Fiction Books Science Fiction Books

One variation per genre, generated in PHP when something asks for them. Add a genre on Books > Genres and the list grows without a build.

Glossary

TermMeaning
attributeA piece of a block's data, declared in block.json with a type (and a source, a default)
source / selectorWhere an attribute is read back from the saved HTML (html, rich-text, text, attribute) and which element
block comment<!-- wp:name {...} -->: the block's name and its source-less, non-default attributes as JSON
RichTextThe editable text component; RichText.Content prints its value in save
InspectorControls / BlockControlsRender controls into the sidebar's Settings tab / the block toolbar
block supportsCore features a block opts into in block.json (color, spacing, typography, align...)
validationThe editor's check that save() still produces the stored HTML
deprecationAn entry in deprecated describing an older attributes + supports + save, with optional migrate
dynamic blockA block whose HTML render.php (or a render_callback) makes on every view; it stores only its comment
get_block_wrapper_attributes()The wrapper's escaped class and style attributes in PHP (supports included)
ServerSideRenderAn editor component that previews a block with the server's render.php
variationA named preset of a block's attributes, listed in the inserter
block binding / sourceA block attribute replaced on every view by a source's value (core/post-meta, pagesco/book)
