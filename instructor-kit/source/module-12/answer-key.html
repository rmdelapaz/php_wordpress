6.2 · Static Blocks: Attributes, Controls & Supports: self-check

Q1
A block attribute is declared "url": { "type": "string", "source": "attribute", "selector": "a", "attribute": "href" }. Where is the URL stored once the post is saved?
A) In the block comment, as JSON
B) In post meta, under the key url
C) In the saved HTML: the href of the first <a> inside the block
D) Nowhere: the editor asks for it again
Why: An attribute with a source lives in the HTML that save() wrote, and the editor finds it again through the selector. Only attributes without a source go into the comment (and only when they differ from their default).
A is wrong: Only source-less attributes such as headingLevel go into the comment.
B is wrong: Post meta needs a binding or code of your own; "source": "meta" is the deprecated old way.
D is wrong: Then every saved card would lose its link.
Q2
On the course site after Lesson 6.2: what does this print?
wp eval 'echo wp_json_encode( parse_blocks( "<!-- wp:pagesco/book-card {\"showBadge\":false} --><div class=\"wp-block-pagesco-book-card\"><h3 class=\"wp-block-pagesco-book-card__title\">Emma</h3></div><!-- /wp:pagesco/book-card -->" )[0]["attrs"] ), "\n";'
{"showBadge":false}
Why: parse_blocks() returns the comment's JSON only. The title Emma is sourced from the HTML, so it is not in attrs; showBadge is there because false differs from its default, true. A card with the badge on would print [].
Q3
Cards are already on the site. Which change to the Book Card needs a new deprecated entry?
A) A new rule in style.scss that rounds the corners more
B) A new sidebar control in edit.js only
C) Wrapping the author in a <cite> in save()
D) A new attribute whose default makes save() print nothing new
Why: Validation compares the stored HTML with what the CURRENT save() returns for the same attributes. A new element changes that HTML, so every stored card turns invalid until a deprecation describes the old save().
A is wrong: CSS is not part of the stored HTML.
B is wrong: edit is never compared with anything.
D is wrong: Lesson 6.2's url and headingLevel were exactly that: no deprecation needed.
Q4
A designer wants the card's heading level in the toolbar that floats above the selected block, like core's Heading block. Where does the control go?
A) Inside <BlockControls> in edit
B) Inside <InspectorControls> in save
C) Inside <InspectorControls> in edit
D) In block.json under supports
Why: BlockControls fills the block toolbar, InspectorControls the sidebar's Settings tab; both belong in edit, which is the editor's interface. save never renders controls.
B is wrong: save returns the stored HTML; controls there would be saved into the post.
C is wrong: That puts it in the sidebar, where the lesson's Card settings panel is.
D is wrong: supports switch on core's own features (colors, spacing); there is no support for a custom control.
Q5
An editor picks the theme's Sage background for a card. What does the post store?
A) The hex color in an inline style
B) The class has-sage-background-color in the HTML and "backgroundColor":"sage" in the comment
C) A row in wp_options
D) Nothing: the theme decides at view time
Why: Preset choices are saved as a slug and a class; the theme's global styles define .has-sage-background-color. Change Sage's hex value in theme.json and every sage card follows, which is why supports beat hand-made color attributes.
A is wrong: Inline styles are for values that are not presets, such as a custom padding per side.
C is wrong: Block settings are content: they live in post_content.
D is wrong: The choice is the editor's, so it has to be stored with the card.
Q6
Why does the course write the badge text Staff pick as a plain string in save() instead of __( 'Staff pick', 'pagesco-books' )?
save() must return the same HTML for the same attributes in every language: a translated string makes cards invalid as soon as someone edits in another locale
Why: Validation re-runs save() in the editor of whoever opens the post. Text in save is content: a literal, or an attribute. Translate edit's labels and placeholders freely (Common Mistake 3).

6.2 · Static Blocks: Attributes, Controls & Supports: predict, then run

P1
Predict the output, then run it.
wp eval 'echo wp_json_encode( parse_blocks( "<!-- wp:heading --><h2 class=\"wp-block-heading\">New this week</h2><!-- /wp:heading -->" )[0]["attrs"] ), "\n";'
[]
Why: A heading at its default level 2 stores nothing in the comment, and its text is rich-text sourced from the h2: [] (an empty array as JSON). Save the same heading as an h3 and you would get {"level":3}.
P2
Predict the output, then run it.
wp eval 'echo wp_json_encode( WP_Block_Type_Registry::get_instance()->get_registered( "core/paragraph" )->attributes["content"] ), "\n";'
{"type":"rich-text","source":"rich-text","selector":"p","role":"content"}
Why: Core declares the paragraph's text with the source rich-text and the selector p: it lives in the HTML. role: content marks it as the block's content (the editor's content-only editing and pattern overrides use it).

6.3 · Dynamic Blocks & Block Bindings: self-check

Q7
The Book List already sits on twenty pages. You change render.php so every item gets a second line. What else must you do?
A) Add a deprecated entry to the block
B) Open and update each of the twenty pages
C) Run npm run build (render.php is copied into build/), then nothing: every page follows on its next view
D) Bump the block's version so caches notice
Why: A dynamic block stores only its comment, so there is no stored HTML to validate. The build copies render.php into build/blocks/book-list/, the file WordPress runs; after that, the next view of every page uses it.
A is wrong: Deprecations describe old save() output; a dynamic block saves none.
B is wrong: Nothing in the pages changed: they hold only the comment.
D is wrong: The version only changes the ?ver= of the block's CSS and JS.
Q8
On the course site after Lesson 6.3 (six Classic books): what does this print?
wp eval 'echo substr_count( do_blocks( "<!-- wp:pagesco/book-list {\"genre\":\"classic\",\"count\":4} /-->" ), "<li class=" ), "\n";'
4
Why: do_blocks() runs render.php with the comment's attributes, exactly as a page view does. count 4 is inside the 1 to 24 clamp, and the genre filter is a tax_query on the slug, so four of the six Classic books.
Q9
In render.php the wrapper is <ul <?php echo get_block_wrapper_attributes(); ?>>, with no escaping function around it. Why is that safe?
A) It is not: wrap it in esc_html()
B) Block attributes are always numbers
C) Only administrators can add blocks
D) get_block_wrapper_attributes() returns attributes that are already escaped (class and style from the supports)
Why: It is the PHP twin of useBlockProps.save(): it builds the class and style attributes and escapes them itself. Core's own blocks print it the same way. Everything else render.php prints is escaped where it is printed.
A is wrong: esc_html() would turn the quotes into entities and break the markup.
B is wrong: Attributes can be strings typed by anyone who can edit posts (genre, for example).
C is wrong: Any editor or author can insert blocks; escaping is about the data, not the person.
Q10
A list item is bound to core/post-meta with the key pagesco_in_stock. What does it show on The Great Gatsby's page (sold out)?
A) Sold out
B) The fallback text of the list item
C) false
D) Nothing: an empty list item
Why: core/post-meta returns the raw stored value: false arrives as an empty string, so the list item is empty (Dune's would say 1). Binding is not formatting; that is why the shop writes its own source, pagesco/book.
A is wrong: That wording comes from the shop's own source, not from core/post-meta.
B is wrong: The fallback shows only when the source returns null (an unknown or protected key).
C is wrong: PHP's false becomes an empty string when it is printed.
Q11
You register a binding source without uses_context. What does a bound paragraph in single-book.html show?
A) Its fallback text, with no error
B) A PHP warning about the missing context
C) The value for the first book in the catalog
D) The value for the post being shown, as usual
Why: A paragraph never asks for postId on its own. uses_context makes WordPress hand postId and postType to every block bound to the source; without it the callback sees no post, returns null, and the fallback stays: silently.
B is wrong: Bindings fail silently by design.
C is wrong: The callback has no post ID at all.
D is wrong: Only with uses_context.
Q12
On the course site after Lesson 6.3: what does this print (book 40 is Animal Farm, published 1945-08-17)?
<?php
$parsed = parse_blocks( '<!-- wp:paragraph {"metadata":{"bindings":{"content":{"source":"pagesco/book","args":{"field":"year"}}}}} --><p>First published</p><!-- /wp:paragraph -->' )[0];
$block  = new WP_Block( $parsed, array( 'postId' => 40, 'postType' => 'book' ) );

echo wp_strip_all_tags( $block->render() ), "\n";
First published in 1945
Why: new WP_Block( $parsed, $context ) renders the paragraph with a made-up context, so pagesco/book's year field runs for book 40 and replaces the fallback. It is Lesson 6.3's Exercise 1 technique, the way a PHPUnit test would check a source (Lesson 8.1).

6.3 · Dynamic Blocks & Block Bindings: predict, then run

P3
Predict the output, then run it.
wp eval 'echo substr_count( do_blocks( "<!-- wp:pagesco/book-list {\"count\":30} /-->" ), "<li class=" ), "\n";'
11
Why: render.php clamps count to 1 to 24, and the catalog has eleven books, so all eleven print. The clamp protects the query from a huge number typed into a comment by hand.
P4
Predict the output, then run it.
wp eval 'echo get_post_meta( 37, "pagesco_in_stock", true ) === "" ? "empty string" : "something else", "\n";'
empty string
Why: Booleans are stored as '1' and '' (the empty string), which is why core/post-meta leaves an empty list item for Gatsby and Catcher, and why Exercise 3 compares pagesco_in_stock with '1'.

The Lesson Pages' Own Quick Quizzes

Lesson 6.2 · Static Blocks: Attributes, Controls & Supports
  1. A In the saved HTML, inside the element the selector points to: A sourced attribute lives only in the saved HTML; the editor reads it back with the selector, and the comment JSON stays free of it.
  2. B A ToggleControl inside InspectorControls, in edit: Whatever edit renders inside InspectorControls appears in the sidebar while the block is selected; PanelBody groups it into a collapsible panel.
  3. C Spreading useBlockProps.save() onto the wrapper in save: Supports add their classes and styles through useBlockProps.save(); a wrapper without it saves none of them.
  4. C {"headingLevel":4}: parse_blocks returns exactly the comment JSON: the sourced title stays in the HTML, and defaults such as showBadge are not filled in.
  5. B A deprecated entry with the previous attributes, supports and save: A deprecated entry with the old attributes, supports and save lets the editor recognize existing cards and open them as valid blocks of the new version.
Lesson 6.3 · Dynamic Blocks & Block Bindings
  1. B Only the block comment with its attributes: A dynamic block saves only its comment with the non-default attributes; render.php produces the HTML on every view.
  2. A 8: count has no default, so it is missing from the comment and render.php uses Settings::get( 'books_per_page' ), now 8.
  3. B The paragraph's fallback text: Keys starting with an underscore are protected; core/post-meta returns null for them, so the paragraph keeps its fallback text, silently.
  4. C Sold out: The context names book 37, the source reads pagesco_in_stock, finds it false and returns the formatted Sold out, which replaces the paragraph's content.
  5. C When something asks for the block's variations, such as the editor: block.json names the file, and WordPress requires it lazily when the variations are requested, for example by the editor through the block-types REST route.

Exit Ticket

  1. Title and level: the title in the saved HTML, inside the element its selector names; the heading level in the block comment, only when it is not the default 3.
  2. render.php and attributes: check optional attributes (isset() or a default in block.json), cast and clamp numbers, sanitize strings (sanitize_key() for a slug), and escape everything printed; start the wrapper with get_block_wrapper_attributes().
  3. A fallback on a book page: a misspelled meta key, a key not registered with show_in_rest or starting with an underscore (core/post-meta), a custom source without uses_context, or a source that returned null for that field.

Common Wrong Answers and What They Reveal

  • Q1 A ("in the comment"). Thinks every attribute is JSON. Show the stored Card test post: the URL is in the href, the comment is empty.
  • Q2 with the title in it. The same picture: parse_blocks() never reads the HTML. Run the command.
  • Q3 A or B. Thinks validation is about files. It compares stored HTML with save(): CSS and edit are never compared.
  • Q5 A ("the hex color"). Remembers inline styles; presets are classes and slugs, so the theme can change the color later.
  • Q7 A ("a deprecation"). Carries Lesson 6.2's rule over to dynamic blocks; there is no stored HTML to validate.
  • Q9 A ("wrap it in esc_html()"). Good instinct, wrong place: the function escapes its own output, and double escaping breaks the attribute.
  • Q10 A ("Sold out"). Confuses core/post-meta with the shop's source. Show Gatsby's first template version: an empty item.
