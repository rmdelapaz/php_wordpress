Session 12: Static and Dynamic Blocks

How to teach the session where the Book Card becomes a real block and the shop gets its first dynamic one: where a static block keeps each attribute and why its stored HTML is a contract, then a render.php that queries the catalog on every view and core blocks bound to the books' own data.

2 lessons 3 hrs session Lessons 6.2–6.3 Session 12 of 18 · Part 2

How to Use This Guide

  • Same rhythm for both lessons: frame (the goal and one mental model) → live demo (you type, they type along) → guided lab (a kit lab, new practice on the lesson's ideas) → start the lesson's own project. The lesson exercises, quiz and journal are homework.
  • Every command below was run on WordPress 7.1.3 / PHP 8.5 to produce the output printed under it: Lesson 6.2's demo on the site exactly as Lesson 6.1 left it (after:lesson_19), Lesson 6.3's on the site after Lesson 6.2 (after:lesson_20). Browser-only results (the editor's validation messages) are quoted from the lesson page, which recorded them in a real 7.1 editor. Ask for a prediction before every run.
  • This session is half JavaScript files the editor runs and half PHP the server runs. Learners copy the .js, .json and .scss files from the lesson pages (they are long, and the lessons explain them line by line); the room's time goes to the PHP side, the stored markup and the mental models, which are what people get wrong alone.
  • Labs live in labs/module-12/ (learners keep the folder in their project folder, next to compose.yaml): _starter files and folders are handouts, _solution files and folders are yours. The block labs need no Node: the Next Events block registers a block.json and a render.php from PHP and is tested with do_blocks().
  • Part 2, Session 4 of 10. Teal blocks are hands-on, amber blocks are watch-outs. Lesson codes (6.2, 6.3) match the course site.
The #1 risk of Session 12: the build eats the session

Both lessons change files that only matter after npm run build, and every laptop builds differently: native Node 24, the node:24 container, a stale npm start in another terminal. Ten learners with a missing build means ten editors saying "This block has encountered an error". Before: the warm-up's W3 to W5 are a build check; anyone whose ls wp-content/plugins/pagesco-books/build/blocks does not show the manifest gets a partner. In the room: you type every file, and the room may watch instead of typing (the files are on the lesson pages); what they must type is the PHP (render.php, BookBindings.php) and the commands. After: the two lesson projects need the built blocks; send the Before the Next Lesson checks home in writing.

Questions and answers
  1. W1 (Lesson 5.5). A shortcode callback ends with echo $html; instead of return $html;. What goes wrong? Answer: The HTML appears at the top of the content (wherever the filter runs), not where the shortcode is: shortcodes RETURN their output. The [pagesco_events] callback returns it.
  2. W2 (Lesson 5.5). Why does EventsTable::find() build its SQL with $wpdb->prepare() even though only the plugin calls it? Answer: Because the location comes from shortcode attributes, REST arguments (Lesson 7.2) and anyone who edits a post: every value goes through placeholders, every time.
  3. W3 (Lesson 6.1). Where does npm run build write, and which file does WordPress read to register the plugin's blocks? Answer: Into build/blocks/ (blocks-manifest.php and book-card on the projector site), and build/blocks/blocks-manifest.php, read by wp_register_block_types_from_metadata_collection() in the Blocks feature.
  4. W4 (Lesson 6.1). You add a second block folder in src/blocks/ and build. What PHP do you add to register it? Answer: None: the manifest lists every built block and the Blocks feature registers them all. Today's Book List proves it.
  5. W5 (Lesson 6.1). You edited src/blocks/book-card/edit.js, reloaded the editor, and nothing changed. First question? Answer: Did you build? The editor loads build/blocks/book-card/index.js. npm start rebuilds on every save while you work.

6.2

Static Blocks: Attributes, Controls & Supports

65 min
Objectives (from the lesson page)
  • Declare attributes in block.json and choose where each one is stored: in the saved HTML (source and selector) or in the block's comment
  • Make text editable on the canvas with RichText and save it with RichText.Content
  • Add settings to the block sidebar with InspectorControls and components from @wordpress/components
  • Opt into color, spacing and typography block supports and read the classes and styles they save
  • Explain block validation, and change save safely with a deprecated entry and migrate

10mFrame: the printed card with a sticky note; HTML or comment; the stored HTML is a contract

Mental model to say

Hold up a printed shop card: "A static block in a post is this card with a sticky note on the back. The printed side is the HTML: every visitor sees it, and the bookseller's words are printed right on it. The sticky note is the comment JSON: the few settings that are not words, such as heading level 2. The editor reads both to rebuild the card for editing. PHP can read the sticky note easily; to find the words it would have to read the print."

Then the board table: source + selector = in the HTML (title, author, the link's href); no source = in the comment, and only when it differs from the default (headingLevel, showBadge, colors). "Lesson 1.3's pagesco_book_card() took the same data as arguments. The difference is WHERE a block keeps them."

Then the contract: "Every time the editor opens a post it runs your CURRENT save() with the attributes it read and compares the result with the stored HTML. Different means invalid. Once content exists, save() may not change without describing the old version: a deprecation."

Three mistakes to expect, and how to coach each
  • Reading the card's text in PHP from $block['attrs'] (the demo's Mistake 1). Coach with the board: "Is the title on the sticky note or on the print?" The fixes: the HTML API, a comment attribute, or a dynamic block. (Self-check Q2, the debug handout.)
  • Changing save() and blaming the editor. "The block broke after my change." Coach: "What does the Console's first validation line say, and does content already exist?" Test posts can be deleted while developing; client content needs a deprecation. (Self-check Q3.)
  • Translating text in save() or using a too-wide selector (Mistakes 3 and 2). Coach: "Will save() return the same HTML in Spanish? Does the selected element contain only its own value?" Insert, save, RELOAD before trusting a change. (Self-check Q6.)

Checks for understanding

Ask these out loud during the demo and the lab:

  • Where is a card's title stored, and where is its heading level? Answer: the title in the HTML (inside the selector's element); the level in the comment, and only when it is not 3.
  • Which hook gives a block's wrapper the supports' classes and styles? Answer: useBlockProps() in edit and useBlockProps.save() in save (Quiz Q3 of the lesson).
  • What happens to the front end when a card turns invalid in the editor? Answer: nothing: the front end prints the stored HTML.
  • What three things does a deprecated entry repeat? Answer: the old attributes, the old supports and the old save (plus an optional migrate).

Mental model to say

"A static block is a printed card: the shop prints it once, and it says the same thing until someone reprints it. A dynamic block is a station's departure board: what is stored is only 'show the next trains from platform 2', and the board looks up the timetable whenever someone glances at it. The post keeps the instruction, the comment; your render.php is the board."

Then the comparison on the board, from the lesson's table: stored = comment + HTML vs comment only; HTML made by save(), once vs render.php, every view; changing markup = a deprecation vs edit render.php; plugin off = HTML stays vs nothing shows.

Before demo B, the third picture: "A bound block is a shelf label with an empty slot. The design is fixed in the template; the slot says 'price of the book on this shelf', and a clerk, the source, fills it every time someone looks."

Checks for understanding

Ask these out loud during the demos and the lab:

  • What does a page with a Book List store? Answer: only the comment with the attributes; the HTML is made on every view.
  • Why does render.php use get_posts() and not a Loop with the_post()? Answer: it leaves the global $post alone, so a block in the middle of someone else's Loop breaks nothing; and it loads the meta in one query.
  • core/post-meta or pagesco/book for the price? Answer: pagesco/book: core/post-meta prints the raw 8.99; the shop's source formats it.
  • When does variations.php run? Answer: only when something asks for the variations (the editor, through REST), not on page views (lesson quiz Q5).

Closing

Exit ticket (3 questions, no notes, 4 minutes)

Put the three questions on the slide. Learners answer in the workbook's Exit Ticket box or on a sticky note. Sort them before Session 13: question 2's pile tells you whether the checkpoint's Part C (blocks) needs a five-minute review in the warm-up.

  1. A static block's title and heading level: where is each stored? Answer: the title in the saved HTML (found by its selector), the heading level in the block comment (only when it differs from its default).
  2. Name two things a dynamic block's render.php must do with its attributes. Answer: treat them as input (isset or a default for optional ones, cast, clamp, sanitize) and escape everything it prints; plus starting the wrapper with get_block_wrapper_attributes().
  3. A bound paragraph shows its fallback text on a book page. Name two causes. Answer: the meta key is wrong, not registered with show_in_rest or protected (core/post-meta), or a custom source lacks uses_context or returns null.
