Objectives (from the lesson page)

Mental model to say

"If the templates are the floor plans of the shop, functions.php is the sheet of instructions the theme hands the building manager when it moves in: we need the shop sign handled by you (theme supports), please deliver these crates of paint and these tools (stylesheets and scripts), there will be a directory board here and a notice board there (a menu location and a widget area). The manager, WordPress, does the actual work at the right moment of each day."

Then the timeline on the board, and the convention: one small, prefixed function per job, each hooked to its moment. "That is the real reason a classic template must call wp_head() and wp_footer(): without them, nobody can add a single stylesheet or script."

Three mistakes to expect, and how to coach each
  • Code at the top level of functions.php. add_theme_support() or wp_enqueue_style() outside a callback. Coach: "Which moment is this for? Put it in a function on that hook." (Self-check Q1 and Q6.)
  • Typed versions and the wrong URL function. '1.0' copied from a tutorial, get_stylesheet_uri() in a parent. Coach: "What happens on your next release? What happens with a child theme?" (Self-check Q3; the lab's TODO 2.)
  • Locations and areas without fixed ids. A location typo, register_sidebar() without id. Coach: "Which string does the template use? Copy it." (Self-check Q4; debug_theme_setup.php.)

Checks for understanding

  • Where does add_theme_support( 'title-tag' ) go? Answer: a functions.php callback on after_setup_theme (the lesson quiz Q1).
  • Why the theme's Version as the version argument? Answer: it changes exactly when you release; browsers then fetch the new file.
  • Who builds the menu, and who decides where it may appear? Answer: the owner builds it; the theme registers locations.
  • Which hook for register_sidebar()? Answer: widgets_init (the lesson quiz Q4).

Workbook self-check, items Q1 to Q6.

Answers: Q1 C) after_setup_theme; Q2 pagesco-classic | inactive | 1.1.0: pagesco is active again; 1.1.0 is the Version the stylesheet is enqueued with (style.css?ver=1.1.0), so raising it on a release makes every browser fetch the new CSS; Q3 A) The page loads the CHILD's style.css under the parent's handle, and the parent's CSS is gone; Q4 B) So a location without an assigned menu prints nothing instead of wp_page_menu()'s list of every page; Q5 D) Not on WordPress 6.8 and later, which load the active theme's languages/ folder itself; it stays for 6.6 and 6.7; Q6 A "called incorrectly" notice naming the handle (scripts and styles should not be enqueued until wp_enqueue_scripts...), plus two follow-on notices; the real damage: top-level code runs on every request, so the CSS also loads on admin screens and the login page.
