4.3 · functions.php: Supports, Assets, Menus & Widgets: self-check

Q1
Which of these actions fires FIRST in a front-end request?
A) wp_enqueue_scripts
B) widgets_init
C) after_setup_theme
D) wp_head
Why: The order of Lesson 4.3's timeline: the theme's functions.php is included, after_setup_theme fires (supports, menu locations), then init with widgets_init at priority 1, then the main query and the template, and wp_head runs wp_enqueue_scripts at priority 1.
A is wrong: It runs inside wp_head, after the query.
B is wrong: It runs on init, after after_setup_theme.
D is wrong: wp_head is printed by the template, near the end.
Q2
At the end of Lesson 4.3, what does this print, and why does the version column matter for the theme's CSS?
wp theme list --name=pagesco-classic --fields=name,status,version
pagesco-classic | inactive | 1.1.0: pagesco is active again; 1.1.0 is the Version the stylesheet is enqueued with (style.css?ver=1.1.0), so raising it on a release makes every browser fetch the new CSS
Why: The enqueue reads the version from the theme header (wp_get_theme( get_template() )->get( 'Version' )), never a typed number.
Q3
pagesco-classic enqueued its stylesheet with get_stylesheet_uri() instead of get_parent_theme_file_uri( 'style.css' ). A client builds a child theme of it. What happens?
A) The page loads the CHILD's style.css under the parent's handle, and the parent's CSS is gone
B) Nothing changes: both functions return the parent's file
C) WordPress loads both files automatically
D) A notice: get_stylesheet_uri() cannot be used in a parent theme
Why: get_stylesheet_uri() is the ACTIVE (child) theme's style.css; get_parent_theme_file_uri() always the theme that holds the code (Lesson 3.4's template and stylesheet). The same reasoning picks wp_get_theme( get_template() ) for the version.
B is wrong: Without a child they are the same, which is why the mistake hides.
C is wrong: Only what is enqueued loads.
D is wrong: There is no such notice; the mistake is silent.
Q4
Why does header.php wrap wp_nav_menu() in has_nav_menu( 'primary' )?
A) It makes the menu load faster
B) So a location without an assigned menu prints nothing instead of wp_page_menu()'s list of every page
C) wp_nav_menu() refuses to run without it
D) It registers the location
Why: With no menu in the location, wp_nav_menu() calls its fallback, wp_page_menu(), which lists all published pages, Sample Page included (Lesson 4.3, Common Mistakes 3). The guard (or 'fallback_cb' => false) keeps the header empty until the owner assigns a menu.
A is wrong: It saves nothing measurable.
C is wrong: It runs fine; that is the problem.
D is wrong: register_nav_menus() registers locations, on after_setup_theme.
Q5
pagesco-classic ships languages/es_ES.l10n.php and says Requires at least: 6.6. Does it still need load_theme_textdomain()?
A) Yes, every theme needs it on every version
B) No, never: translations always load themselves
C) Only plugins need it
D) Not on WordPress 6.8 and later, which load the active theme's languages/ folder itself; it stays for 6.6 and 6.7
Why: Since 6.8 wp-settings.php calls $wp_theme->load_textdomain() for the active theme (the lesson's version note, checked in the 6.7 and 6.8 images). A theme that supports older versions keeps the call; on 7.1 it is harmless.
A is wrong: Measured otherwise on 6.8+.
B is wrong: Not before 6.8.
C is wrong: Plugins and themes follow the same rule since 6.8.
Q6
A must-use plugin calls wp_enqueue_style() at the top level of its file. What does WordPress say, and what is the real damage?
A "called incorrectly" notice naming the handle (scripts and styles should not be enqueued until wp_enqueue_scripts...), plus two follow-on notices; the real damage: top-level code runs on every request, so the CSS also loads on admin screens and the login page
Why: Lesson 4.3's Common Mistake 1. Read the first notice; wrap the call in a function on wp_enqueue_scripts.

4.3 · functions.php: Supports, Assets, Menus & Widgets: predict, then run

P1
Predict the output, then run it.
wp eval 'var_dump( current_theme_supports( "title-tag" ), current_theme_supports( "menus" ) );'
bool(false)
bool(false)
Why: Neither: pagesco-classic declares no supports yet and registers no location. Registering a location (Lesson 4.3) is what switches menus on; nobody needs add_theme_support( 'menus' ).
P2
Predict the output, then run it.
wp eval 'var_dump( current_theme_supports( "title-tag" ), current_theme_supports( "html5", "search-form" ) );'
bool(false)
bool(true)
Why: pagesco declares nothing, yet html5 search-form is true: _add_default_theme_supports() adds it for block themes. title-tag is false although every page has a title: block themes print it unconditionally (the lesson's Exercise 3).

Part 1 Project: self-check (project skills)

Q7
Fernhill is a block theme. What is its style.css for?
A) It names the theme: the header fields WordPress reads (Theme Name, Text Domain, Version, Requires at least ...)
B) It is the theme's stylesheet, loaded on every page
C) It is a fallback when theme.json has an error
D) It registers the patterns
Why: Block themes do not load style.css on the front end (Lesson 3.2's FAQ); the design lives in theme.json, and extra CSS is enqueued (R5: fernhill-style). The header is R1 and the self-check's first line.
B is wrong: Not in a block theme; Fernhill enqueues assets/css/fernhill.css instead.
C is wrong: A broken theme.json is just ignored, with a decode notice.
D is wrong: Pattern files register themselves from patterns/.
Q8
The brief wants links and buttons in the primary color. Where does that go?
A) A hex color typed into each template's markup
B) assets/css/fernhill.css
C) theme.json: styles.elements.link and styles.elements.button with var:preset|color|primary
D) A pattern that wraps every link
Why: The design system lives in theme.json (Lesson 3.2): one preset, used everywhere, and a style variation (Autumn, R4) can recolor it without touching a template. Hard-coded hex in markup costs a rubric point.
A is wrong: The rubric's Partly column names exactly this.
B is wrong: Possible, but not where a variation can change it.
D is wrong: Patterns hold sections, not global styles.
Q9
R6: the blog home lists three posts per page with working pagination. Which way does the brief want?
A) A Query Loop with perPage 3 that does not inherit
B) A pre_get_posts callback in functions.php with the three guards: not the admin, the main query only, the blog home only
C) Settings > Reading set to 3
D) A second WP_Query in the front-page pattern
Why: One main query, changed before it runs, so the Query Loop that inherits it, the pagination and the 404 decision all agree (Lesson 4.2). The self-check's line 11 counts 3 on / and 1 on /page/2/.
A is wrong: A non-inheriting Query Loop runs a second query; /page/2/ then disagrees.
C is wrong: That is the owner's setting, not the theme's, and it changes every list.
D is wrong: The second-query mistake of Lesson 4.2.
Q10
You tried a header change in the Site Editor and clicked Save. Now your edits to parts/header.html no longer show. What happened, and what do you do?
A) The theme cache needs 30 minutes
B) parts/ files are only read on activation: switch themes twice
C) theme.json overrides parts
D) A wp_template_part copy in the database wins over the file: move the change into header.html, then delete the copy
Why: Lesson 3.2's Mistake 3 and 3.3's loop: list the template, template-part and global-styles posts (wp post list), find the change, put it in the file, delete the copy. A copy left behind is also missing from the zip you hand in (R8).
A is wrong: That cache is for pattern files, and development mode is on.
B is wrong: Parts are read on every request.
C is wrong: theme.json declares part areas; it does not replace markup.
Q11
Odette wants the autumn look she can switch on in October (R4). Which file, and what may it change?
styles/autumn.json, titled Autumn, without blockTypes: the same five color slugs with autumn values, nothing else
Why: A style variation is a layer over theme.json (Lesson 3.3); keeping the slugs means every template and pattern recolors by itself. With blockTypes it would be a section style instead.
Q12
You stop working on Fernhill for the day. Which command do you run, and why?
wp theme activate pagesco: the labs, Session 8's assessment and Part 2 (Lesson 5.1) expect pagesco active, the state at the end of Lesson 4.3
Why: The self-check switches nothing; you activate fernhill yourself and switch back yourself (the brief's rules).

The Lesson Page's Own Quick Quiz

Lesson 4.3 · functions.php: Supports, Assets, Menus & Widgets
  1. B In a functions.php callback hooked to after_setup_theme: Theme supports are declared on after_setup_theme, which fires right after functions.php is included and long before any template runs.
  2. C ?ver=7.1.3: Without a version WordPress adds its own, 7.1.3, which does not change when your CSS does, so browsers keep the old file. Pass the theme's Version instead.
  3. A A list of all published pages, from the fallback wp_page_menu(): With no menu found, wp_nav_menu calls its default fallback, wp_page_menu, which lists every published page. fallback_cb false or a has_nav_menu check prevents it.
  4. B widgets_init: widgets_init fires during init (at priority 1), the moment WordPress sets up widgets, on every request including the admin's Widgets screen.
  5. C Add the standard .screen-reader-text CSS that clips it visually but keeps it for screen readers: Core marks text meant for screen readers with screen-reader-text and expects the theme to hide it visually only. Block themes get this CSS from core; classic themes must add it.

Exit Ticket

  1. Hooks: after_setup_theme (supports, menu locations); wp_enqueue_scripts (styles and scripts); widgets_init (widget areas).
  2. The version: it ends the file's URL (?ver=), so a new release means a new URL and every browser and cache fetches the new file; the theme's Version changes exactly when you ship.
  3. Personal. Use the answers to plan the Session 8 studio: group learners by the requirement they named.

Common Wrong Answers and What They Reveal

  • Q1 A or D. Thinks assets come first because they are "the theme". Redraw the timeline.
  • Q3 B. Has never built a child theme of a classic theme; tie it to Lesson 3.4's template/stylesheet.
  • Q5 A. Copied from older tutorials; show the 6.8 version note.
  • Q7 B. Still thinks a block theme loads style.css: Lesson 3.2's FAQ and Lesson 3.4's "stylesheet nobody loads".
  • Q9 A. A non-inheriting Query Loop: the most common Fernhill bug in the studio; /page/2/ gives it away.
