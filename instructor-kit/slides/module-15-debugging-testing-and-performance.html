8.1

Debugging & Testing

Evidence when it breaks; machines that check before it does.

8.1 · Mental model

Debugging is detective work

  1. A symptom: "Supplier not reachable"
  2. Suspects: the network, the address, the key, the code
  3. Evidence: what the code recorded, then make it talk
  4. Rule them out one by one; change code last
WATCH The worst habit: changing code until the symptom disappears.

8.1 · When the site goes down

The recovery mode email

From: WordPress <wordpress@example.com>
To: wordpress@example.com
Subject: [Pages & Co.] Your Site is Experiencing a Technical Issue

Howdy!

WordPress has a built-in feature that detects when a plugin or theme causes a fatal error on your site, and notifies you with this automated email.

In this case, WordPress caught an error with one of your plugins, Pages & Co. Crash Test.
WHY Sent for protected pages (wp-login.php, wp-admin), at most once a day per error.

8.1 · Tests

Integration tests in a WordPress of their own

  • WP_UnitTestCase: a rollback after every test, factories, assertions
  • pre_http_request answers instead of the network
  • wp-env on port 8889: the test library reinstalls its database
  • Always the project's vendor/bin/phpunit (9.6), never bare phpunit
RULE Tests never use the network: they would fail when the supplier is down.

8.2

Performance & Caching

A number first, then a change, then the number again.

8.2 · Mental model

Three places where time goes

  • Server: PHP and the database build the HTML · SAVEQUERIES, the query report
  • Network: the HTML and every file it names · View Source, the Network panel
  • Browser: pixels and clicks · Core Web Vitals: LCP, INP, CLS
RULE Measure several times; change one thing at a time.

8.2 · The object cache

WordPress remembers, within a request

wp eval 'global $wpdb; $before = $wpdb->num_queries;
    get_post_meta( 30, "pagesco_price", true );
    get_post_meta( 30, "pagesco_author", true );
    echo $wpdb->num_queries - $before, " query for two meta values\n";'
1 query for two meta values
WHY The first read loaded all of Dune's meta; the second was free.
8.2 · ... and forgets

Two commands, two requests

wp eval 'wp_cache_set( "note", "Gatsby: back November 15", "pagesco_demo" );
    var_dump( wp_cache_get( "note", "pagesco_demo" ) );'
wp eval 'var_dump( wp_cache_get( "note", "pagesco_demo" ) );'
string(24) "Gatsby: back November 15"
bool(false)
WHY A persistent object cache (object-cache.php: Redis, Memcached) keeps it.

8.2 · Caching your own query

A key that knows when the data changed

$key = 'find:' . md5( $limit . '|' . $location ) . ':'
	. wp_cache_get_last_changed( 'pagesco_events' );
// ... and after every insert or delete:
wp_cache_set_last_changed( 'pagesco_events' );
PATTERN Every write renews the key: old answers are never read again.

8.2 · Core Web Vitals, honestly

What the lab can and cannot say

  • Recorded: LCP about 1480 ms (the hero image), CLS 0.101, INP 16 ms
  • Good: LCP ≤ 2.5 s · INP ≤ 200 ms · CLS ≤ 0.1, at the 75th percentile of the field
  • Lab numbers: compare a change on one machine
  • Field data: real visitors, after the launch

Debrief · 15 minutes

What each check proves, and what it cannot

  • composer lint: the code follows the standard; not that it works
  • PHPUnit: the behaviors it names, in a fresh WordPress
  • The query report: the server's work, not the visitor's
  • Lab Web Vitals: a comparison, not the field
WHY Which of them would have caught this morning's 401? None: the log did.
