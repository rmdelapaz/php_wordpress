WordPress for Developers

By the end you can
  • Describe WordPress 7.1 as a developer sees it: a PHP and MySQL application with themes, plugins, blocks and APIs as extension points
  • Explain the difference between WordPress.org (the software) and WordPress.com (a hosting service), and pick the right one for a project
  • Trace a front-end request from index.php to the finished HTML, naming the core files on the way
  • Say where your code belongs (themes, plugins, must-use plugins in wp-content/) and why you never edit core files
  • Map what you know from PHP Foundations and MySQL Foundations to the way WordPress does the same jobs
  • Describe the Pages & Co. project and plan how you will work through this course
Key ideas
  • WordPress, to a developer, is a PHP application on MySQL that builds every page on request, designed to be extended without being edited: hooks, themes, plugins, blocks and APIs.
  • WordPress.org is the open-source software and its community; WordPress.com is one company's hosting, where your own plugins and themes depend on the plan. The course is self-hosted.
  • One request: index.php → wp-blog-header.php → wp-load.php → wp-config.php → wp-settings.php (core, must-use plugins, plugins, theme, init) → wp() (the main query) → template-loader.php → HTML. Load, then query, then template.
  • wp-content/ is yours (themes, plugins, mu-plugins, uploads, debug.log); everything else in the root is core. Everything else WordPress knows is in the database.
  • Never edit core (or a theme or plugin you did not write): updates replace those files without asking. wp core verify-checksums catches an edited core file.
  • Deprecated messages name the version and the replacement: check how old a tutorial is before you copy from it.
  • Inversion of control: core runs the main program and calls your code through hooks.
Worked example: three clues that a site runs WordPress

You can tell a WordPress site from the outside, and your own site is the best place to learn the clues. In the WP-CLI container shell (docker compose run --rm wpcli sh), ask for the home page and look for the theme's folder in its HTML:

curl -s http://localhost:8080/ | grep -o 'wp-content/themes/[a-z0-9-]*' | sort -u
wp-content/themes/twentytwentyfive

Every stylesheet and script of the theme is loaded from wp-content/themes/<theme folder>/, so the folder name shows in the page. Core's own files come from wp-includes/; count the lines that mention it:

curl -s http://localhost:8080/ | grep -c 'wp-includes/'
22

And the response headers carry the address of the REST API, which every WordPress site has at /wp-json/ (Module 7):

curl -sI http://localhost:8080/ | grep -i '^link'
Link: <http://localhost:8080/wp-json/>; rel="https://api.w.org/"

Three clues, none of them a secret: a site that hides them is still a WordPress site. (On a site that is not your own, View Source in the browser shows the same paths.)

Worked example: where the compose settings end up

compose.yaml sets WORDPRESS_DB_NAME, WORDPRESS_DEBUG and WORDPRESS_CONFIG_EXTRA. Where do they end up? Search the wp-config.php the image wrote, from the WP-CLI container shell:

grep -n "getenv_docker('WORDPRESS_DB_NAME'\|getenv_docker('WORDPRESS_DEBUG'\|WORDPRESS_CONFIG_EXTRA" wp-config.php
44:define( 'DB_NAME', getenv_docker('WORDPRESS_DB_NAME', 'wordpress') );
116:define( 'WP_DEBUG', !!getenv_docker('WORDPRESS_DEBUG', '') );
127:if ($configExtra = getenv_docker('WORDPRESS_CONFIG_EXTRA', '')) {

wp-config.php does not contain your values: it reads them from the container's environment every time it runs (getenv_docker()), and runs the WORDPRESS_CONFIG_EXTRA lines with eval(). Ask the running site for one of them:

wp eval 'echo getenv( "WORDPRESS_DB_NAME" ), " ", DB_NAME, "\n";'
wordpress wordpress

The environment variable and the constant DB_NAME agree. That is why a change to compose.yaml takes effect after docker compose up -d (which recreates the container with the new environment) and why you never need to edit wp-config.php for the course settings.

1.3

PHP the WordPress Way

By the end you can
  • Write PHP that follows the WordPress coding standards, and check it with PHPCS and the WordPress ruleset
  • Choose the right escaping function for each output context (esc_html, esc_attr, esc_url, wp_kses_post) and the right sanitizing function for each input
  • Make strings translatable with __(), esc_html__(), _n() and sprintf(), with a text domain and translator comments
  • Pass callbacks in every form WordPress accepts, and write functions that take an array of arguments merged with wp_parse_args()
  • Handle WP_Error results, and use core's globals ($wpdb, $post, $wp_query) and classes without fighting them
Key ideas
  • WordPress code is a guest in a PHP process shared with core, the theme and every plugin: house rules make that work.
  • The WordPress Coding Standards (tabs, spaces inside parentheses, Yoda conditions, single quotes, array(), DocBlocks); PHPCS with the WordPress ruleset checks them and also finds unescaped output; phpcbf fixes the mechanical part.
  • Prefix every global name (pagesco_): functions, global variables, constants, hooks, options, meta keys, handles; the text domain is the folder slug. A namespace is a prefix.
  • Sanitize early, escape late: wp_unslash() then sanitize_text_field() / sanitize_email() / absint() (or validate); at the echo esc_html(), esc_attr(), esc_url(), wp_kses_post().
  • Translatable strings: __() returns, _e() echoes, esc_html__() for templates, _n() for plurals, sprintf() placeholders with a /* translators: */ comment.
  • Callbacks come as a name, a closure, an arrow function, array( $obj, 'method' ) or a static method; named ones can be unhooked.
  • Arrays of arguments merged with wp_parse_args(); failures as WP_Error, checked with is_wp_error(); read core's globals, never assign them; values from the database are strings, so cast instead of using strict types.
Worked example: the slashes WordPress adds

WordPress adds a backslash before every quote in $_GET, $_POST and $_COOKIE (wp_magic_quotes(), Lesson 1.3). You can watch the round trip without a form: wp_slash() does what WordPress does on the way in, wp_unslash() undoes it.

wp eval '$pagesco_in = wp_slash( "O'\''Reilly" ); var_dump( $pagesco_in, wp_unslash( $pagesco_in ) );'
string(9) "O\'Reilly"
string(8) "O'Reilly"

Nine characters on the way in, eight after wp_unslash(): the backslash is real, not a display artifact. Store the first value and the apostrophe in O'Reilly grows a backslash in the database; that is why every input line in WordPress code starts with wp_unslash() and then a sanitize_*() function: sanitize_text_field( wp_unslash( $_POST['name'] ) ). (The '\'' in the command is the shell's way of writing one apostrophe inside single quotes.)

The Content Model

By the end you can

Key ideas
  • Everything is a post: posts, pages, attachments, revisions, templates, patterns and block-theme menus are rows of wp_posts, told apart by post_type (16 types on a fresh site); PHP sees a row as a WP_Post.
  • Posts are dated and filed under categories and tags; pages are timeless and hierarchical. post_status decides who sees a row; new content defaults to draft, and a draft has no slug.
  • Tools differ in their defaults: WP-CLI lists every status, get_posts() and WP_Query only published content.
  • Taxonomies group content into terms; an upload is an attachment post plus its files and generated sizes.
  • Every update is a revision, and the newest one equals the current post; trash is a status for 30 days, --force deletes for good.
  • Roles bundle capabilities; code checks the capability (current_user_can(), user_can()), including meta capabilities like edit_post with an ID.
  • Every Settings field is an option (a string); content is block markup: parse_blocks() reads it, do_blocks() renders it.

Key ideas
  • Core is wp-admin/, wp-includes/ and the root files; yours is wp-content/ (where drop-ins such as object-cache.php can replace parts of core) and wp-config.php.
  • wp-config.php holds the database connection, eight secret keys and $table_prefix, and its last line loads wp-settings.php: nothing defined after it takes effect.
  • wp-settings.php loads in a fixed order: database, must-use plugins, plugins, pluggable functions, theme, current user, then init and wp_loaded.
  • Twelve tables in five groups (content, taxonomies, users, comments, settings), linked by ID columns but with no foreign keys: integrity lives in PHP, so change data through WordPress.
  • Meta tables are key-value rows: flexible, but every value is text, each condition is one more join, and values are not indexed.
  • Arrays are stored serialized, lengths included: never edit them as text (wp option patch, update_option(), wp search-replace).
  • Autoload: on, auto, auto-on are loaded with every request; off, auto-off are read on demand (one query, then cached). In code: {$wpdb->posts}, never wp_posts.

By the end you can
  • Explain the difference between an action and a filter, and choose the right one for a task
  • Attach callbacks with add_action() and add_filter(), using priorities and the accepted-arguments count correctly
  • Remove a hook someone else added with remove_action() / remove_filter(), and say why a removal silently fails

  • Find the hook you need: in the core source, with has_filter() and $wp_filter, and from the command line with WP-CLI
  • Build the Pages & Co. store notice as a must-use plugin that others can customize through its own hooks
Key ideas
  • A hook is a named point where WordPress calls the functions registered for it: how you change WordPress without editing core.
  • Actions (add_action, do_action) run code at a moment; filters (add_filter, apply_filters) receive a value and must return it.
  • Priority (default 10, lower first, ties in the order added) orders callbacks; accepted args (default 1) must match what the callback asks for: 10, 2.
  • Removing needs the same hook, callback and priority, after the hook was added; remove_action() returns false silently when nothing matches. Closures cannot be removed by anyone else.
  • Your own hooks make code extensible: prefix them, a filter for values and an action for moments, pass context, document them with a DocBlock.
  • Finding hooks: the Code Reference, the function you want to change, grep -rn in wordpress/, and has_filter() / $wp_filter on the running site.
  • "Too early" is the most common hook bug: code at the top of a plugin file runs while plugins load; move it into a callback on init or later.

A filter on wp_mail_from (the sender address: a value, so the closure returns it) and an action on phpmailer_init (a moment: WordPress hands over its mailer object and the closure configures it for Mailpit). Building a Block Theme

By the end you can
  • Write a theme header in style.css that WordPress reads and checks on activation
  • Define a design system in theme.json: settings (palette, fonts, sizes, spacing, layout) and styles (global, elements, blocks), and read the CSS WordPress generates from it

Key ideas
  • Two files make a block theme: style.css (the header WordPress reads and checks on activation: Requires at least, Requires PHP) and templates/index.html.
  • theme.json settings = what is available (palette, font families and sizes, spacing, layout widths, controls); styles = what is applied (the page, elements, single block types).
  • Every preset becomes a custom property and classes: oxblood → --wp--preset--color--oxblood, .has-oxblood-color; var:preset|color|oxblood in theme.json. Use presets, never hex values.
  • Static blocks carry their exact HTML in the file; dynamic blocks (Site Title, Navigation, Query Loop, Post Title, Post Content) are self-closing and rendered by PHP.
  • Template parts live in parts/ and are included by slug; tagName gives the header, main and footer landmarks.
  • Quiet failures: a JSON syntax error drops the whole theme.json (a Notice only with WP_DEBUG); a wrong part slug renders nothing for visitors; a Site Editor copy wins over your file.

Key ideas

  • Templates use patterns by slug: <!-- wp:pattern {"slug":"pagesco/hero"} /-->. front-page.html is above home and index for the front page.
  • Synced patterns are content, referenced by ID (<!-- wp:block {"ref":20} /-->): never in theme files.
  • styles/*.json with blockTypes = a section style (is-style-<slug>); without it = a style variation for the whole site. Choosing one in the Site Editor saves user global styles (a wp_global_styles post).

Key ideas
  • A child theme is a theme folder whose style.css says Template: <parent folder>. WordPress looks in the child first and falls back to the parent; the parent stays untouched and can be updated.
  • Two options: template = the parent, stylesheet = the child. get_template_directory() vs get_stylesheet_directory(); get_theme_file_path() / _uri() = the child's copy if it exists, else the parent's.
  • theme.json is merged (core, parent, child, user), single values key by key, but preset lists are replaced whole: repeat every slug, change only values.
  • Same name replaces: templates, parts, classic PHP templates, styles/ files (by file name only); same slug replaces patterns.
  • functions.php: both run, the child's FIRST. A block child's style.css loads only when enqueued (depend on the parent's real handle). Pluggable parent functions (function_exists()) can be replaced; parent hooks are removed on after_setup_theme.
  • Classic child themes work the same with PHP templates (locate_template(), get_header()); never @import the parent's CSS. One level only: no grandchildren.
  • Which tool? Site Editor (owner, database) · child theme (lasting design changes to someone else's theme) · your own theme · a plugin (features that must survive a theme switch).

The Loop & Template Tags

By the end you can

Key ideas
  • The main query runs before any template and lives in $wp_query; a classic template only walks its result: if ( have_posts() ) { while ( have_posts() ) { the_post(); ... } }, even on single posts.
  • the_post() moves to the next post and sets the global $post every template tag reads; without it the Loop never ends.
  • Template tags come in pairs: the_title() prints HTML-ready text, get_the_title() returns it for you to escape (esc_attr(), esc_url(), esc_html()); the_title_attribute() for attributes. get_the_content() is raw; the_content() renders blocks. the_date() prints once per day.
  • Parts: get_header(), get_footer(), get_template_part( $slug, $name, $args ) through locate_template() (child first); no .php in the slug; false = not found.
  • Conditional tags (is_home(), is_singular( 'post' ), is_page( 'about' ), is_archive(), is_search(), is_404() ...) read the main query: from template_redirect on, never at a plugin's top level.
  • A classic theme with a theme.json is a hybrid: presets and global styles, but no styles.css custom CSS.

Key ideas

  • Loop over your object ($q->have_posts(), $q->the_post()) and finish with wp_reset_postdata(). get_posts() returns an array and needs no reset.

  • the_posts_pagination() paginates the main query; paging a custom query in a template ends in 404s.
  • Argument pairs (cat / category_name, author / author_name, p / name) fail silently with the wrong kind of value. query_posts() is for old tutorials only.

By the end you can
  • Explain when functions.php runs and choose the right hook for theme setup, widgets and assets
  • Declare theme supports such as title-tag and html5 with add_theme_support(), and say which ones block themes get automatically

Key ideas
  • functions.php runs on every request while the theme is active (admin, REST and WP-CLI included): code goes in prefixed callbacks on the right hook.
  • Supports on after_setup_theme: title-tag, automatic-feed-links, post-thumbnails, responsive-embeds, html5 with an array. Block themes get most of them, and their title, automatically.
  • Enqueue on wp_enqueue_scripts: a prefixed handle, get_parent_theme_file_uri(), dependencies, the theme's Version; scripts with 'strategy' => 'defer', 'in_footer' => true.
  • Menus: register_nav_menus() (locations), the owner assigns, wp_nav_menu() behind has_nav_menu(). Widget areas: register_sidebar() with a fixed id on widgets_init, is_active_sidebar() + dynamic_sidebar(); widgets are blocks since 5.8.
  • Accessibility: a skip link, .screen-reader-text CSS, labeled navigation, real buttons, visible focus. Translation: a literal text domain; 6.8+ loads a theme's languages/ itself.

5.1

Your First Plugin

By the end you can
  • Write a plugin header WordPress understands, including the version requirements it checks on activation
  • Organize a plugin as a short main file plus namespaced classes in src/, loaded by Composer's PSR-4 autoloader
  • Start features from one main object on plugins_loaded, and add a new feature by writing one class and listing it
  • Use activation and deactivation hooks and uninstall.php for the right jobs, and say what each must never do
  • Recognize the typical first-plugin failures: direct file access, a missing autoloader, a class the autoloader cannot find, a hook registered too late
Key ideas
  • A plugin is a folder in wp-content/plugins/ with a main file of the same name whose header has at least Plugin Name:. WordPress reads the header without running the file; Requires at least and Requires PHP are checked on activation.
  • Guard every file that can run on its own: defined( 'ABSPATH' ) || exit; (uninstall.php: WP_UNINSTALL_PLUGIN).
  • Namespace + PSR-4: classes live in PagesCo\Books; Composer's autoloader loads PagesCo\Books\X\Y from src/X/Y.php, letter for letter. composer dump-autoload only when composer.json's autoload changes.
  • The main file stays short: header, guard, three constants, the autoloader, the life-cycle hooks, and boot() on plugins_loaded.
  • A feature is a class implementing Feature; its register() adds its hooks. New feature = one class + one line in Plugin::feature_classes().
  • Life cycle: activation sets up once (roles, defaults); deactivation pauses and keeps data; uninstall.php removes the plugin's data. Register both hooks at the top level of the main file.

Custom Post Types, Taxonomies & Meta

By the end you can
  • Register a custom post type with register_post_type() on init, with labels, an archive and REST support
  • Register a custom taxonomy with register_taxonomy() and attach it to the post type
  • Register typed post meta with register_post_meta(), and explain why the keys are public and show_in_rest
  • Add a meta box and extra admin columns so editors can see and change a book's details
  • Flush rewrite rules at the right moment, and seed content safely with a WP-CLI script
Key ideas
  • A custom post type is a new value of wp_posts.post_type: register_post_type( 'book', ... ) on init, with labels, has_archive, a rewrite slug and show_in_rest.
  • A taxonomy groups content: register_taxonomy( 'genre', array( 'book' ), ... ); the second argument is the type it attaches to.
  • Meta is a fact about one item: register_post_meta() gives a key a type, a label and REST visibility. Shop keys have no leading underscore so they stay public and bindable.
  • Rewrite rules live in the database: flush them in the activator (after registering the type and taxonomy, because init has not run on that request), never on init.
  • Values are stored as strings: get_post_meta() returns '412' and '' for false; REST and block bindings cast them to the registered type.
  • Seed with a script that is safe to run twice, and set terms with wp_set_object_terms(), not tax_input, when no user is logged in.

5.3

Security in WordPress

By the end you can
  • Sanitize input on the way in and escape output on the way out, choosing the right function for each context
  • Protect every state change with a nonce and a current_user_can() capability check
  • Write safe database queries with $wpdb->prepare() and explain how SQL injection works
  • Name the common WordPress vulnerabilities (XSS, CSRF, SQL injection, broken access control) and the defense against each
  • Harden a real save handler and an admin action in the pagesco-books plugin
Key ideas
  • One data flow: request → genuine? (nonce) → allowed? (capability) → sanitize → store → escape → page.
  • Escape late, for the context: esc_html() text, esc_attr() attributes, esc_url() links, wp_kses_post() HTML that may keep safe tags; even for data you sanitized.
  • Sanitize and validate on the way in: sanitize_text_field(), absint(), a cast; a value with a shape (a date) is validated and rejected if wrong.
  • Nonces (wp_nonce_field(), wp_nonce_url(), check_admin_referer()) stop forged requests (CSRF); capabilities (current_user_can( 'edit_post', $id )) stop the wrong user. You need both.
  • $wpdb->prepare() with %s, %d, %f, %i: no variable ever goes directly into SQL.
  • Database functions trust their caller: wp_insert_post() and update_post_meta() check nothing; guard every write yourself. save_post handlers skip autosaves and revisions.
Worked example: one value, three destinations

One value with tags, an ampersand and quotes, escaped for three destinations:

wp eval '$v = "Dune: <b>signed</b> & \"rare\"";
echo esc_html( $v ), "\n", esc_attr( $v ), "\n", wp_kses_post( $v ), "\n";'
Dune: &lt;b&gt;signed&lt;/b&gt; &amp; &quot;rare&quot;
Dune: &lt;b&gt;signed&lt;/b&gt; &amp; &quot;rare&quot;
Dune: <b>signed</b> &amp; "rare"

esc_html() and esc_attr() both turn the value into text (the quotes too, so it cannot end an attribute); wp_kses_post() keeps the tags a post may contain and escapes the rest. The function is chosen by the destination: text, attribute, or HTML that may keep safe tags. An unknown value printed into a page is never echoed raw.

By the end you can

Key ideas

Dynamic Blocks & Block Bindings

By the end you can

  • Bind core blocks to post meta with core/post-meta, and write a custom binding source with register_block_bindings_source()
Key ideas
  • A dynamic block stores only its comment. "render": "file:./render.php" makes WordPress run the PHP on every view, with $attributes, $content and $block; the build copies render.php into build/.
  • In render.php treat attributes as input: check optional ones with isset() (WordPress fills in defaults only for attributes that have one), cast, clamp, sanitize; query with get_posts(); start the wrapper with get_block_wrapper_attributes(); escape what you print.
  • An attribute without a default can mean "use the site's setting": the Book List's count follows Books per list.
  • ServerSideRender previews render.php through the block-renderer REST route; @wordpress/core-data fills controls with the site's data.
  • Variations are presets of a block; "variations": "file:./variations.php" builds them in PHP, only when something asks.
  • Block bindings connect core blocks' attributes to sources: core/post-meta returns raw values of registered, public meta; register_block_bindings_source() with uses_context gives formatted ones. They fail silently to the fallback.

6.4

The Interactivity API

By the end you can
  • Explain how the Interactivity API splits the work: server-rendered HTML with directives, then hydration by a store in a script module
  • Scaffold an interactive block into the plugin, and build its viewScriptModule with --experimental-modules
  • Set state and per-element context in PHP with wp_interactivity_state() and wp_interactivity_data_wp_context(), including derived state the server can compute
  • Write a store with store(), state getters, getContext() and actions, and connect it with data-wp-on, bind, class and text
  • Build interactive features that stay accessible and keep working without JavaScript
Key ideas
  • Server first: render.php prints the finished HTML with data-wp-* directives; WordPress evaluates bind, class, style, text, context and each on the server, so the page is right before any JavaScript.
  • "interactivity": true and a viewScriptModule, built with --experimental-modules (silently skipped without it); the module loads only where the block is.
  • State is shared by the store (wp_interactivity_state()), context belongs to one element (wp_interactivity_data_wp_context()), derived state is computed: PHP closures for the server, getters in view.js for the browser, with the same answers.
  • The store: store( namespace, { state, actions } ), getContext(); actions change state and every directive follows. Actions that use the event synchronously need withSyncEvent().
  • Progressive enhancement: real links, state from the address, validated input: the feature works without JavaScript and for assistive technology (aria-current, aria-live, hidden).

Using the REST API

By the end you can
  • Explain routes, endpoints, methods, JSON responses and status codes, and list the routes your site offers
  • Read the catalog from core endpoints and shape the answer with _fields, _embed, context, filters and the pagination headers
  • Authenticate the right way: cookie plus nonce for logged-in JavaScript, application passwords for other programs
  • Call the REST API from JavaScript with apiFetch, and handle its errors
  • Read REST errors (400, 401, 403, 404) and tell "who are you?" from "you may not"
Key ideas
  • The REST API serves the site's data as JSON at /wp-json/ (or ?rest_route=): namespaces (wp/v2), routes, endpoints (route + method). Core builds routes for every type registered with show_in_rest.
  • Shape the answer: _fields (keep _links and _embedded when embedding), _embed, context, filters such as genres (IDs) and search; page with per_page/page and the headers X-WP-Total, X-WP-TotalPages, Link.
  • Cookie + nonce for the site's own JavaScript: without the X-WP-Nonce the request is anonymous, with a wrong one it is refused (CSRF protection).
  • Application passwords for programs: one per program, Basic authentication over HTTPS (or locally), the smallest role that works, revocable; never the account password.
  • apiFetch adds the root URL, the nonce and the locale, sends data as JSON and rejects with the server's error object.
  • Errors are { code, message, data.status }: 400 the request, 401 who are you?, 403 you may not, 404 no such route or item.

Custom REST Endpoints

By the end you can
  • Register routes with register_rest_route() on rest_api_init, as a feature class of the plugin
  • Declare arguments with types, defaults, limits and enums, and add your own validate_callback and sanitize_callback without losing the built-in checks
  • Describe responses with a JSON Schema, and return WP_REST_Response objects with headers and status codes
  • Return errors as WP_Error with the right status, and know what WordPress does with one that has none
  • Write a real permission_callback for every route, and explain why __return_true is only for public reads
Key ideas
  • register_rest_route( 'pagesco/v1', '/books', ... ) on rest_api_init; a route holds endpoints (methods, callback, permission_callback, args) and a schema. The namespace is vendor/version.
  • Arguments with a type are validated and sanitized from their schema (minimum, maximum, enum, required, default). A sanitize_callback of your own replaces that: keep 'validate_callback' => 'rest_validate_request_arg' next to it.
  • Order of work: validate, sanitize, permission, callback. Your callback receives clean, typed values.
  • Return data, a WP_REST_Response (status, headers such as X-WP-Total) or a WP_Error with a prefixed code and an explicit status; without one it is a 500. Do not leak what exists.
  • Every route has a permission_callback: __return_true only for public reads; writes check a capability; rest_authorization_required_code() gives 401 or 403.
  • OPTIONS shows the arguments and the schema; rest_do_request() calls routes from PHP without HTTP.

7.3

External APIs, Transients & WP-Cron

By the end you can
  • Call an external API with wp_remote_get() and wp_remote_post(), and handle each way it can fail: no answer, an error status, or an answer that is not what you expected
  • Keep API keys in wp-config.php and choose wp_safe_remote_get() when a URL comes from a user
  • Cache answers in transients, explain where they are stored and how a persistent object cache changes that, and cache failures briefly too
  • Schedule recurring work with WP-Cron, start and stop it on activation and deactivation, and inspect and run it with WP-CLI
  • Register an ability with the Abilities API and run it over the REST API
Key ideas
  • wp_remote_get() / wp_remote_post() with a timeout you can afford; read answers with wp_remote_retrieve_response_code(), _body(), _header().
  • Three failures, in order: a WP_Error (no answer, timeout), a status outside 2xx (still a normal response), a body that is not the data you expect.
  • Keys and URLs live in wp-config.php (wp config set), not in code; wp_safe_remote_*() for URLs users supply (SSRF).
  • Transients are options with an expiry (two non-autoloaded rows, or the object cache); they can vanish early: read through, cache failures briefly, never store false.
  • WP-Cron runs due events on the next request, as actions, without a user: schedule once on activation with wp_next_scheduled(), clear on deactivation, add the callback on every request.
  • The Abilities API describes units of work (input and output schemas, a permission check) that tools can discover and run, through PHP or /wp-json/wp-abilities/v1/.

By the end you can

  • Explain the object cache, its persistent version and transients, choose between them, and cache your own query with a key that is invalidated when the data changes

  • Explain srcset, sizes, lazy loading and why block templates get no automatic image optimization
  • Measure LCP, CLS and interaction timing in a browser, and say honestly what a local lab measurement can and cannot tell you
Key ideas
  • Measure first, several times, one change at a time. Three places: the server (queries), the network (what the page downloads), the browser (Core Web Vitals).
  • SAVEQUERIES in wp-config.php keeps every query with its time and caller in $wpdb->queries; $wpdb->num_queries counts. For measuring sessions only.
  • Missing options cost a query per request; N+1 (one meta read per item after 'fields' => 'ids') costs a query per item: update_postmeta_cache( $ids ) loads them in one.
  • The object cache remembers within a request; a persistent one (object-cache.php: Redis, Memcached) between requests, and it moves transients out of wp_options. Transients outlive the request on any site.
  • Cache with an invalidation plan: a key with wp_cache_get_last_changed( $group ), renewed by wp_cache_set_last_changed( $group ) on every write.
  • What the browser downloads: block CSS only for blocks on the page, inlined up to 40,000 bytes; script modules deferred; speculation rules prefetch the next page.
  • Images: content images get srcset, sizes, lazy loading and fetchpriority; a block theme's template images get nothing: give them an aspect ratio, and preload the LCP image (wp_preload_resources, fetchpriority). Never lazy-load the LCP image.
  • Core Web Vitals (LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1) are judged on field data; lab numbers compare changes.
