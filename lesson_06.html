🪝 Lesson 2.3: The Hooks System

You now know where WordPress keeps its files and its data. But how do you change what WordPress does without editing a single core file? The answer is hooks: named moments where WordPress stops and asks "does anyone want to run code now?" or "does anyone want to change this value?". Every theme, every plugin and every custom block you will write in this course plugs into WordPress through them, so this lesson is the one the rest of the course stands on.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Explain the difference between an action and a filter, and choose the right one for a task
  • Attach callbacks with add_action() and add_filter(), using priorities and the accepted-arguments count correctly
  • Remove a hook someone else added with remove_action() / remove_filter(), and say why a removal silently fails
  • Create your own action and filter hooks with do_action() and apply_filters() so other code can extend yours
  • Find the hook you need: in the core source, with has_filter() and $wp_filter, and from the command line with WP-CLI
  • Build the Pages & Co. store notice as a must-use plugin that others can customize through its own hooks
  • ⏱️ Time 120 minutes
  • 📋 Prerequisites Lesson 2.2: Core Architecture & the Database
  • 🛠️ You will build pagesco-site.php, a must-use plugin that shows the Pages & Co. store notice and offers its own hooks
  • 🧩 WordPress 7.1 on PHP 8.5 (the hooks API works the same on every supported WordPress version)
  • 🧱 Site your Pages & Co. development site with the content from Lesson 2.1, with WP-CLI

🤔 Why Hooks?

Every page WordPress serves is one long PHP program: index.php loads wp-load.php, which loads your configuration, the core files, your must-use plugins, your plugins and your theme, works out which content was asked for, and finally prints the HTML. You walked through that load order, line by line in wp-settings.php, in Lesson 2.2. Your code never gets to edit that program. Core files are replaced on every update, so a change you make in wp-includes/ disappears the next time WordPress updates itself.

Instead, WordPress announces what it is doing as it goes. At hundreds of points it calls a hook: a name that your code can register a function against. When the program reaches that point, WordPress calls every function registered for that name. There are two kinds:

  • An action says "this is happening now": init (WordPress has loaded), wp_head (the page's <head> is being printed), save_post (a post was just saved). Your function does something: prints markup, registers a post type, sends an email.
  • A filter says "here is a value, change it if you want": the_title (a post title about to be displayed), the_content, excerpt_length. Your function receives the value and returns the value to use, changed or not.
graph TD A["Request: GET /hello-world/"] --> B["wp-config.php, core files"] B --> C["must-use plugins, then plugins"] C --> D["action: plugins_loaded"] D --> E["theme functions.php"] E --> F["action: init"] F --> G["main query finds the post"] G --> H["action: wp_head"] H --> I["filters: the_title, the_content"] I --> J["action: wp_footer"] J --> K["action: shutdown"]

💡 Mental model: a radio show with call-ins

Think of WordPress as a radio host working through a running order. An action is the host saying "we are now at the weather, any callers?": callers may talk, but the show goes on the same way afterwards. A filter is the host saying "here is today's headline, any corrections?": each caller gets the headline, may rewrite it, and hands it to the next caller, and the host reads out whatever comes back from the last one. If a caller keeps the headline and hands back nothing, the host reads out nothing. You will see exactly that bug in Common Mistakes.

Your first hook

Hooks live in a plugin or in a theme's functions.php. For the lessons before Module 5, where you write a real plugin, the quickest place is a must-use plugin: any PHP file in wp-content/mu-plugins/ is loaded on every request, with no activation step, before all normal plugins (Lesson 2.2). You wrote a throwaway one for the debugging demo in Lesson 1.2; now you will see what they are really for. In your Lesson 1.2 project folder that is wordpress/wp-content/mu-plugins/, the folder where you already put mailpit-smtp.php. Create pagesco-hello.php there:

<?php
/**
 * Plugin Name: Pages & Co. Hello Hooks
 * Description: Lesson 2.3 demo: prints a line at the bottom of every page.
 */

function pagesco_hello_footer() {
	echo '<p class="pagesco-hello">Hello from a hook!</p>';
}
add_action( 'wp_footer', 'pagesco_hello_footer' );

Two lines do the work. The function says what to do. add_action( 'wp_footer', 'pagesco_hello_footer' ) says when: "when you reach the wp_footer action, call the function named pagesco_hello_footer". Notice that you pass the function's name as a string, without parentheses: you are not calling it, you are telling WordPress what to call later. Open http://localhost:8080/hello-world/ and scroll to the bottom; in View Source the line sits just before </body>:

http://localhost:8080/hello-world/   (View Source, search for pagesco-hello)

Output

<p class="pagesco-hello">Hello from a hook!</p>

✅ The prefix rule

Every function, hook name, option and global your code adds lives in one shared PHP program with WordPress core and every other plugin on the site. Two plugins that both declare hello_footer() stop the site with "Cannot redeclare". So everything you name gets a unique prefix. In this course it is pagesco_ (or the PagesCo\ namespace once you write classes in Module 5). The WordPress coding standards from Lesson 1.3 check for it.

⚡ Actions: Run Code at the Right Moment

The full signature is add_action( $hook_name, $callback, $priority = 10, $accepted_args = 1 ). The callback can be any of the PHP callables from Lesson 1.3 (and PHP Foundations Lesson 2.4): a function name, a closure, a static method [ 'PagesCo\Notice', 'render' ], or an object method [ $notice, 'render' ]. Named functions are the most common in themes; closures are handy for small things but, as you will see, they are hard for anyone else to remove.

Choosing the right hook is half the job, because each one fires at a known moment with known things ready. This mu-plugin writes one line to the debug log at each of the big actions of a front-end request. error_log() writes to wp-content/debug.log, because your wp-config.php has WP_DEBUG_LOG turned on (Lesson 1.2):

<?php
/**
 * Plugin Name: Pages & Co. Hook Order
 * Description: Lesson 2.3 demo: logs the order of the main actions of a front-end request.
 */

$pagesco_hooks = array( 'plugins_loaded', 'after_setup_theme', 'init', 'wp_loaded', 'template_redirect', 'wp_head', 'wp_footer', 'shutdown' );

foreach ( $pagesco_hooks as $pagesco_hook ) {
	add_action(
		$pagesco_hook,
		function () {
			if ( ! is_admin() && ! wp_doing_cron() && ! defined( 'WP_CLI' ) ) {
				error_log( 'hook order: ' . current_action() );
			}
		}
	);
}

Load http://localhost:8080/hello-world/ once, then look at the end of wordpress/wp-content/debug.log (open it in your editor, or run tail wp-content/debug.log in the WP-CLI container). These are the lines that one request added:

⚠️ "Too early" is the most common hook bug

Code at the top level of a plugin file runs while plugins are still loading: the current user is not known yet, the theme is not loaded, post types are not registered, and pluggable functions such as wp_get_current_user() do not even exist yet (the wp-settings.php tour in Lesson 2.2). If a function returns nothing useful or WordPress tells you it was "called incorrectly", ask first: is this running too early? The fix is almost always to move the code into a callback on init or a later hook.

🔁 Filters: Change a Value on Its Way Through

A filter callback receives a value and must return one. Here is a filter in core, so you can see what calling one looks like from the other side. This is the last line of get_the_title() in wp-includes/post-template.php:

grep -n "apply_filters( 'the_title'" wp-includes/post-template.php

Output

174:	return apply_filters( 'the_title', $post_title, $post_id );

apply_filters( 'the_title', $post_title, $post_id ) hands the title through every callback registered for the_title and returns what comes out. The extra argument, the post ID, is there so callbacks can decide what to do; you will use it in the next section. A small, real filter: WordPress separates the page title and the site name in the browser tab with a dash. The document_title_separator filter lets you choose another character. Add this to pagesco-hello.php:

function pagesco_title_separator( $separator ) {
	return '|';
}
add_filter( 'document_title_separator', 'pagesco_title_separator' );
http://localhost:8080/hello-world/   (the <title> in View Source)

Output

<title>Hello world! | Pages &amp; Co.</title>

The page title, a pipe, the site name. (&amp; is how the & in "Pages & Co." is written in HTML; the browser tab shows a plain ampersand.) The callback ignores the old separator and returns its own. Most filters do something with the value they receive. This one appends a line to the content of every post, using the the_content filter:

function pagesco_content_signature( $content ) {
	return $content . '<p class="pagesco-signature">Thanks for reading, from the Pages &amp; Co. team.</p>';
}
add_filter( 'the_content', 'pagesco_content_signature' );
http://localhost:8080/hello-world/   (the post's content area, as text)

Output

Welcome to WordPress. This is your first post. Edit or delete it, then start writing!
Thanks for reading, from the Pages & Co. team.

💡 Filters are not only for display

Plenty of filters change behavior rather than text: upload_mimes decides which file types may be uploaded, excerpt_length how long excerpts are, login_redirect where users land after logging in. The pattern is always the same: take the value, return the value. Under the hood actions and filters are one system. In wp-includes/plugin.php the whole body of add_action() is return add_filter( $hook_name, $callback, $priority, $accepted_args );; an action is a filter whose return value nobody uses.

🔢 Priorities and Accepted Arguments

When several callbacks hang on one hook, the priority (third argument, default 10) decides the order: lower numbers run first, and callbacks with the same priority run in the order they were added. You can watch it with a hook of your own and wp eval-file, which runs a PHP file with WordPress loaded. Save this as wordpress/priorities.php (the WordPress root, so WP-CLI finds it) and run it from the WP-CLI container:

<?php
add_filter( 'pagesco_demo', fn( $text ) => $text . ' [priority 20]', 20 );
add_filter( 'pagesco_demo', fn( $text ) => $text . ' [priority 5]', 5 );
add_filter( 'pagesco_demo', fn( $text ) => $text . ' [default 10, added first]' );
add_filter( 'pagesco_demo', fn( $text ) => $text . ' [default 10, added second]' );

echo apply_filters( 'pagesco_demo', 'Start:' ), "\n";
wp eval-file priorities.php

Output

Start: [priority 5] [default 10, added first] [default 10, added second] [priority 20]

Priority 5 first, then the two 10s in the order they were added, then 20. Use a lower number when your callback must run before others (WordPress itself uses 1 for _wp_render_title_tag on wp_head, so the <title> comes first), and a higher one, often 20 or 99, when you want the last word on a value other plugins have already changed.

Accepted arguments

The fourth argument says how many of the hook's values your callback wants. It defaults to 1, so even though the_title passes both the title and the post ID, a callback only receives the title unless you ask for two. This filter adds the post ID to titles, which needs both values:

<?php
function pagesco_title_with_id( $title, $post_id ) {
	return "{$title} (#{$post_id})";
}
add_filter( 'the_title', 'pagesco_title_with_id', 10, 2 );

echo get_the_title( 1 ), "\n";
echo get_the_title( 2 ), "\n";
wp eval-file title-ids.php

Output

Hello world! (#1)
Sample Page (#2)

10, 2 means "default priority, give me two arguments". Leave out the 2 and PHP stops with a fatal error (Common Mistakes, number 2). Delete the two demo files when you are done: rm priorities.php title-ids.php.

rm priorities.php title-ids.php

✂️ Removing Hooks

Sometimes the thing to change is a hook someone else added: core, a theme or a plugin. WordPress adds a <meta name="generator"> tag to every page, which tells the world the exact version you run:

http://localhost:8080/   (View Source, search for generator)

Output

<meta name="generator" content="WordPress 7.1.3" />

The tag comes from add_action( 'wp_head', 'wp_generator' ); in wp-includes/default-filters.php. To undo an add_action() you call remove_action() with the same hook, the same callback and the same priority. Add this to pagesco-hello.php:

remove_action( 'wp_head', 'wp_generator' );

Reload the page and search the source for generator: nothing. You can count it from the WP-CLI container too; grep -c prints how many lines match:

curl -s http://localhost:8080/ | grep -c 'name="generator"'

Output

0

(Hiding the version is a small privacy gain, not real security; keeping WordPress updated is what protects you, Lesson 8.4.)

The three rules of removing

  1. Match the priority. A callback added at priority 1 is only removed with remove_action( 'wp_head', '_wp_render_title_tag', 1 ). With the wrong priority remove_action() returns false and changes nothing, with no warning.
  2. Remove after it was added. Core's own hooks are added before any plugin loads, so a plugin can remove them at the top of its file. A hook that a theme adds inside its after_setup_theme callback does not exist yet when your plugin loads: remove it from a later hook, for example init.
  3. You need a handle on the callback. Removing [ $object, 'method' ] needs that same object, which is why well-written plugins keep their main object reachable (a function that returns it, or a static instance() method). A closure added as add_action( 'init', function () { ... } ) can only be removed by code that kept the closure in a variable. Use named functions or methods for anything someone might want to unhook, and remember that when you are tempted to write a closure in a plugin others will extend.

remove_all_actions( 'wp_head' ) and remove_all_filters() exist too. Avoid them: they also remove what core and every other plugin needed on that hook.

🧩 Creating Your Own Hooks

Hooks are not only for core. When your theme or plugin calls do_action() or apply_filters() with a name of its own, other developers (or you, six months later) can change its behavior without editing it. That is what makes a plugin extensible, and it is how big plugins such as WooCommerce let thousands of add-ons work with them. The rules:

  • Prefix the name like everything else: pagesco_store_notice, not store_notice.
  • Use a filter for a value others may change (text, an array of settings, a true/false decision) and an action for a moment others may want to act at ("before the notice is printed").
  • Pass context as extra arguments, the way the_title passes the post ID.
  • Document it with a DocBlock right above the call (what it is, each @param, @since), the same format core uses. Hooks are part of your public API: once people use one, renaming it breaks their sites.
/**
 * Filters the text of the Pages & Co. store notice.
 *
 * @since 1.0.0
 *
 * @param string $text The notice text, plain text (it is escaped when printed).
 */
$text = apply_filters( 'pagesco_store_notice', $text );

You will build exactly this in the project, with an action around it, and then use your own hook from the outside.

🔍 Finding the Hook You Need

WordPress core has well over two thousand hooks, and nobody memorizes them. Four ways to find the right one, from quickest to most thorough:

  1. Search the Code Reference. developer.wordpress.org/reference/hooks lists every core hook with its arguments and the file it lives in.
  2. Read the function you want to change. Find the core function that produces the thing (the Code Reference shows its source), then look for apply_filters or do_action inside it, as you did with get_the_title().
  3. Search the source on your machine. Every core file is in your wordpress/ folder. grep finds where a hook is called; -r searches folders, -n prints line numbers:
grep -rn "do_action( 'wp_body_open' )" wp-includes/

Output

wp-includes/general-template.php:3473:	do_action( 'wp_body_open' );
  1. Ask the running site. Every registered callback is stored in the global $wp_filter: an array of WP_Hook objects keyed by hook name, each holding its callbacks grouped by priority. has_filter() (and has_action()) tells you whether something is attached, and returns its priority:
wp eval 'var_dump( has_action( "wp_head", "_wp_render_title_tag" ), has_filter( "the_content", "pagesco_content_signature" ), has_filter( "the_content", "no_such_function" ) );'

Output

int(1)
int(10)
bool(false)

Priority 1 and priority 10 (a number means "attached, at this priority"), and false for nothing attached. Careful when you test the result: priority 0 is a valid answer that if ( has_filter( ... ) ) would treat as false, so compare with false !== has_filter( ... ). To see everything on a hook, walk $wp_filter. This prints the callbacks on wp_head that run at priority 2 or earlier. For a named function the ID is simply its name:

wp eval 'foreach ( $GLOBALS["wp_filter"]["wp_head"]->callbacks as $priority => $callbacks ) { if ( $priority <= 2 ) { foreach ( $callbacks as $id => $cb ) { echo "$priority  $id\n"; } } }'

Output

0  wp_enqueue_img_auto_sizes_contain_css_fix
1  _wp_render_title_tag
1  wp_enqueue_scripts
1  wp_preload_resources
1  wp_robots
1  wp_post_preview_js
1  wp_print_auto_sizes_contain_css_fix
1  wp_maybe_inline_styles
2  wp_resource_hints
2  feed_links

Yes, 0 is a priority too (and negative numbers work), and _wp_render_title_tag at 1 is why the <title> comes so early in the head. For everyday debugging, the free Query Monitor plugin shows the same information in the admin toolbar for every page you view: which hooks fired, which callbacks ran, in what order, and from which plugin. You will install it in Lesson 8.1.

⚠️ Common Mistakes

Make each mistake on purpose in a scratch file in wp-content/mu-plugins/, look at what WordPress tells you, then delete the file. Reading these messages calmly now is what makes them quick to fix later.

1. A filter that forgets to return

<?php
add_filter( 'the_title', function ( $title ) {
	$title = strtoupper( $title );
} );

Reload http://localhost:8080/hello-world/: the post has no title. View Source shows why, at the very top of the page, and grep -c confirms that the title block printed nothing:

curl -s http://localhost:8080/hello-world/ | head -n 3
curl -s http://localhost:8080/hello-world/ | grep -c 'wp-block-post-title'

Output

Deprecated: str_replace(): Passing null to parameter #3 ($subject) of type array|string is deprecated in /var/www/html/wp-includes/formatting.php on line 5777
<!DOCTYPE html>
0

What it means: the title is gone, here and in every list, menu and widget that shows titles. The closure changes its own copy of $title and returns nothing, and "nothing" in PHP is null, which becomes the title. The only message is a Deprecated notice that points into core, not at your file: the next filter on the_title, core's capital_P_dangit() at priority 11 (it fixes the spelling "Wordpress"), received your null and passed it to str_replace(). It sits above <!DOCTYPE html> because a block theme renders the whole template before it prints the <head>. On a live site, with WP_DEBUG off, there is no message at all. Fix: every filter callback ends with return $title;, also on the paths where it decides to change nothing. When a notice blames a core file, look at what your code handed to it.

rm wp-content/mu-plugins/mistake-no-return.php

function pagesco_register_things() {

(The ... line stands for seven frames inside WP-CLI's own code, left out here.) What it means: add_action() does not check the name; it stores the string. 4. Removing with the wrong priority (silent)

<?php
var_dump( remove_action( 'wp_head', '_wp_render_title_tag' ) );
var_dump( remove_action( 'wp_head', '_wp_render_title_tag', 1 ) );
wp eval-file mistake-remove.php

Output

bool(false)
bool(true)

What it means: the first call looks for _wp_render_title_tag at the default priority 10, finds nothing there and returns false. Only the second, with the priority it was added at, removes it. If you never look at the return value, the first version just "does not work". Fix: look up the priority where the hook is added (grep -rn "_wp_render_title_tag" wp-includes/default-filters.php), and when a removal seems to do nothing, var_dump() its result. (This script only removed the title tag inside its own WP-CLI run; your pages are unchanged.)

🛠️ Step 2: Give it its own hooks (10 min)

Replace the function with this version. It offers a filter for the text, an action just before the bar and one just inside it, and it lets anyone switch the notice off by returning an empty string from the filter. Nothing visible changes yet; you are building the doors other code will use.

<?php
/**
 * Plugin Name: Pages & Co. Site
 * Description: Site-wide features of the Pages & Co. bookstore: the store notice bar.
 * Version:     1.0.0
 * Author:      Pages & Co.
 */

/**
 * Prints the store notice at the top of every front-end page.
 */
function pagesco_render_store_notice() {
	/**
	 * Filters the text of the store notice.
	 *
	 * @since 1.0.0
	 *
	 * @param string $text Plain text; it is escaped when printed. Return '' to hide the notice.
	 */
	$text = apply_filters( 'pagesco_store_notice', 'Free shipping on orders over $35.' );

	if ( '' === $text ) {
		return;
	}

	/**
	 * Fires before the store notice bar is printed.
	 *
	 * @since 1.0.0
	 */
	do_action( 'pagesco_before_store_notice' );

	echo '<div class="pagesco-notice">' . esc_html( $text );

	/**
	 * Fires inside the store notice bar, after the text.
	 *
	 * @since 1.0.0
	 */
	do_action( 'pagesco_store_notice_end' );

	echo '</div>';
}
add_action( 'wp_body_open', 'pagesco_render_store_notice' );

🏋️ Exercise 3: Who Is on the_content?

Write a WP-CLI one-liner (or a small file for wp eval-file) that prints every callback attached to the_content, with its priority, in the order WordPress will run them. Which core function turns blank lines into paragraphs, and at which priority does it run?

💡 Hint

$GLOBALS['wp_filter']['the_content']->callbacks is an array of priority => callbacks. WordPress keeps it sorted by priority. Each callback is an array whose 'function' key holds what was passed to add_filter(): a string, an [ object, 'method' ] array, or a closure.

✅ Solution 
<?php
foreach ( $GLOBALS['wp_filter']['the_content']->callbacks as $priority => $callbacks ) {
	foreach ( $callbacks as $callback ) {
		$function = $callback['function'];
		if ( is_array( $function ) ) {
			$class    = is_object( $function[0] ) ? get_class( $function[0] ) : $function[0];
			$function = $class . '->' . $function[1];
		} elseif ( $function instanceof Closure ) {
			$function = '{closure}';
		}
		printf( "%3d  %s\n", $priority, $function );
	}
}

🏋️ Exercise 4: Count Every Hook on a Page (Stretch)

WordPress has a special hook name, all, whose callbacks run for every action and filter that fires. Write exercise-hook-count.php that counts how many hooks fire while the home page is built, and how many different hook names that is, and writes both numbers to the debug log on shutdown. Front-end requests only.

💡 Hint

An all callback receives the hook name as its first argument. Keep a static array of name => count inside the callback, or a global. On shutdown, array_sum() and count() give you the two numbers. Skip admin, cron and WP-CLI requests as the hook-order demo did.

✅ Solution 
<?php
/**
 * Plugin Name: Exercise: Hook Count
 */

$GLOBALS['pagesco_hook_counts'] = array();

add_action( 'all', function ( $hook_name ) {
	$GLOBALS['pagesco_hook_counts'][ $hook_name ] = ( $GLOBALS['pagesco_hook_counts'][ $hook_name ] ?? 0 ) + 1;
} );

add_action( 'shutdown', function () {
	if ( is_admin() || wp_doing_cron() || defined( 'WP_CLI' ) ) {
		return;
	}
	$counts = $GLOBALS['pagesco_hook_counts'];
	error_log( sprintf( 'hooks fired: %d calls of %d different hooks', array_sum( $counts ), count( $counts ) ) );
} );
http://localhost:8080/

Output (wp-content/debug.log; your numbers will differ)

[25-Oct-2026 21:51:45 UTC] hooks fired: 11896 calls of 616 different hooks

Thousands of hook calls for one page, and the page still renders in a fraction of a second: running a hook with no callbacks costs almost nothing. Your numbers depend on the theme, the plugins and the content, which is why they differ from these. Delete the file afterwards; all callbacks slow every request.

❓ Common Questions at This Stage

Should hooks go in my theme's functions.php or in a plugin?

Ask what should happen when the site switches themes. Anything about looks (a theme's menus, its styles, its block patterns) belongs to the theme. Anything about content and features (the Book post type, the store notice, a REST endpoint) belongs in a plugin, because it must survive a redesign. That is why the store notice lives in a site plugin and not in the pagesco theme you start in Module 3.

Do hundreds of hooks make WordPress slow?

Calling a hook with nothing attached costs well under a microsecond, so the thousands of calls per page that Exercise 4 counts are not a problem. What can be slow is the work a callback does: a database query in a the_title filter runs for every title on the page. Keep callbacks on frequent hooks cheap, and do expensive work once (Lesson 8.2 measures this).

Can I use class methods instead of functions?

Yes, and from Module 5 on you will: add_action( 'init', [ $this, 'register_post_types' ] ) inside a class, or [ Books::class, 'register' ] for a static method. The prefix problem disappears too, because the class lives in the PagesCo\Books namespace. The removal rule from this lesson still applies: to remove an object method someone needs the same object.

What is the difference between do_action( 'x', $a ) and do_action_ref_array( 'x', [ $a ] )?

They call the same callbacks with the same arguments; the second takes the arguments as an array, which helps when you build the list in code. apply_filters_ref_array() is the filter version. You will mostly read them in core rather than write them.

📝 Lesson Summary

🎓 Key Takeaways

  • A hook is a named point where WordPress calls the functions registered for it; it is how you change WordPress without editing core
  • Actions (add_action, do_action) run code at a moment; filters (add_filter, apply_filters) receive a value and must return it
  • The priority (default 10, lower first, ties in the order added) orders callbacks; accepted args (default 1) must match what your callback asks for
  • remove_action / remove_filter need the same hook, callback and priority, after the hook was added; they return false silently when nothing matches
  • Your own hooks make code extensible: prefix them (pagesco_), use filters for values and actions for moments, pass context, document them
  • Find hooks in the Code Reference, in the function you want to change, with grep in wordpress/, and with has_filter() / $wp_filter on the running site
