⚡ Lesson 8.2: Performance & Caching

Lesson 8.1 proved that the Pages & Co. plugin works. Today's question is whether it is fast, and the professional answer starts with a number, not a hunch. You will count what each page really costs the database, see what WordPress already caches for you and what a persistent object cache adds, read what the browser has to download, and measure the Core Web Vitals that search engines and visitors feel. Then you will make four real improvements to the plugin and the theme, each with a before and an after you measured yourself.

📏 Measure Before You Optimize

Picture the shop on a busy Saturday with a long line at the register. You could hire a second cashier, buy a faster card reader or move the gift wrapping elsewhere, and each idea sounds sensible. A good manager first stands next to the register for ten minutes with a notepad: if most of the time goes into wrapping, the card reader money is wasted. Web performance works the same way. Every page view is a line of small jobs, and the slow one is rarely the one you would have guessed.

💡 Mental model: three places where time goes

The server builds the HTML: PHP runs WordPress, your plugin and the theme, and asks the database questions. The network carries the HTML and then every file it names (CSS, JavaScript, images, fonts) to the visitor. The browser turns all of it into pixels and reacts to clicks. Caching makes the server's work cheaper or unnecessary; asset and image choices shrink the network's work; Core Web Vitals measure what the visitor finally experiences. Measure each place with its own tool.

for page in / /books/dune/ /find-a-book/; do

A few hundredths of a second each, on a site that runs on your own machine and has no other visitors. If the first page took much longer, that was PHP compiling WordPress's files after a restart; OPcache keeps the compiled code for the requests after it. These numbers swing from run to run (run the loop twice and compare), so never trust a single measurement, and never compare numbers from different machines. Two habits keep measurements honest: measure the same thing several times, and change one thing at a time.

🔢 What a Page Costs the Database

Every get_option(), WP_Query or $wpdb call that cannot be answered from memory becomes a query. Lesson 2.2's last exercise counted the home page's queries with SAVEQUERIES defined in a must-use plugin, and noticed that it missed the queries WordPress makes before must-use plugins load. Defined in wp-config.php, it records every query of the request. From the WP-CLI container:

wp config set SAVEQUERIES true --raw

Output

Success: Added the constant 'SAVEQUERIES' to the 'wp-config.php' file with the raw value 'true'.

With the constant on, $wpdb keeps every query in $wpdb->queries: an array per query with the SQL, the time it took in seconds, and the caller, the call stack that led to it, as wp_debug_backtrace_summary() writes it (Lesson 8.1). One get_posts() from WP-CLI, with the start of each query it made and the last function in its caller:

wp eval 'global $wpdb; $start = count( $wpdb->queries ); get_posts( array( "post_type" => "book", "posts_per_page" => 2 ) ); foreach ( array_slice( $wpdb->queries, $start ) as $query ) { $caller = explode( ", ", $query[2] ); printf( "%-58s %s\n", substr( preg_replace( "/\s+/", " ", $query[0] ), 0, 58 ), end( $caller ) ); }'

Output

SELECT wp_posts.* FROM wp_posts WHERE ID IN (40,39)        _prime_post_caches
SELECT post_id, meta_key, meta_value FROM wp_postmeta WHER update_meta_cache

Five queries for two books: the IDs, then the two posts' rows, their meta, and their genre terms (two queries), each for both books at once; the last function of each caller names the job. The full caller string is the whole path from the command to the query; in a web request it starts at wp-blog-header.php. Recording costs memory on every request, so SAVEQUERIES is for measuring sessions only; the project turns it off again. Now a tool that reports each web request's total. Create wordpress/wp-content/mu-plugins/pagesco-query-report.php:

<?php
/**
 * Plugin Name: Pages & Co. Query Report (temporary)
 * Description: Writes how many database queries each web request made to the debug log. Needs SAVEQUERIES.
 */

add_action(
	'shutdown',
	function () {
		global $wpdb;

		if ( ! defined( 'SAVEQUERIES' ) || ! SAVEQUERIES || wp_doing_cron() || defined( 'WP_CLI' ) ) {
			return;
		}

		// WP-Cron's own check runs on some requests and not on others: leave it out, so runs compare.
		$queries = array_filter(
			$wpdb->queries ?? array(),
			fn( $query ) => ! str_contains( $query[2], 'wp_cron' )
		);

		// Options something asked for that do not exist (WordPress remembers them for the request).
		$missing = array_filter(
			array_keys( (array) wp_cache_get( 'notoptions', 'options' ) ),
			fn( $name ) => ! str_starts_with( $name, '_' )
		);

		error_log(
			sprintf(
				'%s: %d queries; missing options: %s',
				strtok( $_SERVER['REQUEST_URI'], '?' ),
				count( $queries ),
				$missing ? implode( ', ', $missing ) : 'none'
			)
		);
	}
);
  • On shutdown, the last action of every request, after the page was sent.
  • WP-Cron's check is left out. When a scheduled job is due, the request that notices it makes a few extra queries to start WP-Cron (Lesson 7.3). That happens on some requests and not on others, and would make two measurements of the same page differ.
  • Missing options. When get_option() asks for an option that has no row, WordPress remembers the name in the notoptions cache for the rest of the request. The report prints those names (without transients, whose names start with _).

Reading the cost of one query: EXPLAIN

In Lesson 8.1, PHPCS warned about "possible slow" meta and taxonomy queries in the books route and the Book List, and the ruleset documented them for this lesson. Here is the query behind ?orderby=price, from WP_Query itself:

wp eval '$q = new WP_Query( array( "post_type" => "book", "post_status" => "publish", "posts_per_page" => 6, "meta_key" => "pagesco_price", "orderby" => "meta_value_num", "order" => "ASC" ) ); echo preg_replace( "/\s+/", " ", $q->request ), "\n";'

Output

SELECT SQL_CALC_FOUND_ROWS wp_posts.ID FROM wp_posts INNER JOIN wp_postmeta ON ( wp_posts.ID = wp_postmeta.post_id ) WHERE 1=1 AND ( wp_postmeta.meta_key = 'pagesco_price' ) AND wp_posts.post_type = 'book' AND ((wp_posts.post_status = 'publish')) GROUP BY wp_posts.ID ORDER BY wp_postmeta.meta_value+0 ASC LIMIT 0, 6

A join of wp_posts and wp_postmeta, sorted by the meta value turned into a number (meta_value+0), the shape Lesson 2.2 took apart. EXPLAIN shows how MySQL plans to run it (without the SQL_CALC_FOUND_ROWS keyword, which MySQL 9.7 marks as deprecated):

wp db query "EXPLAIN SELECT wp_posts.ID FROM wp_posts INNER JOIN wp_postmeta ON ( wp_posts.ID = wp_postmeta.post_id ) WHERE 1=1 AND ( wp_postmeta.meta_key = 'pagesco_price' ) AND wp_posts.post_type = 'book' AND ((wp_posts.post_status = 'publish')) GROUP BY wp_posts.ID ORDER BY wp_postmeta.meta_value+0 ASC LIMIT 0, 6\G"

Output

EXPLAIN: -> Limit: 6 row(s)
    -> Sort: (wp_postmeta.meta_value + 0), limit input to 6 row(s) per chunk
        -> Table scan on <temporary>  (cost=7.24..9.08 rows=3.67)

Read it from the innermost line out. MySQL finds the price rows through the meta_key index (a lookup, not a scan of the whole table), joins each to its post by the primary key, removes duplicates in a temporary table (the GROUP BY), and then sorts, because no index can sort by a value that has to be converted first. With eleven books that sort is instant. With fifty thousand it means sorting fifty thousand rows on every request that asks for the cheapest books, and that is what the PHPCS warning means by "possible": the cost grows with the catalog. The honest conclusion for Pages & Co. is to keep the query and know its limit (Exercise 3 measures it with two thousand made-up books); a shop that outgrows it caches the answer, or stores prices where an index can sort them (a custom table, Lesson 5.5).

🗄️ The Object Cache and Transients

Why only two dozen queries? Because WordPress remembers. The object cache is a key-value store in memory: wp_cache_set( $key, $value, $group ), wp_cache_get( $key, $group ), wp_cache_delete(). Core puts nearly everything it loads into it: all autoloaded options in one go (Lesson 2.2), each post, each post's meta, terms, users. Ask twice, and the second answer comes from memory:

wp eval 'global $wpdb; $before = $wpdb->num_queries; get_post_meta( 30, "pagesco_price", true ); get_post_meta( 30, "pagesco_author", true ); echo $wpdb->num_queries - $before, " query for two meta values\n";'

Output

1 query for two meta values

The first read loaded all of Dune's meta into the cache group post_meta; the second cost nothing. Since WordPress 6.1, WP_Query caches its own results the same way, under a key made from its arguments:

wp eval 'global $wpdb; $args = array( "post_type" => "book", "meta_key" => "pagesco_price", "orderby" => "meta_value_num", "posts_per_page" => 3 ); $start = $wpdb->num_queries; $first = new WP_Query( $args ); $middle = $wpdb->num_queries; $second = new WP_Query( $args ); printf( "first query: %d database queries, the same query again: %d\n", $middle - $start, $wpdb->num_queries - $middle );'

Output

first query: 6 database queries, the same query again: 0

But this cache lives in PHP's memory, and PHP forgets everything at the end of each request. Two WP-CLI commands are two requests:

wp eval 'wp_cache_set( "note", "Gatsby: back November 15", "pagesco_demo" ); var_dump( wp_cache_get( "note", "pagesco_demo" ) );'
wp eval 'var_dump( wp_cache_get( "note", "pagesco_demo" ) );'

Output

string(24) "Gatsby: back November 15"
bool(false)

The second request starts with an empty cache: false. So on a normal site the object cache saves repeated work within one request, and every request starts from zero. That is why the transients of Lesson 7.3 exist: a value with an expiry that survives between requests, stored as two non-autoloaded rows of wp_options. Reading one costs one query, once per request:

wp eval 'global $wpdb; $start = $wpdb->num_queries; get_transient( "pagesco_books_supplier_availability" ); $middle = $wpdb->num_queries; get_transient( "pagesco_books_supplier_availability" ); printf( "first read: %d query, second read: %d\n", $middle - $start, $wpdb->num_queries - $middle );'

Output

first read: 1 query, second read: 0

One query instead of a call to the supplier, which takes a hundred times longer and may fail: a good trade, and the reason the Supplier column reads a transient. Which tool for which job:

Caching your own query: a key that knows when the data changed

The hard part of any cache is not storing, it is knowing when the stored answer is no longer true. Core's answer, used for posts, terms and comments, is the last-changed pattern: a group has one timestamp, wp_cache_get_last_changed( $group ), that every write to the data renews (wp_cache_set_last_changed( $group ), WordPress 6.3). Each cached result's key includes that timestamp. After a write, every key is new, so every old answer is simply never read again, without anyone having to find and delete it:

$key    = 'find:' . md5( $limit . '|' . $location ) . ':' . wp_cache_get_last_changed( 'pagesco_events' );
$events = wp_cache_get( $key, 'pagesco_events' );
if ( ! is_array( $events ) ) {
	$events = /* the query */;
	wp_cache_set( $key, $events, 'pagesco_events' );
}
// ...and after every insert or delete:
wp_cache_set_last_changed( 'pagesco_events' );

The key names everything the answer depends on: the arguments and the state of the data. The project caches the events table's query this way, and the PHPCS warning DirectDatabaseQuery.NoCaching from Lesson 8.1 was suggesting exactly that. On a normal site it saves nothing (the Events page asks only once per request). It pays off with a persistent object cache.

💾 A Persistent Object Cache

A persistent object cache keeps the object cache between requests, in a store outside PHP. WordPress supports it through the object-cache.php drop-in (Lesson 2.2): if wp-content/object-cache.php exists, WordPress loads it instead of its own in-memory cache, very early in wp-settings.php. On production that store is usually Redis or Memcached, which hosts offer as a feature (with plugins such as Redis Object Cache to connect them). Your site has neither, but there is a way to try the real thing without a new container: the free SQLite Object Cache plugin keeps the cache in a SQLite file inside wp-content, using PHP's SQLite extension, which the course's WordPress image has. It is a measuring instrument for this lesson, not part of the project, and you remove it in the project. It needs an internet connection to install:

⚠️ What a persistent cache asks of your code

Without one, a stale entry dies at the end of the request. With one, a wrong answer stays until something deletes it: every cached value needs an invalidation plan (Common Mistake 1). Writes that bypass the APIs (SQL typed into wp db query, an import tool) bypass the invalidation too: run wp cache flush after them. Sites that share one Redis need different key prefixes (Redis Object Cache uses WP_CACHE_KEY_SALT). And Site Health recommends a persistent object cache only for larger sites (more than 1,000 posts, comments, terms or users, or more than 500 autoloaded options); for a small shop it is a nice extra, not a must.

💡 Page caching: the next level

An object cache makes building a page cheaper; a page cache skips building it. The finished HTML of an anonymous page view is stored and sent to the next visitor without running PHP at all: by the host (Nginx or Varnish), a CDN, or a plugin through the advanced-cache.php drop-in and define( 'WP_CACHE', true ). Page caches serve only logged-out visitors (anyone logged in sees their own toolbar and nonces), and they must be emptied when content changes, which caching plugins and hosts do on save. The Book Filter caches well: its ?genre= addresses are separate pages, and the filtering itself happens in the browser. Lesson 8.4 looks at what your host provides.

📦 What the Browser Downloads

The HTML is only the beginning: the browser then fetches what it names. Files in <head> that the page needs before it can draw anything (stylesheets, and scripts without defer/async) are render-blocking: each one is a round trip before the first pixel. Prefetching the next page: speculative loading

Since WordPress 6.8, pages for logged-out visitors on sites with pretty permalinks carry speculation rules:

Server time and bytes are causes; visitors feel effects. Google's Core Web Vitals name three effects, and search ranking uses them as one signal among many:

The thresholds apply to the 75th percentile of field data: measurements from real visitors' Chrome browsers over 28 days, published in the Chrome UX Report and shown by PageSpeed Insights for public sites with enough traffic. A local site has no field data at all. What you can do locally is lab measurement: one browser, one machine, a simulated network. Chrome's DevTools have both tools you need: the Lighthouse panel (a lab report with scores and advice; it cannot measure INP, which needs real interactions) and the Performance panel, which shows LCP, CLS and INP live while you use the page.

The browser exposes the same numbers to JavaScript through PerformanceObserver. This snippet prints LCP and CLS; paste it into the Console after a page has loaded:

// Load the page, wait until it has finished, then paste this into the browser's console.
// buffered: true hands each observer the entries recorded since the page started loading.
let lcp;
let cls = 0;

new PerformanceObserver( ( list ) => {
	lcp = list.getEntries().at( -1 ); // the last candidate is the final LCP
} ).observe( { type: 'largest-contentful-paint', buffered: true } );

new PerformanceObserver( ( list ) => {
	for ( const shift of list.getEntries() ) {
		if ( ! shift.hadRecentInput ) { // shifts right after a click or key press do not count
			cls += shift.value;
		}
	}
} ).observe( { type: 'layout-shift', buffered: true } );

setTimeout( () => {
	console.log( 'LCP', Math.round( lcp.startTime ), 'ms:', lcp.url || lcp.element.tagName, '| CLS', cls.toFixed( 3 ) );
}, 500 );

🛠️ Step 1: Cache the events query, and clear it on every change (15 min)

Replace src/EventsTable.php. New are the cache group constant, the cached find(), and a private flush_cache() that install(), add() and delete_before() call after they change the table:

<?php
/**
 * The shop's events, kept in a custom table.
 *
 * @package PagesCo\Books
 */

namespace PagesCo\Books;

/**
 * Creates and upgrades the {prefix}pagesco_events table, and reads and writes its rows.
 */
final class EventsTable implements Feature {

	/**
	 * The schema version this code expects. Raise it whenever schema() changes.
	 */
	public const DB_VERSION = 2;

	/**
	 * The option that records the schema version installed in this database.
	 */
	public const VERSION_OPTION = 'pagesco_books_db_version';

	/**
	 * The object cache group for the table's query results.
	 */
	public const CACHE_GROUP = 'pagesco_events';

	/**
	 * Checks the schema on every request, so a plugin update upgrades the table without a reactivation.
	 */
	public function register(): void {
		add_action( 'init', array( $this, 'maybe_upgrade' ) );
	}

	/**
	 * The table's full name, with this site's table prefix.
	 */
	public static function name(): string {
		global $wpdb;

		return $wpdb->prefix . 'pagesco_events';
	}

	/**
	 * Runs install() when the database is older than this code.
	 */
	public function maybe_upgrade(): void {
		if ( (int) get_option( self::VERSION_OPTION, 0 ) < self::DB_VERSION ) {
			self::install();
		}
	}

	/**
	 * Creates the table, or brings an existing one up to schema(), and records the version.
	 */
	public static function install(): void {
		require_once ABSPATH . 'wp-admin/includes/upgrade.php';

		dbDelta( self::schema() );
		update_option( self::VERSION_OPTION, self::DB_VERSION );
		self::flush_cache();
	}

	/**
	 * The CREATE TABLE statement in the exact shape dbDelta() expects.
	 */
	private static function schema(): string {
		global $wpdb;

		$table   = self::name();
		$collate = $wpdb->get_charset_collate();

		return "CREATE TABLE {$table} (
			id bigint unsigned NOT NULL AUTO_INCREMENT,
			title varchar(200) NOT NULL,
			starts_at datetime NOT NULL,
			location varchar(200) NOT NULL DEFAULT '',
			capacity smallint unsigned NOT NULL DEFAULT 0,
			created_at datetime NOT NULL,
			PRIMARY KEY  (id),
			KEY starts_at (starts_at)
		) {$collate};";
	}

	/**
	 * Adds one event and returns its ID (0 if the insert failed).
	 *
	 * @param string $title     The event's name.
	 * @param string $starts_at Local date and time, Y-m-d H:i:s.
	 * @param string $location  Where in the shop.
	 * @param int    $capacity  Seats, or 0 for an open event.
	 */
	public static function add( string $title, string $starts_at, string $location, int $capacity ): int {
		global $wpdb;

		$inserted = $wpdb->insert(
			self::name(),
			array(
				'title'      => $title,
				'starts_at'  => $starts_at,
				'location'   => $location,
				'capacity'   => $capacity,
				'created_at' => current_time( 'mysql', true ),
			),
			array( '%s', '%s', '%s', '%d', '%s' )
		);

		if ( ! $inserted ) {
			return 0;
		}

		self::flush_cache();
		return (int) $wpdb->insert_id;
	}

	/**
	 * Returns events in date order, optionally only those at one location.
	 *
	 * @param int    $limit    How many events at most.
	 * @param string $location Exact location, or '' for every location.
	 * @return object[] Rows with id, title, starts_at, location, capacity.
	 */
	public static function find( int $limit, string $location = '' ): array {
		global $wpdb;

		// The key names everything the result depends on: the arguments, and when the table last changed.
		$key    = 'find:' . md5( $limit . '|' . $location ) . ':' . wp_cache_get_last_changed( self::CACHE_GROUP );
		$events = wp_cache_get( $key, self::CACHE_GROUP );
		if ( is_array( $events ) ) {
			return $events;
		}

		if ( '' === $location ) {
			$sql = $wpdb->prepare(
				'SELECT id, title, starts_at, location, capacity FROM %i ORDER BY starts_at ASC LIMIT %d',
				self::name(),
				$limit
			);
		} else {
			$sql = $wpdb->prepare(
				'SELECT id, title, starts_at, location, capacity FROM %i WHERE location = %s ORDER BY starts_at ASC LIMIT %d',
				self::name(),
				$location,
				$limit
			);
		}

		$events = $wpdb->get_results( $sql ); // phpcs:ignore WordPress.DB.PreparedSQL.NotPrepared -- $sql comes from $wpdb->prepare() above.
		wp_cache_set( $key, $events, self::CACHE_GROUP );

		return $events;
	}

	/**
	 * Deletes the events that start before a date and time, and returns how many it deleted.
	 *
	 * @param string $datetime Local date and time, Y-m-d H:i:s.
	 */
	public static function delete_before( string $datetime ): int {
		global $wpdb;

		$deleted = (int) $wpdb->query(
			$wpdb->prepare( 'DELETE FROM %i WHERE starts_at < %s', self::name(), $datetime )
		);

		if ( $deleted ) {
			self::flush_cache();
		}
		return $deleted;
	}

	/**
	 * Marks every cached query result as outdated. Call it after each change to the table.
	 */
	private static function flush_cache(): void {
		wp_cache_set_last_changed( self::CACHE_GROUP );
	}
}
  • The key contains the arguments (hashed, so any location string is safe in a key) and the group's last-changed value.
  • is_array(), not a truthiness check such as if ( $events ): a cache miss is false, and an empty result is an empty array, which is falsy but a valid answer worth caching too.
  • flush_cache() renews the last-changed value after each change. 🛠️ Step 2: The missing settings row (10 min)

Every request asked for pagesco_books_settings and found nothing. The fix is a row, created on activation. Which value it holds matters: the defaults include a translated sentence (__( 'Open until 9 p.m. on Thursdays.' )), and storing it would freeze it in the language of the moment of activation. An empty array is the right row: it is autoloaded (add_option()'s default, Lesson 2.2), so reading it costs nothing, and empty, so Settings::get() still fills in every default at runtime, in the site's language. Replace src/Activator.php (the new lines are at the end of activate()):

 * @package PagesCo\Books

	/**

		$author = get_role( 'author' );

			'pagesco_bookseller',
			'Bookseller',

/**
 * Tells the browser, in the head of the front page, to fetch the hero image early and first:
 * it is the page's largest element, so it decides the Largest Contentful Paint (Lesson 8.2).
 *
 * @param array $resources Resources to preload, each an array of link attributes.
 * @return array
 */
function pagesco_preload_hero_image( $resources ) {
	if ( is_front_page() ) {
		$resources[] = array(
			'href'          => get_theme_file_uri( 'assets/images/book-image.webp' ),
			'as'            => 'image',
			'fetchpriority' => 'high',
		);
	}
	return $resources;
}

❓ Common Questions at This Stage

Should I install a caching or optimization plugin?

On most real sites, yes, for page caching, if the host does not cache pages itself (many managed WordPress hosts do, and then a page caching plugin only adds a second layer to debug). Be careful with "optimize everything" plugins that combine, minify, defer and lazy-load automatically: each switch can break a script or slow the LCP image (Common Mistake 3). Turn features on one at a time, and measure each, with the snippet and the Performance panel, before and after.

Is the Book Filter's server rendering of up to 100 books a performance problem?

Measured: Find a Book makes 27 queries, the same as Dune's page, because get_posts() loads all books, their meta and their terms in a handful of queries, however many there are, and the cached version makes none. What grows with the catalog is the HTML (every book's card) and the state JSON. Past a few hundred books, the REST-backed "Load more" design from Lesson 7.2 is the better shape.

What about autoload for my plugin's other options?

Autoload what is read on most requests (settings, the database version), and nothing big that is rarely needed: every autoloaded option is loaded on every request, used or not. Site Health warns when autoloaded options pass 800 KB in total (Lesson 2.2). Transients without an expiration are autoloaded, a reason to always give one. wp option list --autoload=on --fields=option_name,size_bytes shows what a site loads.

Do SCRIPT_DEBUG and WP_DEBUG distort my measurements?

Yes, a little: SCRIPT_DEBUG loads unminified CSS and JavaScript (more bytes, and different inlining, as the Navigation stylesheet showed), and SAVEQUERIES or Query Monitor add work to every request. That is fine for comparing before and after on the same setup, which is what this lesson did. For absolute numbers, measure a staging copy with production settings (Lesson 8.4).

📝 Lesson Summary

🎓 Key Takeaways

  • Measure first, several times, one change at a time: SAVEQUERIES in wp-config.php and $wpdb->queries for the server, the Network and Performance panels for the browser
  • Missing options cost a query per request; loops of get_post_meta() over IDs cost a query per item (N+1): update_postmeta_cache() loads them in one
  • EXPLAIN shows how a meta query runs: an index lookup by meta_key, then a sort that grows with the catalog
  • The object cache remembers within a request; a persistent object cache (an object-cache.php drop-in with Redis or Memcached) keeps it between requests and moves transients out of wp_options; transients outlive requests on any site
  • Cache with a plan to invalidate: keys that include wp_cache_get_last_changed(), renewed on every write
  • Block themes load only the CSS of blocks on the page and inline it up to 40,000 bytes; script modules are deferred and loaded only where used; speculation rules prefetch the next page
  • WordPress optimizes Media Library and content images (srcset, sizes, lazy loading, fetchpriority), but not a block theme's own template images: give them an aspect ratio, and preload the LCP image with wp_preload_resources
  • Core Web Vitals (LCP, INP, CLS) are judged on field data; local lab numbers are for comparing changes
