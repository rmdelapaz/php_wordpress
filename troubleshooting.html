🩺 Start Here: Is Everything Running?

Most problems are one of three things: a container is not running, a command ran in the wrong place, or the site's settings are not what the lessons expect. In your project folder (~/pagesco-dev, from Lesson 1.2):

docker compose ps                 # db (healthy), wordpress and mailpit: Up
wp core version                   # 7.1.3 through the shortcut
wp eval 'var_dump( WP_DEBUG, WP_DEBUG_LOG, WP_DEBUG_DISPLAY, SCRIPT_DEBUG, wp_get_environment_type() );'
wp cron test                      # WordPress can call itself

Output (the last two commands, on a healthy course site)

bool(true)
bool(true)
bool(true)
bool(true)
string(5) "local"
Success: WP-Cron spawning is working as expected.

Lesson 1.2's project, pagesco-check.php, checks the whole setup in one go (WordPress 7.1, PHP 8.5, the site address, pretty permalinks, the environment, debugging, a writable wp-content, the mail plugin and a test email): recreate it from Lesson 1.2 and run wp eval-file pagesco-check.php. Every line should say OK; the label of a FAILED line tells you which section below to read. Two logs answer most other questions:

tail -f wordpress/wp-content/debug.log      # PHP errors, from every request (Ctrl+C stops)
docker compose logs wordpress               # Apache: requests, startup problems; -f to follow

Error messages are explained one by one on the Common Errors page; this page is about the environment around your code.

🐳 Docker and Docker Compose

🔹 docker compose is not found, or a tutorial says docker-compose

The course needs Compose version 2 or newer, written with a space: docker compose version must print a version. The separate docker-compose program and the version: '3.8' line at the top of old files are from before Compose 2 (Lesson 1.2).

  • Windows: install Docker Desktop with the WSL 2 backend and switch on your Ubuntu distribution under Settings > Resources > WSL integration; run every command in the Ubuntu app.
  • macOS: start Docker Desktop once and wait until it says it is running.
  • Linux: Docker Engine and the Compose plugin from Docker's own repository, then sudo usermod -aG docker "$USER" and log out and back in.
  • docker run --rm hello-world proves the installation works.

🔹 "Bind for 0.0.0.0:8080 failed: port is already allocated"

Another program or container already uses port 8080 (or 8025 for Mailpit).

  • docker ps and look at the PORTS column: stop the other project (docker compose stop in its folder) or the other server.
  • One project per site: to try something unrelated, unpack the starter again under another folder name with other ports, or use wp-env or Playground.
  • Changing the course port means three places ("8080:8080", the Listen line in config/apache-8080.conf, the site URL) and every URL in the lessons: free the port instead.

🔹 "no configuration file provided: not found"

You are not in the project folder. Compose looks for compose.yaml in the current folder and its parents.

  • cd ~/pagesco-dev (or any folder inside it), then try again.

🔹 I edited compose.yaml (or .env) and nothing changed

Containers keep the settings they were created with.

  • docker compose up -d recreates exactly what changed; your files and database stay.
  • The wpcli service (and on the rehearsal site, cron) shares the wordpress container's network, so do not use docker compose restart wordpress alone: up -d recreates the dependent containers too (the rehearsal site's compose.yaml says so in its comments).
  • docker compose down removes the containers but keeps wordpress/ and the db_data volume; only down -v deletes the database.

🔹 The site is slow, or Docker Desktop uses a lot of memory

Both are usually about where the files live and how much the virtual machine may use (Lesson 1.2).

  • Windows: keep the project in the Linux file system (your Linux home, ~), not under /mnt/c/: there every page load crosses from Linux to Windows and WordPress becomes many times slower.
  • The course site runs comfortably in 2 to 3 GB; Docker Desktop's Settings > Resources has the memory slider. docker compose stop when you are not working.

🔹 The first wp command takes a minute and prints build lines

Normal, once: Compose builds the course's WP-CLI image from config/wpcli.Dockerfile (the official wordpress:cli-php8.5 plus fixes for MySQL 9.7 and PHP 8.5). Later commands take a second or two, because each one starts a fresh container.

🐧 Linux and WSL: File Ownership

On Linux, and inside WSL, the files in wordpress/ belong to whichever user the containers run as. Without the course fix that is user 33 (www-data), and your editor cannot save. The fix and the repair are in Lesson 1.2.

🔹 "Permission denied" when you save or create a file in wordpress/wp-content/

ls -ln wordpress/wp-content shows 33 33 as owner and group.

  • Before the first start: the three commands below (your numbers go into .env; compose.override.yaml runs wordpress and wpcli as you).
  • Already started without it: the repair, also below. It needs no sudo; your site and content stay.
  • Not sudo in front of your editor (root-owned files) and not chmod -R 777 (every user may write every file).
# Once, in the project folder, before the first "docker compose up -d":
printf 'PAGESCO_UID=%s\nPAGESCO_GID=%s\n' "$(id -u)" "$(id -g)" > .env
cp config/compose.linux.yaml compose.override.yaml
mkdir wordpress

# Repair, if the site already ran as user 33:
docker compose run --rm --user root wpcli chown -R "$(id -u):$(id -g)" /var/www/html
printf 'PAGESCO_UID=%s\nPAGESCO_GID=%s\n' "$(id -u)" "$(id -g)" > .env
cp config/compose.linux.yaml compose.override.yaml
docker compose up -d

🔹 The first start fails with tar: ./index.php: Cannot open: Permission denied in docker compose logs wordpress

Docker created the wordpress/ folder itself, as root, and the image (now running as you) cannot unpack WordPress into it.

  • mkdir wordpress as yourself before the first docker compose up -d. If the root-owned folder is already there, give it to yourself with the repair's first command (the chown above), then docker compose up -d.

🔹 "required variable PAGESCO_UID is missing a value"

compose.override.yaml is there, .env is not (or was deleted with a reset).

  • Create .env again with the printf line above. Keep .env and compose.override.yaml when you start over with docker compose down -v, and recreate wordpress/ with mkdir.

⌨️ WP-CLI and the wp Shortcut

The shortcut and the container shell are set up in Lesson 1.2.

🔹 wp: command not found in a new terminal

The alias exists only in the terminal where you typed it.

  • Add alias wp='docker compose --progress quiet run --rm wpcli wp' to the end of ~/.bashrc (Linux, WSL) or ~/.zshrc (macOS) and open a new terminal.
  • PowerShell (only if you run the project from Windows): function wp { docker compose --progress quiet run --rm wpcli wp @args } in notepad $PROFILE.
  • wp-env users type npx @wordpress/env run cli wp … where the lessons say wp ….

🔹 wp eval-file cannot find my file

Inside the container the current folder is always the WordPress root, /var/www/html, your wordpress/ folder, wherever you typed the command.

  • wp eval-file pagesco-check.php means wordpress/pagesco-check.php; put the file there, or give the path relative to it (wp eval-file pagesco-seed/seed-books.php).

🔹 A command says "Deprecated: Using null as an array offset … Colors.php on line 95"

WP-CLI 2.12's own code on PHP 8.5 (not yours). The course image hides it; a natively installed WP-CLI shows it after each Success or Error line. It does not appear on PHP 8.4.

🔹 A lesson's grep, ls or curl does not work in my terminal

Commands shown "from the WP-CLI container" run inside it, where http://localhost:8080 reaches the site and paths start at the WordPress root.

  • docker compose run --rm wpcli sh opens that shell (prompt /var/www/html $); exit leaves it.
  • Its grep is BusyBox: no --include option. grep -c that finds nothing prints 0 and exits with status 1, which is not a failure.

🔹 A command behaves as if nobody is logged in

WP-CLI runs as no user: capability checks fail, and tax_input in wp_insert_post() is silently dropped (Lesson 5.2).

  • Add --user=admin (or --user=maria) to the command, or wp_set_current_user() in a script.

🔹 A plugin's fatal error stops every WP-CLI command

WP-CLI loads WordPress, and with it the broken plugin (Lesson 8.1).

  • wp --skip-plugins=pagesco-crash plugin deactivate pagesco-crash, or --skip-plugins without a name to skip all plugins for that command.
  • A must-use plugin cannot be skipped this way: fix or move the file in wordpress/wp-content/mu-plugins/.

🗄️ The Database

MySQL 9.7 in the db service; WordPress's tables and how to query them are in Lesson 2.2.

🔹 "Error establishing a database connection"

WordPress cannot log in to MySQL.

  • Is db healthy in docker compose ps? The wordpress service waits for it on start, but a stopped or crashed db gives this page.
  • Did you change the password in compose.yaml after the first start? MySQL keeps the one it was created with: put the old one back and docker compose up -d (Common Mistake 4 of Lesson 1.2), or start over with docker compose down -v.
  • On the rehearsal site, the passwords come from its .env; the database account is created only when the volume is first created.

🔹 wp db query fails with "TLS/SSL error: self-signed certificate in certificate chain"

You are using the official wordpress:cli image (or another WP-CLI) against MySQL 9.7. Its database client refuses the development certificate.

  • Use the course's wpcli service: its image adds a MariaDB client wrapper that accepts the certificate (config/mariadb-local.sh). Against MariaDB (wp-env) the official image works.

Error (official wordpress:cli-php8.5 image, reproduced)

Error: Failed to get current SQL modes. Reason: ERROR 2026 (HY000): TLS/SSL error: self-signed certificate in certificate chain

🔹 Query output is hard to read

wp db query prints tab-separated rows (even in a terminal).

  • End the query with \G for one column per line: wp db query "EXPLAIN SELECT … \G".
  • wp db cli opens an interactive prompt with the familiar +----+ tables (it greets you as "the MariaDB monitor": the course image's client).
  • A graphical tool: publish the port with ports: ["3306:3306"] under db in compose.override.yaml and connect as wordpress / wordpress-dev-only to 127.0.0.1 (another host port if a MySQL server already runs on your computer). There is no phpMyAdmin.

🔹 An option "does not exist" although it is in the table

Its serialized value is broken: a SQL REPLACE() changed a string without fixing its recorded length.

  • Delete it and set it again through WordPress (wp option update, wp option patch update). For addresses across the database, wp search-replace (Lesson 8.4).

🔹 I want to try something risky

Back up first, and keep the file outside wordpress/, which the web server serves.

  • wp db export /tmp/before.sql and wp db import /tmp/before.sql (Lesson 8.3 uses exactly this around its uninstall test), or copy a dump out of the container shell.

🐞 Errors Do Not Show Up

The course site shows every PHP message in the page and in wp-content/debug.log (Lesson 1.2).

🔹 A page is broken but shows no error

Many WordPress mistakes print nothing at all; the Silent Failures table lists the ones in the course.

  • Check that debugging is on with the wp eval line in "Start Here": four times true and "local".
  • Read debug.log, not just the page: the editor's background requests, WP-Cron and REST calls log there without showing anything.
  • For a REST route, look at the response headers: "called incorrectly" notices travel in X-WP-DoingItWrong.
  • The page says "There has been a critical error on this website."? The details are in debug.log.
  • Query Monitor shows queries, hooks, HTTP calls and errors of one page (Lesson 8.1); remove it afterwards.

🔹 Notices appear above <!DOCTYPE html>

Expected in a block theme: it renders the whole template before printing <head>, so anything your code prints (a notice, an echoing shortcode) lands at the very top. Fix the cause; the position is a clue, not the bug.

🔹 The block editor breaks after a notice appears

With WP_DEBUG_DISPLAY on, any notice printed into an admin or REST response breaks the editor's JavaScript. In the course this happened with a missing build/ folder (Lesson 6.1).

  • Read debug.log and the browser's developer tools (Console, and the Network panel's failed requests); fix the first notice and reload.

🔗 Permalinks and 404s

🔹 Every page except the home page is a 404

Pretty permalinks are off or the rewrite rules are missing. A WP-CLI install leaves the plain /?p=1 style.

  • wp option get permalink_structure should print /%postname%/; if not, wp rewrite structure '/%postname%/' (it flushes the rules too).
  • The course site serves .htaccess from wordpress/: it must contain WordPress's rewrite block.

🔹 /books/ or /books/dune/ is a 404

The rewrite rules do not know the post type yet (Lesson 5.2).

  • Is pagesco-books active? Deactivating it unregisters the type and flushes, so its URLs 404 on purpose.
  • wp rewrite flush with the plugin active; wp rewrite list --match=/books/ shows the rules.
  • In your own plugin: flush on activation only, after registering the type and taxonomy in the activator (on the activation request the plugin's own init has not run yet).

🔹 A new page answers 404, or its URL ends in -2

New content is a draft by default (no slug, no URL), and a taken slug gets -2 (Lesson 2.1).

  • wp post get ID --fields=post_status,post_name; create with --post_status=publish --post_name=…; empty the trash of pages you replaced.

🔹 Page 2 of a list is a 404

The main query decides how many pages exist before any template runs (Lesson 4.2): change it with pre_get_posts, not with a custom query in the template.

🎨 Themes and the Site Editor

🔹 The design is suddenly plain (no palette, fonts or colors)

theme.json could not be parsed, so WordPress uses none of it. With debugging on, a notice "Error when decoding a JSON file at path …/theme.json: Syntax error" is at the top of every page.

  • Look for a trailing comma, single quotes or a comment; VS Code underlines errors when the file has its $schema line.

🔹 My change to a template file does not appear

Someone saved that template in the Site Editor: the database copy (wp_template, source custom) wins over the file (Lesson 3.2).

  • wp post list --post_type=wp_template,wp_template_part --fields=ID,post_name shows the copies.
  • Keep the owner's change: export it into the theme first (Lesson 3.3). Then Reset in the Site Editor, or wp post delete ID --force.

🔹 A new pattern does not show up

Check the file header first (a missing Slug is skipped, with a notice), then the cache: without WP_DEVELOPMENT_MODE theme, the list of pattern files is cached for 30 minutes per theme Version (Lesson 3.3, Lesson 8.4).

  • The course site has define( 'WP_DEVELOPMENT_MODE', 'theme' ); since Lesson 3.3: wp config get WP_DEVELOPMENT_MODE.
  • On a live site, raise the theme's Version with every release.

🔹 The store notice has no dark band in the classic theme

Classic and hybrid themes ignore styles.css in theme.json (it is printed for block themes only); pagesco-classic gets the rules from its enqueued style.css in Lesson 4.3.

🔹 Appearance > Menus says "Your theme does not support navigation menus or widgets."

A block theme is active. Menus are Navigation blocks there, edited in the Site Editor; the classic screens open with a classic theme that registers menu locations and widget areas.

🧱 Node, Builds and the Block Editor

All npm commands run in wordpress/wp-content/plugins/pagesco-books (Lesson 6.1).

🔹 Which Node do I need?

Node.js 24 LTS for the block build (node --version prints v24…); wp-env (Lesson 8.1) needs at least 22.13. On Windows, install Node inside your WSL distribution, where the project lives.

  • Without Node: docker run --rm -it --user "$(id -u):$(id -g)" -e HOME=/tmp -v "$PWD/wordpress:/var/www/html" -w /var/www/html/wp-content/plugins/pagesco-books node:24 npm run build from the project folder (PowerShell: leave out --user, write ${PWD}).

🔹 npm install prints warnings and "vulnerabilities"

Expected: "deprecated" lines are about packages deep inside the build tools, the audit counts issues in tools that run only on your machine, and the npm warn install-scripts lines come from npm 11, which no longer runs dependencies' install scripts unless you approve them. The build works without them: leave them unapproved.

🔹 My change does not appear in the editor or on the page

WordPress reads build/, never src/.

  • Run npm run build after every change, or keep npm start running while you work; then reload the editor.
  • Never edit files in build/: the next build replaces them (render.php included).
  • A new block needs no PHP: the Blocks feature registers everything in build/blocks/blocks-manifest.php. Not in the inserter? Check that its folder is in build/blocks/.

🔹 Notices about a missing manifest, and a broken editor

"The specified manifest file does not exist." means build/ is missing (a fresh checkout, a deleted folder). Run npm install and npm run build.

🔹 The interactive block renders but every click reloads the page

Either view.js was not built (the build scripts need --experimental-modules; check ls build/blocks/book-filter for view.js and view.asset.php), or the store namespace in view.js does not match data-wp-interactive (Lesson 6.4). Watch the Network panel's Doc filter: a reload is a new document.

🔹 "Block contains unexpected or invalid content"

The saved HTML of a static block no longer matches its save() (Lesson 6.2).

  • Open the browser console: "Block validation: …" says what differs.
  • You changed save(): add the previous version to deprecated; you changed a source selector: make sure it selects only its own element; you used __() in save(): use literal text.

🌐 REST API: 401 and 403

Authentication in Lesson 7.1, permissions in Lesson 7.2.

🔹 401 rest_not_logged_in while I am logged in

A cookie alone does not authenticate a REST request: without a valid nonce WordPress treats it as anonymous.

  • In wp-admin JavaScript use wp.apiFetch, which sends X-WP-Nonce; with fetch(), send the header yourself.
  • Front-end script modules have no apiFetch module in 7.1: they use fetch(), which is fine for public routes such as GET /pagesco/v1/books (Lesson 7.2).

🔹 401 with curl --user

Basic authentication takes application passwords only; a wrong, revoked or truncated one gets the same anonymous answer, by design.

  • Create one: wp user application-password create maria "Inventory script" --porcelain; Users > Profile shows when each was last used.
  • Application passwords exist only over HTTPS or on a site whose environment type is local: the rehearsal site (production, HTTP) has none.
  • Works locally, not on a host: some hosts (PHP as CGI or FastCGI, some proxies, nginx) do not pass the Authorization header to PHP; WordPress's .htaccess has a line for Apache, nginx needs server configuration.
  • Square brackets in a curl URL are a pattern to curl: write input%5Bslug%5D for input[slug].

🔹 403 rest_cannot_edit or rest_forbidden

You are authenticated, but this user may not do this: Devon (author) cannot edit Maria's books; editing events needs edit_others_posts. Use an account with the capability. A 403 rest_cookie_invalid_nonce means a stale nonce: reload the page.

⏰ WP-Cron

Scheduled events in Lesson 7.3; the live setup in Lesson 8.4.

🔹 A scheduled job did not run

WP-Cron runs due events only when a request comes in and WordPress can call its own wp-cron.php.

  • wp cron test on the course site: "Success: WP-Cron spawning is working as expected." The port-8080-inside-the-container setup of Lesson 1.2 is what makes this work; a 8080:80 mapping breaks it.
  • wp cron event list --fields=hook,recurrence (or --hook=pagesco_books_daily_sync) shows what is scheduled and when.
  • Is the callback added on every request? Inside is_admin() it never runs from wp-cron.php.
  • To run the job's code now without moving its schedule: wp eval 'do_action( "pagesco_books_daily_sync" );' (wp cron event run HOOK reschedules a recurring event to now plus its interval).

🔹 The same event is scheduled many times

Scheduling on init without wp_next_scheduled() adds one per request. Clean up with wp eval 'echo wp_clear_scheduled_hook( "HOOK" ), "\n";' and schedule once, on activation.

🔹 "The DISABLE_WP_CRON constant is set to true. WP-Cron spawning is disabled."

Expected on the rehearsal (production) site: a scheduler runs wp cron event run --due-now instead. docker compose logs cron in pagesco-live shows what it ran; on a real server, check the crontab line.

📬 Email and Mailpit

Mailpit catches every email at http://localhost:8025 (Lesson 1.2).

🔹 No email arrives in Mailpit

wp_mail() returns true only when the message was handed over.

  • Is mailpit-smtp.php in wordpress/wp-content/mu-plugins/? wp plugin list --status=must-use should list mailpit-smtp. Without it, the sender wordpress@localhost is rejected: "Invalid address: (From): wordpress@localhost".
  • Is the mailpit container up (docker compose ps)? The health check's "Test email sent" line fails while it is stopped.
  • The plugin sends to Mailpit only when the environment type is local.
  • Listen for the reason: wp eval 'add_action( "wp_mail_failed", function ( $error ) { echo $error->get_error_message(), "\n"; } ); var_dump( wp_mail( "admin@example.com", "Test", "Hello" ) );'

🔹 wp-env or the rehearsal site sends no email

wp-env includes no Mailpit (and has the same wordpress@localhost problem); the rehearsal site has no mail server, so wp_mail() returns false there. A real site needs an SMTP plugin with the host's mail settings, its password in the server's configuration. Never copy mailpit-smtp.php to a live site: the .gitignore of Lesson 8.4 keeps it out.

🧪 Composer, PHPCS and the Test Site

Set up in Lesson 8.1.

🔹 Composer commands

The course runs Composer in the official composer:2 image, in the plugin folder:

  • alias composer='docker run --rm -it --user "$(id -u):$(id -g)" -v "$PWD:/app" -w /app composer:2 composer' in wordpress/wp-content/plugins/pagesco-books.
  • "Composer could not detect the root package … version" is a harmless note; it disappears once wp-content is a Git repository (Lesson 8.4).
  • composer lint exits with status 0 and prints nothing when the code is clean.

🔹 wp-env will not start, or warns

wp-env 12 needs Node 22.13 or newer. The course's .wp-env.json in the plugin folder is a tests-only site on port 8889 with "testsEnvironment": false (without it wp-env prints a deprecation warning). Always the scoped package: npx @wordpress/env start.

🔹 PHPUnit errors "inside PHPUnit", or the test site is empty afterwards

Bare phpunit in the container is a different, incompatible version: run npx @wordpress/env run cli --env-cwd=wp-content/plugins/pagesco-books vendor/bin/phpunit. The test library reinstalls its database ("Installing…") on every run, which is why the tests get their own site: never point them at a database you care about.

🚀 Deployment and the Rehearsal Site

The rehearsal server pagesco-live runs next to your development site at http://localhost:8081, configured like production (Lesson 8.4).

🔹 The rehearsal site will not start: "copy .env.example to .env and fill it in first"

Its compose.yaml reads every secret from .env.

  • In ~/pagesco-live: cp .env.example .env, replace the two passwords with long random ones, mkdir wordpress deploy backups, and on Linux and WSL add the two PAGESCO_UID/PAGESCO_GID lines and compose.override.yaml as in Lesson 1.2.
  • Run its wp commands from its own folder: the shortcut always means the site whose folder you are in.

🔹 wp db export fails with "when using LOCK TABLES", and leaves a small file

The least-privilege account pagesco_app may not lock tables. Grant exactly that, as root (its password is in .env): docker compose exec db mysql -uroot -p -e "GRANT LOCK TABLES ON pagesco.* TO 'pagesco_app'@'%';". Delete the 831-byte header-only file: it is not a backup.

🔹 After the launch the Events page says "No events are scheduled right now."

The launch database was exported without --all-tables-with-prefix, so wp_pagesco_events is missing (the server log says "Table … doesn't exist"). Export again with the option and check the file: grep -c '^CREATE TABLE' file.sql should print 13.

🔹 Links on the live site still point to localhost:8080

The navigation and the Staff picks post store full addresses. Make the launch file with wp search-replace 'http://localhost:8080' 'NEW-ADDRESS' --all-tables-with-prefix --skip-columns=guid --export=file.sql (try --dry-run --report-changed-only first). WP_HOME and WP_SITEURL fix only the two options, for emergencies.

🔹 After a deploy every page says "There has been a critical error"

Read the server log (docker compose logs wordpress on the rehearsal site). In Lesson 9.1 the cause was a ZIP without a new folder of src/. Roll back to the previous release while skipping the broken plugin: wp --skip-plugins plugin install /deploy/pagesco-books-1.1.1.zip --force; then check npm pack --dry-run before building again.

🔹 A new pattern or a theme change is not live

Production has no development mode, so the list of pattern files is cached (30 minutes, for one theme Version): raise the Version in style.css with every release. Changes made in the Site Editor on the live site are content and stay in its database.

🔹 Application passwords are missing on the live site

wp_is_application_passwords_available() is false on a production site without HTTPS. On a real host with a certificate they work: create a new one there (development passwords were deleted at launch).

✅ The Debugging Checklist

  1. Read the whole message: level, sentence, file, line, and the first frames of the stack trace. Search the Common Errors page for a few words of it.
  2. Is it your code? Paths in wp-content/ are; a notice in wp-includes/ usually means your code handed core a bad value.
  3. Look in wordpress/wp-content/debug.log and docker compose logs wordpress, not just the page.
  4. Check the basics: docker compose ps, the right folder, wp core version, the plugin and theme active (wp plugin list, wp theme list).
  5. Rebuild and flush what caches: npm run build, wp rewrite flush, wp cache flush, the theme Version for patterns.
  6. Make the problem small: a scratch must-use plugin, a wp eval line, one curl request from the WP-CLI container.
  7. Undo what you tried before you try the next thing, and write down what fixed it in your journal.
