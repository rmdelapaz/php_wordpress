🧱 Lesson 6.1: Block Development Setup

Lesson 5.5 ended with a fair complaint: a shortcode works, but editors only ever see [pagesco_book id="30"] in brackets. Blocks are what editors actually see and arrange, and they are written partly in JavaScript. This lesson sets up the toolchain every block developer uses, Node 24 with @wordpress/create-block and @wordpress/scripts, and puts the first block, the start of the Pages & Co. book card, inside the pagesco-books plugin you have been growing since Lesson 5.1. One plugin, one more feature class, one new folder of JavaScript.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Describe a block type as WordPress sees it: block.json metadata, an editor script with edit and save, styles, and (later) PHP rendering
  • Scaffold a block into an existing plugin with npx @wordpress/create-block and --no-plugin, and read every generated file
  • Build blocks with @wordpress/scripts, and say what each file in build/ is for, including index.asset.php and the blocks manifest
  • Register all built blocks from a plugin feature with wp_register_block_types_from_metadata_collection()
  • Recognize the setup mistakes that cost beginners an afternoon: a second plugin by accident, a missing build, and stale build files
  • ⏱️ Time 135 minutes
  • 📋 Prerequisites Lesson 5.5: Shortcodes, $wpdb & Custom Tables
  • 🛠️ You will build the first draft of the pagesco/book-card block in pagesco-books/src/blocks/, built into build/blocks/ and registered by a new Blocks feature
  • 🧩 WordPress 7.1 on PHP 8.5 (the blocks manifest and collection registration need WordPress 6.8+, which the plugin already requires)
  • 🧱 Site your Pages & Co. site from Lesson 5.5, plus Node.js 24 LTS on your computer (or the node:24 Docker image)

🧩 What a Block Is, for a Developer

In Lesson 2.1 you read blocks from the outside: post_content holds HTML wrapped in comments such as <!-- wp:paragraph -->, with attributes as JSON in the opening comment. Now you look from the inside. A block type is a definition that WordPress and the editor share, and it has four parts:

PartWhere it livesWho uses it
Metadata: name, title, icon, category, attributes, supports, filesblock.jsonPHP (registration, REST, translations) and the editor
edit: what the block looks like and does while editinga React component in the editor scriptthe editor only
save: the HTML stored in post_contenta function in the editor scriptthe editor, when saving and when checking a stored block
Styles, and for dynamic blocks a PHP renderCSS files; render.php (Lesson 6.3)the editor and the front end

WordPress itself registers over a hundred block types this way. Ask the registry how many it knows on a bare request (WP-CLI loads WordPress like any other request, Lesson 2.2):

wp eval 'echo count( WP_Block_Type_Registry::get_instance()->get_all_registered() ), "\n";'

Output

116

Every one of those is a block.json in wp-includes/blocks/ plus JavaScript that core ships prebuilt. Your block will join this registry the same way. The important consequence of the table above: a static block's front end needs no JavaScript at all. The editor runs save once, stores the HTML, and visitors get that stored HTML, styled by the block's CSS. JavaScript is for editors.

💡 Mental model: a kit, a workshop and a shelf

Think of the source files in src/blocks/book-card/ as a flat-pack kit: modern JavaScript with JSX and SCSS that no browser reads as is. The build step is the workshop: @wordpress/scripts assembles the kit into plain JavaScript and CSS in build/blocks/book-card/. WordPress only ever looks at the shelf, the build/ folder, through the registration call in your plugin. Change the kit and nothing happens on the shelf until the workshop runs again. That one picture explains most of the mistakes later in this lesson.

graph TD A["src/blocks/book-card"] -->|"npm run build"| B["build/blocks + manifest"] B -->|"Blocks feature, init"| C["block type pagesco/book-card"] C --> D["editor: edit, save"] C --> E["front end: saved HTML, CSS"]

🟢 Node 24 and the Toolchain

Block code is written in modern JavaScript with JSX (the HTML-like syntax of React) and styles in SCSS. Browsers need plain JavaScript and CSS, and WordPress needs to know which of its own scripts your code depends on. The official tool for both jobs is @wordpress/scripts, a package that wraps webpack, Babel, Sass and the WordPress dependency extraction. It runs on Node.js, so Node is the one new program on your machine for this module.

Install Node.js 24 LTS (the long-term-support line; Lesson 5.5 asked you to have it ready). On macOS and Linux, a version manager such as nvm (nvm install 24) keeps versions per project; on Windows, install Node inside your WSL distribution, where the project lives (Lesson 1.2), not in Windows itself. Node brings npm, the package manager, and npx, which runs a package's command without installing it for good. Check both from the plugin's folder, wordpress/wp-content/plugins/pagesco-books, where every command in this module runs:

node --version
npm --version

Output (your patch versions may differ)

v24.21.0
11.19.0

Any 24.x prints v24 first; that is what matters. If you would rather not install Node, use Docker as you did for Composer in Lesson 5.1: the official node:24 image runs the same commands. From your project folder (on Windows PowerShell, leave out --user and write ${PWD}):

docker run --rm -it --user "$(id -u):$(id -g)" -e HOME=/tmp -v "$PWD/wordpress:/var/www/html" -w /var/www/html/wp-content/plugins/pagesco-books node:24 npm run build

Replace npm run build with any command from this module. The examples below show the commands alone, as you type them with Node installed.

💡 Why the browser never downloads React from you

Your block will import from packages such as @wordpress/blocks and @wordpress/block-editor, but those are not bundled into your file. The editor already loads them as global scripts (wp.blocks, wp.blockEditor, React itself), and the build replaces each import with a reference to the global and writes the list of script handles your file needs into index.asset.php. WordPress reads that list and loads the dependencies first. That is why a block's built JavaScript is a kilobyte or two, not hundreds.

🏗️ Scaffolding a Block into pagesco-books

@wordpress/create-block generates a working block so you do not start from an empty folder. Its default, and every quick-start tutorial you will find, creates a whole new plugin: a folder with its own main PHP file, package.json, node_modules/ and a build/ folder (Common Mistake 1 shows it). Pages & Co. already has its plugin, and the course keeps everything the shop does in that one plugin. So you use the mode made for this case, --no-plugin, which writes only the block's own files into a folder you choose.

Run without a slug, create-block asks its questions one by one: in --no-plugin mode it opens with "Let's add a new block to your existing WordPress plugin:", asks for the template variant (static or dynamic), then the block slug, the internal namespace, the display title, a short description, a dashicon, a category and the text domain. Answering the same questions with options is quicker to repeat and to read, so this is the command. Run it in the plugin's folder:

npx @wordpress/create-block@latest book-card --no-plugin --target-dir=src/blocks/book-card --namespace=pagesco --textdomain=pagesco-books --short-description="A book recommended by the Pages & Co. staff."

Reading the JavaScript

Three small files hold the behavior. Without their long comments, index.js registers the block in the editor with the name and settings from block.json, and connects the two functions:

import { registerBlockType } from '@wordpress/blocks';
import './style.scss';
import Edit from './edit';
import save from './save';
import metadata from './block.json';

registerBlockType( metadata.name, {
	edit: Edit,
	save,
} );

edit.js is a React component. useBlockProps() returns the wrapper's attributes (its class wp-block-pagesco-book-card, plus what the editor needs to select and move the block), so you spread them onto the outer element:

import { __ } from '@wordpress/i18n';
import { useBlockProps } from '@wordpress/block-editor';
import './editor.scss';

export default function Edit() {
	return (
		<p { ...useBlockProps() }>
			{ __( 'Book Card – hello from the editor!', 'pagesco-books' ) }
		</p>
	);
}

save.js returns the markup to store, with useBlockProps.save() for the wrapper. It must be a pure function of the block's attributes: same attributes, same HTML, every time (Lesson 6.2 shows what happens otherwise):

import { useBlockProps } from '@wordpress/block-editor';

export default function save() {
	return (
		<p { ...useBlockProps.save() }>
			{ 'Book Card – hello from the saved content!' }
		</p>
	);
}

The two texts differ on purpose, so you can see which function produced what. view.js holds front-end JavaScript (it only logs "Hello World!" to the console); a book card needs none, and its own comment says to delete it in that case, which the project does. style.scss and editor.scss hold the two kinds of styles.

⚙️ Building with @wordpress/scripts

A plugin made by create-block in its default mode comes with a package.json; in --no-plugin mode you add one to pagesco-books yourself, once. It names the build tool as a development dependency and defines two scripts. Create wordpress/wp-content/plugins/pagesco-books/package.json:

{
	"name": "pagesco-books",
	"version": "1.0.0",
	"private": true,
	"description": "The blocks of the Pages & Co. Books plugin.",
	"license": "GPL-2.0-or-later",
	"scripts": {
		"build": "wp-scripts build --webpack-src-dir=src/blocks --output-path=build/blocks --blocks-manifest",
		"start": "wp-scripts start --webpack-src-dir=src/blocks --output-path=build/blocks --blocks-manifest"
	},
	"devDependencies": {
		"@wordpress/scripts": "^37.0.0"
	}
}
  • "private": true stops npm from ever publishing the plugin to the npm registry by accident.
  • --webpack-src-dir=src/blocks tells the build where the block sources are. Its default is all of src/, which in this plugin is mostly PHP; pointing it at src/blocks keeps the build away from your classes.
  • --output-path=build/blocks is where the built blocks go, one folder per block.
  • --blocks-manifest also writes blocks-manifest.php: every block's block.json as one PHP array, so WordPress can register all the plugin's blocks without opening and decoding each JSON file on every request.

Install the tool. npm install reads package.json, downloads @wordpress/scripts with everything it needs into node_modules/ and records the exact versions in package-lock.json:

npm install

While you work: npm start

For day-to-day work, run npm start in a second terminal and leave it running. It builds once, then watches src/blocks/ and rebuilds within a second of every save; you only reload the editor. Stop it with Ctrl+C.

npm start

The development build is not minified and adds .map files (source maps) so the browser's developer tools show your original code. Run npm run build before you commit or deploy, so build/ holds the small production files again.

🔌 Registering the Built Blocks

The block exists on disk; WordPress does not know about it yet. A plugin made by create-block registers its blocks in its main file with one call on init. In pagesco-books, that call becomes a feature, following the rule from Lesson 5.1: one class in src/, one line in Plugin::feature_classes(). Create src/Blocks.php:

<?php
/**
 * The plugin's blocks, built from src/blocks/ into build/blocks/.
 *
 * @package PagesCo\Books
 */

namespace PagesCo\Books;

/**
 * Registers every block in build/blocks/ from the manifest that npm run build writes.
 */
final class Blocks implements Feature {

	/**
	 * Registers the blocks on init, like core registers its own.
	 */
	public function register(): void {
		add_action( 'init', array( $this, 'register_blocks' ) );
	}

	/**
	 * Registers the block types listed in build/blocks/blocks-manifest.php.
	 */
	public function register_blocks(): void {
		wp_register_block_types_from_metadata_collection(
			PAGESCO_BOOKS_DIR . 'build/blocks',
			PAGESCO_BOOKS_DIR . 'build/blocks/blocks-manifest.php'
		);
	}
}

wp_register_block_types_from_metadata_collection( $path, $manifest ) (WordPress 6.8) does two things. It registers the collection, telling WordPress "the block.json files under this path are already in this manifest", which is what wp_register_block_metadata_collection() (6.7) does on its own. Then it calls register_block_type_from_metadata() for every block in the manifest, which registers the block type and its scripts and styles under handles derived from the name. Older plugins call register_block_type( __DIR__ . '/build' ) once per block; that still works, it just reads and decodes each block.json on every request. List the feature after the shortcodes:

sed -i '/Shortcodes\\EventsShortcode::class,/a\			Blocks::class,' wp-content/plugins/pagesco-books/src/Plugin.php
wp eval '$type = WP_Block_Type_Registry::get_instance()->get_registered( "pagesco/book-card" );
echo $type->title, " (", $type->category, ")\n";
echo "editor script: ", implode( ", ", $type->editor_script_handles ), "\n";
echo "styles: ", implode( ", ", $type->style_handles ), " / editor: ", implode( ", ", $type->editor_style_handles ), "\n";
echo "view script: ", implode( ", ", $type->view_script_handles ), "\n";
echo wp_scripts()->registered["pagesco-book-card-editor-script"]->src, "\n";'

❓ Common Questions at This Stage

What goes into Git, and what reaches the server?

Commit the sources (src/blocks/), package.json and package-lock.json; leave out node_modules/ always and usually build/, which anyone can recreate with npm ci (an exact install from the lock file) and npm run build. The server needs the opposite: build/ yes, node_modules/ and the sources no. Lesson 8.4 sets up a .gitignore and a deployment that builds first; until then, simply never copy node_modules/ anywhere.

Do I have to learn React first?

No. Blocks use a small part of React: components as functions that return JSX, props (Lesson 6.2's attributes and setAttributes) and ready-made components from WordPress packages. You know enough JavaScript from earlier courses to read and change them, and the next lessons introduce each piece when it is needed. If you later want React itself, the course's sibling React course (Lesson 9.2) goes deep.

Could I write a block without a build step?

Yes: plain JavaScript using wp.element.createElement() instead of JSX, loaded directly as the editorScript. create-block still offers an "es5" template for it, and it is how blocks were written in the early days. You give up JSX, imports, SCSS and the automatic dependency list, so almost nobody does it for real work. Another way to avoid most JavaScript is a dynamic block (Lesson 6.3), whose output comes from PHP.

Why wp-scripts and not my own webpack setup?

@wordpress/scripts is WordPress's own configuration: it knows the block.json conventions, externalizes every @wordpress/* package and React, writes index.asset.php, RTL styles and the manifest, and its version (37 here) moves with WordPress. You can extend it with a webpack.config.js when you need something unusual, but starting from it saves days, and other WordPress developers recognize your setup at once.

🌟 Going Further: Bonus Challenge

The package.json scripts can do more than build. Add three: "lint:js": "wp-scripts lint-js src/blocks", "lint:css": "wp-scripts lint-style \"src/blocks/**/*.scss\"" and "format": "wp-scripts format src/blocks", run each one, and read what the WordPress JavaScript and CSS coding standards say about the scaffolded files and your edits. 🎓 Key Takeaways

  • A block type is block.json metadata plus an editor script with edit (the editing view) and save (the stored HTML), plus styles; a static block's front end needs no JavaScript
  • npx @wordpress/create-block@latest <slug> --no-plugin --target-dir=… --namespace=… --textdomain=… adds a block to an existing plugin; without --no-plugin you get a new plugin

  • WordPress reads only build/: rebuild after every change (or keep npm start running), and build wherever the plugin is installed from source
