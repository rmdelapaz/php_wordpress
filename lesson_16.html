🔐 Lesson 5.3: Security in WordPress

Last lesson you gave Pages & Co. a form that writes to the database and an API that anyone can read. That is exactly where a WordPress site is attacked. Security in WordPress is not a library you add; it is four habits you apply everywhere data crosses a boundary: sanitize what comes in, escape what goes out, prove a request is genuine with a nonce, and check the user is allowed with a capability, plus $wpdb->prepare() whenever you write SQL by hand. In this lesson you harden the real book meta box you wrote, add a "Mark sold out" action the safe way, and watch each defense turn a working attack into a dead end, on this very site.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Sanitize input on the way in and escape output on the way out, choosing the right function for each context
  • Protect every state change with a nonce and a current_user_can() capability check
  • Write safe database queries with $wpdb->prepare() and explain how SQL injection works
  • Name the common WordPress vulnerabilities (XSS, CSRF, SQL injection, broken access control) and the defense against each
  • Harden a real save handler and an admin action in the pagesco-books plugin

  • 📋 Prerequisites Lesson 5.2: Custom Post Types, Taxonomies & Meta
  • 🛠️ You will build a hardened BookMetaBox save path and a nonce-protected, capability-checked "Mark sold out" row action in pagesco-books

🛡️ The Security Mindset

Every value that enters WordPress from outside, a form field, a URL parameter, a REST body, a cookie, is untrusted: it might be a typo, or it might be crafted to break your page or steal a session. The whole of WordPress security follows one data flow, the one Lesson 1.3 drew: sanitize early (clean a value the moment you receive it), store it, then escape late (make it safe for its destination the moment you print it). Between those two gates sit two questions about every change: is this request genuine (a nonce), and is this user allowed (a capability)?

graph TD A["request: form, URL, REST"] --> B["is it genuine? check the nonce"] B --> C["is the user allowed? current_user_can()"] C --> D["sanitize the values"] D --> E["store in the database"] E --> F["escape for output: esc_html, esc_attr, esc_url"] F --> G["safe HTML in the page"]

💡 Mental model: the shop's back door

Think of your plugin's write handlers as the shop's back door, where deliveries come in. A nonce is checking the delivery has the token you handed the courier this morning, so it is not a stranger with a forged clipboard. The capability check is making sure the person signing for it works here. Sanitizing is unwrapping and inspecting the goods before they go on the shelf. Escaping is how you display a customer's name in the window: you print it as text, never as a sign someone else wrote for you. Skip any one step and the shop is exposed in a different way.

You already met every tool once: escaping and sanitizing in Lesson 1.3, nonces in Lesson 1.3 and current_user_can() in Lesson 2.1, $wpdb->prepare() in Lesson 2.2. This lesson puts them to work together on real code, and shows what each one prevents.

🧹 Escape Late: Stopping XSS

Cross-site scripting (XSS) is when a value someone else controls is printed into your page as HTML, so their markup, often a <script>, runs in your visitor's browser with your site's privileges. The defense is to escape every dynamic value for the context it lands in, at the moment of output. The author of a book comes from a form, so it is never to be trusted. Set Dune's author to a string full of HTML, then see how the Books column (your BookColumns from Lesson 5.2) prints it:

wp post meta update 30 pagesco_author 'Herbert & Sons <script>alert(1)</script>'
wp eval 'ob_start(); do_action( "manage_book_posts_custom_column", "pagesco_author", 30 ); echo ob_get_clean(), "\n";'
wp post meta update 30 pagesco_author 'Frank Herbert'

Output

Success: Updated custom field 'pagesco_author'.
Herbert &amp; Sons &lt;script&gt;alert(1)&lt;/script&gt;
Success: Updated custom field 'pagesco_author'.

The angle brackets and ampersand came back as &lt;, &gt; and &amp;: HTML entities, text the browser shows but does not run. That is esc_html() doing its job in the column's print_column() method. The last command puts the real author back.

🛑 The anti-example: the same column without escaping

Had the column printed the value raw, the stored <script> would run for every editor who opened the Books list, a stored XSS that persists in the database:

// NEVER do this: the author is printed as HTML, so a stored <script> executes.
echo get_post_meta( $post_id, 'pagesco_author', true );

// Always escape for the context. Here the value becomes text:
echo esc_html( get_post_meta( $post_id, 'pagesco_author', true ) );

The context decides the function. Lesson 1.3's family: esc_html() for text, esc_attr() for an HTML attribute value (the meta box uses it on every value="…"), esc_url() for an href or src, and wp_kses_post() when you must allow the same HTML a post may contain. The rule has no exceptions: escape at the point of output, even for data you sanitized on the way in, because you cannot always tell where a value has been.

🧼 Sanitize and Validate Input

Escaping protects output; sanitizing protects what you store. The two are not the same: sanitizing removes what does not belong (tags, control characters), and validating rejects what is the wrong shape (a price of "lots", a date of "soon"). The meta box save from Lesson 5.2 already sanitizes each field; here you will see those functions at work and add the two guards it still needs. Watch the sanitizers clean deliberately bad input:

wp eval '$in = array( "price" => "-5.50", "pages" => "412 pages", "author" => "O\x27Brien <b>Press</b>" );
echo "price:  ", max( 0, (float) $in["price"] ), "\n";
echo "pages:  ", absint( $in["pages"] ), "\n";
echo "author: ", sanitize_text_field( $in["author"] ), "\n";'

Output

price:  0
pages:  412
author: O'Brien Press

A negative price becomes 0, "412 pages" becomes the integer 412, and sanitize_text_field() strips the tags and trims the author to a clean line. Those are the rules a hardened save applies to every field before it touches the database.

⚠️ What the Lesson 5.2 save still needs

Two gaps remain in that first save. First, save_post fires on autosaves and revisions too; without a guard, an autosave with no form data would wipe the fields. The fix is wp_is_post_autosave() and wp_is_post_revision(). Second, the date field was only run through sanitize_text_field(), which happily stores "soon"; a real date needs validating against the Y-m-d format, not just cleaning. You will add both in the project, replacing the save method with a hardened version.

One subtlety you already use: WordPress adds slashes to request data (Lesson 1.3's magic-quotes demo), so the save calls wp_unslash() before sanitizing. Sanitize, validate, then store; never store raw request data and hope to clean it later.

🎫 Nonces and Capabilities

Sanitizing and escaping handle the content of a request. Two more checks handle the request itself. A nonce (number used once) is a token WordPress ties to a user, an action and a few hours; your form prints it and your handler verifies it, which proves the request came from a page your site served to this user, not from a forged link on another site. That attack is cross-site request forgery (CSRF): a page elsewhere quietly makes the logged-in victim's browser fire a request at your site. A capability check (current_user_can(), Lesson 2.1) then asks whether this user is even allowed to do it. You need both: a nonce without a capability lets any logged-in user act; a capability without a nonce can be triggered by forgery.

See the nonce round trip on its own, the two functions a form and a handler use:

wp eval 'wp_set_current_user( 2 );
$token = wp_create_nonce( "pagesco_books_save_details" );
echo "verify good token: ", var_export( (bool) wp_verify_nonce( $token, "pagesco_books_save_details" ), true ), "\n";
echo "verify bad token:  ", var_export( (bool) wp_verify_nonce( "deadbeef", "pagesco_books_save_details" ), true ), "\n";'

Output

verify good token: true
verify bad token:  false

A token made for that action verifies; a made-up one does not. In a form you never call these by hand: wp_nonce_field( 'action', 'name' ) prints the hidden field (the meta box already does), and in a handler check_admin_referer( 'action' ) verifies it and stops the request with a 403 if it is missing or stale. The "Mark sold out" action you build in the project uses exactly that, together with current_user_can( 'edit_post', $id ), so only an allowed user acting from a genuine link can flip a book's stock.

💡 Where WordPress checks for you, and where it does not

The block editor and the REST API check nonces and capabilities for you: Devon (an author) may not edit Maria's books (Common Mistakes, number 2), and the REST API refuses him too, because the book type maps to the standard post capabilities. But the moment you write your own form handler, admin action or AJAX endpoint, those checks are your job. WordPress will not add them; it only gives you the functions.

🗄️ Safe SQL with $wpdb->prepare()

Core APIs such as WP_Query and get_post_meta() build safe SQL for you, and you should prefer them. When you must write SQL by hand (Lesson 2.2, and the custom table in Lesson 5.5), any value you drop into the string is a door for SQL injection: a crafted value that ends your intended query and starts the attacker's. The defense is $wpdb->prepare(), which puts values in through typed placeholders, %s for strings, %d for integers, %f for floats, %i for identifiers, and quotes and escapes each one.

🛑 The anti-example: a value concatenated into SQL

Imagine a shop report that looks up books by an author taken from the URL. Built like this, a value such as ' OR 1=1 -- changes what the query returns, and worse is possible:

// NEVER do this: $author goes straight into the SQL string.
$author  = $_GET['author'];
$results = $wpdb->get_results(
    "SELECT post_id FROM {$wpdb->postmeta}
     WHERE meta_key = 'pagesco_author' AND meta_value = '" . $author . "'"
);

The safe version passes the value as a placeholder. Run it against the catalog, a real report of Frank Herbert's books under $20, and look at the SQL prepare() produced:

wp eval 'global $wpdb;
$author    = "Frank Herbert";
$max_price = 20;
$sql = $wpdb->prepare(
    "SELECT p.post_title, pm_price.meta_value AS price
     FROM {$wpdb->posts} p
     INNER JOIN {$wpdb->postmeta} pm_author ON pm_author.post_id = p.ID AND pm_author.meta_key = \"pagesco_author\"
     INNER JOIN {$wpdb->postmeta} pm_price  ON pm_price.post_id  = p.ID AND pm_price.meta_key  = \"pagesco_price\"
     WHERE p.post_type = %s AND pm_author.meta_value = %s AND pm_price.meta_value + 0 <= %d",
    "book",
    $author,
    $max_price
);
echo $sql, "\n---\n";
foreach ( $wpdb->get_results( $sql ) as $row ) { echo $row->post_title, " $", $row->price, "\n"; }'

Output

SELECT p.post_title, pm_price.meta_value AS price
     FROM wp_posts p
     INNER JOIN wp_postmeta pm_author ON pm_author.post_id = p.ID AND pm_author.meta_key = "pagesco_author"
     INNER JOIN wp_postmeta pm_price  ON pm_price.post_id  = p.ID AND pm_price.meta_key  = "pagesco_price"
     WHERE p.post_type = 'book' AND pm_author.meta_value = 'Frank Herbert' AND pm_price.meta_value + 0 <= 20
---
Dune $14.99

prepare() quoted 'Frank Herbert' and inserted 20 as a number; a value with a stray quote would have been escaped, not treated as SQL. The query returns Dune. One rule covers it: no variable ever goes directly into a query string; it goes through a placeholder in prepare().

📋 The Common Vulnerabilities

The same handful of weaknesses account for most compromised WordPress plugins. Each maps to a defense you have now used:

VulnerabilityWhat happensDefense
Cross-site scripting (XSS)Attacker HTML runs in a visitor's browserEscape on output: esc_html(), esc_attr(), esc_url(), wp_kses_post()
Cross-site request forgery (CSRF)A forged request rides a logged-in user's sessionNonces: wp_nonce_field() + check_admin_referer() / wp_verify_nonce()
SQL injectionA crafted value rewrites your query$wpdb->prepare(), or a core API that does it for you
Broken access controlA user does something their role should forbidcurrent_user_can() on every state change; permission_callback on REST routes (Module 7)
Unsanitized inputBad or malicious data is storedSanitize and validate on input: sanitize_text_field(), absint(), type checks
Exposed secretsKeys in code leak through the repo or a direct requestKeep secrets in wp-config.php / environment; guard files with ABSPATH (Lesson 5.1)

Notice that none of these needs a security plugin: they are habits in your own code. A firewall or a scanner (Module 8 mentions them) is a backstop, not a substitute for escaping and checking.

⚠️ Common Mistakes

1. Escaping for the wrong context

Escaping is not one function; the destination decides. Running a URL through esc_html() mangles it, while a value meant as text needs esc_html(), not esc_url(). See the mismatch:

wp eval '$url = home_url( "/books/?genre=sci-fi&sort=price" );
echo "esc_url:  ", esc_url( $url ), "\n";
echo "esc_html: ", esc_html( $url ), "\n";'

Output

esc_url:  http://localhost:8080/books/?genre=sci-fi&#038;sort=price
esc_html: http://localhost:8080/books/?genre=sci-fi&amp;sort=price

What it means: esc_url() keeps a usable link (encoding the & as &#038; for an attribute); esc_html() turns the same string into display text, which breaks it as an href. Fix: match the function to the context, esc_url() in an href or src, esc_attr() in any other attribute, esc_html() in text.

2. A nonce but no capability check

A common half-measure: the handler verifies the nonce and stops there. But a nonce only proves the request is genuine for this user; it says nothing about whether the user is allowed. A logged-in subscriber visiting your form page gets a valid nonce too. Confirm that a capability is a separate question:

wp eval 'wp_set_current_user( 2 );
echo "editor edit Dune (30):   ", var_export( current_user_can( "edit_post", 30 ), true ), "\n";
wp_set_current_user( 3 );
echo "author edit Dune (30):   ", var_export( current_user_can( "edit_post", 30 ), true ), "\n";'

Output

editor edit Dune (30):   true
author edit Dune (30):   false

What it means: the editor Maria may edit Dune; the author Devon may not (it is not his, and authors cannot edit others' posts). A nonce check would have passed for both. Fix: always pair the nonce with current_user_can() for the specific object, as the hardened save and the stock action do.

3. Trusting that an insert checks permissions

Functions like wp_insert_post() and update_post_meta() do not check capabilities (Lesson 2.1's FAQ warned of this): they assume you already did. A handler that writes without a prior check is broken access control, even with no visible error:

wp eval 'wp_set_current_user( 3 );
$id = wp_insert_post( array( "post_type" => "book", "post_title" => "Snuck in", "post_status" => "publish" ) );
echo "created book as author Devon: ", ( $id ? "ID $id" : "failed" ), "\n";
wp_delete_post( $id, true );'

Output

created book as author Devon: ID 41

What it means: wp_insert_post() created a book even though we set the current user to an author, because the function trusts the caller. The last line deletes it again. Fix: gate every write behind current_user_can() yourself; the database functions will not do it for you.

🛠️ Project: Harden the Plugin

Now apply all of it to pagesco-books: replace the meta box save with a hardened version, and add a "Mark sold out / Mark in stock" action to the Books list the safe way, with a nonce and a capability check. Allow about 30 minutes.

🛠️ Step 1: Harden the meta box save (10 min)

Replace wordpress/wp-content/plugins/pagesco-books/src/Admin/BookMetaBox.php with this version. The render() method is unchanged (it already escaped every value with esc_attr()); the new save() adds the autosave and revision guards, validates the date with a small helper, and clamps the price:

<?php
/**
 * The "Book details" box on the book editing screen (hardened in Lesson 5.3).
 *
 * @package PagesCo\Books
 */

namespace PagesCo\Books\Admin;

use PagesCo\Books\BookPostType;
use PagesCo\Books\Feature;

/**
 * Shows the book meta as a form under the editor and saves it safely with the book.
 */
final class BookMetaBox implements Feature {

	/**
	 * The fields this box edits, so render and save stay in step.
	 */
	private const TEXT_FIELDS = array( 'pagesco_author', 'pagesco_isbn' );

	/**
	 * Hooks the box into the book screen and the save into save_post_book.
	 */
	public function register(): void {
		add_action( 'add_meta_boxes_' . BookPostType::NAME, array( $this, 'add' ) );
		add_action( 'save_post_' . BookPostType::NAME, array( $this, 'save' ), 10, 2 );
	}

	/**
	 * Adds the box to the book editing screen.
	 */
	public function add(): void {
		add_meta_box(
			'pagesco-book-details',
			__( 'Book details', 'pagesco-books' ),
			array( $this, 'render' ),
			BookPostType::NAME,
			'normal',
			'high'
		);
	}

	/**
	 * Prints the form fields, filled with the saved values and escaped for the attribute context.
	 *
	 * @param \WP_Post $post The book being edited.
	 */
	public function render( $post ): void {
		wp_nonce_field( 'pagesco_books_save_details', 'pagesco_books_details_nonce' );

		$author    = get_post_meta( $post->ID, 'pagesco_author', true );
		$price     = get_post_meta( $post->ID, 'pagesco_price', true );
		$pages     = get_post_meta( $post->ID, 'pagesco_pages', true );
		$published = get_post_meta( $post->ID, 'pagesco_published', true );
		$isbn      = get_post_meta( $post->ID, 'pagesco_isbn', true );
		$in_stock  = get_post_meta( $post->ID, 'pagesco_in_stock', true );
		?>
		<p>
			<label for="pagesco-author"><?php esc_html_e( 'Author', 'pagesco-books' ); ?></label><br>
			<input type="text" id="pagesco-author" name="pagesco_author" class="widefat" value="<?php echo esc_attr( $author ); ?>">
		</p>
		<p>
			<label for="pagesco-price"><?php esc_html_e( 'Price (USD)', 'pagesco-books' ); ?></label><br>
			<input type="number" id="pagesco-price" name="pagesco_price" min="0" step="0.01" value="<?php echo esc_attr( $price ); ?>">
		</p>
		<p>
			<label for="pagesco-pages"><?php esc_html_e( 'Pages', 'pagesco-books' ); ?></label><br>
			<input type="number" id="pagesco-pages" name="pagesco_pages" min="1" step="1" value="<?php echo esc_attr( $pages ); ?>">
		</p>
		<p>
			<label for="pagesco-published"><?php esc_html_e( 'First published', 'pagesco-books' ); ?></label><br>
			<input type="date" id="pagesco-published" name="pagesco_published" value="<?php echo esc_attr( $published ); ?>">
		</p>
		<p>
			<label for="pagesco-isbn"><?php esc_html_e( 'ISBN', 'pagesco-books' ); ?></label><br>
			<input type="text" id="pagesco-isbn" name="pagesco_isbn" value="<?php echo esc_attr( $isbn ); ?>">
		</p>
		<p>
			<label>
				<input type="checkbox" name="pagesco_in_stock" value="1" <?php checked( (bool) $in_stock ); ?>>
				<?php esc_html_e( 'In stock', 'pagesco-books' ); ?>
			</label>
		</p>
		<?php
	}

	/**
	 * Saves the fields when the book is saved from this form.
	 *
	 * @param int      $post_id The book's ID.
	 * @param \WP_Post $post    The book.
	 */
	public function save( $post_id, $post ): void {
		// 1. Is this a real submission of our form, not an autosave or a bulk edit?
		if ( ! isset( $_POST['pagesco_books_details_nonce'] ) ) {
			return;
		}
		if ( wp_is_post_autosave( $post_id ) || wp_is_post_revision( $post_id ) ) {
			return;
		}

		// 2. Did it carry our valid nonce?
		if ( ! wp_verify_nonce( sanitize_key( wp_unslash( $_POST['pagesco_books_details_nonce'] ) ), 'pagesco_books_save_details' ) ) {
			return;
		}

		// 3. May this user edit this book?
		if ( ! current_user_can( 'edit_post', $post_id ) ) {
			return;
		}

		// 4. Sanitize and validate every field before it is stored.
		$in = wp_unslash( $_POST );

		update_post_meta( $post_id, 'pagesco_author', sanitize_text_field( $in['pagesco_author'] ?? '' ) );
		update_post_meta( $post_id, 'pagesco_isbn', sanitize_text_field( $in['pagesco_isbn'] ?? '' ) );
		update_post_meta( $post_id, 'pagesco_price', max( 0, (float) ( $in['pagesco_price'] ?? 0 ) ) );
		update_post_meta( $post_id, 'pagesco_pages', absint( $in['pagesco_pages'] ?? 0 ) );
		update_post_meta( $post_id, 'pagesco_published', self::valid_date( $in['pagesco_published'] ?? '' ) );
		update_post_meta( $post_id, 'pagesco_in_stock', isset( $in['pagesco_in_stock'] ) );
	}

	/**
	 * Returns the value only if it is a real Y-m-d date, otherwise an empty string.
	 *
	 * @param string $value The submitted value.
	 * @return string
	 */
	private static function valid_date( $value ): string {
		$value = sanitize_text_field( $value );
		$date  = \DateTime::createFromFormat( 'Y-m-d', $value );

		return ( $date && $date->format( 'Y-m-d' ) === $value ) ? $value : '';
	}
}

The save now runs only for a genuine form submission (not an autosave), by an allowed user, with every value sanitized and the date validated. Confirm the file is valid and the box is still registered on the book screen:

echo isset( $GLOBALS["wp_meta_boxes"]["book"]["normal"]["high"]["pagesco-book-details"] ) ? "Book details box registered\n" : "missing\n";'

🛠️ Step 2: Add a safe "Mark sold out" action (12 min)

Create src/Admin/StockAction.php. It adds a link to each book's row that flips its stock, and handles the click at admin-post.php. Every defense from this lesson is in it: the link is built with wp_nonce_url(), only shown to users who may edit that book; the handler verifies the nonce with check_admin_referer(), checks the capability, then redirects with wp_safe_redirect():

<?php
/**
 * A "Mark sold out" / "Mark in stock" link for each book on the Books screen.
 *
 * @package PagesCo\Books
 */

namespace PagesCo\Books\Admin;

use PagesCo\Books\BookPostType;
use PagesCo\Books\Feature;

/**
 * Adds the row action and handles the request it sends to admin-post.php.
 */
final class StockAction implements Feature {

	/**
	 * The admin-post.php action name, also the start of the nonce action.
	 */
	private const ACTION = 'pagesco_books_toggle_stock';

	/**
	 * Hooks the link into the list and the handler into admin-post.php.
	 */
	public function register(): void {
		add_filter( 'post_row_actions', array( $this, 'add_link' ), 10, 2 );
		add_action( 'admin_post_' . self::ACTION, array( $this, 'handle' ) );
	}

	/**
	 * Adds the link to rows of books the current user may edit.
	 *
	 * @param string[] $actions Row action links.
	 * @param \WP_Post $post    The post in this row.
	 * @return string[]
	 */
	public function add_link( $actions, $post ) {
		if ( BookPostType::NAME !== $post->post_type || ! current_user_can( 'edit_post', $post->ID ) ) {
			return $actions;
		}

		$url = add_query_arg(
			array(
				'action' => self::ACTION,
				'book'   => $post->ID,
			),
			admin_url( 'admin-post.php' )
		);
		$url = wp_nonce_url( $url, self::ACTION . '_' . $post->ID );

		$label = get_post_meta( $post->ID, 'pagesco_in_stock', true )
			? __( 'Mark sold out', 'pagesco-books' )
			: __( 'Mark in stock', 'pagesco-books' );

		$actions['pagesco_stock'] = sprintf( '<a href="%s">%s</a>', esc_url( $url ), esc_html( $label ) );
		return $actions;
	}

	/**
	 * Flips the book's stock flag, then goes back to the Books screen.
	 */
	public function handle(): void {
		$book_id = isset( $_GET['book'] ) ? absint( $_GET['book'] ) : 0;

		check_admin_referer( self::ACTION . '_' . $book_id );

		if ( BookPostType::NAME !== get_post_type( $book_id ) || ! current_user_can( 'edit_post', $book_id ) ) {
			wp_die( esc_html__( 'Sorry, you are not allowed to change this book.', 'pagesco-books' ), 403 );
		}

		$in_stock = (bool) get_post_meta( $book_id, 'pagesco_in_stock', true );
		update_post_meta( $book_id, 'pagesco_in_stock', ! $in_stock );

		wp_safe_redirect( admin_url( 'edit.php?post_type=' . BookPostType::NAME ) );
		exit;
	}
}

List the feature, then confirm the link appears for an editor and is absent for an author who does not own the book:

🏋️ Exercise 1: Prove the Date Validator

The hardened save validates the publication date against Y-m-d. Write a quick check that a real date passes and a wrong-shaped one is rejected, using the same DateTime::createFromFormat() test the save's helper uses.

💡 Hint

A value is valid when DateTime::createFromFormat( 'Y-m-d', $v ) returns an object whose format( 'Y-m-d' ) equals $v again. Try 1965-08-01 and soon.

✅ Solution 
wp eval 'function demo_valid( $v ) {
	$d = DateTime::createFromFormat( "Y-m-d", $v );
	return ( $d && $d->format( "Y-m-d" ) === $v ) ? "valid" : "rejected";
}
echo "1965-08-01: ", demo_valid( "1965-08-01" ), "\n";
echo "soon:       ", demo_valid( "soon" ), "\n";
echo "1965-13-99: ", demo_valid( "1965-13-99" ), "\n";'

Output

1965-08-01: valid
soon:       rejected
1965-13-99: rejected

A real date passes; "soon" and an impossible date are rejected. Validating the shape, not just sanitizing the characters, is what keeps nonsense out of a field other code will trust to be a date.

🏋️ Exercise 2: Escape for a JavaScript Context

You need to drop a book's title into an inline script, say a small analytics call. Neither esc_html() nor esc_attr() is right there. Find the function for a JavaScript string context and show it quoting a title that contains an apostrophe.

💡 Hint

esc_js() escapes a value for use inside a quoted JavaScript string. Try it on The Hobbit (O'Reilly ed.).

✅ Solution 
wp eval 'echo esc_js( "The Hobbit (O\x27Reilly ed.)" ), "\n";'

Output

The Hobbit (O\'Reilly ed.)

esc_js() backslash-escaped the apostrophe so it cannot end the JavaScript string early. For larger data passed to scripts, wp_json_encode() (with wp_add_inline_script()) is the modern choice; esc_js() suits a single inline value.

🏋️ Exercise 3: A Prepared Search With a Placeholder

Write a prepared query that counts how many books cost less than a given price, with the price as a %f placeholder. Run it for $10.

💡 Hint

Join wp_postmeta on pagesco_price, and compare meta_value + 0 < %f. Use $wpdb->get_var() with COUNT(*).

✅ Solution 
wp eval 'global $wpdb;
$limit = 10.0;
$count = $wpdb->get_var( $wpdb->prepare(
	"SELECT COUNT(*) FROM {$wpdb->postmeta} WHERE meta_key = %s AND meta_value + 0 < %f",
	"pagesco_price",
	$limit
) );
echo "books under \$10: ", $count, "\n";'

Output

books under $10: 6

The price went in as a %f placeholder, so even a value typed by a user could not break out into SQL. Core would do this for you through a meta_query; when you hand-write SQL, prepare() is not optional.

🏋️ Exercise 4: Capability-gate a Bulk Change (Stretch)

Write a throwaway script that marks every book out of stock, but only if the current user may edit it, skipping the rest. Run it as the editor Maria, show the counts, then put all the books back in stock. This is the shape a safe bulk action takes.

💡 Hint

Loop the books with get_posts(); for each, check current_user_can( 'edit_post', $id ) before update_post_meta(). Count changed vs skipped. Restore with a second loop setting pagesco_in_stock to 1 (or to each book's seeded value; all eleven were in stock except two).

✅ Solution 
wp eval 'wp_set_current_user( 2 );
$changed = 0; $skipped = 0;
foreach ( get_posts( array( "post_type" => "book", "numberposts" => -1 ) ) as $b ) {
	if ( current_user_can( "edit_post", $b->ID ) ) { update_post_meta( $b->ID, "pagesco_in_stock", false ); $changed++; }
	else { $skipped++; }
}
echo "changed: $changed, skipped: $skipped\n";'
wp eval 'foreach ( get_posts( array( "post_type" => "book", "numberposts" => -1 ) ) as $b ) {
	$sold_out = in_array( $b->post_title, array( "The Great Gatsby", "The Catcher in the Rye" ), true );
	update_post_meta( $b->ID, "pagesco_in_stock", ! $sold_out );
}'
wp post meta get 30 pagesco_in_stock

1

Maria may edit all eleven, so none were skipped; as an author only her own would change. The restore loop puts the catalog back exactly (Gatsby and Catcher out of stock, the rest in), so Dune reads 1 again. A real bulk action adds a nonce on top of this capability loop.

❓ Common Questions at This Stage

Do I still need nonces and capability checks if I use the REST API or the block editor?

For core's own endpoints and the editor, those checks are built in: the editor sends an X-WP-Nonce header and the API enforces the post-type capabilities, so Devon, who may not edit Maria's books, is refused there too. But any route you register needs a permission_callback (Module 7 makes this a rule), and any form, admin action or AJAX handler you write needs its own nonce and capability check. The checks are automatic only for the paths WordPress controls.

What is the difference between sanitizing and validating?

Sanitizing changes a value to make it safe or well-formed, sanitize_text_field() strips tags, absint() forces a non-negative integer. Validating judges a value and accepts or rejects it, is this a real Y-m-d date, is this one of the allowed options. Use both: validate when a value must have a particular shape (reject if not), sanitize when you can safely clean it. The hardened save does both, validating the date and sanitizing the text.

Is esc_html() enough, or should I use wp_kses()?

esc_html() turns everything into text, which is what you want for a name, a price or a title. Use wp_kses_post() or wp_kses() only when the value is meant to contain HTML and you want to allow a safe subset, for example a description that may hold <strong> and links. wp_kses() lets you pass the exact tags and attributes allowed; it is heavier, so reserve it for genuine rich text, not for a field that should be plain.

Should the plugin store secrets like an API key?

Never in the code or the repository. A key belongs in wp-config.php or an environment variable, read at runtime; Module 7's external-API lesson and Module 8's deployment lesson show the pattern. And every PHP file that could run on its own still needs the ABSPATH guard from Lesson 5.1, so a direct request cannot execute it outside WordPress.

📝 Lesson Summary

🎓 Key Takeaways

  • Sanitize input early, escape output late; they are different jobs with different functions
  • Escape for the context: esc_html() for text, esc_attr() for attributes, esc_url() for links, wp_kses_post() for allowed HTML
  • Every state change needs both a nonce (wp_nonce_field() + check_admin_referer()) and a capability check (current_user_can())
  • Guard save_post handlers against autosaves and revisions, and validate values that must have a shape, not just sanitize them
  • Never concatenate a value into SQL: use $wpdb->prepare() with %s, %d, %f, %i, or a core API
  • Database functions like wp_insert_post() do not check capabilities; that is your job
