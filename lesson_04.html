🗂️ Lesson 2.1: The Content Model

Before you write a theme or a plugin, you need to know what WordPress actually stores and how the pieces relate. Site owners see Posts, Pages, Media, Users and Settings as five different menus. A developer sees a much simpler picture: almost everything is a post of some type, sorted by terms, owned by users whose capabilities decide what they may do, configured by options, and written in block markup. In this lesson you take that picture apart with WP-CLI and PHP, then stock the Pages & Co. site with its first staff, pages and news.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Explain why posts, pages, media, revisions, templates and navigation menus are all posts with a different post_type, and read a WP_Post object
  • Choose between posts and pages, use post statuses, and organize content with categories, tags and terms
  • Describe how roles, capabilities and users fit together, and check capabilities rather than roles in code
  • Find the option behind a Settings screen, and read the block markup the editor stores in post_content with parse_blocks()
  • Create users, pages and posts from the command line, with authors, categories, dates and revisions
  • ⏱️ Time 120 minutes
  • 📋 Prerequisites Lesson 1.3: PHP the WordPress Way
  • 🛠️ You will build the Pages & Co. starter content: staff accounts for Maria (editor) and Devon (author), the About Us, Contact and Events pages, and three News posts
  • 🧩 WordPress 7.1 on PHP 8.5 (the content model is the same in every recent version; a few admin labels changed, see the version note)
  • 🧱 Site your Pages & Co. development site from Lesson 1.2, with WP-CLI

📦 Everything Is a Post

Open the admin and you see separate menus for Posts, Pages and Media, and somewhere in the Site Editor there are templates, patterns and navigation menus. Under the hood they are all rows in one database table, wp_posts, and the column post_type says which kind each row is. WordPress calls each kind a post type. Ask your site which ones it has:

wp post-type list --fields=name,label,hierarchical,public

Output

+---------------------+-----------------------+--------------+--------+
| name                | label                 | hierarchical | public |
+---------------------+-----------------------+--------------+--------+
| post                | Posts                 |              | 1      |
| page                | Pages                 | 1            | 1      |
| attachment          | Media                 |              | 1      |
| revision            | Revisions             |              |        |
| nav_menu_item       | Navigation Menu Items |              |        |

Sixteen types, five of which an editor ever thinks of as "content". post, page and attachment (Media) are public: they have URLs. revision stores old versions. The wp_ types belong to block themes and the editor: wp_template and wp_template_part hold templates you edit in the Site Editor (Module 3), wp_block holds synced patterns, wp_global_styles your style changes, and wp_navigation the menus of block themes. nav_menu_item and custom_css serve classic themes. In Lesson 5.2 you will add one more, book, and it will get exactly the same machinery for free: admin screens, revisions, REST API, permissions.

💡 Mental model: one filing cabinet, many labels

Picture one huge filing cabinet. Every document goes into the same kind of folder with the same fields (title, content, author, date, status), and a colored label says what it is: blog post, page, image, old draft, menu. WordPress code that works on "a folder" (saving, revisions, permissions, the REST API) therefore works on every label at once. That is why a custom post type is so powerful, and why you will find templates and menus in the same table as blog posts.

A post as PHP sees it: WP_Post

get_post() returns one row as a WP_Post object, whose properties are the table's columns. Look at the "Hello world!" post (ID 1):

wp post get 1 --fields=ID,post_type,post_status,post_name,post_title,post_author,post_parent,comment_status

Output

+----------------+--------------+
| Field          | Value        |
+----------------+--------------+
| ID             | 1            |
| post_author    | 1            |
| post_title     | Hello world! |
| post_status    | publish      |
| comment_status | open         |
| post_name      | hello-world  |
| post_parent    | 0            |
| post_type      | post         |
+----------------+--------------+

post_name is the slug, the last part of the URL (/hello-world/). post_author is a user ID, post_parent a post ID (0 = none). The dates (post_date, post_date_gmt, post_modified) are left out above because they are the moment your site was installed. Fields that every post type shares live here; anything extra, such as a book's price, goes into post meta, a key-value table attached to the post (Lesson 2.2 shows the table, Lesson 5.2 registers pagesco_price).

📰 Posts, Pages and Statuses

Posts and pages share the table and the editor, but WordPress treats them differently on purpose:

Posts (post)Pages (page)
ForDated content that flows: news, articles, announcementsTimeless content: About, Contact, Shipping, Events
ListedOn the blog page, in archives by date, category, tag and author, in the RSS feedNowhere automatically; you link or menu them

Pages are hierarchical, have no excerpt, and have "page attributes" (parent and order); posts have three taxonomies, pages none. When you register the book type in Lesson 5.2 you will set exactly these switches yourself.

Post statuses

Every row also has a post_status, which decides who can see it:

StatusAdmin labelMeans
publishPublishedPublic at its URL
futureScheduledPublished automatically at its date (by WP-Cron, Lesson 7.3)
draftDraftSaved, visible only in the admin
pendingPending ReviewA contributor submitted it; an editor must publish it
privatePrivatePublished, but only for logged-in users who may read private posts
trashTrashDeleted, restorable for 30 days
auto-draft(none)An empty post the editor created when you clicked "Add"; cleaned up automatically
inherit(none)Revisions and attachments: they take the status of their parent

Careful when you list content: tools differ in their defaults. Compare WP-CLI's list with get_posts():

wp post list --post_type=page --orderby=ID --order=ASC --fields=ID,post_title,post_name,post_status
wp eval 'foreach ( get_posts( array( "post_type" => "page" ) ) as $page ) { echo $page->ID, " ", $page->post_title, " ", $page->post_status, "\n"; }'

Output

+----+----------------+----------------+-------------+

| 3  | Privacy Policy | privacy-policy | draft       |
+----+----------------+----------------+-------------+

WP-CLI lists posts of every status unless you pass --post_status, so the draft Privacy Policy page (which WordPress created for you to finish) is there. get_posts() (Lesson 1.3) and WP_Query (Lesson 4.2) default to 'post_status' => 'publish', so PHP sees only the Sample Page. The front end follows the PHP rule: a visitor never sees a draft.

🏷️ Categories, Tags and Terms

A taxonomy is a way of grouping content, and a term is one group in it. Categories and tags are the two taxonomies posts get out of the box. The only real difference between them is that categories are hierarchical (Fiction > Science Fiction) and tags are flat; editors use categories for a site's few main sections and tags for many small topics.

wp taxonomy list --fields=name,label,hierarchical,public
wp term list category --fields=term_id,name,slug,count

Output

+-----------------------+---------------------+--------------+--------+
| name                  | label               | hierarchical | public |
+-----------------------+---------------------+--------------+--------+
| category              | Categories          | 1            | 1      |
| post_tag              | Tags                |              | 1      |
| nav_menu              | Navigation Menus    |              |        |
| post_format           | Formats             |              | 1      |
| wp_theme              | Themes              |              |        |
| wp_template_part_area | Template Part Areas |              |        |
| wp_pattern_category   | Pattern Categories  |              |        |
+-----------------------+---------------------+--------------+--------+
+---------+---------------+---------------+-------+
| term_id | name          | slug          | count |
+---------+---------------+---------------+-------+
| 1       | Uncategorized | uncategorized | 1     |
+---------+---------------+---------------+-------+

Besides the two you know, post_format (Aside, Gallery, Quote...) is a taxonomy too, and four internal ones help menus, themes and patterns find their items. There is exactly one category, "Uncategorized", with one post: every post must have at least one category, and WordPress assigns the one named in the default_category option when you choose none. You will add a News category in the project. In Lesson 5.2 you register a taxonomy of your own, genre, hierarchical like categories, for books.

Terms are stored once and linked to any number of posts; a term's count is how many published posts use it. In PHP:

wp eval 'foreach ( get_the_terms( 1, "category" ) as $term ) { echo $term->term_id, " ", $term->name, " (", get_class( $term ), ")\n"; } var_dump( has_term( "uncategorized", "category", 1 ) );'

Output

1 Uncategorized (WP_Term)
bool(true)

🖼️ Media: Attachments Are Posts Too

An uploaded file is two things: the file in wp-content/uploads/ and a post of type attachment that describes it (title, alt text, caption, the post it was uploaded to). For images, WordPress also generates smaller copies in the sizes defined under Settings > Media. Twenty Twenty-Five ships a picture of a book cover, so you can import it without downloading anything. By default uploads go into year and month folders (uploads/2026/10/); switch that off for this demo so your paths match the lesson exactly, and switch it back afterwards:

wp option update uploads_use_yearmonth_folders 0
wp media import wp-content/themes/twentytwentyfive/assets/images/book-image.webp --title="The Stories Book cover" --alt="Cover of The Stories Book: a plaster bust on a black background"

wp eval '$meta = wp_get_attachment_metadata( 5 ); echo "original: {$meta["width"]}x{$meta["height"]}\n"; foreach ( $meta["sizes"] as $name => $size ) { echo "$name: {$size["width"]}x{$size["height"]} {$size["file"]}\n"; } echo "medium_size_w option: ", get_option( "medium_size_w" ), "\n";'

wp eval 'echo wp_get_attachment_image( 5, "medium" ), "\n";'

🕓 Revisions, Autosaves and Trash

Every time a post or page is updated, WordPress stores a copy of the new version as a revision post whose parent is the post. The editor's Revisions screen lets you compare and restore them. Watch it from the command line with a throwaway post:

wp post create --post_title="Revision demo" --post_content="Version one." --post_status=draft --porcelain
wp post update 6 --post_content="Version two."
wp post update 6 --post_content="Version three."
wp post list --post_type=revision --post_parent=6 --orderby=ID --order=ASC --fields=ID,post_name,post_content,post_status

Output

6
Success: Updated post 6.
Success: Updated post 6.
+----+---------------+----------------+-------------+
| ID | post_name     | post_content   | post_status |
+----+---------------+----------------+-------------+
| 7  | 6-revision-v1 | Version two.   | inherit     |
| 8  | 6-revision-v1 | Version three. | inherit     |
+----+---------------+----------------+-------------+

Two revisions for two updates (sorted by ID here; both happened in the same second), each named <parent>-revision-v1. Look closely at the content: the newest revision equals the current post ("Version three."). Core's own comment in wp-includes/revision.php says it: "every update is a revision, and the most recent revision always matches the current post". The very first version ("Version one.") has no revision, because creating a post is not an update. In the editor you rarely notice, since the first save of a new post is already an update of the auto-draft the editor created.

wp eval 'var_dump( WP_POST_REVISIONS, wp_revisions_to_keep( get_post( 6 ) ), AUTOSAVE_INTERVAL, EMPTY_TRASH_DAYS );'

Output

bool(true)
int(-1)
int(60)
int(30)
  • WP_POST_REVISIONS is true, so wp_revisions_to_keep() says -1: keep every revision. Many hosts set a number such as define( 'WP_POST_REVISIONS', 10 ); in wp-config.php so busy sites do not collect thousands; false turns revisions off.
  • The editor autosaves every 60 seconds (AUTOSAVE_INTERVAL). An autosave is a special revision, one per user and post, named <parent>-autosave-v1, that the editor offers to restore after a crash.
  • Trash is a status, not a deletion: trashed posts are deleted for good after 30 days (EMPTY_TRASH_DAYS). wp post delete trashes; --force deletes immediately, revisions included.
wp post delete 6 --force
wp post list --post_type=revision --format=count

Output

Success: Deleted post 6.
0

👥 Users, Roles and Capabilities

Three ideas, often mixed up:

  • A capability is one permission with a name: edit_posts, publish_pages, upload_files, manage_options.
  • A role is a named bundle of capabilities: Editor, Author.
  • A user has a role (occasionally several, or extra single capabilities). Code asks "can this user do X?", never "is this user an editor?".
wp role list
wp cap list author

Five roles on a single site (a multisite network adds Super Admin). An author may write, publish, edit and delete their own posts and upload files; the level_* entries are leftovers from WordPress 1.x kept for old plugins. The roles stack up:

RoleCan, in shortTypical person at Pages & Co.
AdministratorEverything: plugins, themes, users, settingsThe owner, the developer
EditorAll posts and pages, anyone's, plus categories and comments; no settings or pluginsMaria, who runs the website content

ContributorWrite own posts, submit them for review; cannot publish or uploadA guest reviewer

In PHP, current_user_can() checks the logged-in user and user_can() any user. Both take a capability. Some capabilities are meta capabilities that need an object: edit_post with a post ID asks "may this user edit this post?", and WordPress maps it to edit_posts, edit_others_posts or edit_published_posts depending on who wrote it and its status.

wp eval 'var_dump( user_can( 1, "manage_options" ), user_can( 1, "edit_post", 1 ), current_user_can( "edit_posts" ) );'
wp eval 'var_dump( current_user_can( "edit_posts" ) );' --user=admin

Output

bool(true)
bool(true)
bool(false)
bool(true)

The last two answers differ only because of --user=admin: WP-CLI runs as nobody unless you name a user, and a nobody can do nothing. The same happens in your code when it runs too early or in a scheduled task. Where the role is stored: in user meta, as a serialized array, plus the old user level:

wp user meta list 1 --keys=wp_capabilities,wp_user_level

Output

+---------+-----------------+---------------------------------+
| user_id | meta_key        | meta_value                      |

| 1       | wp_capabilities | a:1:{s:13:"administrator";b:1;} |

Notice the key starts with the table prefix, wp_, which is why you always use the API ($user->roles, $user->add_role(), add_cap()) rather than this meta. Lesson 5.3 adds capability checks to every form, and the Pages & Co. plugin may add its own capabilities for books.

⚙️ Settings Are Options

Every field on every Settings screen is a row in wp_options, a simple name-value table, read with get_option() and written with update_option() (or wp option get / update). 🧱 The Block Editor as a Developer Sees It

In Lesson 1.1 you switched the editor to its Code editor (Ctrl+Shift+Alt+M, or the ⋮ Options menu) and saw HTML wrapped in comments. That text is exactly what is stored in post_content:

wp post get 1 --field=post_content

Output

<!-- wp:paragraph -->
<p>Welcome to WordPress. This is your first post. Edit or delete it, then start writing!</p>
<!-- /wp:paragraph -->

This is block markup (core calls it the serialized block format). Each block is an HTML comment that opens <!-- wp:paragraph -->, the block's saved HTML, and a closing comment. The rules:

  • The name after wp: is the block type; core blocks drop their core/ namespace (wp:paragraph is core/paragraph), other blocks keep it (wp:pagesco/book-card, Lesson 6.2).
  • Attributes that are not visible in the HTML are stored as JSON in the opening comment: <!-- wp:heading {"level":3} -->.
  • Blocks nest: a list block contains list-item blocks, a group contains anything.
  • Dynamic blocks have no saved HTML at all, just a self-closing comment such as <!-- wp:latest-posts {"postsToShow":3} /-->. PHP renders them on every page view (Lesson 6.3).
  • Content without any block comments is "freeform": the editor shows it in a Classic block (Common Mistakes 4).

Because it is just text, PHP can read it. parse_blocks() turns markup into an array of blocks; save this as wordpress/blocks-demo.php:

<?php
$pagesco_markup = '<!-- wp:heading {"level":3} -->
<h3 class="wp-block-heading">Opening hours</h3>
<!-- /wp:heading -->

<!-- wp:list -->
<ul class="wp-block-list"><!-- wp:list-item -->
<li>Thursday: 9 a.m. to 9 p.m.</li>
<!-- /wp:list-item --></ul>
<!-- /wp:list -->

<!-- wp:latest-posts {"postsToShow":1} /-->';

foreach ( parse_blocks( $pagesco_markup ) as $pagesco_block ) {
	if ( null === $pagesco_block['blockName'] ) {
		continue; // The blank lines between blocks come back as empty "freeform" blocks.
	}
	printf(
		"%-18s attrs=%s inner=%d\n",
		$pagesco_block['blockName'],
		wp_json_encode( $pagesco_block['attrs'] ),
		count( $pagesco_block['innerBlocks'] )
	);
}

echo "\n", do_blocks( $pagesco_markup ), "\n";
wp eval-file blocks-demo.php
rm blocks-demo.php

Output

core/heading       attrs={"level":3} inner=0
core/list          attrs=[] inner=1
core/latest-posts  attrs={"postsToShow":1} inner=0


<h3 class="wp-block-heading">Opening hours</h3>



<ul class="wp-block-list">
<li>Thursday: 9 a.m. to 9 p.m.</li>
</ul>


<ul class="wp-block-latest-posts__list wp-block-latest-posts is-layout-flow wp-block-latest-posts-is-layout-flow"><li><a class="wp-block-latest-posts__post-title" href="http://localhost:8080/hello-world/">Hello world!</a></li>
</ul>

Three blocks: the heading with its level attribute, the list with one inner block, and Latest Posts with its attribute. do_blocks() renders the markup the way a page view does: static blocks print their saved HTML (with the comments removed), and the dynamic Latest Posts block ran PHP to produce a list with a link to "Hello world!", which never appeared in the markup. On the front end, do_blocks() runs as part of the the_content filter (Lesson 2.3 lists it at priority 9).

⚠️ The saved HTML must match what the block would save

For static blocks the editor checks, when it opens a post, that the stored HTML is exactly what the block's own save function produces from the attributes. If you hand-edit the HTML of a block (a different class, a missing wp-block-heading), the front end shows your HTML happily, but the editor marks the block as invalid and offers to recover it. Write block markup in the editor and copy it from the Code editor, or produce it from known-good examples like the ones in this lesson.

🧩 Version note: labels that changed in recent versions

Older tutorials use names the admin no longer shows. "Reusable blocks" became synced patterns in WordPress 6.3 (still the wp_block post type, managed under Patterns in the Site Editor). The "Full Site Editor" is just the Site Editor (Appearance > Editor). The WordPress 7.0 admin redesign changed the look and color scheme of every screen, but menu names and the content model are the same as described here; Settings gained Connectors.

⚠️ Common Mistakes

None of these produces a PHP error. That is what makes them worth seeing once: WordPress does exactly what you asked, which is not what you meant.

1. Forgetting to publish (draft by default)

wp post create --post_type=page --post_title="Gift Cards" --porcelain
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/gift-cards/

3. Checking a role instead of a capability

wp eval '$user = wp_get_current_user(); var_dump( in_array( "editor", $user->roles, true ), current_user_can( "edit_others_posts" ) );' --user=admin

Output

bool(false)
bool(true)

What it means: code meant for "people who can edit everyone's posts" asked whether the user is an editor, and locked out the administrator, who can do more than an editor but does not have that role. It would also break on sites with custom roles such as "Shop Manager". Fix: always check the capability the feature needs: current_user_can( 'edit_others_posts' ).

4. HTML without block comments

wp eval 'foreach ( parse_blocks( "<h2>Opening hours</h2><p>Daily 9 to 6.</p>" ) as $b ) { var_dump( $b["blockName"] ); }'

Output

NULL

What it means: content saved without block comments (by an old plugin, an import, or a script that sets post_content to plain HTML) is one block with no name: freeform content. The front end shows it fine, but the editor wraps all of it in a single Classic block, so the editor's heading and paragraph tools do not apply until someone clicks "Convert to blocks". Fix: when your code writes content that people will edit, write block markup.

🏋️ Exercise 1: Who May Do What?

Write one wp eval command (or a small file for wp eval-file) that prints a table: for the users admin, maria and devon, can they publish_posts, edit_pages, edit_others_posts, upload_files and manage_options? Predict the answers first. Then: may Devon edit the "Book club: Dune" post?

🏋️ Exercise 2: Count the Blocks

Write a script that prints every block in the "Staff picks for the season" post, nested blocks indented under their parent, like an outline. How many blocks does the post contain in total?

💡 Hint

Get the post by slug with get_page_by_path( 'staff-picks', OBJECT, 'post' ), parse post_content, and walk the array with a recursive function that receives the depth. Skip blocks whose blockName is null.

✅ Solution 
<?php
function pagesco_print_blocks( $blocks, $depth = 0 ) {
	$count = 0;
	foreach ( $blocks as $block ) {
		if ( null === $block['blockName'] ) {
			continue;
		}
		echo str_repeat( '  ', $depth ), $block['blockName'], "\n";
		$count += 1 + pagesco_print_blocks( $block['innerBlocks'], $depth + 1 );
	}
	return $count;
}

$pagesco_post  = get_page_by_path( 'staff-picks', OBJECT, 'post' );
$pagesco_total = pagesco_print_blocks( parse_blocks( $pagesco_post->post_content ) );
echo 'Total: ', $pagesco_total, " blocks\n";

❓ Common Questions at This Stage

Should Pages & Co.'s books be posts in a "Books" category?

That is how many sites started, and it breaks quickly: books need fields posts do not have (author, price, ISBN), their own URLs (/books/dune/), their own archive and their own permissions, and they should not appear in the news feed. That is exactly what a custom post type gives you. Lesson 5.2 registers book with a genre taxonomy and price, author and page-count meta.

Can I add my own roles?

Yes, with add_role( 'pagesco_bookseller', 'Bookseller', array( 'read' => true, ... ) ), usually on plugin activation, because roles are saved in the database (the wp_user_roles option) rather than registered on every request. Often adding one capability to an existing role is enough. Lesson 5.1 covers activation hooks.

Is it safe to create content with WP-CLI instead of the editor?

Yes, it calls the same wp_insert_post() as the editor, so hooks run and revisions are stored. One difference matters: the editor and the REST API check the user's capabilities before saving, but wp_insert_post() itself does not. WP-CLI and your own code can therefore do things the user could not do in the admin. That is a feature for scripts and a reason to check capabilities yourself in anything a visitor can trigger (Lesson 5.3).

Where are comments in all this?

Comments have their own tables (wp_comments, wp_commentmeta), each linked to a post by ID, and their settings live under Settings > Discussion. Twenty Twenty-Five shows a comment form under posts. Lesson 2.2 shows the tables; the course does not build comment features, but everything you learn about hooks and queries applies to them.

🎓 Key Takeaways

  • Posts, pages, attachments, revisions, templates and navigation menus are all rows in wp_posts, told apart by post_type; PHP sees them as WP_Post objects
  • Posts are dated and organized by categories and tags; pages are timeless and hierarchical; post_status decides visibility, and new content defaults to draft
  • Taxonomies group content into terms; uploads are attachment posts plus files and generated image sizes
  • Each update stores a revision equal to the new version; trash is a status for 30 days
  • Roles bundle capabilities; code checks capabilities with current_user_can() / user_can(), including meta capabilities like edit_post
  • Every Settings field is an option; content is stored as block markup that parse_blocks() reads and do_blocks() renders
