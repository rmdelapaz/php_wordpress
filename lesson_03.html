🐘 Lesson 1.3: PHP the WordPress Way

You already write good PHP. WordPress code is still PHP, but it lives by house rules that grew out of twenty years of keeping millions of sites running: its own coding standards, a prefix on everything, a family of functions for escaping, sanitizing and translating, callbacks handed around everywhere, functions that take one array of arguments, and errors returned as objects instead of thrown. This lesson does not reteach PHP. It shows you each house rule, why it exists, and the WordPress function that replaces the habit you brought from PHP Foundations, all run on your Pages & Co. site.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Write PHP that follows the WordPress coding standards, and check it with PHPCS and the WordPress ruleset
  • Choose the right escaping function for each output context (esc_html, esc_attr, esc_url, wp_kses_post) and the right sanitizing function for each input
  • Make strings translatable with __(), esc_html__(), _n() and sprintf(), with a text domain and translator comments
  • Pass callbacks in every form WordPress accepts, and write functions that take an array of arguments merged with wp_parse_args()
  • Handle WP_Error results, and use core's globals ($wpdb, $post, $wp_query) and classes without fighting them
  • ⏱️ Time 130 minutes
  • 📋 Prerequisites Lesson 1.2: Your Local Development Environment, and PHP Foundations (functions, arrays, classes, Composer)
  • 🛠️ You will build pagesco_book_card(), a helper that renders a book card the WordPress way and passes PHPCS with zero problems
  • 🧩 WordPress 7.1 on PHP 8.5 (everything here works on any supported WordPress version; WordPress itself still runs on PHP 7.4)
  • 🧱 Site your Pages & Co. development site from Lesson 1.2, plus a throwaway Composer container for PHPCS

🌉 From PHP Foundations to WordPress

In PHP Foundations your code was the whole application. You chose the style, wrote a small e() helper around htmlspecialchars(), read input with filter_input(), threw exceptions, and opened your own PDO connection. In WordPress your code is a guest in a program that core, the theme and every active plugin share. Everything you define lands in the same PHP process, and core has to keep working with code written for versions from a decade ago. That explains every convention in this lesson.

💡 Mental model: moving into a shared house

Your own apartment had your rules. A shared house has house rules, and they exist because of the other people: you label your food (prefixes), you use the shared kitchen tools the way everyone else does (core's functions instead of your own helpers), you leave notes others can read (coding standards and DocBlocks), and you do not rearrange the furniture in the living room (globals). None of the rules is hard. Ignoring them is what causes the fights.

One more difference shapes everything: WordPress 7.1 still runs on PHP 7.4. Core's own code therefore avoids syntax newer than that, and looks old-fashioned next to what you learned. Your theme and plugin are different: they declare their own minimum (a Requires PHP: 8.2 line in the plugin header, Lesson 5.1), and above that line you may use enums, match, readonly properties and the rest of modern PHP. You are learning conventions, not going back in time.

A practice folder

This lesson's examples are small PHP files that WP-CLI runs with WordPress loaded (wp eval-file, Lesson 1.2). Keep them together in a practice folder inside the WordPress root, so the wp container can see them. From your project folder:

mkdir wordpress/pagesco-practice

You delete the folder at the end of the project; nothing in it becomes part of the site.

📐 The WordPress Coding Standards

The WordPress Coding Standards (WPCS) describe how core, the default themes and most professional plugins format PHP. They matter for three practical reasons: code in one style is quicker to review, the plugin and theme directories expect it, and the tool that checks the style also catches real security bugs, as you will see in a minute. Here is a function as PHP Foundations taught you to write it. Save it as wordpress/pagesco-practice/style-before.php:

<?php
function bookTitle($title)
{
    if ($title == "") {
        return "Untitled";
    }
    $out = "<h2>" . $title . "</h2>";
    echo $out;
    return $out;
}

And here is the same function the WordPress way:

<?php
/**
 * Coding standards demo (Lesson 1.3).
 *
 * @package Pagesco
 */

/**
 * Prints a book title as a heading and returns the HTML.
 *
 * @param string $title The book title.
 * @return string The heading HTML.
 */
function pagesco_book_title( $title ) {
	if ( '' === $title ) {
		$title = 'Untitled';
	}
	$out = '<h2>' . esc_html( $title ) . '</h2>';
	echo $out; // phpcs:ignore WordPress.Security.EscapeOutput.OutputNotEscaped -- escaped above.
	return $out;
}

Let a tool check it: PHPCS

PHP_CodeSniffer (PHPCS) reads PHP files and reports every place that breaks a set of rules; phpcbf, which comes with it, fixes the mechanical ones for you. The rules for WordPress ship as a Composer package, wp-coding-standards/wpcs. Lesson 8.1 adds PHPCS to your plugin properly; for now, install it in the practice folder with Composer, which you know from PHP Foundations. Composer is not in the course containers, so start the official Composer image for a moment, with your wordpress/ folder mounted at the same path as in the other containers. 🏷️ Prefix Everything

PHP has one global namespace per request, and in WordPress that namespace is shared by core (thousands of functions such as get_the_title()), the theme and every plugin. Two plugins that each declare format_price() stop the site with a fatal error the moment both are active, and you cannot know which plugins your client will install next year. So everything global that you name gets a unique prefix. In this course that is pagesco_:

What you nameExample
Functions and global variablespagesco_book_card(), $pagesco_books
Classes (outside a namespace) and constantsPagesco_Book_Card, PAGESCO_BOOKS_VERSION
Hook names you create (Lesson 2.3)pagesco_store_notice
Options, meta keys, transientspagesco_books_settings, pagesco_price
Script and style handles, CSS classespagesco-book-filter, .pagesco-notice
Text domain (translation)pagesco (the theme), pagesco-books (the plugin): the folder slug

Classes inside a namespace, such as PagesCo\Books\Plugin in Module 5, need no prefix: the namespace is the prefix. Global variables need one even in files you think of as private, because a plugin file runs in the global scope. Ask WordPress whether a name is taken; the function list below is everything defined in this PHP process:

wp eval 'var_dump( function_exists( "format_price" ), function_exists( "get_the_title" ), count( get_defined_functions()["user"] ) );'

Output (your count may differ)

bool(false)
bool(true)
int(3690)

format_price is free today, get_the_title is core's, and thousands of functions are defined by "user" code: WordPress counts as user code to PHP. You will see what happens when you collide with one in Common Mistakes 2. (You may see old code wrapping functions in if ( ! function_exists( 'x' ) ). That is how classic themes let child themes replace a function, Lesson 3.4; it is not a substitute for a prefix.)

🛡️ Sanitize Early, Escape Late

PHP Foundations taught you to validate input and escape output. WordPress has the same two jobs and a function for each situation. The rule that ties them together is short enough to memorize: sanitize early, escape late. Clean data as soon as it arrives, before you store or use it. Escape it at the last moment, right where it is printed, for the exact place it is printed into.

graph TD A["Request: form, URL, REST"] --> B["wp_unslash, then sanitize_* or validate"] B --> C["Use it, or store it in the database"] C --> D["Read it back later"] D --> E["esc_html, esc_attr, esc_url at the echo"] E --> F["HTML sent to the browser"]

Escaping: pick the function for the context

The same text needs different treatment inside an HTML element, inside an attribute, as a URL and as user-written HTML. Save this as wordpress/pagesco-practice/escape.php and run it:

<?php
$pagesco_title = 'Dune <script>alert("hi")</script> & "Friends"';

echo 'esc_html:    ', esc_html( $pagesco_title ), "\n";
echo 'esc_attr:    ', esc_attr( 'Pages & Co. "staff pick"' ), "\n";
echo 'esc_url:     ', esc_url( 'https://example.com/search?q=dune&page=2' ), "\n";
echo 'esc_url:     ', esc_url( 'javascript:alert(1)' ), "(empty)\n";
echo 'wp_kses_post:', wp_kses_post( ' <p>A <strong>classic</strong><script>alert(1)</script> <a href="https://example.com" onclick="steal()">link</a></p>' ), "\n";
echo 'twice:       ', esc_html( esc_html( 'Pages & Co.' ) ), "\n";
wp eval-file pagesco-practice/escape.php

Output

esc_html:    Dune &lt;script&gt;alert(&quot;hi&quot;)&lt;/script&gt; &amp; &quot;Friends&quot;
esc_attr:    Pages &amp; Co. &quot;staff pick&quot;
esc_url:     https://example.com/search?q=dune&#038;page=2
esc_url:     (empty)
wp_kses_post: <p>A <strong>classic</strong>alert(1) <a href="https://example.com">link</a></p>
twice:       Pages &amp; Co.
  • esc_html() turns <, >, & and quotes into entities: the script is shown as text, never run. Use it for text between tags.
  • esc_attr() does the same for text inside an attribute value, title="..." or value="...". Always quote the attribute.
  • esc_url() checks the protocol and encodes the URL for HTML (the & becomes &#038;). A javascript: URL comes back empty. Use it for every href and src; esc_url_raw() is the version for URLs you store or redirect to, not print.
  • wp_kses_post() keeps the HTML a post may contain (<strong>, links) and strips the rest: the <script> tags and the onclick attribute are gone, and what was between the script tags is left as harmless text. Use it when the value is supposed to be HTML.
  • The last line shows a kindness: WordPress's escapers do not double-encode an entity that is already there, so escaping twice prints the same as once. That does not make "escape everything twice" a plan; it means you can escape at output even when you are not sure whether something upstream already did.

Each has a translating twin that escapes a translated string in one call, which you will use constantly in themes: esc_html__() returns, esc_html_e() echoes, and the same for esc_attr__() / esc_attr_e(). The next section shows them.

✅ Why "late"?

Escaping depends on where the value goes, and only the line that prints it knows that. A title escaped "early" for HTML is wrong in a JSON response, an email subject or an attribute. Escape at the echo, and a reviewer (or PHPCS) can verify each output by looking at one line. Core does the same: the_title() leaves escaping to the template that prints it.

Sanitizing: clean what comes in

Sanitizing functions take untrusted input and return the safe version of what you expect. Save wordpress/pagesco-practice/sanitize.php:

<?php
var_dump(
	sanitize_text_field( "  Dune <b>Messiah</b>\n by Frank   Herbert " ),
	sanitize_email( ' Maria.Lopez@Example.com ' ),
	sanitize_key( 'Book Club!' ),
	sanitize_title( 'Dune: Part Two' ),
	absint( '-12 books' ),
	is_email( 'maria@@example.com' )
);
wp eval-file pagesco-practice/sanitize.php

Output

string(29) "Dune Messiah by Frank Herbert"
string(23) "Maria.Lopez@Example.com"
string(8) "bookclub"
string(13) "dune-part-two"
int(12)
bool(false)
  • sanitize_text_field(): one line of plain text. Tags stripped, line breaks and extra whitespace collapsed. The default for form fields; sanitize_textarea_field() keeps line breaks.
  • sanitize_email(), sanitize_key() (lowercase letters, digits, dashes and underscores: option names, array keys), sanitize_title() (turns text into a URL slug).
  • absint(): a non-negative integer, for IDs and counts. Note that -12 became 12; when a negative number should be rejected rather than flipped, validate instead.
  • is_email() is a validator: it answers yes or no (false here) instead of cleaning. Validate when you can say exactly what is allowed (an ID that must exist, one of three sort orders: in_array( $order, array( 'asc', 'desc' ), true )); sanitize when you can only describe the shape.

WordPress adds slashes to your input

One surprise for PHP developers: for historical reasons, WordPress adds backslashes before quotes in $_GET, $_POST, $_COOKIE and $_SERVER on every request (core calls it wp_magic_quotes()). Remove them with wp_unslash() before you sanitize. See it with a tiny must-use plugin that prints a query-string value at the bottom of the page. It uses the same add_action( 'wp_footer', ... ) line as the demo in Lesson 1.2; Lesson 2.3 explains hooks properly. Save wordpress/wp-content/mu-plugins/pagesco-slashes.php:

<?php
/**
 * Plugin Name: Pages & Co. Slashes Demo
 * Description: Lesson 1.3 demo: shows what WordPress does to a quote in $_GET.
 */

function pagesco_slashes_demo() {
	if ( ! isset( $_GET['pagesco_q'] ) ) {
		return;
	}
	$raw   = $_GET['pagesco_q']; // phpcs:ignore -- shown raw on purpose, escaped below.
	$clean = sanitize_text_field( wp_unslash( $_GET['pagesco_q'] ) );

	echo '<p class="pagesco-q">raw: ' . esc_html( $raw ) . ' | clean: ' . esc_html( $clean ) . '</p>';
}
add_action( 'wp_footer', 'pagesco_slashes_demo' );
http://localhost:8080/?pagesco_q=O%27Reilly%20%3Cb%3Ebooks%3C%2Fb%3E   (View Source, search for pagesco-q)

Output

<p class="pagesco-q">raw: O\&#039;Reilly &lt;b&gt;books&lt;/b&gt; | clean: O&#039;Reilly books</p>

The URL sends O'Reilly <b>books</b>. The raw value arrived as O\'Reilly (escaped here, so the quote prints as &#039; and the tags as text). The clean one is unslashed, then sanitized: quote kept, tags gone. Save a raw value and every apostrophe in your database grows a backslash. Delete the demo:

rm wp-content/mu-plugins/pagesco-slashes.php

🛑 Two more rules for anything that changes data

Sanitizing and escaping protect the content. A request that changes something (a form that saves, a link that deletes) also needs to prove it came from your own form, with a nonce, and that the user may do it, with current_user_can(). Database queries with values go through $wpdb->prepare(). You will meet each of them in its lesson (5.3, 5.5); from that lesson on, no form in this course skips them.

🌍 Strings Ready for Translation

WordPress runs in more than two hundred languages, and a site owner picks one in Settings. That only works if every string a visitor or admin sees goes through a translation function instead of being echoed as a literal. Your theme and plugin work the same way, with one addition: a text domain, the second argument, that says whose translation file to look in. It is the folder slug: pagesco for the theme, pagesco-books for the plugin. The family:

Variables go into a translated string through sprintf() placeholders, never by concatenating fragments: a translator must see the whole sentence, because word order changes between languages. A /* translators: */ comment directly above explains each placeholder. Save wordpress/pagesco-practice/i18n.php:

<?php
$pagesco_count  = 3;
$pagesco_author = 'Frank Herbert';

printf(
	/* translators: %s: author name. */
	esc_html__( 'More books by %s', 'pagesco' ) . "\n",
	esc_html( $pagesco_author )
);

foreach ( array( 1, $pagesco_count, 1178 ) as $pagesco_n ) {
	printf(
		/* translators: %s: number of books. */
		esc_html( _n( '%s book in stock', '%s books in stock', $pagesco_n, 'pagesco' ) ) . "\n",
		esc_html( number_format_i18n( $pagesco_n ) )
	);
}

No translation exists for the pagesco domain yet, so you get the English text, and that is normal: wrapping costs nothing today and makes translation possible later. number_format_i18n() formats numbers for the site's language (1,178 in English, 1.178 in Spanish). The text domain must be a plain string, never a variable or constant: translation tools read your source code without running it. Lesson 8.3 generates the translation template and shows how translation files reach a site; WordPress then loads them by itself, just in time, when the first string of a domain is requested.

📞 Callbacks in Every Shape

A callback is a value that says "call this later", the callable type from PHP Foundations Lesson 2.4. WordPress asks for callbacks everywhere: for every hook (Lesson 2.3), every shortcode, every REST route, every block's render function and every settings field. It accepts every form PHP has. Save wordpress/pagesco-practice/callbacks.php:

<?php
function pagesco_shout( $text ) {
	return strtoupper( $text ) . '!';
}

class Pagesco_Formatter {
	public $suffix = ' (staff pick)';

	public function pick( $text ) {
		return $text . $this->suffix;
	}

	public static function quote( $text ) {
		return '"' . $text . '"';
	}
}

$pagesco_formatter = new Pagesco_Formatter();

$pagesco_callbacks = array(
	'function name'   => 'pagesco_shout',
	'closure'         => function ( $text ) {
		return ucfirst( $text );
	},
	'arrow function'  => fn( $text ) => strrev( $text ),
	'object method'   => array( $pagesco_formatter, 'pick' ),
	'static method'   => array( 'Pagesco_Formatter', 'quote' ),
	'static, string'  => 'Pagesco_Formatter::quote',
	'first-class'     => pagesco_shout( ... ),
);

foreach ( $pagesco_callbacks as $pagesco_label => $pagesco_callback ) {
	printf( "%-15s %s\n", $pagesco_label, call_user_func( $pagesco_callback, 'dune' ) );
}
wp eval-file pagesco-practice/callbacks.php

Output

function name   DUNE!

arrow function  enud
object method   dune (staff pick)
static method   "dune"
static, string  "dune"
first-class     DUNE!

call_user_func() is what WordPress does internally with your callback when the time comes. Which form to use:

  • A prefixed function name, 'pagesco_shout': the classic choice in themes and small plugins. Anyone can find it, and anyone can unhook it (Lesson 2.3).
  • An object method, array( $this, 'register' ): the norm inside plugin classes (Module 5). Removing it later needs the same object.
  • A static method, array( 'Class', 'method' ) or 'Class::method'; with a namespace, array( Plugin::class, 'activate' ).
  • Closures and arrow functions: fine for tiny, private things. They have no name, so other code cannot remove them, and the first-class callable syntax pagesco_shout( ... ) (PHP 8.1) creates a closure too.

Many WordPress helpers take a callback as data. Escaping a whole list is one line with array_map(), and map_deep() does the same for nested arrays:

wp eval 'print_r( array_map( "esc_html", array( "Dune", "Tom & Jerry", "<b>1984</b>" ) ) );'

🧾 Arrays of Arguments and WP_Error

Count the options of a function such as get_posts(): post type, status, number, order, author, category, date range, and dozens more. Positional parameters would be unusable, so core takes one associative array and fills in defaults for every key you leave out. It is the most common shape in the WordPress API: get_posts(), WP_Query, wp_insert_post(), register_post_type(), wp_remote_get() and register_rest_route() all work this way. Save wordpress/pagesco-practice/args.php:

<?php
$pagesco_pages = get_posts(

		'post_type'   => 'page',
		'post_status' => array( 'publish', 'draft' ),

		'order'       => 'ASC',

);

	printf( "%d  %-15s %s\n", $pagesco_page->ID, $pagesco_page->post_title, $pagesco_page->post_status );

echo count( get_posts( 'post_type=page&post_status=draft' ) ), " draft page(s)\n";

Write your own with wp_parse_args()

Your functions should offer the same shape when they have more than two or three options. wp_parse_args( $args, $defaults ) merges what the caller passed over your defaults (and accepts an array, an object or a query string). Add this to wordpress/pagesco-practice/price.php:

<?php
/**
 * Formats a book price for display.
 *
 * @param float        $amount The price.
 * @param array|string $args   Optional. currency, decimals, free_label.
 * @return string The formatted price (plain text, not escaped).
 */
function pagesco_format_price( $amount, $args = array() ) {
	$defaults = array(
		'currency'   => '$',
		'decimals'   => 2,
		'free_label' => 'Free',
	);
	$args     = wp_parse_args( $args, $defaults );

	if ( 0.0 === (float) $amount ) {
		return $args['free_label'];
	}
	return $args['currency'] . number_format_i18n( (float) $amount, (int) $args['decimals'] );
}

echo pagesco_format_price( 14.99 ), "\n";
echo pagesco_format_price( 1178, array( 'decimals' => 0 ) ), "\n";
echo pagesco_format_price( 9.5, array( 'currency' => '€ ' ) ), "\n";
echo pagesco_format_price( 0, 'free_label=Gift' ), "\n";

Gift

Callers name only what they change, in any order, and you can add a new option next year without breaking a single call. The price of the pattern is that PHP cannot check the keys for you: a typo such as 'decimal' => 0 is silently ignored. Document the keys in the DocBlock, as core does.

Errors come back as WP_Error

Core predates widespread use of exceptions, so most functions that can fail return a WP_Error object instead of throwing. It carries an error code (a string you can test), a message and optional data. Check for it with is_wp_error() before you use the result:

<?php
$pagesco_result = wp_insert_user(
	array(
		'user_login' => 'admin',
		'user_pass'  => 'not-used',
	)
);

if ( is_wp_error( $pagesco_result ) ) {
	echo 'Code:    ', $pagesco_result->get_error_code(), "\n";
	echo 'Message: ', $pagesco_result->get_error_message(), "\n";
} else {
	echo "Created user {$pagesco_result}\n";
}

// Some functions return 0 on failure unless you ask for the WP_Error with a last argument of true.
var_dump( wp_insert_post( array( 'post_title' => '' ) ) );
echo wp_insert_post( array( 'post_title' => '' ), true )->get_error_message(), "\n";

The user admin exists, so wp_insert_user() returned a WP_Error with the code existing_user_login. wp_insert_post() with nothing in it returned 0 by default, and the error object only when asked with true: read the "Return" line of a function's page in the Code Reference before you rely on it. Your own functions can return new WP_Error( 'pagesco_not_found', __( 'Book not found.', 'pagesco-books' ) ), and REST endpoints (Lesson 7.2) turn such an error into a proper HTTP error response. Exceptions still exist in modern WordPress code, mostly inside classes; at the boundary to WordPress, return a WP_Error.

💡 declare(strict_types=1) and WordPress

WordPress core does not use strict types, and values that come from the database or a form are strings: get_option( 'posts_per_page' ) returns "10", meta values and IDs from URLs are strings. In PHP Foundations every file started with declare(strict_types=1);, which makes PHP refuse such a string where an int is declared (Common Mistakes 4). In WordPress code, leave strict types out of files that call into core or receive its values, and cast deliberately instead: (int) get_option( 'posts_per_page' ), absint( $id ). Self-contained classes in your plugin may use strict types; the course says so where it does.

1. Escaping with the wrong function (silent)

🛠️ Step 1: Write the helper (12 min)

Create wordpress/pagesco-practice/book-card.php. Read each comment as you type: it says which rule the line follows.

<?php
/**
 * Pages & Co. book card helper (Lesson 1.3 practice).
 *
 * @package Pagesco
 */

/**
 * Returns the HTML of one book card.
 *
 * @param array $book {
 *     Book data.
 *
 *     @type string $title  Title.
 *     @type string $author Author name.
 *     @type float  $price  Price in dollars.
 *     @type int    $pages  Number of pages.
 *     @type string $url    Link to the book.
 * }
 * @param array $args {
 *     Optional. Display options.
 *
 *     @type int    $heading_level Heading level, 2 to 6. Default 3.
 *     @type bool   $show_price    Whether to show the price. Default true.
 *     @type string $class         CSS class of the card. Default 'pagesco-book-card'.
 * }
 * @return string The card HTML, escaped and ready to print.
 */
function pagesco_book_card( $book, $args = array() ) {
	// Array of arguments: callers pass only what they change.
	$args = wp_parse_args(
		$args,
		array(
			'heading_level' => 3,
			'show_price'    => true,
			'class'         => 'pagesco-book-card',
		)
	);

	// Validate: a heading level outside 2-6 falls back to the default.
	$level = absint( $args['heading_level'] );
	if ( $level < 2 || $level > 6 ) {
		$level = 3;
	}

	// Escape late, per context: attribute, URL, text.
	$html  = '<article class="' . esc_attr( $args['class'] ) . '">';
	$html .= sprintf(
		'<h%1$d><a href="%2$s">%3$s</a></h%1$d>',
		$level,
		esc_url( $book['url'] ),
		esc_html( $book['title'] )
	);

	// Translatable strings with placeholders and translator comments.
	$html .= '<p>' . esc_html(
		sprintf(
			/* translators: %s: author name. */
			__( 'by %s', 'pagesco' ),
			$book['author']
		)
	) . '</p>';
	$html .= '<p>' . esc_html(
		sprintf(
			/* translators: %s: number of pages. */
			_n( '%s page', '%s pages', (int) $book['pages'], 'pagesco' ),
			number_format_i18n( (int) $book['pages'] )
		)
	) . '</p>';

	if ( $args['show_price'] ) {
		$html .= '<p class="price">' . esc_html( '$' . number_format_i18n( (float) $book['price'], 2 ) ) . '</p>';
	}

	return $html . '</article>';
}

The function returns HTML instead of echoing it, so the caller decides where it goes; because every piece was escaped while it was built, the result is safe to print. That is the one situation where "escape late" happens inside a function, and the DocBlock says so.

🏋️ Exercise 3: Options for the Price

Extend pagesco_format_price() from the arrays-of-arguments section with a new option 'sale' => 0 (a discount in percent). When it is above 0, return the discounted price followed by the old one in parentheses: $11.99 (was $14.99). Every existing call must keep working unchanged. Test with 14.99, array( 'sale' => 20 ) and with no options.

💡 Hint

Add the key to $defaults; that is what keeps old calls working. Compute $amount * ( 100 - $sale ) / 100 and round it to two decimals before formatting. A small inner helper (or a closure) avoids writing the formatting twice.

✅ Solution 
<?php
function pagesco_format_price( $amount, $args = array() ) {
	$args = wp_parse_args(
		$args,
		array(
			'currency'   => '$',
			'decimals'   => 2,
			'free_label' => 'Free',
			'sale'       => 0,
		)
	);

	$format = fn( $value ) => $args['currency'] . number_format_i18n( $value, (int) $args['decimals'] );

	if ( 0.0 === (float) $amount ) {
		return $args['free_label'];
	}
	$sale = absint( $args['sale'] );
	if ( 0 < $sale ) {
		$now = round( (float) $amount * ( 100 - $sale ) / 100, 2 );
		return $format( $now ) . ' (was ' . $format( (float) $amount ) . ')';
	}
	return $format( (float) $amount );
}

echo pagesco_format_price( 14.99 ), "\n";
echo pagesco_format_price( 14.99, array( 'sale' => 20 ) ), "\n";
echo pagesco_format_price( 0 ), "\n";
wp eval-file pagesco-practice/exercise-price.php

Output

$14.99
$11.99 (was $14.99)
Free

The arrow function captures $args automatically, which is exactly what arrow functions are for. For a real shop, the words "was" and "Free" would go through __() too.

🏋️ Exercise 4: List Helpers Instead of Loops (Stretch)

WordPress has helpers for lists of arrays or objects that save you many loops: wp_list_filter(), wp_list_pluck() and wp_list_sort(). Using the four books below, print the titles of the books that are in stock, sorted by price from cheapest, as one comma-separated line, without writing a foreach.

$pagesco_books = array(
	array( 'title' => 'Dune', 'price' => 14.99, 'in_stock' => true ),
	array( 'title' => 'The Great Gatsby', 'price' => 8.99, 'in_stock' => false ),
	array( 'title' => 'Animal Farm', 'price' => 8.49, 'in_stock' => true ),
	array( 'title' => '1984', 'price' => 9.99, 'in_stock' => true ),
);
💡 Hint

wp_list_filter( $list, array( 'in_stock' => true ) ) keeps matching items; wp_list_sort( $list, 'price', 'ASC' ) sorts; wp_list_pluck( $list, 'title' ) collects one field. Then implode().

✅ Solution 
<?php
$pagesco_books = array(
	array( 'title' => 'Dune', 'price' => 14.99, 'in_stock' => true ),
	array( 'title' => 'The Great Gatsby', 'price' => 8.99, 'in_stock' => false ),
	array( 'title' => 'Animal Farm', 'price' => 8.49, 'in_stock' => true ),
	array( 'title' => '1984', 'price' => 9.99, 'in_stock' => true ),
);

$pagesco_in_stock = wp_list_filter( $pagesco_books, array( 'in_stock' => true ) );
$pagesco_sorted   = wp_list_sort( $pagesco_in_stock, 'price', 'ASC' );

echo implode( ', ', wp_list_pluck( $pagesco_sorted, 'title' ) ), "\n";

❓ Common Questions at This Stage

Can I use modern PHP (enums, match, readonly, typed properties) in WordPress code?

Yes, in your own theme and plugin, as long as you declare the minimum: a Requires PHP: 8.2 header (Lesson 5.1) makes WordPress refuse to activate the plugin on an older PHP, with a clear message, instead of crashing. Core itself sticks to PHP 7.4 syntax because it must run everywhere. A plugin meant for the public directory often chooses a lower minimum to reach more sites; a plugin for one client can use whatever their host runs.

Do I really have to write array() instead of []?

WPCS 3 reports short arrays because core uses the long form, and plugins submitted to the directory are usually checked against WPCS. Many agencies switch that one rule off in their PHPCS configuration (Lesson 8.1 shows how a phpcs.xml.dist ruleset excludes rules) and write []. The course uses array() in theme and plugin files and allows [] in short demos. Pick one per project and let the tool enforce it.

Why not just use htmlspecialchars() and my e() helper?

htmlspecialchars() is roughly what esc_html() does, but the WordPress functions know the site's character set, do not double-encode existing entities, have filters that security plugins can hook, and come in context-specific versions (esc_url() has no PHP equivalent). Reviewers and PHPCS also recognize them; a home-made helper gets flagged as unescaped output.

Is WordPress procedural or object-oriented?

Both. The public API you call is mostly functions, because that is what keeps twenty years of themes and plugins working. Underneath are classes (WP_Query, WP_Post, WP_REST_Server, WP_Block), and newer parts such as the HTML API and the Interactivity API are designed object-first. Your plugin in Module 5 will be object-oriented with a namespace and Composer autoloading; it talks to WordPress through functions and hooks.

📝 Lesson Summary

🎓 Key Takeaways

  • WordPress code shares one PHP process with core and every plugin, so it follows house rules: the WordPress Coding Standards, checked with PHPCS and the WordPress ruleset
  • Prefix every global name (pagesco_); text domains are the folder slug
  • Sanitize early (wp_unslash() + sanitize_text_field(), absint(), validators), escape late per context (esc_html(), esc_attr(), esc_url(), wp_kses_post())
  • Wrap visible strings in __() / esc_html__() / _n(), with sprintf() placeholders and translator comments; _e() functions echo
  • Callbacks come as names, closures, array( $obj, 'method' ) or static methods; named ones can be unhooked
  • Many-option functions take one array merged with wp_parse_args(); failures come back as WP_Error, checked with is_wp_error()
  • Read core's globals ($wpdb, $post, $wp_query), never assign to them, and prefer the function that wraps them; values from the database are strings, so cast instead of using strict types
