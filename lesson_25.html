📞 Lesson 7.3: External APIs, Transients & WP-Cron

In Lessons 7.1 and 7.2 the Pages & Co. site answered other programs. Today it calls one. The shop's book distributor has an API that says how many copies it has of each book and when its next delivery comes, and the booksellers want that next to their own stock. Calling another server is easy; doing it well means planning for the days it is slow, down or wrong, not asking it on every page view, and doing the regular work on a schedule. That is wp_remote_get(), transients and WP-Cron, and at the end you let other programs ask your site a question through the Abilities API.

🎯 Learning Objectives

By the end of this lesson, you will be able to:

  • Call an external API with wp_remote_get() and wp_remote_post(), and handle each way it can fail: no answer, an error status, or an answer that is not what you expected
  • Keep API keys in wp-config.php and choose wp_safe_remote_get() when a URL comes from a user
  • Cache answers in transients, explain where they are stored and how a persistent object cache changes that, and cache failures briefly too
  • Schedule recurring work with WP-Cron, start and stop it on activation and deactivation, and inspect and run it with WP-CLI
  • Register an ability with the Abilities API and run it over the REST API
  • ⏱️ Time 150 minutes
  • 📋 Prerequisites Lesson 7.2: Custom REST Endpoints
  • 🛠️ You will build a supplier client in the plugin, a cached Supplier column on the Books screen, the daily pagesco_books_daily_sync job (which also removes past events), and the pagesco/check-stock ability
  • 🧩 WordPress 7.1 on PHP 8.5 (the HTTP API, transients and WP-Cron work the same on every supported version; the Abilities API needs 6.9)
  • 🧱 Site your Pages & Co. site from Lesson 7.2, the WP-CLI container, and Maria's "Inventory script" application password in $PASS; no internet connection needed (except for the last exercise)

☎️ The Shop Picks Up the Phone

When a bookseller wants to know whether the distributor has more copies of The Great Gatsby, they call. Sometimes the line is busy, sometimes nobody answers, sometimes the person reads the wrong list. A good bookseller writes the answer on a sticky note with the time ("Riverside: Gatsby back mid-month, asked at 10 a.m."), so the next colleague who wonders does not call again, and at closing time somebody works through a checklist: update the notes, clear out yesterday's event posters.

💡 Mental model: the phone, the sticky note and the closing checklist

The phone is WordPress's HTTP API: wp_remote_get() and friends call another server and give you its answer, or tell you that there was none. The sticky note is a transient: a value with an expiry time, which may also fall off the wall early, so you always check whether it is still there. The closing checklist is WP-Cron: jobs that run on a schedule. WordPress has no clock of its own, though: the checklist is worked through when the next visitor walks in after closing time.

Put together, a page that shows supplier data never waits for the supplier when a fresh note exists, and the daily job keeps the note fresh:

🧪 A Supplier to Call: the Sandbox

Pages & Co. and its distributor, Riverside Books, are fictional, so their API does not exist on the internet. Real suppliers, payment providers and shipping companies give developers the same thing this course gives you: a sandbox, a test version of the API that answers like the real one, with test data and a test key. Ours is three small files inside your WordPress folder, plain PHP that does not load WordPress, so it works offline and every answer in this lesson is reproducible. Be clear about what that means: your site calls http://localhost:8080/supplier-sandbox/v1/…, which is your own Apache, and in production the same code would call https://api.riverside.example/v1/… instead. Nothing else changes.

The supplier's documentation (as far as the sandbox implements it) says:

EndpointDoesAnswers
GET /v1/availability?isbns=…copies available for up to 100 ISBN-13s, comma-separated200 {"supplier","items":[{"isbn","available","next_delivery"}],"unknown":[…]}
POST /v1/ordersorders copies; JSON body {"isbn","quantity"}201 with the order, 422 with {"error","message"}
every requestheader X-Api-Key401 without a valid key

Create the folder wordpress/supplier-sandbox/ (next to wp-content, not inside it) with these three files. First an .htaccess that gives the two PHP files the documented addresses:

# The supplier sandbox answers at /supplier-sandbox/v1/availability and /supplier-sandbox/v1/orders.
RewriteEngine On
RewriteRule ^v1/(availability|orders)$ $1.php [L]

The availability endpoint. It checks the key, can imitate a slow or a broken day (?simulate=slow, ?simulate=down: the real API has no such switch, but you need bad days to test against), and answers from a fixed list of the shop's eleven editions:

<?php
/**
 * Supplier sandbox: GET /supplier-sandbox/v1/availability?isbns=9780441172719,9780743273565
 *
 * A stand-in for the Riverside Books distribution API, for local development only.
 * Plain PHP, not WordPress. ?simulate=slow or ?simulate=down imitates a bad day.
 */

header( 'Content-Type: application/json; charset=utf-8' );

if ( 'sandbox-7f3a9c' !== ( $_SERVER['HTTP_X_API_KEY'] ?? '' ) ) {
	http_response_code( 401 );
	echo json_encode( array( 'error' => 'invalid_api_key', 'message' => 'Send a valid API key in the X-Api-Key header.' ) );
	exit;
}

$simulate = $_GET['simulate'] ?? '';
if ( 'slow' === $simulate ) {
	sleep( 4 );
}
if ( 'down' === $simulate ) {
	http_response_code( 503 );
	header( 'Content-Type: text/html; charset=utf-8' );
	header( 'Retry-After: 120' );
	echo '<h1>Service Unavailable</h1><p>Scheduled maintenance. Please try again later.</p>';
	exit;
}

// Copies at the supplier, and the next delivery date when there are none.
$stock = array(
	'9780441172719' => array( 24, null ),         // Dune
	'9780451524935' => array( 31, null ),         // 1984
	'9780060935467' => array( 12, null ),         // To Kill a Mockingbird
	'9780743273565' => array( 0, '2027-11-15' ),  // The Great Gatsby
	'9780141439518' => array( 18, null ),         // Pride and Prejudice
	'9780547928227' => array( 9, null ),          // The Hobbit
	'9780060850524' => array( 7, null ),          // Brave New World
	'9780316769488' => array( 5, null ),          // The Catcher in the Rye
	'9780544003415' => array( 3, null ),          // The Lord of the Rings
	'9781451673319' => array( 15, null ),         // Fahrenheit 451
	'9780451526342' => array( 22, null ),         // Animal Farm
);

$items   = array();
$unknown = array();
foreach ( array_filter( explode( ',', $_GET['isbns'] ?? '' ) ) as $isbn ) {
	if ( isset( $stock[ $isbn ] ) ) {
		$items[] = array(
			'isbn'          => $isbn,
			'available'     => $stock[ $isbn ][0],
			'next_delivery' => $stock[ $isbn ][1],
		);
	} else {
		$unknown[] = $isbn;
	}
}

echo json_encode( array( 'supplier' => 'Riverside Books (sandbox)', 'items' => $items, 'unknown' => $unknown ) );

And the orders endpoint, which checks an order and confirms it without storing anything:

<?php
/**
 * Supplier sandbox: POST /supplier-sandbox/v1/orders with a JSON body {"isbn":"…","quantity":10}
 *
 * A stand-in for the Riverside Books distribution API, for local development only.
 * It checks the order and answers like the real API, but stores nothing.
 */

header( 'Content-Type: application/json; charset=utf-8' );

if ( 'sandbox-7f3a9c' !== ( $_SERVER['HTTP_X_API_KEY'] ?? '' ) ) {
	http_response_code( 401 );
	echo json_encode( array( 'error' => 'invalid_api_key', 'message' => 'Send a valid API key in the X-Api-Key header.' ) );
	exit;
}
if ( 'POST' !== $_SERVER['REQUEST_METHOD'] ) {
	http_response_code( 405 );
	header( 'Allow: POST' );
	echo json_encode( array( 'error' => 'method_not_allowed', 'message' => 'Orders are created with POST.' ) );
	exit;
}

$order    = json_decode( file_get_contents( 'php://input' ), true );
$isbn     = is_array( $order ) ? (string) ( $order['isbn'] ?? '' ) : '';
$quantity = is_array( $order ) ? (int) ( $order['quantity'] ?? 0 ) : 0;

if ( ! preg_match( '/^97[89]\d{10}$/', $isbn ) ) {
	http_response_code( 422 );
	echo json_encode( array( 'error' => 'invalid_isbn', 'message' => 'isbn must be an ISBN-13 without dashes.' ) );
	exit;
}
if ( $quantity < 1 || $quantity > 50 ) {
	http_response_code( 422 );
	echo json_encode( array( 'error' => 'invalid_quantity', 'message' => 'quantity must be between 1 and 50.' ) );
	exit;
}

http_response_code( 201 );
echo json_encode(
	array(
		'order'             => 'RB-' . substr( $isbn, -4 ) . '-' . $quantity,
		'isbn'              => $isbn,
		'quantity'          => $quantity,
		'expected_delivery' => '2027-11-08',
	)
);

📡 wp_remote_get and Its Answers

PHP can fetch URLs in many ways (file_get_contents(), the cURL extension, Guzzle). In WordPress code use the HTTP API: wp_remote_get(), wp_remote_post(), wp_remote_head() and wp_remote_request() for other methods. They work on every host whatever PHP was compiled with (WordPress bundles the Requests library), use the CA certificates WordPress ships, honor proxy settings from wp-config.php, and offer filters such as pre_http_request, which lets tests replace the network (Lesson 8.1). A first call, as a scratch script in the WordPress folder (wordpress/supplier-ask.php):

<?php
$response = wp_remote_get(
	'http://localhost:8080/supplier-sandbox/v1/availability?isbns=9780743273565',
	array(
		'timeout' => 5,
		'headers' => array( 'X-Api-Key' => PAGESCO_BOOKS_SUPPLIER_KEY ),
	)
);

if ( is_wp_error( $response ) ) {
	echo 'No answer: ', $response->get_error_message(), "\n";
	return;
}

echo implode( ', ', array_keys( $response ) ), "\n";
echo wp_remote_retrieve_response_code( $response ), ' ', wp_remote_retrieve_response_message( $response ), "\n";
echo wp_remote_retrieve_header( $response, 'content-type' ), "\n";

$data = json_decode( wp_remote_retrieve_body( $response ), true );
print_r( $data['items'][0] );

Output

    [isbn] => 9780743273565
    [available] => 0

A response is an array (with the original object in http_response); read it with the wp_remote_retrieve_*() helpers rather than by its keys: they also accept a WP_Error and then return '' instead of failing. Header names are case-insensitive. The body is a string: you decode it, and you decide what a valid answer is. The arguments you will use most:

Three ways to fail

Every call to another server can end in one of three ways besides success, and each looks different in PHP. A script that provokes all three: two against the sandbox, one against a host that does not exist:

<?php
$key = array( 'X-Api-Key' => PAGESCO_BOOKS_SUPPLIER_KEY );
$url = 'http://localhost:8080/supplier-sandbox/v1/availability';

// 1. An answer, but an error status: wrong key.
$wrong = wp_remote_get( $url, array( 'headers' => array( 'X-Api-Key' => 'guess' ) ) );
echo 'Wrong key:  ', is_wp_error( $wrong ) ? 'WP_Error' : 'response', ' ', wp_remote_retrieve_response_code( $wrong ), ' ', wp_remote_retrieve_body( $wrong ), "\n";

// 2. An answer, an error status, and HTML instead of JSON: the supplier is down.
$down = wp_remote_get( $url . '?simulate=down', array( 'headers' => $key ) );
echo 'Down:       ', wp_remote_retrieve_response_code( $down ), ', Retry-After ', wp_remote_retrieve_header( $down, 'retry-after' ), ', JSON: ';
var_dump( json_decode( wp_remote_retrieve_body( $down ), true ) );

// 3. No answer at all: the host does not exist.
$nowhere = wp_remote_get( 'http://supplier.invalid/v1/availability' );
echo 'No host:    ', is_wp_error( $nowhere ) ? 'WP_Error' : 'response', ' ', $nowhere->get_error_code(), ': ', $nowhere->get_error_message(), "\n";

Output

Wrong key:  response 401 {"error":"invalid_api_key","message":"Send a valid API key in the X-Api-Key header."}
Down:       503, Retry-After 120, JSON: NULL
No host:    WP_Error http_request_failed: cURL error 6: Could not resolve host: supplier.invalid (Domain name not found)
  • An error status is not a WP_Error. For WordPress, a 401 or 503 is a perfectly good HTTP response: you get an array, and only wp_remote_retrieve_response_code() tells you it failed. Code that only checks is_wp_error() treats the supplier's error page as data (Common Mistake 1).
  • Error answers may not be JSON. The 503 came from a maintenance page: json_decode() returns NULL. Retry-After: 120 says when to try again; polite clients respect it.
  • No answer is a WP_Error with the code http_request_failed and the transport's message. (.invalid is a top-level domain reserved never to exist, handy for this test.)

The third kind has a slow cousin: the supplier answers, but too late. With a timeout of 2 seconds against the slow sandbox (it waits 4):

<?php
$started  = microtime( true );
$response = wp_remote_get(
	'http://localhost:8080/supplier-sandbox/v1/availability?simulate=slow',
	array(
		'timeout' => 2,
		'headers' => array( 'X-Api-Key' => PAGESCO_BOOKS_SUPPLIER_KEY ),
	)
);
echo $response->get_error_code(), ': ', $response->get_error_message(), "\n";
printf( "Waited %.1f seconds\n", microtime( true ) - $started );

Output (your milliseconds will differ slightly)

http_request_failed: cURL error 28: Operation timed out after 2056 milliseconds with 0 bytes received
Waited 1.9 seconds

Two seconds lost, and then nothing. On a page view, a visitor waits that long for nothing; with the default of 5 seconds and three such calls on one page, fifteen. That is why pages should read cached answers and leave the calling to background jobs, and why every call names a timeout it can afford.

Sending data: wp_remote_post

wp_remote_post() takes the same arguments. To send JSON, encode the body yourself and say so in a header; without the header, an array body is sent as an HTML form. An order for ten copies of The Catcher in the Rye, and one for eighty:

<?php
foreach ( array( 10, 80 ) as $quantity ) {
	$response = wp_remote_post(
		'http://localhost:8080/supplier-sandbox/v1/orders',
		array(
			'timeout' => 5,
			'headers' => array(
				'X-Api-Key'    => PAGESCO_BOOKS_SUPPLIER_KEY,
				'Content-Type' => 'application/json',
			),
			'body'    => wp_json_encode(
				array(
					'isbn'     => '9780316769488',
					'quantity' => $quantity,
				)
			),
		)
	);
	echo wp_remote_retrieve_response_code( $response ), ' ', wp_remote_retrieve_body( $response ), "\n";
}

Output

201 {"order":"RB-9488-10","isbn":"9780316769488","quantity":10,"expected_delivery":"2027-11-08"}
422 {"error":"invalid_quantity","message":"quantity must be between 1 and 50."}

201 Created with the order, then 422 Unprocessable Content with a message you can show a bookseller. The same three-way check applies to every POST, with one more rule: a request that changes something and timed out may still have arrived, so before retrying an order, ask the supplier whether it exists (good APIs accept an idempotency key for this).

URLs from users: wp_safe_remote_get

The supplier's URL comes from wp-config.php, which only you control. When a URL comes from a user (a "fetch the cover from this address" field, a webhook target), use the wp_safe_remote_*() functions: they refuse addresses in private networks and odd ports, so nobody can make your server request http://192.168.1.1/admin or a cloud provider's metadata service on their behalf (server-side request forgery, SSRF). Your own site's address stays allowed:

<?php
foreach ( array( 'http://192.168.1.10/', 'http://127.0.0.1:8080/', 'http://localhost:8080/supplier-sandbox/v1/availability' ) as $url ) {
	$response = wp_safe_remote_get( $url );
	echo str_pad( $url, 58 ), is_wp_error( $response ) ? $response->get_error_message() : wp_remote_retrieve_response_code( $response ), "\n";
}

Output

http://192.168.1.10/                                      A valid URL was not provided.
http://127.0.0.1:8080/                                    A valid URL was not provided.
http://localhost:8080/supplier-sandbox/v1/availability    401

The private addresses are refused before any connection; localhost:8080 is allowed because it is the site's own host (and it answers 401: no key). Remove the scratch scripts:

🗒️ Transients: Answers with an Expiry Date

A transient is an option with an expiry time. Three functions cover it:

set_transient( 'pagesco_books_supplier_availability', $value, 12 * HOUR_IN_SECONDS ); // true on success
$value = get_transient( 'pagesco_books_supplier_availability' );                      // false when missing or expired
delete_transient( 'pagesco_books_supplier_availability' );

The value can be anything update_option() accepts (arrays are serialized). The name is prefixed like every option (pagesco_books_, the spine's transient prefix) and at most 172 characters. MINUTE_IN_SECONDS, HOUR_IN_SECONDS, DAY_IN_SECONDS and WEEK_IN_SECONDS make the lifetime readable. With WP-CLI, look at where a transient really lives:

wp transient set pagesco_books_demo 'Gatsby: back November 15' 600
wp transient get pagesco_books_demo
wp db query "SELECT option_name, autoload FROM wp_options WHERE option_name LIKE '%pagesco_books_demo'"
wp transient delete pagesco_books_demo
wp transient get pagesco_books_demo

Output

Success: Transient added.
Gatsby: back November 15
option_name	autoload
_transient_timeout_pagesco_books_demo	off
_transient_pagesco_books_demo	off

Success: Transient deleted.
Warning: Transient with key "pagesco_books_demo" is not set.

Two rows in wp_options (Lesson 2.2): _transient_pagesco_books_demo with the value and _transient_timeout_pagesco_books_demo with the expiry as a Unix timestamp, both not autoloaded, so a transient costs nothing on requests that do not read it. When get_transient() finds the timeout passed, it deletes both rows and returns false; expired transients nobody reads are removed by core's daily delete_expired_transients cron job. wp transient get on a missing transient prints a warning, as the last command shows. Site transients (set_site_transient()) are the same for a whole multisite network.

Transients and the object cache

WordPress keeps an object cache in memory during every request (wp_cache_get(), wp_cache_set()): that is why reading an option twice costs one query (Lesson 2.2). By default it is forgotten at the end of the request. A site can add a persistent object cache with the object-cache.php drop-in (Lesson 2.2) and Redis or Memcached, and then transients change home: set_transient() writes to the cache instead of wp_options, and the rows above never exist. Your site has none:

wp eval 'var_dump( wp_using_ext_object_cache() );'

Output

NULL

Code that uses the transient functions works the same either way, with one rule that matters most with a cache: a transient may disappear before it expires (a cache that runs out of memory evicts it; a deploy may flush it). The expiry is a maximum, never a promise. So every read is "use it if it is there, otherwise get it again", and nothing that cannot be fetched again (an order, a setting) may live only in a transient. Lesson 8.2 sets up and measures a persistent object cache.

The read-through pattern, and caching failures

The usual shape: try the transient, and only when it is missing call the API and store the answer. A demonstration that counts real HTTP requests with the http_api_debug action, which fires after each one:

<?php
$requests = 0;
add_action(
	'http_api_debug',
	function () use ( &$requests ) {
		++$requests;
	}
);

function pagesco_demo_gatsby() {
	$cached = get_transient( 'pagesco_books_demo_gatsby' );
	if ( false !== $cached ) {
		return $cached;
	}

	$response = wp_remote_get(
		'http://localhost:8080/supplier-sandbox/v1/availability?isbns=9780743273565',
		array( 'headers' => array( 'X-Api-Key' => PAGESCO_BOOKS_SUPPLIER_KEY ) )
	);
	$data     = json_decode( wp_remote_retrieve_body( $response ), true );
	$value    = $data['items'][0] ?? array();

	set_transient( 'pagesco_books_demo_gatsby', $value, 10 * MINUTE_IN_SECONDS );
	return $value;
}

for ( $view = 1; $view <= 3; $view++ ) {
	$gatsby = pagesco_demo_gatsby();
	echo "View $view: next delivery {$gatsby['next_delivery']}, HTTP requests so far: $requests\n";
}
delete_transient( 'pagesco_books_demo_gatsby' );

Output

View 1: next delivery 2027-11-15, HTTP requests so far: 1
View 2: next delivery 2027-11-15, HTTP requests so far: 1
View 3: next delivery 2027-11-15, HTTP requests so far: 1
rm cache-demo.php

One request for three views, and a thousand views would still be one request per ten minutes. (The demo skips the error checks to stay short; the project's code does not.) Now the subtle part: what if the call fails? If you cache nothing, every view calls the broken supplier again and waits for its timeout, which turns the supplier's bad day into yours. So cache the failure too, briefly: the project stores "the supplier is not reachable" for five minutes, a good answer for twelve hours. And never cache false itself: get_transient() returns false for "missing", so a stored false looks like no note at all. Store an array such as array( 'items' => array(), 'error' => '…' ) instead.

⏰ WP-Cron: Work on a Schedule

Operating systems have a clock that starts jobs (cron on Linux). WordPress cannot count on one, so it keeps a list of scheduled events in the option cron and, on an ordinary page request, checks whether any is due. If one is, it calls its own wp-cron.php in the background (a "loopback" request to its own URL, which is why Lesson 1.2's Apache listens on 8080 inside the container too) and the events run there, as actions: an event is a hook name, a time, a recurrence and arguments, and running it means do_action( $hook, ...$args ). Three consequences of "the next visitor starts it":

  • Times are earliest times. A job due at 3:00 runs with the first request after 3:00: at 3:00:01 on a busy shop, at 7:45 on a quiet one. Jobs must not depend on an exact time.
  • No visitors, no jobs. On production sites, the usual fix is define( 'DISABLE_WP_CRON', true ); in wp-config.php (no more loopbacks on page views) plus a real system cron entry that runs wp cron event run --due-now every five minutes. Lesson 8.4 sets that up.
  • Jobs run without a user. In wp-cron.php nobody is logged in: current_user_can() is false for everything, and is_admin() is false. A job does its work directly and checks no capabilities; that is safe because nobody can trigger it with input of their own (Common Mistake 3 shows the opposite trap).

⚠️ wp cron event run moves a recurring event

wp cron event run pagesco_books_daily_sync runs the job now, which is what you want while developing, but WP-CLI also reschedules a recurring event from now: a job planned for 3:00 tomorrow that you run at 10:15 moves to 10:15 tomorrow (measured on WordPress 7.1 with WP-CLI 2.12). To run the work without touching the schedule, fire the hook yourself: wp eval 'do_action( "pagesco_books_daily_sync" );', as the project does.

🛠️ Step 2: The client and the cached column (20 min)

The client knows HTTP and the supplier's API; nothing else in the plugin does. It is not a feature (it adds no hooks), just a class the features use. Create wordpress/wp-content/plugins/pagesco-books/src/Supplier/Client.php:

<?php
/**
 * The supplier's API (Riverside Books), over HTTP.
 *
 * @package PagesCo\Books
 */

namespace PagesCo\Books\Supplier;

use WP_Error;

/**
 * Asks the supplier what it has, and places orders. Every method returns data or a WP_Error, never both.
 *
 * The address and the API key come from wp-config.php: PAGESCO_BOOKS_SUPPLIER_URL and PAGESCO_BOOKS_SUPPLIER_KEY.
 */
final class Client {

	/**
	 * Seconds to wait for the supplier before giving up.
	 */
	private const TIMEOUT = 5;

	/**
	 * GET /availability: copies at the supplier and the next delivery date, keyed by ISBN.
	 *
	 * @param string[] $isbns ISBN-13s without dashes.
	 * @return array<string, array{available: int, next_delivery: string}>|WP_Error
	 */
	public function availability( array $isbns ) {
		$url = $this->url( 'availability' );
		if ( is_wp_error( $url ) ) {
			return $url;
		}

		$response = wp_remote_get(
			add_query_arg( 'isbns', rawurlencode( implode( ',', $isbns ) ), $url ),
			array(
				'timeout' => self::TIMEOUT,
				'headers' => $this->headers(),
			)
		);

		$data = $this->decode( $response );
		if ( is_wp_error( $data ) ) {
			return $data;
		}
		if ( ! isset( $data['items'] ) || ! is_array( $data['items'] ) ) {
			return new WP_Error( 'pagesco_supplier_bad_response', __( 'The supplier answered without a list of items.', 'pagesco-books' ) );
		}

		$availability = array();
		foreach ( $data['items'] as $item ) {
			$availability[ (string) ( $item['isbn'] ?? '' ) ] = array(
				'available'     => (int) ( $item['available'] ?? 0 ),
				'next_delivery' => (string) ( $item['next_delivery'] ?? '' ),
			);
		}

		return $availability;
	}

	/**
	 * POST /orders: orders copies of a book. Returns the supplier's order confirmation.
	 *
	 * @param string $isbn     ISBN-13 without dashes.
	 * @param int    $quantity How many copies.
	 * @return array|WP_Error
	 */
	public function order( string $isbn, int $quantity ) {
		$url = $this->url( 'orders' );
		if ( is_wp_error( $url ) ) {
			return $url;
		}

		$response = wp_remote_post(
			$url,
			array(
				'timeout' => self::TIMEOUT,
				'headers' => $this->headers() + array( 'Content-Type' => 'application/json' ),
				'body'    => wp_json_encode(
					array(
						'isbn'     => $isbn,
						'quantity' => $quantity,
					)
				),
			)
		);

		return $this->decode( $response );
	}

	/**
	 * The full address of one of the supplier's endpoints, from the URL in wp-config.php.
	 *
	 * @param string $endpoint The endpoint's path, such as availability.
	 * @return string|WP_Error
	 */
	private function url( string $endpoint ) {
		if ( ! defined( 'PAGESCO_BOOKS_SUPPLIER_URL' ) || ! defined( 'PAGESCO_BOOKS_SUPPLIER_KEY' ) ) {
			return new WP_Error( 'pagesco_supplier_not_configured', __( 'The supplier is not configured in wp-config.php.', 'pagesco-books' ) );
		}

		return trailingslashit( PAGESCO_BOOKS_SUPPLIER_URL ) . $endpoint;
	}

	/**
	 * The headers every request sends: what we accept, and who we are.
	 */
	private function headers(): array {
		return array(
			'Accept'    => 'application/json',
			'X-Api-Key' => PAGESCO_BOOKS_SUPPLIER_KEY,
		);
	}

	/**
	 * Turns an HTTP response into data, or into a WP_Error for each way it can go wrong.
	 *
	 * @param array|WP_Error $response What wp_remote_get() or wp_remote_post() returned.
	 * @return array|WP_Error
	 */
	private function decode( $response ) {
		// 1. No answer at all: DNS, connection refused, timeout.
		if ( is_wp_error( $response ) ) {
			return $response;
		}

		$code = wp_remote_retrieve_response_code( $response );
		$data = json_decode( wp_remote_retrieve_body( $response ), true );

		// 2. An answer, but not a success: 401, 404, 422, 503...
		if ( $code < 200 || $code > 299 ) {
			return new WP_Error(
				'pagesco_supplier_http_error',
				sprintf(
					/* translators: 1: HTTP status code, 2: the supplier's message. */
					__( 'The supplier answered %1$d: %2$s', 'pagesco-books' ),
					$code,
					is_array( $data ) && isset( $data['message'] ) ? $data['message'] : wp_remote_retrieve_response_message( $response )
				),
				array(
					'status'      => $code,
					'retry_after' => wp_remote_retrieve_header( $response, 'retry-after' ),
				)
			);
		}

		// 3. A success that is not the JSON we expect.
		if ( ! is_array( $data ) ) {
			return new WP_Error( 'pagesco_supplier_bad_response', __( 'The supplier\'s answer is not JSON.', 'pagesco-books' ) );
		}

		return $data;
	}
}
  • Configuration comes from the two constants; without them the client returns a WP_Error instead of calling a guessed address. trailingslashit() accepts the URL with or without its final slash.
  • decode() is the three-way check from the section above, in one place. Each failure becomes a WP_Error with a prefixed code, an HTTP status code in its data when there was one, and the Retry-After value.
  • One request for the whole catalog: availability() sends all ISBNs at once, and returns an array keyed by ISBN, with real types.
  • order() uses wp_remote_post() with a JSON body (Exercise 1 uses it).

The feature keeps the answer and shows it. Create src/Supplier/Availability.php:

<?php
/**
 * What the supplier has of each book, cached in a transient.
 *
 * @package PagesCo\Books
 */

namespace PagesCo\Books\Supplier;

use PagesCo\Books\BookPostType;
use PagesCo\Books\Feature;

/**
 * Keeps the supplier's availability for the whole catalog in one transient, and shows it on the Books screen.
 */
final class Availability implements Feature {

	/**
	 * The transient that holds the last answer (or the last error).
	 */
	public const TRANSIENT = 'pagesco_books_supplier_availability';

	/**
	 * Keep a good answer for 12 hours; the daily sync refreshes it anyway.
	 */
	private const LIFETIME = 12 * HOUR_IN_SECONDS;

	/**
	 * After a failure, wait 5 minutes before asking again.
	 */
	private const RETRY = 5 * MINUTE_IN_SECONDS;

	/**
	 * Adds a Supplier column to the Books screen.
	 */
	public function register(): void {
		add_filter( 'manage_' . BookPostType::NAME . '_posts_columns', array( $this, 'add_column' ), 20 );
		add_action( 'manage_' . BookPostType::NAME . '_posts_custom_column', array( $this, 'print_column' ), 10, 2 );
	}

	/**
	 * The cached availability; asks the supplier only when there is no cached answer.
	 *
	 * @return array{items: array, error: string}
	 */
	public function get(): array {
		$cached = get_transient( self::TRANSIENT );

		if ( is_array( $cached ) ) {
			return $cached;
		}

		return $this->refresh();
	}

	/**
	 * Asks the supplier now and caches the answer: for 12 hours, or for 5 minutes if it failed.
	 *
	 * @return array{items: array, error: string}
	 */
	public function refresh(): array {
		$result = ( new Client() )->availability( $this->catalog_isbns() );

		if ( is_wp_error( $result ) ) {
			$value = array(
				'items' => array(),
				'error' => $result->get_error_message(),
			);
			set_transient( self::TRANSIENT, $value, self::RETRY );

			return $value;
		}

		$value = array(
			'items' => $result,
			'error' => '',
		);
		set_transient( self::TRANSIENT, $value, self::LIFETIME );

		return $value;
	}

	/**
	 * The ISBNs of the published books that have one.
	 *
	 * @return string[]
	 */
	private function catalog_isbns(): array {
		$ids = get_posts(
			array(
				'post_type'      => BookPostType::NAME,
				'post_status'    => 'publish',
				'posts_per_page' => 100,
				'fields'         => 'ids',
			)
		);

		$isbns = array_map( fn( $id ) => (string) get_post_meta( $id, 'pagesco_isbn', true ), $ids );

		return array_values( array_filter( $isbns ) );
	}

	/**
	 * Adds the Supplier column after the shop's own Stock column.
	 *
	 * @param string[] $columns Column keys and headings.
	 * @return string[]
	 */
	public function add_column( $columns ) {
		$columns['pagesco_supplier'] = __( 'Supplier', 'pagesco-books' );

		return $columns;
	}

	/**
	 * Prints a book's Supplier cell: copies there, or the next delivery date.
	 *
	 * @param string $column  The column key.
	 * @param int    $post_id The book in this row.
	 */
	public function print_column( $column, $post_id ): void {
		if ( 'pagesco_supplier' !== $column ) {
			return;
		}

		$isbn         = (string) get_post_meta( $post_id, 'pagesco_isbn', true );
		$availability = $this->get();
		$item         = $availability['items'][ $isbn ] ?? null;

		if ( '' !== $availability['error'] ) {
			esc_html_e( 'Supplier not reachable', 'pagesco-books' );
		} elseif ( null === $item ) {
			echo '&mdash;';
		} elseif ( $item['available'] > 0 ) {
			/* translators: %s: number of copies. */
			echo esc_html( sprintf( _n( '%s copy', '%s copies', $item['available'], 'pagesco-books' ), number_format_i18n( $item['available'] ) ) );
		} elseif ( '' !== $item['next_delivery'] ) {
			/* translators: %s: a date. */
			echo esc_html( sprintf( __( 'None; next delivery %s', 'pagesco-books' ), mysql2date( get_option( 'date_format' ), $item['next_delivery'] ) ) );
		} else {
			esc_html_e( 'None', 'pagesco-books' );
		}
	}
}
  • get() is the read-through pattern; refresh() always asks, and caches a success for 12 hours or a failure for 5 minutes, in the same shape (items, error), so a cached failure is an array and never false.

The job, as a feature. Create src/DailySync.php:

<?php
/**
 * The shop's daily WP-Cron job.
 *
 * @package PagesCo\Books
 */

namespace PagesCo\Books;

use PagesCo\Books\Supplier\Availability;

/**
 * Once a day: refresh the supplier's availability and remove events that are over.
 */
final class DailySync implements Feature {

	/**
	 * The cron hook. WP-Cron fires it as an action, so the callback is added like any action.
	 */
	public const HOOK = 'pagesco_books_daily_sync';

	/**
	 * Connects the job to its hook, on every request: WP-Cron runs on whichever request finds it due.
	 */
	public function register(): void {
		add_action( self::HOOK, array( $this, 'run' ) );
	}

	/**
	 * Schedules the job once a day, from 3 a.m. tomorrow in the site's time zone. Called on activation.
	 */
	public static function schedule(): void {
		if ( wp_next_scheduled( self::HOOK ) ) {
			return;
		}

		$first = new \DateTimeImmutable( 'tomorrow 03:00', wp_timezone() );
		wp_schedule_event( $first->getTimestamp(), 'daily', self::HOOK );
	}

	/**
	 * Removes the job. Called on deactivation.
	 */
	public static function unschedule(): void {
		wp_clear_scheduled_hook( self::HOOK );
	}

	/**
	 * The job itself. It runs without a logged-in user, so it checks no capabilities and prints nothing.
	 */
	public function run(): void {
		$availability = Plugin::instance()->feature( Availability::class );
		if ( $availability instanceof Availability ) {
			$availability->refresh();
		}

		// Events that started before today are over (Lesson 5.5's promise).
		EventsTable::delete_before( wp_date( 'Y-m-d 00:00:00' ) );
	}
}
  • register() adds the callback on every request, unconditionally (Common Mistake 3).
  • schedule() asks wp_next_scheduled() first (Common Mistake 2), and starts at 3 a.m. tomorrow in the site's time zone (wp_timezone(), Settings > General), a quiet hour, rather than "now".
  • run() reaches the Availability feature through Plugin::instance()->feature() (Lesson 5.1) and deletes events that started before today, so tonight's event stays on the page until tomorrow.

			return new WP_Error( 'pagesco_book_not_found', __( 'No book was found with that slug.', 'pagesco-books' ), array( 'status' => 404 ) );

❓ Common Questions at This Stage

Should the supplier push changes to us instead (webhooks)?

Often, yes. If the supplier can call a URL when stock changes, the shop gets news within seconds and makes no requests at all; the URL would be a POST route of your own (Lesson 7.2) whose permission_callback checks a signature or a shared secret the supplier sends, since the supplier has no WordPress user. Many integrations use both: webhooks for speed, a daily pull to catch anything a webhook missed.

What about heavy or many jobs, such as 5,000 books one by one?

WP-Cron runs every due event in one request, with PHP's time limit (30 seconds in the course container). For queues of many small jobs, plugins use Action Scheduler, the library WooCommerce ships (also available on its own): it stores jobs in its own tables, runs them in batches, retries failures and shows them under Tools > Scheduled Actions. For the shop's one daily call, WP-Cron is enough.

Should the API key go into the plugin's settings page instead?

For a plugin other people install, often yes: a site owner cannot edit wp-config.php on every host. Then store it in an option that is not autoloaded, never print it back into the form (show "a key is saved" and a field to replace it), and remember that anyone with a database export has it. The wp-config.php constant or an environment variable is better for your own sites, because it keeps the key out of the database and out of backups of it. Some plugins accept both: a constant, if defined, wins over the setting.

Can I see what my site sends and receives?

The http_api_debug action (used in the transients demo) fires after every request with the response, the arguments and the URL; logging it is a quick way to see your integration's traffic. Query Monitor (Lesson 8.1) shows every HTTP request a page made, with its time and status.

🎓 Key Takeaways

  • Call other servers with wp_remote_get() / wp_remote_post() and read answers with wp_remote_retrieve_response_code(), _body() and _header(); always set a timeout you can afford
  • Check three failures in order: a WP_Error (no answer, timeout), a status outside 2xx (still a normal response), and a body that is not the data you expect
  • Keys and environment-specific URLs live in wp-config.php, not in code; use wp_safe_remote_*() for URLs that users supply
  • Transients are options with an expiry (two non-autoloaded rows, or the persistent object cache when there is one); they can vanish early, so read through and never store false; cache failures briefly
  • WP-Cron runs due events on the next request, as actions, without a user: schedule once on activation with wp_next_scheduled(), clear on deactivation, add the callback on every request
  • The Abilities API describes units of work (input and output schemas, a permission check) that tools can discover and run, through PHP or /wp-json/wp-abilities/v1/
