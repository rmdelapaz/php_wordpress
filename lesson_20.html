🃏 Lesson 6.2: Static Blocks: Attributes, Controls & Supports

The Book Card from Lesson 6.1 says "a staff pick is coming soon" and nothing else. Today it becomes the real thing: a card in which a bookseller types the title, the author and why they love the book, directly on the canvas, picks a heading level and a link in the sidebar, and colors it from the theme's palette without a line of CSS from you. Along the way you will learn the one rule that makes static blocks both simple and strict: the saved HTML is the data, so changing save later needs care.

By the end of this lesson, you will be able to:

  • Add settings to the block sidebar with InspectorControls and components from @wordpress/components
  • Opt into color, spacing and typography block supports and read the classes and styles they save
  • Explain block validation, and change save safely with a deprecated entry and migrate

🗃️ Attributes: Where a Block Keeps Its Data

In Lesson 1.3 you wrote pagesco_book_card( $book, $args ): an array of book data in, escaped HTML out. A block does the same job, split across the editor and the stored post. Its data are attributes, declared in block.json with a type and, optionally, a default. edit receives them and changes them with setAttributes(); save receives them and returns HTML. What makes block attributes different from PHP arguments is the question of where they are stored, and there are two answers:

Declared withStoredRead back byGood for
"source": "html" (or "text", "attribute", "query") and a "selector"inside the saved HTML itselfthe editor, by finding the selector in the HTMLContent people type: titles, text, links, image URLs
no sourceas JSON in the block comment: <!-- wp:pagesco/book-card {"headingLevel":2} -->the editor and PHP (parse_blocks())Settings: levels, toggles, choices, IDs

Content stored in the HTML is not duplicated: "Dune" is in the post once, inside the <h3>, and the editor finds it again through the selector. Values equal to their default are left out of the comment altogether. (Old tutorials also show "source": "meta"; it is deprecated, and Lesson 6.3 does the same job with block bindings.)

💡 Mental model: a printed card with a sticky note

A static block in a post is like a printed shop card with a sticky note on the back. The printed side, the HTML, is what every visitor sees, and the bookseller's words are printed right on it. The sticky note, the comment JSON, holds the few settings that are not visible as words, such as "heading level 2". The editor reads both to rebuild the card for editing. PHP can read the sticky note easily, but would have to read the print to find the words (Common Mistake 1).

The card's first three fields

The Book Card gets three content attributes, each sourced from an element with its own class. Replace src/blocks/book-card/block.json. Besides the attributes, the version moves to 0.2.0 and the block gets keywords and an example for the inserter preview:

On the canvas, editable text comes from RichText, a component of @wordpress/block-editor: an element you can type into, with a toolbar for the formats you allow. It takes the tag to render, its current value and an onChange that stores the new value with setAttributes(), React's usual "controlled input" pattern. Replace src/blocks/book-card/edit.js:

import { __ } from '@wordpress/i18n';
import { RichText, useBlockProps } from '@wordpress/block-editor';
import './editor.scss';

export default function Edit( { attributes, setAttributes } ) {
	const { title, author, pick } = attributes;

	return (
		<div { ...useBlockProps() }>
			<RichText
				tagName="h3"
				className="wp-block-pagesco-book-card__title"
				value={ title }
				onChange={ ( value ) => setAttributes( { title: value } ) }
				placeholder={ __( 'Book title', 'pagesco-books' ) }
				allowedFormats={ [] }
			/>
			<RichText
				tagName="p"
				className="wp-block-pagesco-book-card__author"
				value={ author }
				onChange={ ( value ) => setAttributes( { author: value } ) }
				placeholder={ __( 'Author', 'pagesco-books' ) }
				allowedFormats={ [] }
			/>
			<RichText
				tagName="p"
				className="wp-block-pagesco-book-card__pick"
				value={ pick }
				onChange={ ( value ) => setAttributes( { pick: value } ) }
				placeholder={ __( 'Why do you recommend it?', 'pagesco-books' ) }
				allowedFormats={ [ 'core/bold', 'core/italic' ] }
			/>
		</div>
	);
}

allowedFormats={ [] } keeps the title and author plain; the recommendation may be bold or italic, nothing else. save is the mirror image: RichText.Content prints a stored value inside the tag you name. Replace src/blocks/book-card/save.js:

import { RichText, useBlockProps } from '@wordpress/block-editor';

export default function save( { attributes } ) {
	const { title, author, pick } = attributes;

	return (
		<div { ...useBlockProps.save() }>
			<RichText.Content
				tagName="h3"
				className="wp-block-pagesco-book-card__title"
				value={ title }
			/>
			<RichText.Content
				tagName="p"
				className="wp-block-pagesco-book-card__author"
				value={ author }
			/>
			<RichText.Content
				tagName="p"
				className="wp-block-pagesco-book-card__pick"
				value={ pick }
			/>
		</div>
	);
}

The class names follow the BEM pattern core uses (block__element), so the selectors in block.json find exactly one element each. The text in save is never escaped by hand: RichText.Content writes the HTML the editor's RichText produced (only the formats you allowed), and when a user without the unfiltered_html capability saves the post, WordPress filters the content through KSES as for any post (Lesson 5.3). Last, the styles. Replace src/blocks/book-card/style.scss:

.wp-block-pagesco-book-card {
	border: 1px solid currentColor;
	border-radius: 4px;
	padding: 1.25rem 1.5rem;
}

.wp-block-pagesco-book-card__title {
	margin: 0;
}

.wp-block-pagesco-book-card__author {
	margin: 0.25rem 0 0;
	font-style: italic;
}

.wp-block-pagesco-book-card__pick {
	margin: 0.75rem 0 0;
}

Build, and ask WordPress which attributes the registered block has:

npm run build > /dev/null
wp eval 'echo implode( ", ", array_keys( WP_Block_Type_Registry::get_instance()->get_registered( "pagesco/book-card" )->get_attributes() ) ), "\n";'

Output

title, author, pick, lock, metadata, className, style

Your three, plus attributes WordPress adds to every block: lock (locking in the editor), metadata (a custom name in List View, and the bindings of Lesson 6.3), className (the "Additional CSS class(es)" field under Advanced) and style, where block supports keep per-block design values (the supports section fills it).

🎚️ Controls in the Sidebar

Some settings are not text on the card: the link to the book's page in the shop and the heading level (an <h3> fits under a post's <h2> sections, but a card at the top of a page might need an <h2>). Lesson 1.3's helper took exactly this as $args['heading_level']. In the editor such settings go into the block sidebar through InspectorControls: anything you render inside it appears in the sidebar's Settings tab while the block is selected. The controls themselves come from @wordpress/components, WordPress's library of admin UI: PanelBody (a collapsible panel), TextControl, SelectControl, ToggleControl and many more.

Two new attributes. url is sourced from the href of a link, so it lives in the HTML too; headingLevel has no source and a default of 3, so it goes into the comment only when it is not 3. Replace src/blocks/book-card/block.json:

Replace src/blocks/book-card/edit.js. The component now returns two things side by side, the sidebar panel and the card, wrapped in a fragment (<> … </>), React's way of returning several elements without an extra wrapper:

import { __ } from '@wordpress/i18n';
import {
	InspectorControls,
	RichText,
	useBlockProps,
} from '@wordpress/block-editor';
import { PanelBody, SelectControl, TextControl } from '@wordpress/components';
import './editor.scss';

export default function Edit( { attributes, setAttributes } ) {
	const { title, author, pick, url, headingLevel } = attributes;

	return (
		<>
			<InspectorControls>
				<PanelBody title={ __( 'Card settings', 'pagesco-books' ) }>
					<TextControl
						__next40pxDefaultSize
						label={ __( 'Link to the book', 'pagesco-books' ) }
						type="url"
						value={ url || '' }
						onChange={ ( value ) => setAttributes( { url: value } ) }
					/>
					<SelectControl
						__next40pxDefaultSize
						label={ __( 'Heading level', 'pagesco-books' ) }
						value={ headingLevel }
						options={ [ 2, 3, 4, 5, 6 ].map( ( level ) => ( {
							label: 'H' + level,
							value: level,
						} ) ) }
						onChange={ ( value ) =>
							setAttributes( { headingLevel: Number( value ) } )
						}
					/>
				</PanelBody>
			</InspectorControls>
			<div { ...useBlockProps() }>
				<RichText
					tagName={ 'h' + headingLevel }
					className="wp-block-pagesco-book-card__title"
					value={ title }
					onChange={ ( value ) => setAttributes( { title: value } ) }
					placeholder={ __( 'Book title', 'pagesco-books' ) }
					allowedFormats={ [] }
				/>
				<RichText
					tagName="p"
					className="wp-block-pagesco-book-card__author"
					value={ author }
					onChange={ ( value ) => setAttributes( { author: value } ) }
					placeholder={ __( 'Author', 'pagesco-books' ) }
					allowedFormats={ [] }
				/>
				<RichText
					tagName="p"
					className="wp-block-pagesco-book-card__pick"
					value={ pick }
					onChange={ ( value ) => setAttributes( { pick: value } ) }
					placeholder={ __( 'Why do you recommend it?', 'pagesco-books' ) }
					allowedFormats={ [ 'core/bold', 'core/italic' ] }
				/>
			</div>
		</>
	);
}
  • tagName={ 'h' + headingLevel } makes the title an h2 to h6 on the canvas too, so the editor shows what visitors will get.
  • A SelectControl returns the chosen value as a string; Number( value ) keeps the attribute an integer, as block.json declares. A value of the wrong type is dropped when the block is read back.
  • __next40pxDefaultSize opts the controls into the 40-pixel input height that WordPress components are moving to; without it, recent versions log a deprecation notice in the browser console.
  • The link is not editable on the canvas, so the editor needs no <a> around the title; clicking a link while editing would only get in the way.

In save, the heading is wrapped in the link only when there is a URL. The link wraps the heading rather than sitting inside it, which matters for the selectors (Common Mistake 2 shows why). Replace src/blocks/book-card/save.js:

import { RichText, useBlockProps } from '@wordpress/block-editor';

export default function save( { attributes } ) {
	const { title, author, pick, url, headingLevel } = attributes;

	const heading = (
		<RichText.Content
			tagName={ 'h' + headingLevel }
			className="wp-block-pagesco-book-card__title"
			value={ title }
		/>
	);

	return (
		<div { ...useBlockProps.save() }>
			{ url ? (
				<a className="wp-block-pagesco-book-card__link" href={ url }>
					{ heading }
				</a>
			) : (
				heading
			) }
			<RichText.Content
				tagName="p"
				className="wp-block-pagesco-book-card__author"
				value={ author }
			/>
			<RichText.Content
				tagName="p"
				className="wp-block-pagesco-book-card__pick"
				value={ pick }
			/>
		</div>
	);
}
npm run build > /dev/null

💡 The block toolbar is the other place for controls

InspectorControls fills the sidebar; its sibling BlockControls fills the toolbar that floats above the selected block, where core puts alignment, bold or the heading level of the Heading block. Use the toolbar for the one or two settings people change constantly, and the sidebar for everything else. The card's heading level could live in either place; Going Further moves it to the toolbar.

🎨 Block Supports: Features for Free

A shop will want a sage card for summer and an ink one for the book club. You could add color attributes, controls and CSS yourself, or you could say "this block supports background color" and let WordPress do all of it: the controls, the attributes, the classes and the inline styles, using the palette of the active theme. Preset choices are saved as classes (has-sage-background-color, has-small-font-size) and their slugs in the comment; the padding, a value per side, as an inline style that points at the theme's spacing preset. The classes work because the theme's global styles define them, for every block alike:

curl -s http://localhost:8080/card-test/ | grep -o '\.has-sage-background-color{[^}]*}'

Output

.has-sage-background-color{background-color: var(--wp--preset--color--sage) !important;}

Change Sage's hex value in theme.json and every sage card follows, because the post stores the slug, never the color. That is the main reason to prefer supports over color attributes of your own.

✅ What to opt into

Support what an editor should reasonably change, and leave out what would break the design. A card benefits from background and text color, padding and font size. Other supports worth knowing: align (wide and full width, or floating left and right), anchor (an HTML id for links to the card), shadow, and "className": false or "customClassName": false to switch off the generated or the custom class. The block.json reference in the Block Editor Handbook lists them all.

🧬 Changing save(): Validation and Deprecations

Every time the editor opens a post, it checks each static block: it runs your current save with the attributes it read, and compares the result with the HTML stored in the post. If they differ (beyond insignificant details such as attribute order or whitespace), the block is invalid. This check, block validation, is what keeps the editor from silently rewriting content it does not understand. It also means the stored HTML is a contract: once posts contain your block, its save output may not change without telling the editor about the old version.

Time to test the contract. The shop wants a small "Staff pick" badge on top of each card, with a sidebar toggle to hide it. That needs a boolean attribute, showBadge, defaulting to true. Replace src/blocks/book-card/block.json:

	"apiVersion": 3,
	"name": "pagesco/book-card",
	"version": "0.2.0",
	"title": "Book Card",
	"category": "widgets",
	"icon": "book",
	"description": "A book recommended by the Pages & Co. staff.",
	"keywords": [ "staff pick", "recommendation" ],
	"textdomain": "pagesco-books",
	"attributes": {
		"title": {

The deprecated array

A block's deprecated setting is a list of earlier versions, newest first. Each entry repeats what that version had: its attributes, its supports (deprecations do not inherit them, and the color classes come from supports) and its save. When the stored HTML fails validation against the current save, the editor tries each deprecation in turn; the first whose save reproduces the stored HTML wins, and the block opens as a normal, valid block of the current version. An optional migrate( attributes ) converts the old attributes to the new shape on the way. ⚠️ Which changes need a deprecation?

Anything that changes the HTML save returns for content that already exists: a new element, a different tag or class, a reordered element, a new attribute whose default renders something. CSS changes never do (styles are not part of the stored HTML), and neither do changes to edit alone. A new attribute whose default renders nothing new is safe too, as url and headingLevel were in the controls section. When in doubt, open an old post in the editor after the build: the console tells you.

1. Reading HTML-sourced attributes in PHP

A PHP developer wants to log every Book Card's title as it is rendered, and filters the block's output with render_block_{name}, which passes the parsed block as the second argument. As a throwaway must-use plugin:

	},

Error

Warning: Undefined array key "title" in /var/www/html/wp-content/mu-plugins/mistake-card-title.php on line 9
<!-- Book Card:  -->

What it means: title is sourced from the HTML, so it is not in the comment, so parse_blocks() never puts it into $block['attrs']: PHP does not run the editor's selectors. The warning comes before the doctype (the block theme renders the content first), and the comment ends up empty. Even the WP_Block object WordPress passes as a third argument only fills in defaults of comment attributes (it would report showBadge as true for the old card, which has no badge). Fix: in PHP, treat a static block's content as finished HTML. If PHP must know a value, either store it as a comment attribute (no source), read it out of the HTML with the HTML API (Exercise 1), or make the block dynamic so PHP renders it in the first place (Lesson 6.3). Remove the plugin:

rm wp-content/mu-plugins/mistake-card-title.php

2. A selector that catches more than you meant

The first draft of this lesson's save put the link inside the heading, which looks natural, while title kept its selector .wp-block-pagesco-book-card__title:

<Heading className="wp-block-pagesco-book-card__title">
	<a href={ url }>
		<RichText.Content value={ title } />
	</a>
</Heading>

Block validation: Expected token of type `StartTag` (Object), instead saw `Chars` (Object).
Block validation: Block validation failed for `pagesco/book-card` (Object).

Content generated by `save` function:

… <h3 class="wp-block-pagesco-book-card__title"><a href="http://localhost:8080/books/the-hobbit/"><a href="http://localhost:8080/books/the-hobbit/">The Hobbit</a></a></h3> …

Content retrieved from post body:

… <h3 class="wp-block-pagesco-book-card__title"><a href="http://localhost:8080/books/the-hobbit/">The Hobbit</a></h3> …

What it means: "source": "html" reads the inner HTML of the selected element, and the heading's inner HTML included the link. So on reload title became <a href="…">The Hobbit</a>, save wrapped it in a second link, and the two versions no longer matched. Nothing warned at save time; the first sign was the next edit. Fix: let each sourced element contain only its own value. The course's save puts the link around the heading (valid in HTML5) and sources url from the link's own class. After every change to selectors or save, insert a block, save, and reload before you trust it.

3. Translating text in save()

The badge text looks like a classic case for __(): <p className="…__badge">{ __( 'Staff pick', 'pagesco-books' ) }</p>. Built that way, a card saved on an English editor and reopened by an editor whose language has a translation for "Staff pick" (simulated here with Spanish "Recomendado") fails validation:

Block validation: Expected text `Recomendado`, saw `Staff pick`.
Block validation: Block validation failed for `pagesco/book-card` (Object).

What it means: save must return the same HTML for the same attributes, on every computer, in every language. A translated string makes the output depend on the user's locale, so every card turns invalid the moment someone edits in another language (or the site language changes). The same goes for dates, random IDs or anything else that is not an attribute. Fix: text in save is content: write it as a literal, as the course does, or make it an attribute the editor can change. Translate the editor's interface (labels, placeholders, the panel title) freely: edit is never compared with anything. The course's edit keeps the badge literal too, so the canvas shows what the page will.

🏋️ Exercise 1: Read the Card in PHP, Properly

Common Mistake 1 showed that $block['attrs'] has no title. Read the title and the link of every Book Card in the Staff picks post from the block's HTML instead, with WordPress's HTML API, and print title => url.

💡 Hint

Each parsed block has the stored HTML in $block['innerHTML']. WP_HTML_Tag_Processor walks the tags: next_tag( array( 'class_name' => 'wp-block-pagesco-book-card__link' ) ), then get_attribute( 'href' ). For the text inside the title, WP_HTML_Processor::create_fragment() can also visit text: after next_tag() on the title, next_token() moves to its text and get_modifiable_text() returns it.

✅ Solution 
<?php
$post = get_page_by_path( 'staff-picks', OBJECT, 'post' );

foreach ( parse_blocks( $post->post_content ) as $block ) {
	if ( 'pagesco/book-card' !== $block['blockName'] ) {
		continue;
	}

	$tags = new WP_HTML_Tag_Processor( $block['innerHTML'] );
	$tags->next_tag( array( 'class_name' => 'wp-block-pagesco-book-card__link' ) );
	$url = $tags->get_attribute( 'href' );

	$html = WP_HTML_Processor::create_fragment( $block['innerHTML'] );
	$html->next_tag( array( 'class_name' => 'wp-block-pagesco-book-card__title' ) );
	$html->next_token();

	echo $html->get_modifiable_text(), ' => ', $url, "\n";
}

Output

The Hobbit => http://localhost:8080/books/the-hobbit/

The HTML API parses HTML the way browsers do, so it is safe where regular expressions are not (attribute order, quotes, entities). It is the right tool whenever PHP must look inside stored block HTML. Remove the script: rm card-titles.php.

The same filter can add supports, change a default or the category: a handy tool when you adapt someone else's block.

❓ Common Questions at This Stage

When should a block be static, and when dynamic?

Static when the content is written by an editor and belongs to the post, as a recommendation does: it costs nothing at view time and survives even if the plugin is removed (the HTML stays). Dynamic when the output depends on data that changes elsewhere (prices, stock, the latest books, the current user) or must change everywhere at once when the design changes: then PHP renders it on every view, and save returns null. Lesson 6.3 builds the dynamic book list and binds card fields to book meta.

What if I deactivate pagesco-books?

The front end keeps showing the stored card, styled only by the theme (the block's CSS is gone, but the color classes are the theme's). In the editor, the block becomes "unsupported" and can be kept as is or converted to HTML. Reactivate and everything is back. That robustness is a quiet advantage of static blocks over shortcodes, whose brackets would appear as text.

Do I need a deprecation while I am still developing?

Only for content you want to keep. While a block exists only on your test site, delete the test posts and move on, as this lesson did after the demo. The moment a block is on a client's site, or released, every change to save needs one. Many teams also keep a test post with one block of every version, so a quick look in the editor after each build shows any validation errors.

Can a block be edited through the REST API or WP-CLI, without the editor?

Yes, as you did with the course tools: post_content is text, and any tool can write block markup. The catch is the validation from this lesson: markup that does not match what save produces opens as invalid in the editor. So scripts should write markup copied from the editor's Code editor, or leave static blocks to people and generate dynamic blocks, whose stored form is just the comment.

📝 Lesson Summary

🎓 Key Takeaways

  • Attributes with a source and selector live in the saved HTML; attributes without one live in the comment JSON, and only when they differ from their default. PHP's parse_blocks() sees only the comment
  • RichText edits text on the canvas, RichText.Content saves it; setAttributes() is the only way to change attributes
  • InspectorControls puts @wordpress/components controls into the sidebar; BlockControls into the toolbar
  • Block supports (color, spacing, typography…) add the attributes, controls, classes and styles for you, through useBlockProps, with the theme's presets
  • save must be a pure function of the attributes: no translations, dates or random values. The editor validates stored HTML against it
  • Changing save for existing content needs a deprecated entry (old attributes, supports and save, optional migrate)
